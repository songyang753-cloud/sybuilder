# SYBuilder 集成契约

## 1. 集成方式

SYBuilder 是一个套件，不是一个超大 Skill。`product-flow` 管阶段和产物，`coding-standards` 管实现约束，`four-node-review` 管终审。集成只能通过本契约声明的阶段、输入、输出和门禁完成，不得把另一个 Skill 的全文复制成第二正本。

## 2. 强制接线

| 阶段 | 主责 Skill | 必须消费 | 必须产出 | 缺失时 |
|---|---|---|---|---|
| S1–S7（运行前先预检） | `product-flow` | 上游决策、调研证据、冻结 PRD/设计契约 | 带 ID 的产品、设计和验收正本 | `UNABLE` |
| S8 | `product-flow` + `coding-standards` | 冻结 PRD、设计/交互、调研证据 | 技术方案、算法方案、测试方案与实现约束 | `coding-standards` 不可用时不得声称联合方案完整 |
| S9 开发 | `coding-standards` | S8 联合方案与可验收切片 | 实现、测试、门禁回执与变更证据 | 任一必检项未能执行即 `UNABLE` |
| S9 测试与 GUI 验收 | `product-flow` | 同一构建、冻结 PRD、测试方案 | 测试工程师 GUI 实走报告；其后才能产出产品经理 GUI 走查报告 | 不可用自动化结果代替人的实走 |
| S9 终审 | `four-node-review` | 可独立上线切片、真实 diff、上述全部证据 | 风险分档、覆盖账、多视角收敛和终审结论 | 工具缺失/覆盖不全只能记 `UNABLE` |

## 3. 单一正本

- 产品要求和验收 ID 以 `product-flow` 产物为正本。
- 编码规则以 `coding-standards` 为正本，其他 Skill 只引用锚点。
- 终审收敛算法以 `four-node-review` 为正本，`product-flow` 只声明何时触发和要交什么。
- 任何加入套件的外部 Skill 必须声明它消费和生产的契约 ID，不得再建一份同名清单。

## 4. 扩展 Skill 准入条件

扩展项必须同时声明：

1. `stage`：接入哪个阶段。
2. `consumes`：读取哪些上游产物/ID。
3. `produces`：生成哪些新产物/ID。
4. `required`：必需还是可选。
5. `fallback`：不可用时如何分类；必需项不得声称已通过。
6. `license`：来源和许可证是否允许合并或分发。
7. `verification`：至少一条可重复的正例与一条反例。

## 5. 融合与引用的选择

- **融合**：只适用于许可证兼容、内容已逐条去重、且融合后只保留一个正本的情况。
- **引用**：适用于变动快、独立维护或许可证不确定的外部 Skill。
- **不接入**：没有输入/输出契约、降级会假绿、或无法说明授权来源的 Skill。

## 6. 内部模块与平台适配器

- 研究、制图、设计质量、原型与仓库执法属于可重复运行的核心能力，随仓库内置，并由
  `shared/module-registry.json` 登记唯一入口。
- 飞书、钉钉、Figma、浏览器/桌面 GUI 属于外部平台。SYBuilder 只提供适配器契约，
  不复制平台实现、不保存账号或 token。
- 人读文档共用一份 Markdown 语义源；用户在飞书与钉钉中选一个作为本次对外正本。
  两个平台都必须完成正文、表格和真实图片的写后回读。
- 外部平台不可用时，受控 Markdown 只能是候选稿；状态是 `UNABLE`，不是“已交付”。

## 7. 批准与版本

结构门只验证批准记录的字段与明确结论，不认证批准人的身份。批准记录必须写清主体
`human/agent`、授权依据、适用范围、产物版本和证据来源；agent 的专业角色审查不得写成
人类负责人签名。需要用户决定的范围/付费/发布/风险接受，仍须对应真实授权。
S8 是方案，不是测试执行；S9.2 是测试证据；S9.3 是在同一候选构建、冻结 PRD 下的
独立产品走查。变更构建或产品合同后，先前批准不能直接继承。

门禁输入绑定包含规则与显式文件/目录参数；间接消费的文件也必须声明并纳入输入。
历史门禁/回执缺版本证据时仍可查阅，不得补填当前哈希假装当时测过；重新执行后签发。
