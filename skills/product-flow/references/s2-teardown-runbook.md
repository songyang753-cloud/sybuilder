# S2 单竞品深度拆解运行手册（`teardown`）

> 本文件只服务“把一个产品拆到最细可验证颗粒，并形成可直接反哺 PRD 的协作文档报告”；飞书或钉钉由任务合同选择，统一执行 `scripts/_documents.py`。
> 多竞品横向比较继续读 `competitive-research.md`；完整五线研究继续读 `s2-research.md`。

## 一、模式选择

| 模式 | 何时用 | 主要输入 | 完成边界 |
|---|---|---|---|
| `teardown` | 一个桌面/Web 产品需要深度遍历、反向规格和 PRD 输入 | 指定产品、端、版本、账号/档位、研究决定 | 一份单品协作文档报告 + 全量结构语料 + 远端验收回执 |
| `competitive-pack` | 已有多个通过验收的单品语料，需要逐级横向对比 | ≥2 份已通过 `teardown` 的包 | 从根任务沿各自实际路径逐层投影到最细功能；不固定三/四级，不重新浅扫代替单品验收 |
| `full-research` | 需要完成 S2 五条线并进入 S3 | S1 + 下游消费者声明 | 现有完整 S2 产物与三份定向协作文档报告 |

⛔ 单竞品任务不为满足数量门槛伪造 8–12 个样本；多竞品报告也不得绕过单品验收，直接用官网摘要拼矩阵。

## 二、固定的是叶子合同，不是层级数

功能层级使用可变长度路径，例如：

`工作区 / 任务 / 运行 / 失败后重试`

`L0/L1/L2` 只可作为兼容投影。真正的叶子停止条件是：该行为已经能被独立发现、授权、定价、执行、失败、恢复和验收；继续往下只是内部实现且不改变用户可观察结果。

每个叶子功能必须有：

| 字段 | 要求 |
|---|---|
| `AF-ID / 功能路径 / 层级深度 / 父节点` | 路径可任意深；同一路径下 ID 唯一 |
| 角色、场景、页面与入口 | 读者能从产品表面找到它 |
| 前置条件、对象与输入 | 包含账号、权限、套餐、端和必要数据 |
| 字段、默认值与校验 | 没有则写 `N/A + 理由`，不得留空 |
| 一个主要动作 | 含多个可独立动作必须继续拆 |
| 操作前状态 → 操作后状态 | 必须是用户可观察状态，不以“无状态变化”搪塞 |
| 结果与反馈 | 写界面结果、提示原文或可观察变化 |
| 失败、取消、中断与恢复 | 不适用时写理由；只写 happy path 不完整 |
| 权限/端/档位/额度 | 防止把某个账号看到的能力泛化成全产品 |
| 证据等级与证据 ID | `verified / observed / reported / blocked` 不得相互提升 |
| 下游输入 | 至少说明对 PRD、设计/交互、技术/算法、测试的影响或 `N/A + 理由` |

## 三、T0–T8 顺序

### T0 任务合同与安全边界

输出 `teardown/brief.md`：产品、版本、端、账号/套餐、研究决定、允许动作、禁止副作用、授权状态、预期核心旅程、最终文档平台与授权目标；必须逐项确认边界。

未填完整时停止；浏览授权不自动包含购买、订阅、发送、发布、删除、改真实账号或新增系统权限。

### T1 产品表面盘点

输出 `surface-inventory.json`：导航、页面、标签、抽屉、弹窗、设置、帮助、快捷键、定价/权限面和初始状态。每个发现项有稳定 `SURF-ID`、页面路径与控件/入口。

### T2 真实 GUI 串行遍历

输出 `traversal-events.json` 与原始截图。每次操作至少记录：

`EVENT-ID / SURF-ID / 页面 / 目标控件 / 操作前状态 / 动作 / 输入 / 操作后状态 / 结果 / 分类 / 证据 ID`。

分类只允许：

- `verified`：实际操作并看到结果；
- `observed`：只看到入口或展示；
- `blocked`：登录、权限、付费、地区或安全边界阻断；
- `side-effect`：因外部副作用边界未执行；
- `non-feature`：装饰、内容或无功能语义元素。

⛔ 控件文字出现不等于 `verified`。

从 `templates/traversal-events.json` 起稿；截图清单从 `templates/evidence-manifest.json` 起稿。两者必须用 `EVENT-ID / SHOT-ID / AF-ID` 互相反查。

### T3 覆盖账本对账

100% 发现项必须归类；目标不是 100% 全部执行。任何未归类项、`verified` 缺操作前后状态、结果或证据，都阻断进入 T4。

### T4 原子功能与反向规格

输出 `atomic-feature-ledger.md`。先从 SURF/EVENT 归并叶子，再补充案头事实；每个叶子反查至少一个事件或明确的降级来源。

### T5 旅程、交互、状态与异常

输出 `journeys.md`、`state-coverage.md`、`field-specs.md`：

- 核心旅程必须含触发、前置、主路径、可选路径、失败/阻断、取消/中断、恢复和完成反馈；
- 状态矩阵至少覆盖首次、空、加载、成功、部分失败、失败、无权限、弱网/离线、极值、恢复；
- 每个状态和异常反查叶子功能与证据。

### T6 人读报告编排

使用 `templates/competitor-teardown-report.md`。每个功能域按“用户目标 → 端到端体验 → 叶子功能正文 → 规则/状态/异常 → 真实截图 → 对我方含义”编排。

⛔ 最细功能只放在图、附件或机器表中不算完成；正文图片不得集中堆在文末。

### T7 三角色语义评审

输出 `research-quality-review.md`：产品总监、UX/交互负责人、测试负责人分别给出 `PASS / FAIL / UNABLE`、问题 ID、影响和关闭证据。任一 P0/P1 未关闭不得发布。

### T8 个人飞书发布与远端验收

只使用官方 `lark-cli --as user`。发布前 `whoami` 必须显示 user 身份、token ready；本地图片通过 Markdown `@./相对路径` 或 DocxXML `<img path="@./..."/>` 写入真实图片块。

发布后回读并生成 `feishu-delivery-receipt.json`，至少验证：标题、章节、叶子功能数量、表格数量、真实图片实体数量、非空图片 token、图片所在章节、无占位文字/本地绝对路径、正文未截断。

## 四、正文投影合同

每个功能域必须包含：

1. 用户为何进入该域；
2. 入口与完成目标；
3. 主路径和关键分支；
4. 该域全部叶子功能；
5. 每个承重叶子的字段、规则、状态、反馈与失败恢复；
6. 与文字相邻的真实截图；
7. 对 目标产品 PRD、设计、技术和测试的输入。

`最细功能正文索引` 必须覆盖原子功能词典的完整 AF 集合。索引不是替代正文：它只证明每个叶子在正文中有章节、证据和下游去向。

## 五、横向比较消费规则

`competitive-pack` 只读取已验收单品包，并按同一功能全集投影：

1. 根任务/业务域层比较用户任务和覆盖边界；
2. 每个中间父节点逐层比较产品模型与实现路线，直到该分支不再有下一层；
3. 最细功能层比较入口、字段、规则、状态、结果、恢复、权限、档位与代价。

新增叶子后，所有正式竞品都必须回填 `FULL / PARTIAL / ABSENT / UNKNOWN / N/A`，不得只留在发现它的产品中。

## 六、完成定义

- `teardown`：遍历覆盖、报告结构/深度、受众、飞书远端四类门禁全部 PASS；
- `competitive-pack`：所有输入单品包已 PASS，且 `research-gate` PASS；
- `full-research`：保留现有 S2 全部门禁，并额外满足所有单品与远端验收要求；
- FAIL、UNABLE、NOT-RUN 均不算完成。

## 七、黄金样本回归(改 S2 门禁后必跑)

改动任何 S2 门禁(traversal-coverage / report-structure / feishu-delivery)后跑:

```bash
python3 tests/s2-golden/run-golden.py
```

它证两件事:①一份**内部自洽**的单品报告能**同时**过三门(门之间不自相矛盾=互相可满足);
②把黄金样本改坏的 7 个破坏性反例(删索引表 / 删状态异常段 / 已验证缺后态 / 未归类控件 /
证据未投影正文 / 飞书远端图片空 / 权限阻塞谎报已验证)**各自触发对的那道门**。
⛔ 改门禁后不跑它,等于不知道自己是把报告变严了还是把黄金样本也误伤了。
