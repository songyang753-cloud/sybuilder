# 多维度专家评审机制

> ⚠️⚠️ **评审的三个等级，不许混叫**（2026-09-07 按 Codex 外审 P0-10 立）：
> ① **结构化自审** —— 同一作者扮演多视角。本文的视角轮换若由作者本人执行，就是这一级；
>   结论只能当「作者的自查清单」（09-04 实测 D-5：11 个视角全由作者扮演，分数不可信）。
> ② **独立评审** —— 来自独立上下文/独立评审者（另一个会话、另一个人、外部 Codex）。
> ③ **真实用户验证** —— 目标用户完成真实任务。独立评审证明「说明是否清楚」，冒充不了这一级。
> 报告里必须写明本轮评审是哪一级；把 ① 写成 ② 是「声称≠实际」的一种。

> **发现分级契约**（2026-09-08 借鉴 AI-Native SDLC 的 REVIEW.md 精神）：
> 每条发现标 **[I] Important**（影响正确性/安全/可用性/产品含义）或 **[N] Nit**（措辞/风格/微调）。
> ① **每轮每视角 Nit ≤5 条**——超出只保留最重要的并注明「另有 N 条略」；
>   无上限的 nit 会淹没 Important（与门禁假阳性让人脱敏同理）。
> ② **收敛只看 Important**：「连续两轮零 [I]」即该视角收敛，[N] 不阻断收敛（但要处置或显式忽略）。
> ③ [I]/[N] 不独立阻断流程——阻断阈值由人拍板兜底（发现是输入，拍板是决定）。
> ④ 同型 [I] 第二次出现 → 回写规范；第三次 → 加工具（既有纪律，此处只是挂进分级）。
> ⑤ **引证门**（借 gstack #1539；09-09 按 Codex 复审修正维度——**可核验性与严重度正交**）：
>   每条发现带**与其证据类型相称的定位物**：代码=file:line+逐字原文；文档=章节+原句；界面=场景号/截图；
>   **缺失类**（该有而没有）=写清「在哪查过、用什么查的」（absence query）；聚合类=列出所依据的具体条目。
>   给不出定位物 → 标 `unverified` 并**阻止定案**（不驱动修改；unverified 的 [I] **不算零**——
>   收敛前须补证或由拍板显式处置），⛔ 但**不改它的 [I]/[N] 等级**——把引不出原文的严重问题
>   降成 Nit，等于拿可核验性冒充严重度（第一版就这么写错了）。⛔ 不许编个定位物绕过。
> ⑥ **证据三态**（借 gstack devex-review 方法学）：每视角结论标 **TESTED**（真跑了/真开页面看了）
>   / **PARTIAL**（跑了一部分）/ **INFERRED**（只从产物文本推断），报告末尾给计数 `tested=N / inferred=M`。
>   INFERRED 不是缺点，**冒充 TESTED 才是**（「声称≠实际」的评审版）。

产品方案在 **S5.3** 进行多维度专家评审（S4 产品方案终审同样适用本视角表）。每个视角由 AI 扮演对应领域专家，从该领域最专业的角度提出修改意见。

## 一、评审架构

### 何时触发

- **S5.3 评审**：S5.2 交互规格书初稿完成后
- **S6 出场前评审**：demo 锁定前的终审（可选，产品判断是否需要）
- **用户随时调用**：`product-flow --only S5.3` 对当前产物跑一轮

### ⭐ 防锚定：证据与判断必须隔离

**跑任何带工具证据的视角时**，A（人的设计评审）与 B（工具检测结果）**必须分开跑，
且 A 必须先于 B 进入上下文**。

理由：检测器的输出是确定性的，但**它仍然会锚定判断**——先看到「工具报了 3 条」的人，
很容易就只在那 3 条附近找问题，而工具查不到的那一类会被整体跳过。

- 条件不允许隔离时，**必须在报告首行打 `⚠️ DEGRADED` 横幅**，说明本轮判断可能被证据锚定
- 合成两者时，要明确标注三类：**两者一致 / 工具抓到人漏的 / 工具误报**

### 运行规则

1. **每轮换一个视角**。
2. **视角表未跑满一遍不得宣告收敛**——不许只跑两三个顺手的视角就说收敛了。
3. **收敛判据**：每个视角**连续两轮零 [I]**（分级契约见篇头；[N] 不阻断，须处置或显式忽略）；全部适用视角零 [I] 即评审收敛——⛔ 不以「跑满轮数」冒充质量，一轮已收敛即可停，三轮仍有 [I] 就继续。
   ⚠️ 只有一大轮零发现**不算收敛**——第一大轮的修订本身可能引入新问题，必须再跑一遍验证。
   ⚠️ 「同一视角连续零发现」是收敛的**证据**，不是要被排除的东西；要防的是**没换视角、没换证据**就宣称跑了新一轮（见 M5 证据独立性）。
4. 每轮留痕：`视角 / 提了什么 / 改了什么 / 提了但没采纳的及理由`
5. **发现分级**：结构性问题必须修；非结构性建议记录但可不改

### 评审输入

评审者需要读的产物（按阶段不同而不同）：

| 阶段 | 必读产物 |
|------|---------|
| S5.3 | 设计简报 + DESIGN.md + interaction-spec.md + decisions.md + PRD(五章+附件) |
| S6 出场前 | 上述全部 + demo HTML + selftest 报告 + 技术栈对照表 |

## 二、11 个评审视角

### 视角 1 · 算法总监

**身份**：负责 AI/ML 技术方向和算法团队的总监。关注算法能力与产品承诺的匹配度。

> ⭐ **与视角 8（算法负责人）的分界**（2026-08-31 切清，此前两者在「流式」「阈值」上重叠）：
> | | 视角 1 · 算法总监 | 视角 8 · 算法负责人 |
> |---|---|---|
> | 问的是 | **能不能做到**（能力 vs 承诺） | **怎么接进去**（接口、状态、失败面） |
> | 典型句式 | 「这个 95% 是在哪个集上测的」 | 「超时了前端拿到什么」 |
> | 同一件事的两面 | 流式：**会不会语义截断**（内容风险） | 流式：**中间态怎么渲染、停止怎么 abort**（实现契约） |
> | 同一件事的两面 | 阈值：**这个阈值有没有实测依据** | 阈值：**跨过阈值时用户看到什么** |
> ⛔ 两个视角**不许给出同一条发现**——重复即说明帽子没换干净（M5 证据独立性）。

**专问什么**：
- PRD 里承诺的 AI 功能，当前算法能力**真的能交付**吗？有没有把 demo 效果当成工程效果写进了 PRD？
- 算法能力边界表（附件 B.2）里的数字是**实测还是估计**？评测集和线上分布一致吗？
- AI 状态扩展表的超时策略合理吗？P99 延迟和超时阈值之间有没有足够余量？
- 降级方案（Fallback）真的能兜住吗？规则方案的效果够用户接受吗？
- 流式输出的中间态有没有**语义截断风险**（半句话停下来被用户当结论）？
- 反馈数据（👍👎）的收集方案能不能反哺模型迭代？数据流通到训练要经过几层？

**典型发现**：
- 「PRD 写的准确率 95% 但这是在英文评测集上的，中文场景没有基线」
- 「流式输出的停止按钮停了，但后台推理没有 abort，白白烧算力」
- 「Rate Limited 状态里的额度重置时间，中台接口目前不提供这个字段」

### 视角 2 · UI 专家（视觉设计）

**身份**：资深 UI 设计师。关注视觉系统的完整性、一致性和品质感。

**三段式执行**（不要直接开始挑刺，先分类再提取再判定）：

**① 先分类**——营销页 / 应用 UI / 混合。**分类不同，规则集不同**，用错规则集的评审等于没评。
　　⭐ **三套规则集在 `references/design-rulesets.md`**（落地页规则 / 应用 UI 规则 / 通用规则）。
　　📌 这里曾经只有分类器没有分支——写着「分类不同规则集不同」，然后给了一套通用的 12 问。

**② 提取实测设计系统**（读实现，不读设计稿）：字体族数 · 非灰颜色数 · h1–h6 尺寸表 · 间距值分布。
自动报警阈值：字体 >3 · 非灰颜色 >12 · 标题跳级 · 间距不在 4/8 倍数上。

**③ 逐条判定这 12 个问题**（每条都要能回答「是/否」+ 给出证据，不许含糊）：

| # | 问题 | 判据 |
|---|---|---|
| 1 | 首屏 3 秒内说清楚这是什么吗？ | 眯眼测试：截图高斯模糊后层级是否还在 |
| 2 | 每行字符数在 45–75 吗（66 理想）？**正文字号达到该载体的下限吗**（见 `visual-spec.md` 1.1，不要在这里另记一个数）？caption ≥11px？ | 可量 |
| 3 | 对比度：正文 ≥4.5:1 · 大字 ≥3:1 · UI 组件 ≥3:1 | **逐元素报最差的 5 个** |
| 4 | 字阶遵循比例（1.25 或 1.333）？标题:正文 ≥2.5×？ | 可量 |
| 5 | 圆角有层级吗？嵌套满足「内圆角 = 外圆角 − 间隙」吗？ | 可量 |
| 6 | 只有一个强调色且全页一致？饱和度 <80%？ | 可量 |
| 7 | 全页只有一个主题吗（不许某节反色）？ | 可量 |
| 8 | 每个 CTA 文字在其背景上可读？桌面有 CTA 折行吗？主 CTA ≤3 词？ | 可量 |
| 9 | 同意图的 CTA 是否重复出现？ | 重复即 Fail |
| 10 | 连续同一 layout family 的 section 是否 ≥3？eyebrow 数量 ≤ ceil(节数/3)？ | 可量 |
| 11 | **把所有装饰性阴影去掉后，这设计还高级吗？** | 定性但可答 |
| 12 | 卡片是真的必要（卡片本身是交互对象），还是只是装饰性网格？ | 定性但可答 |

**④ 7 条硬否决**（命中任一即打回，不进入打分）：
① 通用 SaaS 卡片网格作第一印象 ② 漂亮图片但品牌弱 ③ 强标题但无明确动作
④ 文字后面压着杂乱图像 ⑤ 多个 section 重复同一情绪陈述 ⑥ 无叙事目的的轮播
⑦ **App UI 由堆叠卡片而非布局构成**

**⑤ 打分**：五维 0–10（哲学契合 / 视觉层级 / 工艺 / 功能性 / 原创性），
总档 8+ 优 / 6–7.9 良 / 4–5.9 需改 / <4 不及格。
⭐ **不是 10 分就说清 10 分长什么样，然后把它做到那儿**（`design-rulesets.md` 第八节）：
评分 → 差距（「4 分是因为…；10 分会有…」）→ 直接改 → 重评 → 真正的设计选择交人拍板。
⭐ **任一维度 <7 分时，直接产出那个 10 分的样子**（Figma 稿或交互稿片段），不要用文字描述——
**它让「现在」和「应该」之间的差距变得可见，而不是抽象。**
⭐ **提意见用四种句式**（`design-rulesets.md` 第九节）：
「我注意到…」观察 /「我好奇…」疑问 /「如果…会怎样」建议 /「我认为…因为…」有理由的判断。
每条都要挂回用户目标，并给出具体改法。**「感觉不对」不是意见。**
⚠️ **修复条目 >7 条必须归并**——「五处间距不一致」算一条，不算五条。

**⑥ 暗色模式单独查**（不是反色）：surface 用高度表达层级 · 文字用 off-white(~#E0E0E0) 不用纯白 ·
主强调色**去饱和 10–20%** · `html` 上有 `color-scheme`。

**典型发现**：
- 「DESIGN.md 里 body 用 oklch 但 border-color 用 hex，下游实现必然不一致」
- 「Toast 和 Modal 的圆角值不同（8px vs 12px），同层级组件应统一」
- 「空状态插图的风格和品牌调性不搭——产品定位专业工具但插图画风是卡通」

### 视角 3 · UE 专家（交互体验）

**身份**：资深交互设计师 / UX 研究员。关注用户行为路径的完整性和操作效率。

**必跑的 8 项**（前 3 项是本视角的骨架，不许省）：

**① Trunk Test（每屏必跑）**——把用户空降到这一屏，6 问全清 = PASS，4–5 = PARTIAL，≤3 = FAIL。
**FAIL 一律记 HIGH，不论视觉多好看。**

**② Goodwill 水库走查**——起 70 分，按下表逐步计分，画出阶梯：

| 扣分 | 分值 | 加分 | 分值 |
|---|---:|---|---:|
| 隐藏信息 | −15 | 主任务显眼 | +10 |
| 格式惩罚（要求用户按特定格式输入） | −10 | 成本透明 | +5 |
| 多余信息 | −10 | 省掉步骤 | +5 each |
| 插屏 | −15 | 优雅报错 | +10 |
| 粗糙 | −10 | 出错时道歉 | +5 |
| 歧义选择 | −5 each | | |

<30 = critical UX debt · 30–60 = needs work · >60 = healthy。

**③ Mindless-choice 审计**——逐个决策点（按钮/链接/下拉/弹窗选项）判：
「点了会发生什么，是不是一眼可知？」**需要停下来想「这是不是对的选择」的，记 HIGH。**

**④ 前三注视点**——写出「我的视线最先落到的 3 个东西是 X/Y/Z」。
若这 3 个不是设计者想让人先看的，**说明视觉层级在撒谎**。

**⑤ 一人称叙述走查**——以「我在看这个页面…视线先到 logo，然后是一堵我直接跳过的文字墙…
等等，那是个按钮吗？」的方式写。
⚠️ 硬判据：**必须点名具体元素、位置、视觉权重。点不出具体名字就说明没真走查，是在生成套话。**

**⑥ 三态完备**——loading（骨架形状必须匹配真实内容布局）/ empty（文案+主操作+视觉，
不是光一句「暂无数据」）/ error（发生什么 + 为什么 + 下一步怎么做）。**任一缺失即 HIGH。**

**⑦ Happy talk 字数比**——统计页面可见总词数，每个文本块分类为「有用内容」或「happy talk」
（「欢迎使用…」开头、自吹自擂、能听出 blah blah 的），报出 `本页 X 词，其中 Y 词（Z%）是 happy talk`。
配套：**任何超过一句的可见指令 = 设计失败**，同时标记那条指令和它在补偿的那个交互。

**⑧ 认知负荷量化**——工作记忆 ≤4 项 · 导航顶层 ≤5 · 表单每组 ≤4 字段 ·
仪表盘首屏 ≤4 指标 · 定价 ≤3 档 · 下拉 ≤7 项。

**⑨ 五人格走查**（比抽象的「易用性」具体得多；按界面类型挑 2–3 个跑）

| 人格 | 特征 | 他会先撞到什么 |
|---|---|---|
| **急躁的老手** | 键盘为主、目标明确、不读说明 | 快捷键缺失 · 必经的中间步骤 · 确认框 |
| **谨慎的新手** | 怕点错、边看边想 | 不可逆操作没有撤销 · 术语不解释 · 空态没有下一步 |
| **被打断的人** | 做到一半被叫走，十分钟后回来 | 状态没保存 · 回来后不知道自己在哪 · 草稿丢了 |
| **手不方便的人** | 只用键盘 / 用辅助技术 | 焦点陷阱 · 只在 hover 下出现的功能 · 无 label 的图标按钮 |
| **数据很多的人** | 库里有十万条 | 全选的语义 · 虚拟滚动 · 批量操作的部分失败 |

⚠️ 每个人格走查时**必须点名具体元素**，写「我作为 X，在 Y 页面点了 Z，然后卡在了…」。
写不出具体的元素名，说明没真走，是在生成套话。

**⑩ 内容边界测试**（六种输入，逐个试，不许只试正常值）

| 输入 | 要暴露什么 |
|---|---|
| **1 个字符** | 布局会不会塌 |
| **1000 个字符** | 会不会撑破容器、有没有截断策略 |
| **空** | 空态设计有没有 |
| **emoji + CJK 混排** | 字体回退、行高、截断位置 |
| **德语/芬兰语长词** | 文案膨胀（德语 +30% / 法语 +20% / 芬兰语 +30–40%；**中文 -30%**） |
| **极端数量**（0 条 / 10000 条） | 空态与性能两头 |

⭐ 空间预算要**预留 30–40%** 给文案膨胀。中文设计直接搬到德语界面必然撑破。

**另查**：关键功能是否藏得太深（>3 次点击）· 同一操作（删除/收藏/分享）在不同页面触发方式是否一致 ·
不可逆操作是否缺确认或撤销 · 触摸热区 ≥44pt（桌面指针目标 ≥24pt）。

**典型发现**：
- 「删除操作直接 Toast 成功，没有 Undo——但删除数据是不可逆的」
- 「搜索结果页没有『空结果』态的设计，用户搜不到东西会看到白屏」
- 「设置页 15 个选项平铺，没有分组——认知负荷太高」

### 视角 4 · 市场总监

**身份**：负责品牌定位、市场传播和用户获取。关注产品在市场上的竞争力和传播性。

**专问什么**：
- 产品的**核心卖点在界面上一眼能看出来**吗？还是藏在三级页面里？
- **首屏**传达了什么信息？对新用户来说这是什么产品一目了然吗？
- 品牌调性在界面里**一致**吗？有没有某个页面画风突变（比如技术风突然混进卡通图标）？
- 文案的**语气**和品牌一致吗？有没有过度技术化的术语出现在用户面前？
- 竞品差异化的设计在**第一次体验**中就能感知到吗？还是要深度使用才发现？
- 付费引导文案的**转化路径**清晰吗？从"额度用尽"到"完成购买"几步？

**⛔ 强制产出物（写不出＝本视角 FAIL）**：

#### 1 · 五秒测试（**必须找一个没参与过这个项目的人真做**）
> 给他看首屏 **5 秒**，然后遮住，问三个问题。

### 视角 5 · 营销总监

**身份**：负责增长、运营、用户留存和转化。关注用户生命周期各阶段的体验转化。

**专问什么**：
- **引导转化漏斗**完整吗？注册→激活→核心价值→留存→付费 每一步的转化率有考虑吗？
- 新用户 **Aha Moment**（顿悟时刻）设计了吗？用户在哪个操作之后会说"这东西有用"？
- **分享/传播**的触点够吗？用户在什么场景下有动力分享？分享出去的内容长什么样？
- **留存钩子**在不在？用户第二天/第七天回来的理由是什么？有没有推送/提醒的设计？
- 数据**埋点**设计了吗？关键路径的每一步都能追踪到吗？
- **A/B 测试**的技术预留做了吗？关键转化节点能不能快速换文案/布局？
- 免费→付费的**感知价值**够吗？免费版是不是太好用导致没人升级？

|---|---|---|---|---|---|
| 注册 / 进入 | | | | | |
| 激活（第一次真的用起来） | | | | | |
| **Aha Moment** | | | | | |
| 留存（第 2 天 / 第 7 天回来） | | | | | |
| 付费（若有） | | | | | |

⛔ **「有考虑」不是答案。** 每一格要么是数字，要么是标了 `ASM-###` 的 UNKNOWN。
⚠️ **一个 UNKNOWN 不可怕，五个全是 UNKNOWN 说明这个产品还没有增长假设**
——那要回 S3，不是往下走。

#### 2 · Aha Moment 单点定义（**必须落到一个具体动作**）
| 必答 | 你的答案 |
|---|---|
| 用户做完**哪一个具体动作**之后会说「这东西有用」 | |

| 本视角提的每个问题 | 7.1 里有没有对应事件 | 没有的话补哪个 |

**典型发现**：
- 「用户完成了核心操作但没有任何庆祝/确认——错过了强化 Aha Moment 的机会」

### 视角 6 · CEO

**身份**：产品的最终决策者。关注战略方向、资源投入产出比和用户核心价值。

**专问什么**：
- **如果只留一个功能**，剩下的全砍，用户还会用吗？那个功能在设计里足够突出吗？
- 资源投入和**预期回报**匹配吗？最复杂的那个交互真的值得投入吗？
- 有没有**过度设计**？哪些交互可以更简单？简单到什么程度用户仍然满意？
- **竞品对比**：拿着这个方案和竞品放一起，用户会选谁？为什么？
- **上线时间**：这个方案的设计复杂度是否与上线节奏匹配？有没有可以砍到 MVP 的部分？
- 用这个方案给投资人/合作伙伴**演示**，五分钟能讲清楚核心价值吗？
- 三个月后这个产品长什么样？现在的设计**能不能优雅地长出新功能**还是要推翻重来？

**⛔ 强制产出物（写不出＝本视角 FAIL，不许口头「考虑过了」）**：

#### 1 · 唯一功能测试（The One Test）
> **如果只留一个功能，其余全砍，用户还会用吗？**

| 必答 | 你的答案 |
|---|---|
| 留哪一个（写 `F-xx`） | |
| 留下它之后，用户还会用吗 | ☐ 会 ☐ **不会** |
| 若「不会」——**那说明核心价值不在任何单个功能里，而在组合里**，写出这个组合最少几个 | |
| 这个功能/组合在设计里**足够突出**吗（第一屏能不能看见） | ☐ 是 ☐ 否→**这是设计缺陷，回 S5** |

⭐ **这个测试的价值不在答案，在于它逼你说出一个具体的 `F-xx`。**
说不出具体编号 = 你还不知道这个产品是干什么的。

#### 2 · 砍到 MVP 的顺序表（**必须排序，不许并列**）
| 砍的顺序 | 功能 | 砍掉后谁会不满 | 为什么它排这个位置 |
|---|---|---|---|
| 第 1 个砍 | `F-xx` | | |
| 第 2 个砍 | `F-xx` | | |
| **最后才砍** | `F-xx` | | |

⛔ **「都很重要」不是答案**——排不出顺序说明还没做过取舍。
⚠️ 这张表在**工期被压缩时会被直接执行**，所以现在排的顺序就是将来砍的顺序。

#### 3 · 成本 / 使用率 失衡项
| 功能 | 占总成本 | 预估使用率 | 判定 |
|---|---|---|---|
| `F-xx` | %  | % | ☐ 保留 ☐ **砍** ☐ 降级 |

⭐ 只需列**成本占比最高的三个**。⚠️ 使用率填不出来 → 它是 `ASM-###`，
按 `evidence-levels.md` 至少要 E1，⛔ 不许拍脑袋填一个数当事实。

**典型发现**：
- 「设计了 12 个功能的完整交互但其实 3 个核心功能就够上线——先砍到 MVP」
- 「最复杂的那个拖拽排序功能成本占全部的 40%，但用户用到的概率不到 10%」

### 视角 7 · 研发负责人

**身份**：负责工程团队和技术架构。关注方案的可实现性、维护成本和技术债。

**专问什么**：
- 交互规格书的**组件层级**映射到代码的组件树是否合理？有没有过度嵌套或反直觉的结构？
- 状态管理的**复杂度**可控吗？有没有跨组件的隐式依赖（A 组件的状态影响 B 组件但没写出来）？
- **API 契约**（数据依赖表）和后端现有接口兼容吗？需要新建几个接口？
- 动效规格在**目标设备**上跑得动吗？嵌入式浏览器 / 低端安卓 / iOS 老版本？
- 自定义组件的**维护成本**评估过吗？有没有能用组件库现成组件替代的地方？
- 这个交互方案**能不能增量交付**（一个功能一个功能上线）还是必须全做完才能用？
- **技术债**风险：有没有"先做了再说"的临时方案可能永远不会清理？

**⛔ 强制产出物（写不出＝本视角 FAIL）**：

> ⭐ 这个视角在 2026-08-31 的 S4/S6/S7 联合评审里**打了 11 个视角中的最低分（4/10）**，
> 理由是「物料在『让研发能往下走』这一维不及格」。补强制产出物就是补这一维。
> ⚠️ **本视角问的是「能不能做、要多久」，不是「怎么做」**——
> 技术方案是研发主导的产出（铁律 35），这里只判**产品/设计侧给的东西够不够支撑它**。

#### 1 · 增量交付切片表（**能不能一个一个上线，还是必须全做完才能用**）
| 切片 | 包含哪些 `F-xx` | 单独上线后用户能完成什么完整的事 | 依赖前一片吗 |
|---|---|---|---|
| 第 1 片 | | | — |
| 第 2 片 | | | ☐是 ☐否 |

⛔ **切不出「单独上线也能完成一件完整的事」的片 = 这是个大爆炸交付**，
必须写明并让人拍板接受，⛔ 不许默认它。
⚠️ 与 S4 硬约束「垂直切片优于水平分层」是同一条：
**「先做完所有页面再接接口」不是切片，那是分层。**

#### 2 · 自研 vs 现成对照（只列需要自研的）
| 要自研的组件 | 为什么现成的不行 | 粗估人周 | 现成替代品是什么 | 用替代品要牺牲什么 |
|---|---|---|---|---|

⭐ **最后两列是关键**：说不出替代品，说明没查过；
说不出牺牲什么，说明"必须自研"这个结论没有依据。

#### 3 · ⭐ 技术债登记位（此前全流程没有这个位置）
| 债 | 是什么临时方案 | 为什么现在必须这么做 | **什么条件下必须还** | 谁记着这件事 |
|---|---|---|---|---|

⛔ **「先做了再说」如果没有还款条件，它就不是技术债，是永久方案**——
⚠️ 那要按永久方案的标准来评审，不能享受"临时"的豁免。

**典型发现**：
- 「交互规格要求侧栏和主内容区联动动画，但 React 的 layout 重算会导致 200ms 卡顿」
- 「数据依赖表里的实时推送用 WebSocket，但运维说网关不支持长连接——要降级为轮询」
- 「这个设计需要 3 个自研组件（拖拽列表/流式输出/多候选卡片），每个约 2 人周」

### 视角 8 · 算法负责人（算法实现）

**身份**：负责具体算法模型的训练、部署和优化。关注算法接口定义和工程化约束。与算法总监互补——总监看战略和能力边界，负责人看实现和接口。

**专问什么**：
- AI 状态扩展表里的**流式输出**，模型推理框架支持 streaming 吗？token 级还是 sentence 级？
- **置信度阈值**设了多少？不同场景应该用不同阈值还是全局一个？谁来调这个阈值？

⛔ **产品不定**：用什么模型、置信度用 logprob 还是别的、tokenizer 装在哪、部署配置。

⚠️ 一格填不出来 = 那个状态上线后会**没有任何界面**，用户看到的是空白或卡死。

| 必答 | 你的决定 |

### 视角 9 · 多端一致性（双端产品必跑，单端产品跳过）

**身份**：负责跨端体验统一的产品/设计负责人。关注同一功能在 web、桌面、移动端之间的行为是否自洽。

**专问什么**：
- 功能清单里每个标了「两端」的功能，第四章**回答三选一了吗**——两端同一套交互 / 降级版 / 只在一端存在？
- 同名功能在两端的**行为一致**吗？还是名字一样但点下去做的事不同？
- 降级的那一端，**降级边界写清楚了吗**？用户在弱端会不会以为功能坏了？
- 手势与键盘：移动端的滑动操作在桌面端对应什么？桌面端的快捷键在移动端怎么替代？
- 同一份文案在两端的**控件上限不同**（移动端 Toast 更窄），核过吗？
- 数据在两端**同步的实时性**说清了吗？一端改了另一端多久能看到？

**典型发现**：
- 「功能清单标了『两端』，但第四章只写了 web 的交互，移动端到设计阶段才发现没人定义过」
- 「移动端是只读、web 端可编辑，但 PRD 里没写这是有意降级，研发以为是漏了」
- 「Toast 文案 30 字在 web 装得下，移动端上限 18 字装不下」

⚠️ **不回答三选一 ＝ 到 S7 必然返工**，这是本流水线复发率最高的一类返工。

   紫/靛渐变 · **三列特性网格（彩色圆圈图标+粗标题+两行描述，对称重复 3 次——最容易辨认的 AI 布局）** ·
   彩色圆圈图标作章节装饰 · 全部居中 · 统一大圆角 · 装饰色块/浮动圆圈/波浪 SVG ·
   emoji 当设计元素 · 卡片彩色左边框 · 通用 hero 文案 · 千篇一律的章节节奏 · system-ui 作主字体
3. 再跑 **Litmus 7 问**（YES/NO）：
   首屏品牌是否毫无疑义 / 有无强视觉锚点 / 只扫标题能否读懂 / 每节是否只有一个任务 /
   卡片真的必要吗 / 动效是否改善了层级 / **把装饰性阴影全去掉后还高级吗**

**输出格式**：`AI Slop Score: <A-F> — <一句刻薄的定性判词>`

⚠️ **这是反 slop 三层里的第 2 层。** 第 1 层是门禁（机械），第 3 层是生成期约束
（Design Read / memorable-thing / SAFE-RISK 提案）。**只做这一层等于没做。**

### 视角 11 · 架构与可演进性（CTO 视角）

**身份**：技术负责人 / 架构师。**关注的不是「能不能做出来」，而是「三个月后还改不改得动」。**

**为什么必须独立成一个视角**：视角 7「研发负责人」问的是**可实现性与工时**——
那是「这一版做不做得完」。而模块边界、技术债、可观测性、发布与回滚，是**下一版还能不能动**。
本流水线此前把它整块留给 S8 的 `engineering-standards` / `four-node-review`，
而**那时架构已经被 PRD 与设计稿定死了**——S8 能审出问题，却已经改不动。
CEO 视角里那句「三个月后能不能优雅地长出新功能」是产品问法，不是架构判据。

**专问什么**：
- **模块边界**：3.1 的模块划分，是按**业务能力**切的，还是按**技术分层**（前端/后端/数据库）切的？
  按分层切会让每个需求都横跨所有模块 —— 与 S4 硬约束「垂直切片优于水平分层」是同一条。
- **变更半径**：改动最频繁的那个功能，会波及几个模块？**改一个按钮圆角要改 60 处**是设计侧的病，
  它在架构侧的同型是「改一条业务规则要动 6 个服务」。
- **数据模型的单向门**：哪些结构一旦上线就改不动了（用户已有数据、对外接口、埋点 schema）？
  这些是**单向门**，必须在 S4 就拍板，不能等 S8。
- **可观测性**：出了问题怎么定位？日志/指标/链路追踪的设计在哪一章？
  「上线后拿不到验证目标的数据」是营销的痛，「上线后拿不到定位故障的数据」是这里的痛。
- **发布与回滚**：7.2 的回滚条件在技术上**真的可执行**吗？数据迁移做了还能回滚吗？
- **技术债的显式登记**：这一版有意欠下的债，写在哪？谁在什么条件下会还？
  没有登记位的技术债 = 永远不会被还的债。
- **依赖与供应链**：新引入的依赖有多少？许可证核过吗？哪个是单点？
- **可演进性的具体检验**：拿产品路线图里**下一个还没做的功能**，问「按现在这套结构，它加得进来吗」。

**⛔ 强制产出物（写不出＝本视角 FAIL）**：

#### ⭐ 单向门清单（**必须在 S4 拍板，S8 拍不了**）
| 单向门 | 一旦上线为什么改不动 | 现在的决定 | **改错了的代价** | 已拍板？ |
|---|---|---|---|---|
| 数据模型（用户已产生数据的那部分） | 迁移要动存量 | | | ☐是 ☐**否** |
| 对外接口 / 协议 | 别人已经在用 | | | ☐是 ☐否 |
| **埋点 schema** | 报表依赖它，一改就断 | | | ☐是 ☐否 |
| 文件 / 导出格式 | 用户手里已有旧文件 | | | ☐是 ☐否 |
| 计费 / 额度口径 | 涉及钱，改了要对账 | | | ☐是 ☐否 |

⛔ **有一行「否」就不许进 S5**——这些是 `s3-definition.md` 说的单向门：
**其余 70% 信息即可决定，但决定必须现在做**。
⚠️ **不在这张表上的东西默认是双向门，就该快速决定**，⛔ 不要在双向门上追求完美。

#### 变更半径抽样（挑改动最频繁的三个功能）
| `F-xx` | 改一条业务规则要动几个模块 | >3 个的话，问题出在模块边界还是需求本身 |
|---|---|---|

⭐ 「改一个按钮圆角要改 60 处」是设计侧的病，
**它在架构侧的同型就是「改一条业务规则要动 6 个服务」**——同一个病，两张脸。

**典型发现**：
- 「模块按前端/服务/存储切，于是 25 个功能里有 23 个横跨全部三个模块——这不是模块，是分层」
- 「埋点 schema 没定版本字段，上线后一改就断，而报表依赖它——这是个单向门，现在不拍板以后拍不了」
- 「回滚条件写了『核心指标跌 5% 即回滚』，但那次发布带了一次不可逆的数据迁移」
- 「三个自研组件都没有 owner，也没进技术债登记——它们会在半年后变成没人敢碰的地方」

⚠️ **本视角必须在 S4 终审就跑**，不能推到 S8。**S8 能审出架构问题，但那时改的代价已经最高。**

## 三、评审执行流程

### 标准流程（S5.3 完整评审）

```
第一大轮：11 视角各跑一遍（单端产品跳过视角 9，跑 10 个）
  R1  算法总监        → 发现 + 修订
  R2  UI 专家         → 发现 + 修订
  R3  UE 专家         → 发现 + 修订
  R4  市场总监        → 发现 + 修订
  R5  营销总监        → 发现 + 修订
  R6  CEO             → 发现 + 修订
  R7  研发负责人       → 发现 + 修订
  R8  算法负责人       → 发现 + 修订
  R9  多端一致性       → 发现 + 修订（仅双端产品）
  R10 AI Slop         → 发现 + 修订　⚠️ **任何时候不许跳**（铁律 16）
  R11 架构与可演进性    → 发现 + 修订　⚠️ **S4 终审必跑**，推到 S8 就来不及了

⚠️ 📌 这张列表曾经**只列到 R9** —— 少的正好是那个「任何时候不许跳」的视角 10。
   照着流程执行的人会永远跳过它，而流程本身看起来完整。
   **现在由 `consistency-gate.py` 的 `perspective-count` 规则守着：
   视角库里有几个视角，这张表就必须列几个。**

第二大轮：全部视角复审（检查第一轮修订是否引入新问题）
  各视角复审 → 结构性发现?

  所有视角均零结构性发现 → 收敛
  否则 → 修订 → 再跑一轮
```

### 快速评审（S6 出场前 / 时间紧张）

从 10 个视角中选最相关的 3-4 个跑（双端产品必含「多端一致性」；**视角 10 AI Slop 任何时候都不许跳**）：

| 产品类型 | 推荐快审视角 |
|---------|------------|
| AI 产品 | 算法总监 + UE 专家 + 研发负责人 + 算法负责人 |
| 消费级 App | UE 专家 + 营销总监 + CEO + UI 专家 |
| B2B 工具 | 研发负责人 + UE 专家 + CEO + 市场总监 |
| 设计驱动产品 | UI 专家 + UE 专家 + CEO + 市场总监 |
| 双端产品 | 多端一致性 + UE 专家 + 研发负责人 + UI 专家 |

### 轻量评审（单个产物变更）

只改了某一个产物（如只改了 DESIGN.md），只跑与该产物最相关的 2 个视角。

```markdown

| # | 发现 | 严重度 | 建议修订 | 影响范围 |
|---|------|--------|---------|---------|

| # | 建议 | 理由 | 采纳？ | 不采纳理由 |
|---|------|------|--------|-----------|

```

## 五、评审中的诚实边界

- **AI 扮演专家不等于等价替代真人专家**。AI 的评审覆盖的是「有经验的人一定会问的问题」，覆盖不了「只有在这家公司待过三年才知道的坑」。
- **评审报告里必须写**：本轮由 AI 扮演，如有领域盲区请真人补充复审。
- **跨视角冲突**（CEO 说砍功能 vs 营销说这是卖点）不由 AI 裁决——冲突记录后**提交用户拍板**。
- **视角的发现如果互相矛盾**（研发说做不了 vs CEO 说必须做），两条都保留，标注冲突，不偷偷只留一条。
