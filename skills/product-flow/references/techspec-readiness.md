# S8 联合方案就绪度：S2–S7 够不够写出技术、算法与测试方案

> **用户 2026-08-31 定的验收标准**：
> **研发、算法与测试要根据 S2–S7 输出 S8 联合方案，然后才研发。所以 S2–S7 必须让需求「准确、明确、细节 ok」。**
>
> 判据因此不是「能不能开始写代码」，而是**「能不能据此写出一份技术、算法与测试联合方案」**——这是更早、也更严的一道线。
>
> ⚠️ 本文件与 `testcases-readiness.md` **对称**：那份判「PRD 够不够写用例」，
> 这份判「S2–S7 够不够进入 S8」。**同一条纪律：不够就报缺口，绝不猜补。**

---

## 〇、三个词各自怎么验

| 词 | 含义 | 谁来验 |
|---|---|---|
| **准确** | 每条需求可归三来源之一（用户 / 查证 / 登记的假设），**没有第四种** | M2 + `research-gate` 的来源判据 |
| **明确** | 无歧义、可判定、无含糊形容词 | `requirements-quality-gate.py` |
| **细节 ok** | **足以支撑技术选型与架构决策** | **本文件（此前没有任何东西验这一层）** |

⭐ 前两个已有机制，**第三个是这次补的**。它和前两个不是一回事：
一条需求可以既准确又明确，却**细不到能让人做技术决策**——
「支持批量导入，单次上限 500 张」是准确且明确的，但它没告诉技术方案：
**数据怎么存、并发怎么处理、失败一半怎么办、十万张时还成立吗。**

---

## 〇之二、⭐⭐ 职责边界（用户 2026-08-31 明确，这条决定了本表怎么用）

> **S2–S7 是产品与设计主导的**，目的是把**需求、设计、交互**说明确。
> **研发、算法与测试负责人据此在 S8 共写一份飞书联合方案，然后 S9 才开发。**

| 谁 | 给什么 | 一句话判据 |
|---|---|---|
| **产品**（S2/S3/S4） | **是什么 · 给谁 · 做到什么程度 · 什么算对** | 「**这件事该不该这样**」——产品能拍板 |
| **设计/交互**（S5/S6/S7） | **长什么样 · 怎么操作 · 各状态什么样** | 「**用户看到什么、能做什么**」 |
| **研发**（技术方案） | **怎么做到** | 「**用什么技术、怎么实现**」——产品不该替它决定 |
| **算法**（算法方案） | **是否需要算法、如何证明有效并可退化** | 「**基线、数据、评测、成本、监控和回滚是否成立**」 |
| **测试**（测试方案） | **如何证伪风险与验收交付** | 「**在哪一层、用什么数据和判据证明**」 |

### ⛔ 本表**不要求**产品给这些（它们属于技术方案）
接口路径与协议 · **错误码的命名** · 分页用 offset 还是 cursor · 索引与存储选型 ·
**前后端各自怎么判权限** · 迁移脚本怎么写 · 部署与环境搭建。

### ✅ 但产品**必须**给它们对应的那一面
| 技术方案要决定的 | 产品必须先给的 |
|---|---|
| 错误码怎么命名 | **有哪些错误场景 · 用户看到什么 · 能不能重试** |
| 分页方式与索引 | **数据量级 · 单页要显示多少 · 可按什么排序筛选** |
| 权限在哪一层校验 | **角色×操作矩阵 · 越权时用户看到什么** |
| 迁移脚本怎么写 | **老数据能不能丢 · 老用户会看到什么 · 回滚时用户视角发生什么** |
| 日志与指标怎么埋 | **上线后要能回答哪些问题** |

⭐ **判据**：一件事如果**换一个技术栈答案就变**，它属于技术方案；
如果**换技术栈答案不变**，它属于产品/设计，必须在 S2–S7 给出。

⚠️ **我在本轮评审中越过这条线一次**：曾把「错误码表」「前后端各自怎么判权限」
「迁移脚本」写进 PRD 模板要求产品填——**那是替研发做技术决定**。已收回为上表右列的形态。

## 一、判定表（逐项核，缺了写清缺什么）

|---|---|---|---|---|---|
| T1 | **功能范围与批次** | 产品 | 做什么、不做什么、**哪些是本期** | 技术方案不知道给哪个范围做设计 | S3 定义 · PRD 3.2 |
| T2 | **业务实体与关系** | 产品 | 有哪些实体、主键、实体间关系与基数 | ⛔ **建不了数据模型**——这是技术方案的地基 | **缺口，见下** |

## 二、结论只有三种（与用例就绪度同一纪律）

| 结论 | 条件 | 该做什么 |
|---|---|---|
| **可写方案** | T1–T9 齐备，T10–T14 齐备或明确不适用 | 进入 S8，分别完成技术/算法/测试并联合对账 |
| **部分可写** | 部分模块齐备 | 对齐备的写；缺的列缺口，方案里标 `[待补需求·不设计]` |
| **不可写** | T2 / T3 / T6 大面积缺失 | **只出缺口报告，停在这里** |

⛔ **不存在第四种，尤其不存在「基本可以，我按常规假设一下」**——
那是把技术假设伪装成需求，**而它会被当成需求实现出来，且没人知道它是假设**。

## 三、四个缺口的具体补法（本轮已补进模板）

### T2 · 数据实体与关系（附件 D 新增 D.0）
字段规格回答「这个框填什么」，**回答不了「系统里有哪些东西、它们什么关系」**。
→ 附件 D 增 **D.0 实体关系**：实体 · 主键 · 关系与基数（1:1 / 1:N / N:M）· 生命周期（谁创建谁删除）。

### T6 · 数据量级与增长（NFR 存储类下）
「能跑」和「十万条也能跑」是**两个不同的技术方案**。
→ 明确：当前量级 · 12 个月预计 · 单用户上限 · 单次操作上限。

### T8 · 外部依赖的集成契约与失败模式（五章 5.4 扩表）
只写「依赖 X 服务」不够。→ 增列：**契约形态 · 配额/限流 · 超时 · 失败时降级到什么 · 谁负责**。

### T11/T12 · 迁移兼容与验收环境（七章 7.2 扩）
→ 增：**已有数据怎么迁 · 迁移后还能不能回滚 · 老版本客户端怎么办**；
**研发自测环境 · 测试数据来源与脱敏要求**。

## 四、怎么用

**S4 出场时**跑一遍本表（人工逐项），把结论写进 PRD 附件 H.1 下方：

```
技术方案就绪度：可写 / 部分可写 / 不可写
缺口：T6 数据量级未定（owner: <产品>，到期 <日期>）
```

⚠️ **S7 定稿之后、S8 开工之前，必须再跑一遍**——
因为设计与交互阶段常常引入新的技术约束（某个动效要求虚拟列表、某个状态要求长连接）。

## 五、诚实边界

- 本表判的是**「够不够写」，不是「写得对不对」**。方案质量归 S8 的研发/算法/测试交叉评审、`s8-solution-gate.py` 的结构检查与人工批准。
- ⭐ **它也判不出「需求本身是不是对的」**——一份细节完备但方向错误的需求，
  会顺利通过本表，然后被高效地实现成一个错的产品。**那道关在 S3。**
