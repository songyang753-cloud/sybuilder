> 复述一次就多一处会过期的副本。

## ⛔ 先声明：哪些是标准，哪些是团队约定

**装傻会害人**。下面三条如实写在前面，模板与本文都不许把团队约定说成标准：

| 说法 | 实情 |
|---|---|
| BPMN 2.0 是业务流程图的标准 | ✅ **真**。OMG 官方规范，formal/2014，定位原文是「de-facto standard for business processes diagrams」 |
| **BPMN 规定了 AI 节点怎么画** | ❌ **假**。标准里**没有**任何 AI 节点记法。有论文系统论证这个空白：BPMN 缺少表达 agent 置信度、策略、决策过程的建模构件，置信度「只能用文本注释写自然语言」而这会「导致歧义和误解」。⇒ 本文第 1 节的 AI 追加档全部是**团队约定** |
| 「产品架构图 / 技术架构图 / 系统架构图」三分法 | ❌ **无任何国际标准**。中文产品圈行业惯例。英文世界的 "product architecture" 指制造业的模块化产品设计，与此无关 |
| 「生态层」「优化层」是 AI 架构的层 | ❌ **查无依据**。中英双语定向检索（含 `"ecosystem layer"` / `"optimization layer"` 精确匹配）**零命中**。⛔ 不许写进任何图 |
| `BPMN 2.0 = ISO/IEC 19510:2013` | ⚠️ **未证实**。该编号只在二手源出现且无年份，ISO 官网访问受限。⛔ 不许引用这个精确编号 |
| 向量库 / embeddings / 知识图谱的图示记法 | ❌ **没有任何标准**。第 5 节的画法是从 DFD 构件定义与 EDPB 结论推导的，属团队约定 |

## 第一性约束：图与 PRD 必须 ID 对齐、颗粒度同族

**一句话**：图里不许出现 PRD 表格里没有的东西；表格里的东西也不许在该出现的图上缺席。

| 图 | 节点 ID 族 | 对应表 |
|---|---|---|
| 产品模块图（原称产品架构图） | `M-xx` | 6.1 模块设计 |
| 功能架构图 | `F-xx` | 6.2 功能清单 |
| 信息架构 / 站点地图 | `P-xx` | 6.3 页面结构 |
| 业务流程图 | 泳道=角色；每个系统动作标 `F-xx` | 七章功能卡 |
| 数据生命周期图 | data store ↔ 附件 D 实体 | 附件 C.1 数据清单 |
| **用户流程图**（4.4） | ⛔ **无 ID 族**（见第 7 节末尾的理由） | —— |

**颗粒度两条硬规则**：

1. **层内同级**——单张图内节点 ID 只允许**一种前缀族**。出现 `F-01` 与 `FR-001` 并排即越级（`FR` 属附件 A，比 `F` 细一层）。
2. **图表同级**——一张图的粒度 = 它对应的那张表的粒度。功能架构图画到 `F` 级，就不许出现比 `F` 更细的东西。

**这条约束决定了工具选型**：图源必须**文本可解析**，否则节点 ID 提不出来，对账无从谈起。

## 1 · 业务流程图（五章）

**定位**：BPMN 2.0 的**受限子集**——用泳道、起止事件、XOR 判定、异常事件，⛔ **不启用** task 类型图标与复杂网关。业务方读得懂，研发接手时可无损升级为可执行 BPMN。

**为什么不用完整 BPMN**：Camunda 官方参考手册原话——task 类型「主要用于建模**技术可执行**的流程」，「实践中极少使用」。PRD 的读者是业务方与设计。

**为什么必须有泳道**：泳道图（Rummler-Brache, 1990）的全部要点是**让交接可见**——组织的价值流横向穿过部门，问题出在部门之间的 white space。ISO 5807 那套「矩形/菱形/椭圆」符号**天生不表达角色**（它管的是程序与数据流），所以才需要叠加泳道。

### ⭐ 三类流程都要画（2026-09-15 新增；⛔ 只画主流程 = 没画）

| 类别 | 画什么 | 漏掉的后果 |
|---|---|---|
| **主流程** | 业务正常走通的闭环路径，含各环节功能职责 | —— |
| **分支流程** | 条件分叉出去的**合法**路径（不同角色/档位/入口） | 研发把分支当异常处理，或干脆不做 |
| **异常流程** | 失败/超时/无权限/无数据/风控拦截/用户放弃/AI 低置信 | **上线后才发现没人定义过失败长什么样** |

三类可同图（泳道＋颜色区分）或分三张；⛔ 「异常见附件 E」不算——附件 E 是逐功能的状态与边界，
回答不了「异常在**业务流转**上走到哪」。

### ⭐ 图例约定（⛔ 团队约定，BPMN 标准无 AI 节点记法）

| 记法 | 含义 |
|---|---|
| 蓝色色块 | 正常流程节点（用户操作 / 系统动作） |
| 黄色色块 + 菱形 | **AI 模型判定节点**，必须注明模型能力类型（如「语义意图识别」） |
| 红色色块 | 异常处理节点 |
| 绿色色块 | 降级策略节点 |
| 紫色色块 | 数据收集节点（埋点 / 样本回流） |
| 虚线框 | 参数可配置节点（运营可调，⛔ 改它不需要改流程） |

节点内建议标注：`【输入】` `【输出】` `【参数】参数名` `【可扩展】`。

> 🚨 **这里有一处真冲突，本规范选择显式记录而不是抹平**：
> 外部资料要求「用菱形框**标注判定规则**」并在节点内写 `【参数】`；
> 而下面 AI 追加档**第 11 条**是「阈值**数值不写在图上**」。
> **调和口径**：图上写**参数名与判定语义**（`置信度是否达标？(conf_threshold)`），
> ⛔ **不写当前取值**（`≥0.8`）；取值的唯一正本是 PRD 附件 B.2。
> ⇒ 判定规则在图上可读（满足前者），调参不必改图重评审（满足后者）。
> ⚠️ 若某天团队决定把取值也画上去，⛔ 不要直接改第 11 条 —— 先在此处写下新的取代理由。

### 基线档判定清单

1. 把所有箭头删掉，信息量是否明显下降？没下降 → **这是功能清单不是流程图**
2. 每条泳道回答的是「**谁**」而不是「什么模块」？
3. 一张图内泳道粒度统一吗（⛔ 不混「销售部 / 张三 / CRM」）？
4. 同组织内的不同角色是**同一 pool 的多条 lane**，而不是多个 pool？
5. 每个 XOR 判定 ≥2 条出边，标签**互斥且穷尽**前一个活动的全部结束状态？
6. 判定所需的事实，由该网关**之前**的活动产出了吗？（⛔ **网关不是任务**）
7. 每个外部依赖有失败分支？每个等待有超时路径？有用户中途放弃的路径？
8. 异常分支终点明确（回到某步 / 走人工 / 终止并告知），⛔ 没有断头箭头？
9. 单层活动 ≤10 个？超了折叠成子流程？

### AI 追加档（⛔ 全部是团队约定，标准无规定）

10. 每个 AI 节点**≥2 条出边**（达标 / 不达标）。**只有一条出边 = 把概率性节点画成了确定性节点**
11. 阈值**数值不写在图上**——阈值是会漂移的运营参数（0.85→0.9），画进图等于每次调参都要改图评审。图上只留「置信度是否达标？」，数值进参数表/决策表
12. AI→人工是**显式带标签的边**，⛔ 不是隐含的「失败就人工」
13. 切换那一刻，接手的人拿得到三样：**当前处境 / 下一步做什么 / 怎么做**（Google PAIR "Return control to the user"）
14. 人工兜底**也失败**的路径画了吗（升级 / 终止 / 告知）？
15. **有没有离线质检回流支路**——PAIR 的 background errors（系统工作不正常，**用户和系统都没察觉**）在主流程上是一条**永不触发的边**。不画出来，实现时就没人做
16. 每个 AI 节点在附件 B.2 有对应行（延迟 / 准确率 / 阈值 / 降级）？
17. **泳道默认四条都考虑过了吗：用户 / 系统 / 第三方 / 算法** —— ⭐「算法」单列，
    ⛔ 不要混进「系统」；这样 AI 节点天然成组，人机切换的边一眼可见
18. 异常边覆盖了**七类**吗：弱网 / 接口失败 / 超时 / 无权限 / 无数据 / **风控拦截** /
    **模型失败·低置信度（AI 特有）**（清单与四列结构见模板附件 E.2）

## 2 · 功能架构图（6.2）

**权威定义**（SEBoK，INCOSE + IEEE Systems Council + SERC 共同治理）：系统为达成使命目标，把输入变换成输出的那组相互关联的**变换过程**。⚠️ 这里的 function 接近数学/编程意义的 `y = f(x)`，不是系统工程里泛指的「为达成目标所做的动作」。

⚠️ **功能架构 ≠ 行为架构**：功能架构关心*输入→输出的变换*，行为架构关心*动作的时序与执行*。

### 必含元素（SEBoK 的六项，⭐ 标的两项是最常漏的）

1. 系统用以达成目标的**功能能力**
2. 这些功能的**输入与输出**
3. 把输入变换成输出的**步骤**
4. 步骤归拢成**可独立执行**的子功能，并定义各自 I/O
5. ⭐ **各系统模式下 I/O 与执行的差异**（冷启动 vs 稳态、在线 vs 离线、正常 vs 降级、免费 vs 付费）
6. ⭐ **内部与外部接口**——⛔ 不只是对外接口

### 基线档判定清单

1. 图上每个方块能写成**动词短语**吗？只能写成名词 → **它是组件不是功能**
2. 每个方块的输入/输出，说得出具体的数据/事件吗？（⛔ Pitfall: 忘了 I/O 只画动作 = 画成了功能清单的树）
3. 每个功能对得上哪条业务目标 `OBJ-xx`？答不出的**删掉**
4. 子功能**可独立执行**吗？两块之间除了图上那根箭头，还有隐藏的共享状态吗？
5. 同一张图上抽象层级一致吗？（⛔ 「用户登录」与「JWT 签名校验」并排即越级）
6. 这张图是**先有场景再画的**，还是先列清单再画的？（SEBoK proven practice：**先场景，后分解树**——只有前者合格）
7. 图上出现具体技术选型（Redis / K8s / 模型名）了吗？出现即**移去附件 N**
7b. ⭐ **拆到叶子了吗**（2026-09-15 新增）：验收判据是——任何一个叶子节点，
   **研发问你「这个具体怎么做」时，你不需要再解释第二遍**。
   ⛔ 叶子写成「排序功能」这种同义反复 ＝ 没拆完；只拆一层就停 ⇒ 研发反复来问细节然后返工。
   ⚠️ 挑**看起来最简单**的模块做示范（如「搜索」）——**越简单的东西越容易被漏拆**：
   一个搜索模块内部其实是「搜（筛选/排序）」与「主动引导（热搜/排行榜/历史词/好友）」**两套完全不同的逻辑**。
7c. ⭐ 本图与 PRD 6.2 功能清单表**双向集合相等**吗？图上每个叶子 `F-xx` 在表里有行，表里每个 `F-xx` 在图上有叶子

### AI 追加档

8. **在线推理链路（inference pipeline）与离线回训链路（ML pipeline）在图上分开了吗**——⛔ 这是中文圈最常见的错误：画成一张图
9. 回训箭头**标了触发条件**吗（on demand / schedule / new training data / performance degradation / concept drift）
10. 训练用特征与服务用特征是**同一来源**吗（training-serving skew）？图上看得出吗
11. 模型产出到上线之间，有 **model validation** 节点吗（对 baseline 做对比）
12. ⭐ **`model monitoring` 与「服务器监控 / 日志」分开命名了吗**——前者在 AI 产品里是**功能**（它产出「是否触发重训」这个决策，Google 列为 8 步流程第 8 步、AWS 列为六阶段最后一阶段），后者才是运维。⛔ 不分开，评审时永远吵不清

## 3 · 产品模块图（6.1）

⚠️ **本图的三分法是团队约定，无国际标准**（见文首声明）。

**切分线**（⛔ 越过即换图）：

| 出现了什么 | 该去哪 |
|---|---|
| 具体技术选型 / 部署拓扑 / 协议 / 服务器 | **附件 N 技术架构图** |
| 类 / 接口 / 表结构 | C4 L3/L4，不进 PRD |
| 功能模块 + 信息流转 + 系统边界 | ✅ 就是本图 |

**三层**（行业惯例）：用户感知层（在何种场景通过何种方式触达用户）/ 功能模块层（哪些模块实现核心功能、与哪些外部平台有信息交互）/ 数据层（数据从哪来、沉淀到何处去）。

### ⭐ 画的顺序决定这张图成不成立（2026-09-15 新增；⛔ 顺序反了图就废了）

1. 先写**业务域**大类标签（导购 / 交易 / 营销）——**不是功能名**；
2. 再往每个域右侧补**模块**方块（导购＝Home｜Search｜Detail，交易＝支付｜售后，营销＝优惠券｜积分｜拼团）；
3. 最后把同一域的方块**圈起来**——⭐ **一圈就是一个团队的边界**。

⛔ **一上来就写「首页、搜索、购物车、优惠券…」这堆功能名，这张图就废了**：
它退化成功能清单（那是第 2 节），失去顶层视角。
**判据（⚠️ 允许两种合法分组，⛔ 不允许不分组）**：每个模块方块必须挂在一个**顶层分组**下，
分组 2–5 个、每组 2–4 个模块。顶层分组二选一：

| 分组方式 | 什么时候用 | 例 |
|---|---|---|
| **业务域** | 产品跨多个团队 —— ⭐ **一圈就是一个团队边界**，这是本图最值钱的用法 | 导购 / 交易 / 营销 |
| **行业三层** | 单团队产品，重点是讲清「谁触达用户、谁实现能力、数据去哪」 | 用户感知层 / 功能模块层 / 数据层 |

⛔ 不合法的是**第三种**：既不是业务域也不是三层，直接平铺一堆功能名。
⚠️ 2026-09-15 记：本仓自带的 `product-architecture.example.d2` 用的是**三层**分组 ——
若本条只认业务域，规范就会判自己的示例不合格。**两种都收，是核对过示例之后的结论，不是和稀泥。**
⭐ 这张图的两个定性：**最具顶层视角**（给老板与跨团队看的第一张图）、**区分团队职能**
（一圈就是一个团队，谁该被拉进这个会一目了然）。

### 基线档判定清单（1–10 抄 C4 官方 review checklist，可直接引用）

1. 图有**标题**吗？
2. 能看出这是**哪一类图**吗？
3. 能看出这张图的**范围（scope）**吗？
4. 有**图例 / key** 吗？
5. 每个元素都有**名字**吗？
6. 每个元素的**类型（抽象层级）**都能看出来吗？
7. 每个元素**做什么**都能说清吗？
8. 每条箭头都有**描述其意图**的标签吗？
9. 描述文字和**箭头方向一致**吗？
10. 所有**颜色 / 形状 / 图标 / 线型 / 箭头头 / 边框样式**的含义都懂吗？
11. 外部系统边界画了吗？自研与第三方分得出来吗？
12. 同层子模块**互斥不重叠**吗？（一个问题只在同一层解决）

### AI 追加档

13. 哪些模型**自研可控**、哪些**第三方黑盒**，图上分得出来吗
14. 每个模型节点写了**输入/输出契约与能力边界**吗（⛔ 不写内部结构——契约而非实现）
15. 模型失效或效果不达预期时的**产品侧降级路径**在图上吗
16. 第三方 API 依赖画在**外部系统边界之外**吗？（C4 官方对外部系统的定义就是「你不拥有、不负责的依赖」，天然黑盒语义）⛔ **不设「生态层」**
17. ⛔ A/B 测试**不入**架构图——它是运营能力，与其余层**性质不同质**（其余层是「构成」，它是「流程」）

## 4 · 信息架构（内容组织）+ 站点地图（6.3）

**权威定义**（Rosenfeld & Morville）：IA 是**组织系统 / 标签系统 / 导航系统 / 搜索系统**在站点与内网中的组合（第 4 版新增 **metadata** 为并列要素）。

⚠️ 作者本人拒绝给单一定义（"Were you expecting a single definition? Keep dreaming!"）——引用时应说明这是四条定义之一。

### ⛔ 五个词必须分清（中文圈把它们混用，这是最大的误用源）

| 想表达 | 该叫 | 一句判据 |
|---|---|---|
| 内容分类 / 命名 / 导航 / 搜索 | **信息架构（内容组织）** | 箭头表示「A 属于 B」 |
| 页面层级树 | **站点地图** | 「IA 是抽象，sitemap 是制品」 |
| 数据从哪来、经过什么、落到哪 | **数据流图 DFD** | 箭头表示「数据被传过去了」；⛔ **无判断、无循环** |
| 采集→标注→训练→推理→删除 | **数据生命周期图** | 见第 5 节 |
| 用户完成一个任务的步骤 | **用户流程图** | 有菱形判断与回环 |

两句可直接做判据（NN/g）：
- **「IA 不是屏幕上的 UI，IA 指导 UI。IA 记录在表格和图里，不在线框图里。」**
- **「sitemap ⊂ IA；IA 是抽象，sitemap 是制品。」**——且 sitemap **故意不完整**（完整到 IA 的程度会把干系人淹没）

### 基线档判定清单

1. 内容类型与功能清点过吗（content inventory）
2. 按什么维度分类——主题 / 时间 / 受众 / 任务？
3. 每个类目对用户显示的名字是什么？为什么是这个词不是同义词？有**受控词表**吗
4. 从首页到任意内容有几条路？分别是哪几种导航（全局 / 局部 / 上下文 / 补充）

## 5 · 数据生命周期图（附件 C.5，AI 产品必填）

⚠️ 这不是可选项，是**合规硬要求**。且⛔ **GDPR Art.30 要求的是书面记录不是图**——图是摘要，**表是正本**，不许拿图交差。

### 三条法源

| 来源 | 要求 |
|---|---|
| **EDPB Opinion 28/2024** | 个人数据可能「**被吸收进模型参数**」，用个人数据训练的模型**不能一概认为是匿名的** ⇒ **删除链路必须画到向量库、索引、缓存、模型权重本身** |
| **EU AI Act Art.10(2)** | 数据来源与**原始采集目的**(b) · **标注 / 清洗 / 更新 / 富化 / 聚合**(c) · 数据集假设(d) · **偏见审视，尤其当输出会影响未来输入时**(f) · 缓解措施(g) · 数据缺口(h) |
| **GDPR Art.30 / Art.35** | 保留期限、接收方、跨境传输；DPIA 需要「对预期处理操作的**系统性描述**」 |

⚠️ AI 产品**基本必然落入 DPIA 范围**——Art.35(1) 明确触发条件含「尤其使用新技术」，35(3)(a) 点名「自动化处理，包括画像」。

### 判定清单

1. 每类数据从哪来？**原始采集目的**是什么
2. 做了哪些准备操作——标注 / 清洗 / 更新 / 富化 / 聚合？各由**谁**做、在哪做（是否外包、是否跨境）
3. 数据落在哪几个 store？原始库 / 特征库 / **向量索引** / 缓存 / 日志 / **模型权重**，一个都没漏吗
4. 每个 store 的**保留期限**？**删除触发条件**？
5. ⭐ 用户行使删除权时，删除要打到**哪几个 store**？**向量索引和模型权重在链路里吗**
6. 有**反馈回路**吗——线上输出是否回流成下一轮训练输入
7. 数据集做了哪些**前提假设**（假设它测量和代表了什么）
8. **偏见审视**做了吗？缓解措施是什么？已识别的**数据缺口**怎么补
9. 每个环节对得上 NIST AI RMF 七阶段里的哪一个？哪个阶段是空白（⚠️ 尤其 Operate and Monitor）
10. 这张图能**直接生成** Art.30 的书面记录与 DPIA 的系统性描述吗

### 记法（⛔ 团队约定，无标准）

| 元素 | 画成 | 依据 |
|---|---|---|
| 向量数据库 / 索引 | **data store** | DFD 原文：「warehouse 的呈现独立于实现」——向量库合法地就是一个 data store |
| Embedding 生成（切块、向量化） | **process** | 符合 DFD process 定义（把输入变换成输出） |
| **模型权重** | **data store，并标注「可能含个人数据」** | EDPB 的 "absorbed in the parameters" |
| 标注 / 打标 | **process**，写明标注方、是否外包、是否跨境 | AI Act 10(2)(c) 点名 annotation, labelling |
| 反馈回路 | **显式回流箭头** | AI Act 10(2)(f) |

### ⚠️ 中文渲染的实测事实

- macOS **没有任何 CJK 的 `.ttf`**（PingFang / Hiragino / STHeiti 全是 `.ttc`，D2 不收）⇒ 需另备 Noto Sans SC

## 7 · 用户流程图（4.4）

> ⚠️ 本节是补的：模板 4.3 要求这张图，而前六节都没覆盖它 ——
> 于是产品经理**拿不到任何判定依据**就要画。2026-09-12 自查发现。

### ⛔ 先分清三个常被混用的东西

| 名字 | 有没有分支 | 画的是什么 | 什么时候用 |
|---|---|---|---|
| **任务流 task flow** | ⛔ 没有分支 | 一条**唯一**的成功路径 | 只想说明「顺利时是这么走的」 |
| **用户流程图 user flow** | ✅ 有菱形判断与回环 | **单个用户**完成一件事的步骤序列，含岔路与失败 | 4.4 要的是这张 |
| **线框流程图 wireflow** | ✅ 有 | 在流程节点上直接贴**界面缩略图** | 交互稿阶段，不是 PRD 阶段 |

🚨 **出处必须说清楚，因为我第一版写错了并当场被查证推翻**：

| 说法 | 真实出处 |
|---|---|
| **wireflow** | ✅ NN/g 的文章 *Wireflows: A UX Deliverable for Workflows and Apps* |
| **user flow** | ⚠️ NN/g 术语表定义为「完成一个常见任务所需的**典型或理想**步骤」，<br>并说它可以用 **wireflow / 流程图 / 任务图**来**表现** |
| 「task flow 无分支 / user flow 有分支」的**三分法** | ⛔ **团队约定**。这是 UX 圈流行说法，⛔ **不是 NN/g 的定义**，也没有 ISO/IEEE 级标准 |

⚠️ **注意这里有一处真实冲突，别装作没有**：
NN/g 的 user flow 是「典型或理想步骤」，而**本模板 4.3 明确要求画出岔路与失败分支**。
⇒ **我们的要求比那个通行定义更严**。理由：只画理想路径的图，
⛔ 恰恰回答不了 PRD 最需要回答的那个问题 ——「用户在哪儿会卡住」。
⇒ 所以下面的判定清单**按我们的更严口径**写；⛔ 不要拿它去声称「NN/g 要求这样画」。

### ⛔ 它与五章业务流程图的边界（模板里已写死，这里给判定法）

| | 用户流程图（4.4） | 业务流程图（五章） |
|---|---|---|
| 主语 | **一个**用户 | **多个**角色 |
| 泳道 | ⛔ 通常不用泳道 | ✅ 泳道=角色 |
| 关注 | 这个人**依次做了什么、在哪儿会卡住** | 事情**在角色之间怎么流转、谁签字** |
| 一句话判定 | 「换个人来做会不会不一样？」**不会** ⇒ 用户流程图 | **会** ⇒ 业务流程图 |

⚠️ 最常见的误用：**把业务流程图缩小成一条线就当用户流程图** ——
丢掉了岔路和失败分支，于是这张图只回答了「顺利时怎么走」。

### 基线档判定清单

这张图画完之后，应该能回答：

1. 用户**从哪儿进来**？（入口不止一个就要全画）
2. **成功路径**是哪条？⛔ 它必须是图上可一眼指出的一条连续线。
3. 每个菱形判断的**两条分支都画了吗**？（只画 yes 不画 no 是最常见的缺口）
4. **失败/放弃**之后去哪？⛔ 不许悬空 —— 悬空就是在图上说「用户消失了」。
5. **回环**在哪？（重试、返回上一步、改输入后再来一次）
6. 哪些步骤是**用户做的**、哪些是**系统做的**？（两种节点要能区分）
7. 这条流程**在哪一步最可能流失**？⭐ 画不出这个，说明还是在画理想路径。
8. 每个终点是不是都是**真终点**？（既不是死胡同，也不是「然后呢？」）

### AI 追加档（⛔ 团队约定，无标准）

AI 参与的步骤，图上必须显式出现这三样，⛔ 缺一条这张图就是在粉饰：

| 必画 | 为什么 |
|---|---|
| **不确定分支** | AI 给不出高置信结果时用户看到什么？⛔ 不许只画「AI 返回结果」那条 |
| **人工接管入口** | 用户怎么绕过 AI 自己来？⛔ 没有这条＝把人锁死在模型里 |
| **纠错回路** | 结果不对时用户怎么告诉系统？纠正后**回到哪一步**？ |

⚠️ 记法与五章一致：判定用 ◆、人机切换用 ⇄、AI 不可用的降级用**虚线**。
⭐ 与五章那条同源的纪律：**降级路径必须画出去向**，
⛔ 不画就等于默认它走绿线 —— 读图的人会以为那条路不存在。

2. **真实流失点**：第 7 问靠的是画图人的判断，⛔ 不是数据。有埋点数据就用数据推翻它。
3. 用户流程图**没有 ID 族**（不像 M/F/P），所以 `diagram-id-gate` **不对账这张图** ——
   ⛔ 这是刻意的：4.3 的步骤是行为不是功能条目，硬给它编号会造出第二套编码体系。
   ⚠️ 代价是它比其余六类**少一层机器检查**，只能靠上面的清单人工过。

## 8 · 页面关系图（6.3）

> 2026-09-15 新增。它此前**被规范漏掉了**：模板 6.3 只要求 IA + 站点地图，
> 而「一共有多少页面、它们怎么跳转」这个研发排期与设计出图**必须回答**的问题，
> 在整份规范里没有任何一类图承载。⇒ 同 [[feedback_deliverable_required_but_unspecified]]：
> **要求交付的集合 ≠ 定义了判据的集合**。

**它回答什么**：节点＝页面，连线＝跳转。受众是研发排期与设计出图。

### ⛔ 与相邻三类图的分工（本节存在的全部理由）

| 图 | 回答什么 | 回环 | 节点是什么 |
|---|---|---|---|
| 信息架构 / 站点地图（第 4 节） | 页面**怎么组织**（层级） | ⛔ 无 | 类目 / 页面 |
| **页面关系图（本节）** | 页面之间**怎么跳转**（全量拓扑） | ✅ **允许** | **页面 `P-xx`** |
| 用户流程图（第 7 节） | **一个用户**怎么走完**一件事** | 按任务 | 步骤 |
| 业务流程图（第 1 节） | **跨角色**的业务流转 | ✅ | 活动 / 泳道 |

### 基线档判定清单

1. 每个节点是**一个页面**并带 `P-xx` 编号吗？（⛔ 节点写成「搜索功能」＝画成功能树了，那是第 2 节）
2. 每条连线有**触发条件**标签吗（「搜索」「点击商品」「点击提交」）？
3. 页面集合与 6.3 站点地图**双向集合相等**吗？差集非空即红
4. ⭐ **与 4.4 用户流程图并排对照过吗**——4.4 写用户心智（找→了解→下单→收），
   本图画系统实现（首页→搜索结果页→商品详情页→支付页→成功页），**必须一一对得上**。
   判据：4.4 的每一步都能指出由哪个 `P-xx` 承载；本图每个 `P-xx` 都服务于至少一条 4.4 路径。
   ⛔ 对不上 ⇒ 要么页面做了没服务主路径，要么主路径某步没有页面承载
5. 有**回到上游**的边吗（支付页 → 购物车、详情页 → 首页）？只有单向主链＝漏了返回与重入
6. 有**失败/取消**后的落点吗（支付失败去哪、取消登录回哪）
