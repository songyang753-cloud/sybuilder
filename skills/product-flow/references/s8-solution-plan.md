# S8 · 技术、算法与测试方案（飞书原生交付）

## 一、定位与边界

S8 是独立的**方案阶段**，不是研发阶段的一个小步骤。它把 G7.5 已冻结的产品、视觉与交互合同转成一份可以实施、验证、灰度和回滚的联合方案。三类专业判断必须在写代码前闭环：

1. 研发总监回答“系统怎样可靠、安全、可维护地实现”；
2. 算法负责人回答“是否需要算法，数据和评测能否证明它优于基线”；
3. 测试负责人回答“哪些风险必须被怎样证伪，什么条件才准许发布”。

**唯一主交付件**是飞书原生文档《<产品/版本> 技术、算法与测试方案 vX.Y》，模板为 `templates/s8-solution-plan.md`。本地 md 仅作受控源稿/镜像；OpenAPI、JSON Schema、DDL、C4/D2 图源、评测配置、测试清单等机器产物保留各自权威文件，在飞书文档中记录 URI、版本、hash 与用途，不复制成另一套事实。

⛔ S8 不写业务范围、交互或视觉的新结论；发现产品不可行或必须改合同，形成 delta 回到 G7.5 对应权威重新批准。⛔ S8 通过不等于已开发，代码和执行证据归 S9。

## 二、完整运行与独立运行

| 运行方式 | 最小输入 | 必须输出 | 最高声明 |
|---|---|---|---|
| 完整运行 S8 | G7.5 冻结且原生证据可读的 PRD v1.0、Figma、HTML、spec、调研与图源 | 飞书联合方案 + 受控镜像 + 外部契约锚点 + 三专业批准 + 回读 receipt | `module-approved`；随后才可进入 S9.1 |
| `--only S8` / `--only solution` | 可识别版本的产品/设计/交互原件或等价合同 | 同一飞书联合方案；缺失上游按 Gap 三分法处理 | `module-approved`；若只有 md/截图/链接则最多 `review-ready` |

独立运行仍执行 Route→Intake→Gap→Work→Validate→Backfill/Handoff→Claim 七步小闭环，不伪造 G7.5；结果要列清未验证的跨产物一致性和未关闭依赖。

## 三、八步执行法

### 1. Intake：锁定输入版本

读取 PRD/Figma/HTML 原件而非摘要，记录 URI、revision/version/build、hash 与回读 receipt。运行 `techspec-readiness.md` 与 `testcases-readiness.md`：

- READY：继续；
- PARTIAL：只对可判定范围写方案，缺口标 `[待补需求·不设计]`；
- BLOCKED：只出缺口报告，禁止用技术假设填产品事实。

### 2. Frame：三专业共同建模

先共同确定范围、关键质量属性优先级、单向门、最大损失场景、算法适用性和发布批次，再分头写。这样可避免技术按一种错误预算设计、算法按另一种指标优化、测试又按第三种口径验收。

算法适用性必须二选一：

- `APPLICABLE`：进入完整算法方案；
- `N/A + 理由 + 复核人 + 重启条件`：明确不适用。空白不是 N/A。

### 3. Draft：三轨并行，但共享一份合同

- **技术轨**：上下文/约束→可编辑技术架构图→模块边界→接口合同→数据方案→存储方案→性能容量方案→可靠性安全可观测性→ADR→迁移发布恢复。
- **算法轨**：问题定义→非算法基线→指标/错误预算→数据合同→候选与实验→部署监控退化回滚。
- **测试轨**：风险模型→功能测试→边界/异常/恢复测试→接口/契约/集成测试→性能/容量/稳定性测试→安全/兼容/无障碍/算法测试→环境数据→TDD/变异→准入退出→回归灰度。
  ⭐ 测试轨的**用例部分**按 `references/s8-testcases.md` 执行（五件套产出、`coverage_check` 四态对账、缺口唯一登记入口）——2026-09-15 补：SKILL.md 一直声称「S8 联合方案的测试章读 s8-testcases.md」，而本文此前零引用，声称没有落点。

三轨只能通过 `TECH/ALG/TEST/RISK` ID 和权威文件锚点共享精确事实，不在各章节各抄一份接口或阈值。

### 4. Contract first：先闭合接口，再排任务

接口、事件、schema、状态、不变量、错误、超时、幂等、重试、降级、权限、版本、迁移和回滚必须先有可判定合同。算法输入输出、低置信度和人工接管也属于接口合同。合同未定时，不得用文件级任务清单伪装成可执行计划。

技术轨至少形成五个可独立复核的方案块，且用 ID 接回同一张追溯表：

1. `DIAG/MOD`：技术架构图、模块职责、依赖方向、部署与信任边界；
2. `API`：各模块接口、协议/schema、错误、鉴权、超时、幂等、重试 owner、版本与兼容；
3. `DATA`：数据对象、权威源、血缘、生命周期、口径、质量、隐私与删除；
4. `STORE`：介质选择、schema/index/partition、容量、事务一致性、备份恢复、RPO/RTO、加密、迁移与成本；
5. `PERF`：工作负载、基线、绝对达标线、相对回归线、P95/P99、吞吐、资源/成本上限、扩缩容与 load/stress/soak/scale 验证。

图不是装饰：C4 Context/Container/Component 及按风险适用的部署、数据流、时序图必须有可编辑图源、版本和它所支持的决策，并与 `MOD/API/DATA/STORE` 双向对账。

### 5. Trace：双向追溯与覆盖

建立 `FR/NFR/AC ↔ TECH ↔ ALG/N-A ↔ TEST ↔ VS` 矩阵：

- 每个产品 ID 都有技术与测试承接；
- 每个 AI/算法需求都有基线、指标、数据、失败与测试承接；
- 每个技术/算法/测试项都能反查产品合同或工程基线；
- 孤儿项、静默降级、阈值变软、用户可感知差异均为阻断。

### 6. Plan：按纵向切片排实施

计划按依赖拓扑与最小端到端切片排序，不按前端/后端/测试水平分层。每个切片必须写精确文件/接口、接受标准、RED 证据、GREEN 验证、人工走查、证据路径和回滚方式。实现偏离时，S9.1 在同一 commit 定位更新飞书方案及受控镜像并说明影响；未更新不得进入 S9.2。

#### `coding-standards` 在 S8 与 S9 的分工

- **S8 只做适用性与落位**：记录项目规范、`coding-standards` 与语言/框架标准的真实路径和版本；按改动场景激活规则组，把条款锚点映射到 `TECH/TEST/VS`。不复制【必须】条款，避免双正本。
- **S9.1 做执行**：实现者在开工前读取锚定版本；缺陷类改动先红后绿，AI 写码激活 K 层，写操作/迁移/运行期能力按需激活 M 层；提交前跑正本自检并留下实际代码遵循证据。`selfcheck.sh` 通过只代表规范自身可用，不代表项目代码合规。
- **冲突与豁免**：项目明确规范优先；冲突写入 `STD-xxx`。违反【必须】不得用普通豁免放行；其余豁免须带理由、风险、owner、到期日与复审触发条件。

#### `four-node-review` 在 S8 与 S9 的分工

- **S8 只配置终审预案**：提出风险档建议、必审包初稿、计划节点、重点 lens 与独立验证入口，不在方案阶段伪造已审结论。
- **S9.2 以其正本执行终审**：开审前由人确定 S/A/B/C；工程化建立必审包分母；逐节点记录 `CLEAN/DIRTY/UNABLE`、覆盖差集、lens、发现证伪、独立新鲜证据和最终回归。S/A 走完整 entry/gates/security/review/qa/bench；B/C 按正本裁剪并写理由。
- **边界**：Node 4 功能 QA 证明应用行为与风险；S9.3 仍负责 PRD/Figma/HTML/最终应用四方产品一致性，二者不得互相顶替。

### 7. Challenge：三方交叉质询

研发总监挑战算法的数据/延迟/成本与测试环境；算法负责人挑战指标能否代表业务和数据是否泄漏；测试负责人挑战失败模式、回滚和每条“已被守住”的判据是否真会红。至少回答模板中的七个质询；不能回答的形成 `SL-xxx`，不靠会签掩盖。

### 8. Publish：飞书写入、回读、批准、生效

1. 首次建文档：`doc-sync-guard.py record` 后写入飞书；
2. 写入后：飞书 CLI 回读，`doc-sync-guard.py check --readback` 核结构指纹；
3. 后续迭代：只用定位 replace/insert/append，不全文 overwrite，避免图片、白板、评论和远端改动被抹掉；
4. 研发总监、算法负责人（或 N/A 复核人）、测试负责人分别批准；产品负责人确认“无产品 delta”或 delta 已回灌批准；
5. `s8-solution-gate.py`、飞书回读和人工批准全部成立，才签发 S8 `module-approved`。

## 四、三位负责人的最低质量线

### 研发总监

- 至少一个真实替代方案，ADR 说明选择依据、代价和重审条件；
- 架构图必须配模块职责、边界和数据流，不接受“只有框图”；
- 接口/数据/状态合同覆盖失败、并发、幂等、兼容和迁移；
- 安全、隐私、性能容量、可观测性、部署、灰度、回滚均有可执行判据；
- 文件级计划能被陌生工程师实施，不含“按需”“完善”“后续优化”等占位词。

### 算法负责人

- 先证明规则/检索/人工等非算法基线不够，再选择模型；
- 指标同时覆盖业务结果、离线效果、分群切片和延迟/成本/安全护栏；
- 数据来源、许可、标注、切分、泄漏、污染、偏差、隐私和版本可追溯；
- baseline 与候选同口径对比，记录全部必要复现实验信息，不只报最好一次；
- 低置信度、漂移、供应商/模型不可用时有降级、人工接管、监控、重训和回滚。

### 测试负责人

- 风险优先，在能证明行为的最低层测试；跨边界用集成，关键用户任务用 E2E；
- 功能与业务规则、边界值、空值/极值、异常与恢复、接口/契约/集成、性能容量稳定性是显式方案块，不得只藏在一张大表；
- happy、empty、boundary、error、recovery、permission、concurrency 与异常边不漏；
- 覆盖迁移、回滚、视觉交互、无障碍、兼容、安全、可靠性和算法评测；
- TDD 的失败必须为正确断言和正确原因；关键规则有独占反例/变异测试，先证明变异命中生产对象；未执行、跑不了分别记 SKIPPED/UNABLE；
- 准入、暂停、退出、缺陷级别、风险接受、回归、冒烟、灰度与上线验证口径可判定。
- 为 S9.2 设计测试工程师从真实 GUI 入口完整实走主流程、关键分支、失败与恢复的计划，并为 S9.3 产品经理基于冻结 PRD 的独立 GUI 走查准备同口径流程、账号、数据、环境和证据要求；两次实走不得互相替代。

## 五、出场门禁

以下任一不成立，S8 不得声明 APPROVED：

- [ ] 输入原件版本与回读能力已登记；缺口未被假设掩盖；
- [ ] 技术、算法/N-A、测试三章均完整，联合对账无冲突；
- [ ] 双向追溯无缺口、无孤儿项、无静默改变产品合同；
- [ ] 技术架构图、模块接口、数据、存储、性能容量、算法评测、分型测试、实施、迁移/发布/恢复均可执行；
- [ ] `coding-standards` 的版本与场景激活映射已登记，S9.2 的风险档建议与终审预案已登记；
- [ ] 研发/算法/测试三专业批准和产品 delta 结论均非占位；
- [ ] 飞书文档写后回读通过，URL/revision/receipt 与受控镜像一致；
- [ ] `s8-solution-gate.py` 退出码 0；所有必跑门无失败、SKIPPED、UNABLE。

## 七、诚实边界

- `s8-solution-gate.py` 只证明受控源稿的结构、ID 和批准字段不是明显缺失，证明不了方案技术上正确；正确性归三专业评审和后续真实执行。
- 飞书链接不等于飞书原生证据；没有回读 receipt 时最高只能 `review-ready`。
- 预测的性能、成本、效果与风险不是事实；必须标估算口径，并在 S9/S10 用实测结算。
- 算法 N/A 是合法结论，空白或“后续再看”不是。
