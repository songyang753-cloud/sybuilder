# S9 · 质量门：编码规范 · 安全规范 · 测试标准

S9 的「写代码」不是自由发挥。本文分别约束 **S9.1 开发与持续验证**和 **S9.2 工程测试、审计与质量终审**——不满足就不叫做完，与功能是否跑通无关。

⚠️ **本文是通用基线**。项目已有自己的规范时**以项目为准**，本文只补它没覆盖的部分；两者冲突时在报告里写明按哪边执行，不要静默二选一。

## 零、两套外部 skill 如何接入，而不是复制

| 来源 | S8 方案阶段 | S9.1 开发阶段 | S9.2 终审阶段 |
|---|---|---|---|
| `coding-standards` | 锚定实际路径+commit/hash；建立 `STD-ID→TECH/TEST/VS` 适用映射、冲突与豁免 | 写每个纵向切片时执行激活条款；`selfcheck.sh` 只验规范源自洽，逐条合规另留证据 | 核对 diff 与 `STD-ID`，查假绿、漏接线、范围外副作用和豁免是否仍成立 |
| `four-node-review` | 仅提出风险建议档、预计覆盖包与节点；不在 S8 冒充已执行 | 为每个切片保留可独立运行入口、RED→GREEN 和新证据 | 由人最终定 S/A/B/C 档，立确定性覆盖合同，跑 entry→gates→security→review→qa→bench，出独立飞书报告 |

**版本与优先级**：运行时发现真实安装位置，记录路径 + commit/hash；禁止把某台机器的 `~/.claude/...` 当通用路径。项目明确规范 > `coding-standards` > 语言/框架通用补位。引用正本，不复制其 30 条【必须】、承重层或长期增长的铁律清单，避免两份正本漂移。

**阶段边界**：S9.2 的 Node `qa` 是工程与功能质量审查，不能替代 S9.3 的 PRD/Figma/HTML/最终应用四方产品验收；`CLEAN` 也不等于“四方一致”。

## 一、安全门（最高优先级，其余都可以让路）

### 1.0 先跑机械层（人勾清单挡不住任何东西）

```bash
python3 scripts/sec-scan.py <代码目录> > /tmp/sec.log 2>&1; rc=$?   # ⚠️ 要退出码就别接管道
```
覆盖 **SEC-1 硬编码密钥 / SEC-3 SQL 与命令拼接 / SEC-8 错误信息泄露 / SEC-9 日志落敏感数据** 四条。

⚠️ **其余 6 条（SEC-2/4/5/6/7/10）机械查不了**，只能人工与专项审查——
它们的合法结论是「已人工审查，发现 N 处」，**不是 ✅**。
⚠️ **机械层报绿 ≠ 安全达标**，只 ≠ 有机械可查的破绽。

📌 为什么要有这一步：本节原本是一张**人勾的清单**，而本 skill 自己的判词是
「清单挡不住任何东西，门禁才挡得住」。同一条判词对 PRD 成立，对安全一样成立——
何况这里是唯一被标注「最高优先级，其余都可以让路」的部分。

### 1.1 提交前强制清单（每条都要有结论，不许空着）

| # | 检查 | 判据 |
|---|---|---|
| SEC-1 | **无硬编码密钥** | 源码里没有 API key／密码／token／证书私钥；一律走环境变量或密钥管理，且启动时校验必需项存在 |
| SEC-2 | **输入校验** | 所有外部输入（用户输入、API 响应、文件内容、消息队列）在**边界处**校验，schema 优先，fail fast；**文件上传属输入**：大小上限、类型白名单＋服务端内容嗅探（不信文件名/Content-Type）、路径穿越文件名拒收 |
| SEC-3 | **注入防护** | 数据库查询一律参数化，禁止字符串拼接；命令执行禁止拼接用户输入 |
| SEC-4 | **XSS 防护** | 用户内容输出前转义；富文本走白名单净化，不用黑名单 |
| SEC-5 | **CSRF 防护** | 状态变更接口有 CSRF 保护或等价机制（同源校验／自定义头／token） |
| SEC-6 | **认证与授权分开验** | 认证＝你是谁；授权＝你能不能动这条数据。**逐接口验对象级授权**，不是只验登录态 |
| SEC-7 | **限流** | 对外接口有速率限制，尤其登录、验证码、导出、搜索 |
| SEC-8 | **错误不泄露** | 对外错误信息不含堆栈、SQL、内部路径、真实存在性（「用户名或密码错误」而不是「用户不存在」）；详细信息只进服务端日志 |
| SEC-9 | **日志不落敏感数据** | 密码、token、身份证、手机号、支付信息不进日志；必要时脱敏后再记 |
| SEC-10 | **依赖与配置** | 依赖无已知高危漏洞；生产配置不开调试端点、不用默认口令 |

⚠️ **发现即停**：命中任何一条 → 先修，**并检查同类问题在别处是否还有**（一处硬编码密钥往往意味着还有第二处）。
⚠️ **密钥一旦进过版本库就视为泄露**，必须轮换——删掉那行代码不算修复，历史里还在。

### 1.2 必须触发深度安全审查的改动

碰到这些，**不允许只做常规 review**：认证授权 · 用户输入处理 · 数据库查询 · 文件系统操作 · 外部 API 调用 · 加密与随机数 · 支付与资金 · 个人数据导出/删除 · 权限模型变更。

**深度安全审查该用哪些具体技术(借 trailofbits/skills 逐条)** —— ⛔ "做了深度审查"不是一句话，要点名用了哪几项:

| 技术 | 用在哪 | 判据 |
|---|---|---|
| **差异审查**(differential-review) | 版本/补丁间 | 比对两版找**安全回归**，不是只看新增行 |
| **补丁验证**(post-patch-validation) | 修完安全问题后 | 证明补丁**真的堵住了原漏洞**(复现漏洞的用例转绿)，不是"改了代码假设修好" |
| **不安全默认**(insecure-defaults) | 配置/依赖 | 生产配置不开调试端点、不用默认口令、依赖无已知高危(接 SEC-10) |
| **常量时间分析**(constant-time-analysis) | 加密/比较密钥/token | 敏感比较无**时序侧信道**(`==` 提前返回即泄露) |
| **属性测试**(property-based-testing) | 输入校验/解析器 | 用随机/边界输入证伪不变量，而非只测几个样例 |
| **语义规则**(semgrep-rule-creator) | 发现一处漏洞后 | 为该模式写 semgrep 规则**全仓找同类**(一处硬编码密钥往往有第二处) |

⚠️ 这些是"深度审查"的**可点名内容**：报告里写"已做深度安全审查"必须列出对本次改动实际用了上表哪几项 + 各自结论，否则等同没做(对齐 `/cso` 的 self_reported≠tested)。

### 1.3 安全需求从哪来（这条最容易断）

⚠️ **S9 不许凭空发明安全需求，但也绝不能因为 PRD 没写就不做安全。**
两者不矛盾，处理方式不同：
- **通用基线（本文 1.1 的 SEC-1~10）**：属于工程标准，**不需要 PRD 授权，默认执行**。
- **产品级安全规则**（谁能看谁的数据、留存多久、导出要不要审批、是否需要二次验证）：**必须来自 PRD 附件 C**。PRD 没写 → 登记 `GAP`／`TBD` 回 S4 补，**不要自己替产品决定权限模型**。

📌 这是本流水线曾经的结构性漏洞：上游没有安全需求的采集位置，下游又被铁律禁止猜补，结果整条链路"合规地"把安全漏掉了。修法＝`prd-complete.md` 的**附件 C 安全与合规**（必填）+ 本节的双轨制。

### 2.0 从“读过规范”到“实现证据”的强制接口

1. S8 已为每类改动生成 `STD-ID` 和激活条款；S9.1 不得临时凭记忆选规则。
   - **先 discover 项目既有约定再写(借 agent-os `discover-standards`/`inject-standards`)**：S9.1 开工前从**当前代码库**提取既有约定(命名/目录结构/错误处理/日志/测试组织惯例),新代码**匹配项目本身**而非仅匹配通用 `coding-standards`;且**只注入与本次改动相关的标准子集**,别用整套通用规范淹没那相关的少数条(注入无关规则=噪音,反而降低遵从)。这把 §二"项目明确规范 > coding-standards"从优先级声明,补上"项目规范从哪来"的采集动作。
2. 每个切片的 RED/GREEN、静态检查、运行验证和人工复核都回填对应 `STD-ID`；`selfcheck.sh PASS` 不能代替这些证据。
3. 项目规则冲突或无法满足时登记：理由、风险、owner、到期/重审条件；不得删除门禁或放宽断言来换绿。
4. AI 参与写码时默认激活其 AI 协作层；接口、并发、迁移、定时任务、数据发布物、回滚等场景按索引追加相应规则组。
5. 终审以真实 diff、运行入口和生产接线路径为对象；“文件里存在”不等于“运行时生效”。
6. **降门槛监测(借 addyosmani `constraint-driven-development`)**：⛔ 不许**悄悄降低质量门槛来换绿**。每次终审必须扫本次 diff 有没有以下「削弱质量条」的形态——命中即**默认阻断，须走豁免(理由/风险/owner/到期)**，不许静默合入：

| 削弱形态 | diff 信号(点名) |
|---|---|
| 加抑制注释 | 新增 `@ts-ignore` / `eslint-disable` / `# noqa` / `# type: ignore` / `//nolint` / `# pragma: no cover` |
| 删/跳过测试 | 删掉测试函数、新增 `.skip` / `xit` / `@pytest.mark.skip` / `t.Skip` / 注释掉断言块 |
| 剥断言 | `assert`/`expect` 被删或改成永真(`assert True` / `expect(true)`) |
| 阈值改小 | 覆盖率/性能/超时门槛数字被**调低**(80→60)、`--max-*` 放大 |
| 假实现 | 新增 `TODO`/`pass`/`NotImplemented`/`return null` 占位冒充完成 |
| 关门禁 | 删门禁调用、把 required 改 optional、把断言退化成 warning |

> 这是「⭐ 想让锚点说谎变绿」「为了变绿而关掉检查」的**可机械检测版**——`constraint-driven-development` 的核心正是「把质量条写成契约 + 盯着 diff 不让 agent 偷偷降它」。⇒ **已实现**:`scripts/bar-weakening-scan.py [<git-diff文件>]`(claude 自持,默认读 `git diff HEAD`,消费方=S9.1/S9.2)扫上表五类形态,命中未豁免即红;双向自证已跑绿(正例0/五类变异各命中/无效2)。


| 维度 | 判据 | 违反的典型信号 |
|---|---|---|
| **不可变优先** | 不原地改传入的对象/集合，返回新值 | 函数改了调用方的入参，调用方却不知道 |
| **KISS** | 能用简单写法就不用巧写法 | 为了少写三行引入一层抽象 |
| **DRY** | 重复出现第三次再抽象 | 只出现两次就急着抽公共函数，参数越加越多 |
| **YAGNI** | 不写没被要求的功能、配置项、扩展点 | 「以后可能要支持多租户」于是先加了开关 |
| **函数长度** | < 50 行 | 一个函数里同时做取数、转换、落库、发通知 |
| **文件长度** | 典型 200~400 行，上限 800 | 一个文件塞了整个模块 |
| **嵌套深度** | ≤ 4 层，优先早返回 | 连续 5 层 if 才到真正的逻辑 |
| **魔法数字** | 有含义的阈值/超时/上限必须具名常量 | 代码里散落 `86400`、`3`、`0.85` |
| **命名** | 变量/函数 camelCase；类型/组件 PascalCase；常量 UPPER_SNAKE；布尔用 is/has/should/can 前缀 | `flag`、`data2`、`tmp` |
| **错误处理** | 显式处理，不静默吞；用户侧友好、服务端详细 | `catch {}` 空块；把异常转成 `return null` 后无人检查 |

⚠️ **改动范围纪律**：只碰必须碰的。不顺手重构邻近代码、不改无关格式、风格跟随现有代码。
**判据：diff 里每一行都能追溯到某个 `FR`**——追溯不到的行，要么删掉，要么说明它为什么必须存在。

## 三、测试标准

| 项 | 要求 |
|---|---|
| **流程** | TDD：先写测试 → **看它真的失败** → 最小实现 → 通过 → 重构 |
| **行覆盖** | ≥ 80%（新增/改动代码），且**分母只算真跑过的**。⚠️ 这是**代码行**覆盖，**不是需求覆盖** |
| **层次** | 单元（函数/组件）+ 集成（接口/数据库）+ E2E（关键用户流程），三类都要有 |
| **结构** | AAA：Arrange-Act-Assert 三段清晰 |
| **命名** | 描述行为而非实现：`无匹配时返回空数组` 而不是 `test1` |
| **来源** | 需求级用例来自 `s8-testcases.md` 的产出，顺 `FR → TC` ID 链 |

### 3.1 七类显式测试域（适用性逐项判定，不能藏进“其他”）

| 测试域 | 最低内容 | 主要追溯 |
|---|---|---|
| 功能与业务规则 | 正向、状态转换、角色/规则、关键任务终态 | FR/AC/TEST |
| 边界、异常、并发与恢复 | 空/零/最小/最大/越界/超长/重复/乱序/超时/取消/中断恢复/回滚 | AC/NFR/RISK/TEST |
| 接口、契约与集成 | schema、认证、对象级授权、错误码、幂等、重试、限流、版本兼容、外部依赖三态 | API/TECH/TEST |
| 性能、容量与稳定性 | baseline、load、stress、spike、soak、scale；P95/P99、吞吐、错误率、资源和成本 | PERF/NFR/TEST |
| 安全与隐私 | 机械扫描 + 威胁模型/人工/专项审查；产品规则与工程基线分轨 | SEC/RISK/PRD-C |
| 兼容、无障碍与交互工程质量 | OS/浏览器/设备/升级降级、键盘/焦点/读屏/对比度/reduced-motion | NFR/TEST |
| 算法评测与退化 | 非算法 baseline、离线/切片/鲁棒/偏差、线上护栏、延迟成本、漂移、低置信度接管 | ALG/NFR/TEST |

测试层级按风险选**能证明行为的最低有效层**：单元/组件守局部规则，契约/集成守跨边界，关键用户任务才用 E2E。并非每个改动机械地凑齐三层；但每个适用风险必须有覆盖，裁剪要有证据和批准。新增/改动代码行覆盖默认 ≥80%，若项目有更严格门槛从其规定；无法达到须写风险接受四件套，且不得用行覆盖替代需求覆盖、分支覆盖或变异有效性。

### 3.2 测试工程师 GUI 全流程实走（S9.2 必做）

自动化测试、接口测试和代码覆盖率无法证明用户在真实界面里能完成任务。测试工程师必须在同一候选构建上，从用户可见入口亲自走完 S8 `GUI-FLOW-ID` 的全部适用项：

1. **真实界面**：Web 通过真实浏览器 GUI；macOS/移动端在取得许可后操作真实应用。浏览器自动化或 computer-use 可以执行与留证，但每一步必须是用户可见的点击、输入、键盘、拖放或系统反馈；API、DOM 注入、深链直达、脚本改状态只用于诊断。
2. **完整分母**：主流程、关键分支、失败与恢复、角色/权限四类分别报 `n/m`。从中途页面开始、只跑 happy path 或缺少跨页面终态，不得称“完整”。
3. **逐步证据**：每条 `GUI-S92-ID` 绑定 build/commit、设备/OS/浏览器、角色账号、数据版本、时间和操作者；视频/截图/trace 能逐步复核反馈与最终数据状态。
4. **失败闭环**：发现绑定 Finding、修复 commit 与同环境 GUI 复验；局部接口变绿不能关闭 GUI 缺陷。任一必走项未执行或证据无法绑定当前构建，结论为 `FAIL/UNABLE`。
5. **角色边界**：本步回答“测试合同是否满足”，不回答“这是不是一个正确且优秀的产品”。后者由 S9.3 产品经理重新操作，S9.2 的证据不能直接复用为 S9.3 的已走证明。

⚠️ **"看它真的失败"不可省**：没红过的测试不能证明它在测东西——它可能因为断言写错而永远通过。
⚠️ **行覆盖不等于测得准**：配合 `s8-testcases.md` ④.5 的用例集自检（假想需求被改坏，有没有测试会失败）。
⚠️ **⭐ 行覆盖与需求覆盖是两件事，必须分开叫、分开报。**
   · **行覆盖**（本节，≥80%）＝代码里有多少行被执行过
   · **需求覆盖**（`s8-testcases.md`）＝每个 `FR` 有没有用例、每条用例能不能反查到 `FR`
   📌 两者此前**同名并列打勾**——**用行覆盖 80% 去交需求覆盖的差**，是这种同名最典型的用法，
   而且看不出来：一份 `FR` 一条用例都没有的代码，行覆盖照样能到 90%。

## 四、Review 严重度与放行标准

| 级别 | 含义 | 处置 |
|---|---|---|
| **CRITICAL** | 安全漏洞 / 数据丢失风险 | **阻断**，修完才能合 |
| **HIGH** | 功能缺陷或明显质量问题 | 合并前应修 |
| **MEDIUM** | 可维护性问题 | 尽量修 |
| **LOW** | 风格与小建议 | 可选 |

**放行与风险档共同生效**：CRITICAL 一律阻断。S 档不接受任何 Open Item；A 档 CRITICAL/HIGH 必须清零；B/C 可按开审前的裁剪合同执行，但所有未解决项必须有影响、owner、到期/解除条件，且不得突破 S8 或 S9.3 的停止线。

## 4.1 `four-node-review` 终审执行合同（S9.2）

### 风险档与最低强度

| 档 | 典型范围 | 必跑节点 | 连续 CLEAN 轮次 | 附加要求 |
|---|---|---|---:|---|
| S | 不可逆、生产数据、资金、权限、安全边界、对外发布物 | 全节点 | 3 | 生产数据核查；安全发现证伪三票；Open Item=0 |
| A | 核心链路、跨模块、对外 API | 全节点 | 3 | 标准终审 |
| B | 边缘功能、内部工具、单模块局部改动 | gates/review/qa | 2 | 裁剪节点写依据 |
| C | 文档、注释、纯配置、格式化 | gates + review | 1 | 先证明 diff 真的只有这些，溢出即升档 |

分档由有授权的人在 S9.2 开审前决定；S8 只能建议。中途只允许升档，降档须退出本轮、写可复核理由后重新入场。规模只决定如何分批，不决定跑多严。

### 覆盖、三态、独立证据与证伪

1. 先用工程手段从真实 diff/manifest 建 `PKG-ID` 覆盖合同；扩展名白名单和 OCR 输出只能作为子集，差集必须补齐。每轮覆盖包数必须为 `m/m`。
2. Entry 核版本、意图、可运行入口、RED→GREEN、环境/数据和 S8 对账。入场不满足先修，不用后续节点掩盖。
3. 节点按 `entry/gates/security/review/qa/bench` 记录；合法轮次结论只有 `CLEAN/DIRTY/UNABLE`。未审完、工具不可用、包漏审均为 UNABLE，不计清洁轮次且整体不可放行。
4. 每轮换镜头并产生可独立复核的新证据；同一输出、同一摘要或子执行者自报“全绿”不能重复计轮。
5. 候选发现经反驳/证伪后再定级；反例必须命中被测对象，并因预期断言和预期原因变红。记录候选数 C、确认数 N 与 `precision=N/C`。
6. 每个修复重跑受影响节点、相关包和最终全量回归。S9.2 的唯一汇总交付件为飞书《工程测试与四节点终审报告》，模板 `templates/s9-quality-report.md`，受控镜像跑 `s9-quality-report-gate.py`。

## 4.2 三条防假绿硬机制（2026-09-18 逐行读 gstack + alibaba/open-code-review 源码提炼）

> 这三条把「连续 N 轮 CLEAN」「已完成/已测」「覆盖无缺口」从**声称**收成**可证伪的硬约束**。前两条落在本会话自持的 S9.1（`s9-dev-slice-gate.py`）与 S9.4（`s9-launch-rollback-gate.py`）门禁里强制；第三条属 S9.2 `s9-quality-report-gate.py`（codex 名下 + merge 模型）—— 以 `.proposals` patch 交 codex，不在 main 直接改其门禁。

### ① 评审新鲜度＝内容指纹，不是轮次计数或 commit hash（借 gstack Review Freshness）
- S9.2「连续 N 轮 CLEAN」的每一轮，必须绑定**起止工作树内容指纹**（tracked edits + 非忽略 untracked source 都算），而非 commit hash 或轮次序号。
- ⛔ **相同 commit hash 或「零改动」不能当新鲜依据**——那只证明「没变」，不证明「被重新审过」。起止内容不同＝`STALE`（本轮作废）；缺指纹＝`UNVERIFIED`（不计 CLEAN 轮次）。
- 修完缺陷必须跑**真·全量重评 + 新起始指纹**，不能只补记日志；**上线遥测不算一次评审通过**（"Ship telemetry is not a review pass."）。
- 与我方已有判据的接口：证据独立性门（每轮换镜头 + 独立新证据）继续成立，本条补上「新证据必须覆盖**当前内容指纹**」这一维——防止「三轮都在审同一份旧内容」。

### ② 完成度四级，自报与独立证明严格分层（借 gstack `/cso`）
- 每条「已完成/已测/已守住」声明必须标完成度：`asserted`（只断言）< `self_reported`（执行者自报，如 selfcheck 绿）< `tested`（有测试证据）< `independently-verified`（流程外不可伪造见证）。
- ⛔ **被测代码与验证器同进程时，最高只能到 `self_reported`**——同进程可伪造 reporter 输出，故不给 `tested`；`tested`/`independently-verified` 只留给流程外见证（对照组 / 隔离 runner / target-independent witness）。
- 这正是 S9.1「`selfcheck` 绿 ≠ 代码合规」的一般化：selfcheck 是 `self_reported`，不是 `tested`。逐条 STD-ID 实现证据才升到 `tested`。

**每类完成声明的证据要求(借 obra/superpowers `verification-before-completion` 的「无新鲜验证证据不许声称完成」+ Gate Function)**:声称任何状态前必须 `IDENTIFY(什么命令能证明)→RUN(整条、fresh 跑)→READ(读全输出、查退出码、数失败数)→VERIFY(输出是否真支持这个声称)→才声称并附证据`。下表逐条把"够/不够"钉死:

| 完成声明 | 需要的证据(才算 tested/verified) | **不够(仍是 asserted/self_reported)** |
|---|---|---|
| 测试通过 | 测试命令输出 0 失败(本条消息内新跑) | 上一次的运行、"应该过" |
| 门禁绿 | 门禁输出退出码 + 无发现(fresh) | 部分跑、外推、旧结论 |
| bug 已修 | 复现原始症状的测试转绿(红→绿闭环) | 改了代码、"应该修好了" |
| 需求已满足 | 逐条 FR/AC 对账清单 | 测试过了(测试≠需求覆盖) |
| agent 完成 | VCS diff 实际改动 + 独立证据 | agent 自报 success |

⚠️ 红旗即停:出现"应该/大概/看起来"、在验证前表达满意("好了/完美/搞定")、想"就这一次"跳过验证——都是在说谎不是在验证。**这正是 S9.1 完成度分级的执行纪律版**。

### ③ 确定性覆盖封存，preview==实审，安全文件不许被规则漏审（借 open-code-review `selectFiles`/`registerCoverage`/`grouping`）
- S9.2 的 `PKG-ID` 覆盖合同必须由**纯确定性函数**从真实 diff 封存（无 LLM、无副作用、输入序即输出序），使「预览要审哪些」与「实际审了哪些」**同源不漂移**（open-code-review 用纯 `selectFiles` 治 preview/real 漂移 #782）。
- **安全敏感文件（密钥路径 / 鉴权 / 加密）排在任何 include/exclude 用户规则之前**——任何用户 glob 都不能把它排除出审查（open-code-review：`IsSecretPath` 先于用户规则）。对应我方 SEC 门：安全文件的审查覆盖是**不可被裁剪的下界**。
- 大改动集按语义分组、**每组 ≤N**（open-code-review `maxFilesPerGroup=10`）、每组**隔离上下文 sub-agent 分治**，保证大改动集也稳、不「偷工减料只审几个文件」（这正是通用 agent 做 review 的三大病症之一：覆盖不全）。

## 五、提交与交付

- **commit 格式**：`<type>: <描述>`，type ∈ feat / fix / refactor / docs / test / chore / perf / ci。

## S9.3 产品经理 GUI 走查 · 四方一致性执行合同

**入场硬条件**：S9.2 对同一 build/commit 的质量结论必须为 `PASS`；`CONDITIONAL/FAIL/UNABLE` 均不得开始产品放行。验收者必须访问四件原物（PRD/Figma/HTML/最终应用），不是读四份摘要，并依据冻结 PRD 与产品经验亲自在 GUI 中重新走查：

1. **独立实走**：为每条 `PM-GUI-ID` 从用户可见入口开始，覆盖主流程、关键分支、失败恢复、角色/权限和开放探索；记录真实分母、逐步反馈、最终业务/数据状态以及带构建/环境/角色/时间的独立证据。S9.2 录像可作背景，不能冒充本次操作；同一人兼任时必须另开会话、重置数据并声明角色冲突。
2. **行为**：最终应用回放**同一份** `spec/flows.json` ——
   `node scripts/flow-walk-gate.mjs <应用入口> --flows spec/flows.json`；
   HTML 与最终应用跑同一契约，「与交互稿一致」才有实测依据（PRD↔应用验业务规则，
   HTML↔应用验行为，Figma↔应用验视觉——三条各自对，不许互相顶替）。
3. **产品判断**：逐项判断用户价值、功能与业务规则、信息架构与文案、交互效率/反馈/容错恢复、视觉层级与质感、多端与无障碍、体感性能与信任，以及脚本外开放探索；“能打开/能点”不等于产品成立。
4. **视觉**：同 SCN 检查点截图与 Figma/HTML 基准比对（布局/内容/状态/token/端形态）。
5. **偏差**：允许的实现差异走 `deviation-register.md` 登记批准——
   ⛔「技术实现不同」不豁免**用户可感知**差异；未批准高影响偏差 >0 不得过 S9.3。
6. **回流**：产品 delta 回对应权威并重开 G7.5；影响技术/算法/测试方案则重开 S8；实现变化后必须让 S9.2 对新构建重新 PASS。不得在走查现场静默改原物。
   - ⭐ **gap 四分类(借 spec-kit `/converge`)**：逐条对照冻结 PRD 把差距归成 **`missing`(该做没做)/`partial`(做了一半)/`contradicts`(做反了)/`unrequested`(做了没要求的)**,**每条 append 成新任务**、循环到收敛,⛔ **「声明做完」不算证据,以读到的真实行为为准**。
7. **诚实**：任一原物不可访问 → 该方一致性 UNABLE，总门不得沿用旧 PASS；
   `finish-bar` 的 `production-validated` 挂本合同 + 真实上线观察。
