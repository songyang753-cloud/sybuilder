完整正本在 `references/format-boundaries.md`；历史迁出说明保留于 `references/s10-retro-in-skill.md` 的 M9 小节。
执行必须先检查远端漂移、取得写入授权，再由所选平台适配器写入并同版回读全文和逐图映射；API 成功不等于交付成功。

## M1 · ID 贯穿链（治「后面全靠猜」）

```
F-03 登录失败锁定                    ← S4 功能清单
 └ FR-031 MUST 连续失败 5 次锁定      ← S5 附件A
    ├ AC-1 Given…When…Then…
    ├ AC-2 计数器 15 分钟重置
    └ AC-3 锁定期输对密码仍拒绝
 └ demo 场景 `#f03-locked`            ← S6
 └ Figma 图层 `F-03/锁定态`           ← S7
 └ 测试用例 TC-031-2 覆盖 FR-031/AC-2 ← S8
 └ commit「feat: FR-031 登录锁定」    ← S8
```

**硬约束**：编号只增不改。功能砍了就标 `F-03 [已取消]` 并写理由，**绝不回收编号给别的功能**——回收编号会让历史记录、缺陷单、测试用例全部指向错误对象，且这种错没有任何自动手段能发现。

### M2 · 三来源原则（治编造）

写进任何产物的每个事实，标注出处：`[用户]` / `[查证·来源·日期]` / `[ASM-###]`。
⚠️ 「事实」＝外部可核查的主张、关键假设、决策依据——**面向用户的界面文案与叙述句不挂标签**（给 PRD 每句话贴来源是噪声，不是严谨）。
- **ASM**（假设）＝我已经按它往下写了，**更危险**，必须在 PRD 附件 B 集中列出等人否决。
- **TBD**（待确认）＝还需别人回答，**必须带 owner**，无 owner 的 TBD 等于永远不会被解决。
- ⚠️ 竞品信息一律 `[查证]` 且必须能给出链接与访问日期；**「业界一般都这么做」是编造的高级形态**，禁止出现。

### M3 · 视角轮换收敛（治「三轮其实是同一轮」）

S3/S4/S5 的迭代收敛统一按此执行：

- 每轮**换一个视角**评审，视角表见各阶段章节。
- 视角表**未跑满一遍不得宣告收敛**——不许只跑两三个顺手的视角就说收敛了。
- 收敛判据：**连续两大轮**（视角表各跑满一遍）所有视角都提不出结构性问题。只有一大轮零发现不算——第一大轮的修订本身可能引入新问题。
- ⚠️ 要防的不是「零发现」，而是**没换视角、没换证据就宣称跑了新一轮**（见 M5）。
- 每轮必须留痕（写进 `state.md` 与 `reviews/`）：`本轮视角 / 提了什么 / 改了什么 / 为什么这么改 / 提了但没采纳的及理由`。
- 「提了但没采纳」这一栏是防止同一个建议在后面几轮反复被提、假装成新发现。

⚠️ **这套机制的诚实边界**：它防的是「三轮其实是同一轮」，防不住「我系统性地看不见某一类东西」——一个人换五顶帽子仍有共同盲区。**所以 S6 的 demo 与 S8 的真跑测试不可省略**，它们是唯二能引入外部信息的环节。

**共同盲区的四条解法**（能用哪条用哪条，用了哪条、没用哪条都要写进报告）：
1. **换个上下文再审**：新开一个干净会话、只喂产物不喂过程，让它当评审者。同一个模型在无污染上下文里会看见不同的东西——「一个 agent 制造的 bug，另一个同模型 agent 能找出来」。
2. **换个模型审**：把方案交给另一个模型做 staff engineer 评审，模型差异本身就是视角差异。
3. **对抗式提问**：不要问「这个方案有问题吗」（会得到礼貌的肯定），要问 **「向我证明这行得通」「挑刺，不许放过我」**——把默认姿态从辩护改成证伪。

4. **⭐ 找真人用一次**（3 人 × 15 分钟，拿 S6 的 demo）。
   前三条全部是「换一个我」——换上下文、换模型、换提问姿态。**它们共享同一个盲区来源：
   没有任何外部信息进来。** 10 个评审视角也全部由 AI 扮演，评审章节自己就写着
   「覆盖不了只有在这家公司待过三年才知道的坑」。
   S6 被定义为「整条流水线**唯一一次让方案脱离文字被眼睛检验**」——而那双眼睛还是同一个模型的。
   ⚠️ **这是全流程唯一一处真实外部证据，也是最便宜的一处**：demo 已经能点，不需要写任何代码。
   ⚠️ **没做要在报告里显式声明「本轮无真实用户走查」**，不许沉默跳过——
   沉默跳过会让报告读起来像「已经验证过了」。

（1–3 来源：社区实践综述 `shanraisshan/claude-code-best-practice`，2026-08-16 查证；
与本机 `four-node-review` 的「对抗式证伪投票」同源。第 4 条来自 2026-08-30 多视角评审：
**全流程零真实用户是当时发现的最大证据缺口**。）

### M4 · 跨产物对账门（治交接处失真）— 本流水线最有价值的一道

⚠️ **2026-08-31 全链 review 的发现**：M4 长期只有 G1–G4，**从 S4→S5 才开始**——
也就是说 **S1→S2、S2→S3、S3→S4 三个交接完全没有对账**，
而 S3→S4 恰恰是「最贵的决定」流向 PRD 的那一环。现补 **G0 / G0.5 / G0.8**（`chain-gate.py`），
七道门覆盖全链。

**每次阶段交接必跑，只读不改，产出对账报告。**

| 交接 | 对账什么 | 不通过的表现 |
|---|---|---|
| **S1→S2** | S1 点名的方向是否都被调研覆盖 | 调研跑偏，查的不是用户要的 |
| **S2→S3** | 每个 `OPP-xx` 机会是否都有归宿（采纳/拒绝/推迟） | **调研成果被沉默丢掉**，S2 白做 |
| **S3→S4** | 定义 18 项是否都有 PRD 承接位；**量化与约束级别有没有被降级** | 最贵的决定流不进 PRD |
| S4→S5 | 功能清单每个 `F-xx` 是否都有交互说明 | 有功能没人设计 |
| S5→S6 | 附件 A 每个 `FR/AC` 是否都有对应 demo 场景或明确标注「不演示·理由」 | demo 看着完整实则漏演关键路径 |
| S6→S7 | demo 每个场景是否都有 Figma 画面 | 研发拿到的稿子缺状态 |
| S7→S8 | 每个 `FR` 是否都有测试用例；每个测试用例是否都能反查到 `FR` | 需求没测 / 测了没人要的东西 |

**判据是双向的**：正向漏（需求没落地）和反向漏（做了没需求的东西）**同样是缺陷**。反向漏尤其危险——它意味着有人在没有需求依据的情况下自己发挥，而这部分永远不会被测试覆盖。

对账不通过 → **回上一阶段补，不允许带病进入下一阶段**。带病进入的代价在后面每一步都要重付一次。

### M5 · 证据独立性（治「一份证据当三轮用」）

宣称「这一轮跑过了」时，四查：
1. **新鲜性**——本轮真跑过，「上轮跑过没改所以还绿」不成立。
2. **跨轮不同**——三轮的截图/输出哈希必须不同（相同＝拍的同一个状态）。⚠️ 语境限定：本条只适用于「**三个不同注入状态**」的渲染证据；重新独立验证而产物本就未变的场景不适用——那种新鲜度由运行记录证明，不强迫内容变化。
3. **内容锚点**——从证据本身能看出它是本轮这个视角产出的。
4. **可独立复核**——别人拿着这份证据能自己再验一遍。

⚠️ 实战判据：`md5 -q *.png | sort | uniq -c`，几张「不同状态」的截图必须是几个不同哈希；相同就说明注入根本没生效，而截图照出、结论看着成立。

### M6 · 诚实缺口（治「看起来全绿」）

- 没真跑的一律记 **SKIPPED**，**绝不并进通过率**（分母只算真跑过的）。把 skip 当 pass 的报告比没有报告更危险。
- ⭐ **结论有四类，不是三类**：PASS / FAIL / **N/A 不适用** / UNABLE 跑不了。
  「前置条件不成立所以这条规则没测到东西」**必须单列为 N/A，不许记成 PASS**——
  记成 PASS 会让报告显示「全部通过」，而它实际上什么都没验；
  等到条件成立、规则本该生效时，没人知道它从没真跑过。
  **判据**：一条规则若对正确实现与错误实现给出同样的结果，它对该对象就是 N/A。
- 环境没就绪 ≠ 跑了不合格，两者必须用不同状态码/标记区分。
- **Open Item 必须带**：owner + 到期日 + 复审触发条件 + 缓解措施。缺任何一项即视为「未修问题」，不得计入通过。
- 工具的**发现**可采信，工具的**沉默**不可采信——低召回工具没报问题不等于没问题，不得据此宣告干净。
- ⭐ **「我没找到」≠「不存在」。** 宣布某样东西「外部没有、必须自己定」之前，先问两句：
  **「这个问题的正本在哪个领域？我翻的是不是那个领域？」**
  📌 真实教训：翻遍 16 个高分**设计 skill 仓**（12.4 万行）后判定
  「多选语义/右键菜单/撤销重做/快捷键仲裁外部给不了」，于是自己写了一份规范。
  随后发现它们的正本根本不在设计语料里，而在**平台人机界面指南**——
  一核对，自写的规范**被推翻 1 条、补出 10 条**，其中「撤销栈要设上限」与平台指南的
  「不要设不必要的上限」**方向完全相反**。
  自己填的空会被后续工作当成既定事实引用，**比单纯漏掉更难纠**。
  **有权威正本的三类**：平台交互（HIG / Windows Guidelines）· 无障碍（WCAG / ARIA APG）· 法规合规。
  这三类一律先找正本，不许用通用语料的缺失反推「不存在」。

### M7 · 逃逸缺陷回流（这条流水线唯一的进化机制）

任何在**后一阶段**才被发现、但**本该在前一阶段**被抓到的问题，必须回填 `lessons.md`：
```
逃逸缺陷：<问题>
本该被谁抓到：S5 · 交互完整性视角
为什么没抓到：□视角缺失 □视角在但判据太泛 □对账门没覆盖这一类
处置：<加视角 / 把具体实例写进判据 / 改对账规则>
```
**不做回流，这套流程只会永远记住去年的坑。** 精确率、覆盖数都是内部自评，逃逸缺陷是唯一的外部指标。

### M8 · 验证工具自证（治「门禁本身是坏的」）

> *"AI writes your code. AI writes your tests. **But who tests the tests?**"*
> —— `mbj/mutant`（变异测试工具，2179★），2026-08-16 查证

**这条流水线的每一道门都是软件，软件都会坏。** 门坏了不会报错——它会安静地一路放行，而你以为它在把关。所以：**任何验证工具在被信任之前，必须先自证它会出声。**

#### ⚠️ 自证绿 ≠ 判据承重（**两件事，2026-09-05 起有工具**）

`--self-test` 变异的是**被测物**（夹具）⇒ 只证明「喂坏输入时门会红」。
它**证明不了**「某条判据承重」—— 一道门可以有 20 个反例、次次全绿，
而其中某条判据从没有任何反例守着，整条删掉自证照样绿。

| 工具 | 变异什么 | 回答什么 |
|---|---|---|
| `<gate> --self-test` | 被测物（夹具） | 喂坏输入时门会不会红 |
| `scripts/reverse-test.py` | **门禁自己**（你指定的那几行） | 这几行承不承重 |
| `scripts/mutation-sweep.py` | **门禁自己**（逐条判据） | 有没有哪条判据**没人守** |

```bash
python3 scripts/reverse-test.py <门禁> --replace "<旧>" "<新>" -- <跑它的命令> --expect 1
python3 scripts/mutation-sweep.py            # 逐条把判据置真，看自证红不红
```

⭐⭐⭐ **判「不承重」时不许直接下结论**，有**三种**成因且**外观完全一样**：

| # | 成因 | 怎么识别 |
|---|---|---|
| ① | 这几行确实没在守什么 | 拿一个已知坏样本撞它 |
| ② | **它在守，但还有另一条路兜住了** | 数一下有几条兜底路径；同时打掉全部才会红 |
| ③ | ⭐ **变异打错了靶子** | **看工具打印的「删掉的是 →」那一行**，核对删的是不是你以为的那段 |

②实测：`currentEnd()` 的两个来源互为兜底，单独打掉任一个 → 9 条关键路径走通 9、断掉 0；
两个同时打掉才断掉 2。⇒ **冗余判据必须让每一路各有一个只有它能接住的用例。**

③最难识别，**因为它每一步都"成功"了**：变异执行了、文件确实改了、语法合法、门禁跑完了。
实测两次都出在正则上（`^(\s*)` 里的 `\s` **包含换行**，匹配起点漂到上一行；
以及要求行首导致 `if (x) bad.push(...)` 同行写法一条都扫不到）。
⇒ 工具因此**必须打印它到底删了什么** —— 那是唯一能把 ③ 与 ①② 区分开的信息。
（三分法由并行会话 fm-agent 归纳。）

| `scripts/unexecuted-check.py` | 不变异，**追执行** | 这条判据**跑过没有**（前提从没成立 ⇒ 它等于不存在） |
| `scripts/unexecuted-check.py --unable` | 同上 | 这个**「跑不了」出口**会不会出声（锚点写错时**两头都不出声**） |

⭐⭐ **三件工具查的不是同一件事，缺一个就有一整类看不见：**
变异按**规则**置真 ⇒ 够不到规则**内部的分支**；
未执行检查只盯**判据行** ⇒ 看不见 `report()` 那一层；
只有专门问「UNABLE 出口有没有被触发」，才发现
**自证全走内部函数 / `quiet` 路径，报告层从没被覆盖过** ——
而退出码映射、UNABLE 透传、诊断措辞**全住在那一层**。
⇒ 每道门至少要有一条**走完整命令行路径**的用例（子进程跑，断言退出码）。

⚠️ `mutation-sweep.py` 的**量程**写在它自己的 `--help` 里，**扫不到的门会明确列出来**——
「⏭️ 量程外」不是「没问题」。

#### 四类失效形态（都出现过，不是假想）

| 形态 | 表现 | 实例 |
|---|---|---|
| **fail-open 假绿** | 永远返回通过 | 退出码处理有误，CI 一路绿灯，直到第三轮外部审核才发现 |
| **结论掩盖** | 报的数字是真的，但掩盖了更大的问题 | 用例覆盖对账给出「覆盖率 100% + 双向全覆盖 + passed」，而那份 PRD 有 8 个缺口、整整一个功能零用例 |
| **假阳性** | 报了不存在的问题 | 对账用 grep 匹配路径，把跨目录的完整路径截断，误报文件缺失 |
| **覆盖静默缩水** | 实际测的比宣称的少 | 工具白名单不含目标文件类型，扫描面悄悄变小而报告照常「通过」 |

⚠️ 注意后两类：**光有「能变红」还不够**。假阳性会让人对门禁脱敏，最后所有告警都被无视；覆盖缩水则是绿得毫无意义。

#### 四步自证（开跑前做，不是出问题后再做）

1. **正例 → 必须绿。** 证明它不是永远报错。
2. **每类缺陷各造一个反例 → 必须红。** 只造一个反例不够——一个工具可能只认得出其中一类。
3. **无效输入 / 环境缺失 → 必须报错退出，绝不许返回绿。** 「跑不了」和「跑了没问题」是两回事，折叠成一个状态就是 fail-open。
4. **人工核实它报出的每一条。** 自动计数会**同时高估失败与成功**——模板回显、引用的反例文本都会伪装成命中。（借自 superpowers `writing-skills` 的验证方法论）

**证据要求**：贴出退出码与输出。只说「我验过了」不算。

#### 变异测试：判断「这套检查到底在不在测东西」

故意把被测对象改坏（`===` 改成 `!=`、阈值 5 改成 6、权限判断取反），然后重跑检查：

- **检查仍然全绿 → 变异存活 → 这套检查没在测东西**，哪怕覆盖率是 100%。
- **检查失败 → 变异被杀死 → 这才是好结果。**

> 「传统覆盖率经常说谎」：覆盖率只记录测试**走过**哪些行，从不确认测试**断言了正确结果**。就像用护照盖章证明工作成果——它只证明你去过机场和酒店。

#### 对照组：这道门有没有必要存在

**问：没有这道门时，问题会不会真的漏过去？** 如果去掉它、问题照样被别的环节挡住，那它只是在制造安全感，不是在把关——删掉，别维护。
（借自 superpowers：任何guidance 都要有 no-guidance 对照组，对照组不出问题就没有可修的东西。）

#### 已知的具体假绿形态（照着排查）

- **无断言的检查**：调用了却不验证任何结果 → 100% 覆盖、0% 测试。
- **被跳过的检查**：skip 掉的项制造「全部通过」的假象——**skip 必须显式计数并单独呈现**。
- **占位数据永远走不到真实分支**：用 `Foo`、`test`、`123` 这类合成值，含空格/特殊字符/超长的分支永远不被触发。
- **手工 try-catch 代替「预期抛错」**：没抛异常时，报告只显示「某个值是 null」，看不出真正坏在哪。

#### 什么时候必须重跑自证

工具改动后 · 路径或目录结构变化后 · 运行环境变化后。
⚠️ **「上次跑过、没改所以还绿」不成立**——这正是 M5 证据独立性要防的东西。
