# S8 · 用例工程（PRD → 测试用例）

**身份：用例工程，不是测试执行。** 产出用例集与覆盖对账，不跑测试、不写自动化脚本代码（那是 TDD 链和 CI 的事）。

本模块可以**单跑**——手上只有一份别人写的 PRD、不走完整十阶段时，直接按本文执行即可，不需要 `.product-flow/` 那套目录。

## 核心信条

**这一步的价值不在于"生成得多"，而在于"缺什么敢说缺"。**

⚠️ 一份没有字段级规格的 PRD，正确产出是**缺口报告**，不是一堆看起来很像用例的东西。猜出来的用例测的是我的想象，不是需求——它会通过评审、进入执行、然后测出一堆与真实需求无关的结论，而所有人都以为已经测过了。

📌 这条铁律来自真实事故：一份登录 PRD 通篇没有字段规格（长度、格式、错误文案一概没有），测试侧**根本生成不出用例**。当时若"顺手补齐"，产出的会是一份自洽但完全虚构的用例集。

## 执行顺序（不可颠倒）

```
① 就绪度判定 ── 不合格 ──> 出缺口报告，停在这里，回去补 PRD（回 S4/S5）
      │合格 / 部分合格
      ▼
② 抽取需求项（FR/AC/功能点）
      ▼
③ 逐项设计用例
      ▼
④ 双向覆盖对账（正向 + 反向）
      ▼
④.5 用例集自检（这套用例能抓到东西吗）
      ▼
⑤ 输出用例集 + coverage.json + 诚实缺口清单
```

**部分合格**＝对合格的部分生成用例；不合格的部分**列进缺口报告并在用例集中标 `[待补规格·不生成]`**，绝不用推测填上。

## ① 就绪度判定（本模块最重要的一步）

详见 `testcases-readiness.md`。速查：

| 维度 | 缺了会怎样 | 没有它能生成用例吗 |
|---|---|---|
| 字段级规格（类型/必填/长度/取值/校验/错误文案） | 输入类用例全靠猜 | ❌ 不能 |
| 异常场景 | 只能生成 happy path，漏掉一半用例 | ❌ 不能 |
| 状态清单（空/加载/失败/无权限/极值） | 状态类用例缺失 | ❌ 不能 |
| 验收标准 `FR/AC` | 没有判定基准，用例无法给出预期结果 | ❌ 不能 |
| 权限与角色定义 | 越权类用例无从设计 | ⚠️ 部分 |
| 数据边界（最大条数、并发、超时） | 性能/边界用例无依据 | ⚠️ 部分 |

**判定结论只有三种**：`可生成` / `部分可生成（附缺口清单）` / `不可生成（附缺口清单）`。
⚠️ **不许有第四种**，尤其不许出现"基本可以，我按常规补一下"。

## ② 抽取需求项

按 PRD 形态选适配器，见 `testcases-adapters.md`（结构化附件 A / 六章制 / 裸文档 / 用户故事）。
走完整流程时是形态 A——`templates/prd-complete.md` 的附件 A 就是标准输入（配套附件 D 字段规格、附件 E 状态机与异常）。

### ⭐⭐ 还要读交互规格的三张表（2026-08-31 补：此前用例工程完全不知道它们存在）

| 读什么 | 在哪（⭐ 2026-09-15 更正：机器正本是 spec/ 下的 JSON，md 表只是人读摘要且「不写不影响对账」） | 用来做什么 | 不读的后果 |
|---|---|---|---|
| **场景清单** | **`spec/states.json`（正本）**；`templates/interaction-spec.md` 的表=人读摘要 | 用例的**场景覆盖**按它对账 | 用例覆盖了需求却漏掉状态——⭐ **需求全覆盖不等于状态全覆盖** |
| **元素标识表** | **`spec/elements.json`（正本）**；同上 md 表=人读渲染 | 用例的**选择器**直接用这些标识符 | 用例里各起各的选择器，**改一个按钮所有用例静默失效** |
| **状态四类**（适用性列） | `templates/interaction-spec.md`「完整状态列表」+ `interaction-patterns.md` | 每个**标了「适用」的状态**都要有用例 | 标了适用却没人测，等于没定义 |

⛔ **标了「不适用 + 理由」的状态不许生成用例**——那会造出测试不存在功能的用例。
⚠️ **已上线产品**（反向提取型）：场景清单的等价物是 `.product-flow/baseline.md`，
用它的场景表当输入，判据不变。

抽取结果必须是一张可核对的清单：`需求 ID | 出处（章节/行）| 类型 | 是否可测`。
⚠️ **不可测的要标出来**（例：「界面美观友好」——无判据，不可测）。不可测的需求是 PRD 缺陷，进缺口报告。

## ③ 设计用例

方法见 `testcases-design.md`（等价类、边界值、状态迁移、异常路径、权限矩阵、安全用例、pairwise 组合）。

### ⭐ 先生成骨架，再人工补齐（2026-09-02）

S5.2 若产出了 `spec/flows.json` 与 `spec/states.json`，**关键路径与状态类用例直接生成**：

```bash
python3 scripts/flows-to-testcases.py <spec目录> <cases输出目录>
```

⭐ 好处不是省事，是**选择器与 demo 同源** —— 此前用例与 demo 各起各的选择器，
「改一个按钮所有用例静默失效」。生成出来的步骤用的是 role + 可访问名称，
与 `flow-walk-gate` 走的是同一套。
⛔ 它**只覆盖关键路径与状态可达两类**，等价类/边界值/权限矩阵/安全用例仍要人补；
且缺 `fr` 的流程会被**拒绝生成**（反查不到需求的用例不许存在）。
⛔ 本脚本不声称覆盖率 —— 声称覆盖率的是下面的 `coverage_check.py`。

用例格式：

```markdown
### TC-011-2　所属 FR-011 · AC-2
**标题**：锁定计数器 15 分钟后重置
**前置**：账号已连续输错 3 次，未达锁定阈值
**步骤**：1. 等待 15 分钟无操作　2. 再次输错密码
**预期**：计数从 1 重新计，不触发锁定
**依据**：附件A FR-011 AC-2　**类型**：边界　**优先级**：P0
```

**硬要求**：
- 每条用例必须有 `所属 FR/AC`——**反查不到需求的用例不许存在**。
- 预期结果必须来自 PRD 原文，不是我的判断。原文没写预期？那是缺口，不是让我来定。
- 用例 ID `TC-<FR号>-<序号>`，只增不改。

## ④ 双向覆盖对账

```bash
python3 scripts/coverage_check.py <requirements.md> <cases 目录> -o coverage.json --gaps readiness.md
```

- **正向**：每个 `FR/AC` 有用例？没有 → 需求没测。
- **反向**：每个用例能反查到 `FR/AC`？不能 → 在测没人要的东西。

⚠️ **反向漏更危险**：它意味着有人在没有需求依据的情况下自己发挥，这部分永远没人负责。

退出码：`0`=对账通过且缺口已核（`--gaps` 提供且无未解决缺口、无用例级 SKIPPED）｜`1`=有漏/格式违规/重复 TC-ID｜`2`=输入无效｜**`3`=对账通过但不能声称被测充分**（有缺口、有用例级 SKIPPED、或没给 `--gaps` 缺口状态未知）。
⭐ 2026-09-15 起「不带 `--gaps`」本身就是 3——0 的语义是「无未解决缺口」，没核过的事工具不替你声称。

### ⭐ 用例级 SKIPPED 的书写约定（2026-09-15 补——此前只活在脚本注释里，照文档交付的人无从知道）

- 标记写在**用例头行的末尾**：`### TC-012-1 所属 FR-012 **SKIPPED**`（`**跑不了**`/`**未执行**` 等价；⛔ 必须加粗且在行尾——裸文字或行中出现不识别，防止标题里的自然语言被误标）；
- 紧随的正文里必须有理由行：`**SKIPPED 理由**：<为什么没跑>`（`跳过理由`/`未执行理由` 等价）。⛔ 不写理由＝静音开关，判 1；
- ⛔ 写在其它位置（步骤里、备注里）**不被识别**——会被当成正常用例计进覆盖率。

### ⚠️ 覆盖率不许单独呈现（真跑一次才发现的坑）

**覆盖率的分母只含「PRD 里真实存在的需求」。PRD 本身缺失的需求没有编号，进不了分母。**
所以一份撑不起用例的 PRD 完全可能跑出 **100% 覆盖率 + 双向全覆盖**——看起来全绿，实际上一整个功能一条用例都没有。

📌 2026-08-16 端到端演练实录：一份含 3 个功能的 PRD，其中 1 个功能无任何验收标准、1 个只有主路径，对账结果仍是「覆盖率 100%、双向全覆盖、passed=true」。**这是本流水线自己差点产出的假绿。**

**硬约束**：报告覆盖率时**必须同时给出就绪度结论与未解决缺口数**，`--gaps` 不是可选项。
只贴一个「覆盖率 100%」的结论，等同于谎报。

## ④.5 用例集自检：这套用例能抓到东西吗

**覆盖率高不等于测得出问题。** 一套全绿的用例可能什么都抓不到——它只是把实现现状重述了一遍。

自检方法（借鉴变异测试思路：**让测试怀疑自己**）：
1. 挑 3~5 条 P0 用例，**假想需求被改坏**（阈值 5 改成 6、锁定时长 15 分钟改成 0、越权判断取反）。
2. 逐条问：**这套用例里有没有哪一条会因此失败？**
3. 没有任何一条会失败 → 这个需求实际上**没有被覆盖**，哪怕它在覆盖率表里是绿的。

⚠️ 这类"假覆盖"最常见于：只写了 happy path、预期结果写成「正常」「成功」而没写具体值、边界只测了中间值。
⚠️ **发现假覆盖属于缺口，不是可选优化**——按缺口的唯一登记入口处理：
**回填 `readiness.md` 的缺口清单表并顺延 GAP 编号**（`testcases-readiness.md` 的硬约束），
`gaps.md` 里记录现象与影响时**引用**该 GAP 编号，⛔ 不在 gaps.md 另发号。
（2026-09-15 改——旧文「写进 gaps.md」与「缺口登记只有一个入口」互斥，照旧文执行会复刻 GAP-09 孤儿编号事故。）

（思路来源：`avelikiy/great_cto` 的 "QA that distrusts itself"，2026-08-16 查证。⚠️ 该仓 README 里并无网传的「12-angle code review」，未予引用。）

## 本模块铁律

1. **就绪度不合格 → 出缺口报告并停下**，不生成用例。
2. **每条用例可反查到需求 ID**，反查不到的不许存在。
3. **预期结果只能来自 PRD 原文**，不能来自我的常识。
4. **缺口如实列出，不用推测填补**；不生成的部分标 `[待补规格·不生成]`。
5. **覆盖率分母只算真核过的需求项**，未核的记 SKIPPED，不并进覆盖率。
   ⚠️ **且覆盖率必须与就绪度结论、未解决缺口数一起呈现**——单独的覆盖率数字必然被读成「已测充分」，而它不是。
   ⚠️ **`[待补规格·不生成]` 只适用于「有编号但规格不全」的需求**。真实场景里更多的缺口是「PRD 里连这条需求都没有」——那类缺口**没有编号可标**，只能进 `readiness.md` 的 GAP 清单，`coverage.json` 里看不到它们。这是本工具的固有盲区，报告里必须点明。
6. **不可测的需求要指出来**（无判据、纯形容词），那是 PRD 缺陷。
7. **不跑测试、不写自动化代码**——越界就变成了另一件事，且做不好。

## 常见合理化（出现即停）

| 借口 | 现实 |
|---|---|
| 「PRD 没写，但一般都是这么做的」 | 「一般都这样」是编造的高级形态，读起来最像事实 |
| 「先按常见做法生成，后面再让人确认」 | 没人会确认。用例一旦成型就会被当成需求本身执行 |
| 「只报缺口显得没产出，先给个 80%」 | 掺了猜测的 80% 比诚实的 0% 更贵——它让所有人以为已经测过了 |
| 「字段规格可以照竞品推断」 | 竞品的规格不是本产品的需求 |
| 「报缺口是甩锅，我应该帮忙补全」 | 补全需求是产品的职责。替他决定＝替他背锅，且他不知道自己被决定了 |
| 「这条需求虽然模糊但我能理解意图」 | 你的理解无法被验收。写不出预期结果就是不可测 |

## 红旗——出现就停下重来

- 正在写一条**预期结果在 PRD 里找不到出处**的用例
- 正在给**没有字段规格**的输入功能写边界值用例
- 用例里出现「应该」「合理」「正常情况下」等无判据词
- 覆盖率算出来很好看，但分母包含了没真核的项
- 缺口报告为空——**真实 PRD 极少全项齐备，空缺口清单本身就是可疑信号**
