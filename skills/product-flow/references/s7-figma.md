# S7 · Figma 高精度视觉母版 · 专节全文（从 SKILL.md 迁出）

## S7 · Figma 高精度设计稿
本阶段把 PRD 的每个 `F-xx` 变成**可交接给研发的高精度、可编辑设计稿**。四条按顺序读：

### ⭐⭐ S7 前置：先建「基座库」，再铺任何全量屏（探索切片除外）

**这是 2026-08-30 调研 + 实战得出的最重要一条。** 高精度可编辑稿的本质是
**「实例化组件 + 绑定变量」**，不是「画得像」。没有基座就铺量，只会得到
「看着像稿子、但每个色值都是硬编码、改一个按钮圆角要改 60 处」的东西——
我第一次做 25 屏就是这个下场。
⚠️ **顺序有两头坑**：反过来「先锁令牌再画第一屏」会把探索钉死在没人看过的表格里。
正确时序＝**探索切片（≤B 锁，1–2 屏真实内容，允许直接写值，⛔ 不进正稿库、不当正稿交付）
→ B 锁批准 → 从批准切片提炼令牌、建基座 → 全量铺开全绑实例/变量**（架构正本 S7.0–S7.5）。
本节以下的「建库」步骤全部指 B 锁之后那一步。

**完整 API 序列、坑与写后校验见 `references/figma-baseline.md`。**

⚠️⚠️ **开工前必须先探两个底，不探就会白干**：
1. **`addMode` 的模式数上限** —— Starter(免费)=1 / Professional=4 / Org=40。
   **免费座位很可能连 Dark 模式都加不上**，抛错就得把双模式降级成「两套变量 + 一层语义别名」。
   这是结构性决定，必须在建库前定，不能建到一半发现。
2. **字体可用性** —— `listAvailableFontsAsync()` 现查；服务端无 `PingFang SC`，中文用 `Noto Sans SC`。

**基座 = 三样，缺一不可**：

| # | 做什么 | 产出 |
|---|---|---|
| 1 | **Variables 集合**，至少 Light/Dark 两个 Mode | 语义色（bg/text/border/state）+ 数值（space/radius/size），**每个变量显式设 `scopes`** |
| 2 | **Text Styles** | Display/Title/Body/BodyStrong/Caption；中文行距 ≥1.4；**中文不用 italic** |
| 3 | **Master Components（带完整变体）** | 至少：Button / Pill / NavItem / SegmentedControl / Card / ListRow / Toggle / SearchField / EmptyState / Toast / Modal |

**令牌值从哪来**（不许自由发挥，这是防 AI slop 的关键）：
- 有已上线程序 → **量真实程序**（`scripts/capture-live-ui.js`）
- 行业基线 → `ui-ux-pro-max`（192 配色 / 74 字体搭配）+ `impeccable`（129 条 OKLCH 品牌种子）
- **视觉高度锚定一个真实配方**：`~/.claude/skills/web-design-engineer/references/style-recipes/` 有 **25 个真实品牌配方**（linear / raycast / aesop / stripe-press / muji-kenya-hara / vignelli…），带精确 hex、字体、间距、留白比例。**选一个当锚，不要东拼西凑**；`cc-design` 另有 20 个设计流派可选。
- 中文产品 → `chinese-font-selector`：可商用授权分级 + 中英混排规则（**英文字体在前、中文在后**；中文无斜体）

⚠️ **锚点可以只借设计语言、不照搬底色**：Raycast 是深色底，而照片类产品必须浅色（内容才是主角）。借它的间距阶/圆角阶/快捷键 chip/浮层阴影，底色走自己的——用 Variables 的 Light/Dark 两个 Mode 两头都覆盖。

**配套 skill（2026-08-30 已装，star 数已核实）**：
- `figma-preflight`（claude2figma 190★）—— **每次设计会话开工前必跑**：验 MCP 连接、审已连接的库、载入 Token Map
- `figma-style-binding` —— 强制所有视觉值绑 Styles/Variables，写后自动 QA
- `component-rules` —— 强制「先查库里有没有现成组件」再造，Auto Layout 结构与语义命名
- `reference-interpreter` —— 截图/URL → 结构化 Design Brief（映射到令牌），**等确认再动手**
- `prototype-to-figma`（138★）—— demo/原型 → 按交互状态逐帧拆成 Figma，无匹配组件打 "No DS match" 徽章，出 Dev Mode 原生标注

⚠️ **这些 skill 都以「文件已链接一套已发布的组件库」为前提。基座不建，装了也会退化成画矩形。**

### ⭐ S7 铁律：Figma 设计稿必须是**高精度 + 可编辑**

**可编辑 ＝ 用真实图层搭出来**：Frame / Rectangle / Text / AutoLayout 各就各位，颜色字号间距都是可改的属性。
**不可接受的做法**（看着像设计稿，实际不是）：
- ❌ 把程序截图当图片贴进 Figma 充当「设计稿」——那是贴图，设计师改不动一个像素
- ❌ 整屏画成一张大图 / 一个 Vector
- ❌ 文字用图片代替，或用色块糊出文字的形状

**高精度 ＝ 尺寸、颜色、字号、间距都取自真实来源**，不是目测近似：
- 有已上线的程序 → **先从真实程序取规格**（CDP 抓 `getComputedStyle` + `getBoundingClientRect`），再按这份规格在 Figma 里重建。
  现成工具：**`scripts/capture-live-ui.js`**（启 Electron + CDP → 关引导弹窗 → 导出 `spec-*.json` 规格与截图）
- 没有程序 → 按 `DESIGN.md` 令牌值搭
- ⚠️ **只信 DOM 规格会翻车**：规格可能显示一切正常，画面其实被首启弹窗/遮罩盖住。**必须同时截图肉眼确认**

### ⛔ 自检三问不够用 —— 它是一道假绿门禁

原来这里写的是三问：能不能双击改字 / 能不能改填充色 / 尺寸是量的还是估的。
**实测证明这三问会对「堆矩形」的稿子全部放行**：某项目 25 屏、1654 个节点、
**0 个组件实例、0 处变量绑定、1314 处硬编码填充**，而三问全部通过。

因为三问检验的是「**是不是贴图**」，而堆矩形也是真图层。
「不是贴图」离「可交接」还差着整个组件化与令牌化。

**判据换成四个可计算比率**，跑 `scripts/figma-editability-gate.py`（走 REST API，
**不消耗 MCP 写入配额**，可反复跑）：

| 指标 | 默认档 | strict 档 |
|---|---|---|
| 组件实例化率 | ≥60% | ≥80% |
| 变量/样式绑定率 | ≥50% | ≥75% |
| 硬编码填充数 | ≤60 | ≤10 |
| AutoLayout 覆盖率 | ≥80% | ≥90% |

**基座建成后 strict 档必须过**——它是「基座真的建成了」的可证伪判据，
比「我跑完了建库脚本」可信得多。判据详情见 `references/design-quality-gates.md`。

### ⭐ S7 铁律：设计稿按「载体」出对应端的形式，不许一套稿糊两端

**载体在 PRD 3.2 功能清单表里已经定死了**（`两端` / `仅 web` / `仅移动端`），设计稿必须照着出：

| 功能的载体 | 要出几套稿 | 画板尺寸 |
|---|---|---|
| **两端** | **两套：PC + 移动端** | PC `1440×900`（或 `1280×800`）· 移动端 `390×844`（iPhone 15）或 `375×812` |
| 仅 web | 一套 PC | 同上 PC |
| 仅移动端 | 一套移动端 | 同上移动端 |
| 桌面客户端（Electron/原生） | 一套桌面 | 按真实窗口量，不要套 web 栅格 |

⚠️ **两端不是「同一张稿缩一下」**，至少这四处必须重新设计，否则到研发必返工：

| 维度 | PC | 移动端 |
|---|---|---|
| 导航 | 左侧栏常驻（200-280px）· 顶栏 | 底部 Tab（≤5 项）· 抽屉 · 返回手势 |
| 信息密度 | 多列网格、并排面板、悬浮预览 | 单列/双列、面板改全屏页或半屏抽屉 |
| 交互 | Hover / 右键菜单 / 键盘快捷键 | 无 Hover · 长按 · 左右滑 · 触摸热区 ≥44pt |
| 文案上限 | 较宽松 | **更窄**（同一句 Toast 在移动端常装不下，见附件 F 的字数上限列） |

⚠️ **Figma 图层命名带端**：`F-03/PC/收藏筛选`、`F-03/移动端/收藏筛选`，供 M4 对账时按端逐一核。
⚠️ **PRD 第四章的「设计稿」列，两端功能要放两个链接**（PC 稿 + 移动端稿），不是一个。
⚠️ **降级版要在稿上标出来**：功能清单说「降级版」的，移动端稿必须画出降级后的样子，并在稿上标注哪些能力不提供——**不标注就会被当成漏做**。

### S7 Figma 写入前置（照这个顺序做，否则会卡在「没有 fileKey」）

> ⛔ **账号、team、组织不写在流程里——它们是运行前探测出来的，不是规则的一部分。**
> 本 skill 声称「与具体公司无关、可分发」，硬编码任一账号都与这个定位冲突；
> 而且**过期的账号记录会主动制造错误结论**：2026-08-31 一次外部评审就因为读到一份
> 过期的全局账号记录，把本文件判成写错了账号——**实际是那份记录过期了，方向正好反过来**。
> 📌 具体账号只认本次 `whoami` 返回值，不从任何个人目录或历史记忆文件读取；
> **不在本文件里复述**（复述一次就多一处会过期、会泄漏的副本）。

1. **探账号**：先跑 `whoami`，**用它返回的账号，不要用任何文档里写着的账号**。
   记下返回的 plan 列表与座位类型——下一步要用。
2. **探可写位置**：`use_figma` 必须先有 `fileKey`。没有现成文件就 `create_new_file`，
   `planKey` 取上一步 `whoami` 返回的那个 plan。
   ⚠️ **View 座位不等于不能写**：自己 drafts 里新建的文件可写（2026-08-29 实测推翻过一次相反的判断）。
   ⚠️ 不在当前账号可见范围内的组织/企业文件**够不着**——遇到这种需求走降级路径，不要硬试。
   ⛔ 这两步的结果**写进本项目的 `.product-flow/env.md`**，不要回写进本 skill。
3. **写入契约**：
   - 换页必须 `await figma.setCurrentPageAsync()`，不能直接设 `figma.currentPage`
   - 文本先 `loadFontAsync`；**中文字体用 `Noto Sans SC`**（`PingFang SC` 服务端不存在，会变豆腐块）
   - 脚本**原子执行**，报错整段不生效
   - 结果靠 `return` 回传，**`console.log` 不回传**
   - 禁用：`loadAllPagesAsync` / `setPluginData` / `createImageAsync`（不支持）
4. **命名**：每个 `F-xx` 一个 Page 或 Section，图层命名含功能编号（如 `F-01-导入`），供 M4 对账。
5. **边界**：**Figma 只做 UI 界面**；架构图 / 功能树 / 页面流程图留在 PRD 里用 `fireworks-tech-graph`，不要搬进 Figma。
6. 设计稿完成后，把链接嵌回 **PRD 第四章的「设计稿」列**（`[F-xx 设计稿](figma链接#node-id=xxx)`）。设计稿展示「长什么样」，逻辑列写「怎么交互」，**改了一边另一边必须同步**。

⚠️ **可分发性边界**：项目设计基线、协作文档 CLI 等可能属于**当前环境专属**，换一台机器就不存在。
（Figma 账号已不在本文件里——它是**运行前 `whoami` 探测**的结果，写进项目的 `.product-flow/env.md`。）
本 skill 的**流程与判据不依赖它们**——PRD 模板已自包含，协作文档写入可换成任何工具或人工粘贴。
迁移到新环境时，把上表的「首选」逐项换成当地等价工具即可，**不要因为某个工具不存在就跳过该阶段**。
