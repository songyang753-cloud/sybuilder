# S5 · 设计交互迭代

## 交付契约

1. **PRD 第四章的交互说明补全**：每个 `F-xx` 写清页面结构、控件、状态机、反馈、跳转。
2. **附件 A 验收标准**：`FR-###`/`NFR-###` + Given/When/Then，末尾**可追溯矩阵**（需求→目标→功能→FR/AC）。
3. **状态清单**：每个界面的空态 / 加载态 / 成功 / 失败 / 无权限 / 极值（超长文本、0 条、10000 条）。

## ⭐ 动笔前先分类（不分类就动手，规则集必然用错）

**营销页 / 应用 UI / 混合**——三者的正确答案互相冲突：
落地页要**被记住**（强锚点、有表达力的排版、2–3 处有意的动效、首屏当海报）；
应用 UI 要**被忘记**（安静的表面层级、密集但可读、少颜色、卡片只在它就是交互时才出现）。

**三套规则集见 `references/design-rulesets.md`**，同时那份文件里还有：
七条硬否决 · Litmus 七问 · **可辩护的品味与 12 条认知模式** · 0–10 评分法 · 结构化评审语法。

## ⭐ 动笔前的三件事（第 3 层反 slop，比任何黑名单都根本）

在写第一行令牌之前，先交出三句话。**这三句是后面所有设计决策的裁决依据**：

1. **Design Read**：「我把这个读作：给 <谁> 的 <什么产品>，<什么调性>，倾向 <什么设计系统>。」
2. **Memorable-thing**：「用户第一次看到这个产品后，我要他记住的**唯一一件事**是什么？」
   一句话回答。**之后每个设计决策都要回查它。**
   > Design that tries to be memorable for everything is memorable for nothing.
3. **SAFE / RISK 提案**：一次性提出美学方向/装饰/布局/色彩/排版/间距/动效七项，
   加「这套为什么自洽」，然后标出——
   - **2-3 条 SAFE**（符合品类惯例的，说明为何这里要求稳）
   - **RISK 提案制**（**故意背离品类惯例的**，每条写清：是什么 / 为何成立 / 得到什么 / 代价什么）——
     默认 2–3 条；**零提案合法但必须写理由**（严格品牌约束、低风险局部改动是正当理由）——
     写法：`为何没有值得评估的突破：<理由>` 或 `本轮零 RISK 提案，理由：<理由>`，
     ⛔ 冒号后必须是实质内容（`design-intent-gate` 两种措辞都认，空理由与占位符都红）

⚠️ **RISK 是提案制：零提案必须写「为什么这里不值得冒险」——写不出理由的零提案才是模板货。**
设计自洽只是及格线，真正的问题是「你在哪里冒险，或为什么不冒」（契约同 `templates/design-brief.md`）。

⚠️ **跨代要求分两轴，方向相反**（`scripts/taste-memory.py`，详见 `design-orchestration.md` 〇之二）：
**品味轴收敛**（明暗/档位/字体气质/色温/密度/动效 —— 与档案强信号一致，偏离要写理由）·
**执行轴发散**（具体字体族/强调色/视觉锚点/布局 —— Greenfield/Overhaul 不许复用上代）。
⛔ **Preserve 模式下执行轴反过来：必须保持。**
📌 老规则把「明暗方向」放进了发散轴，那是切错了地方 —— 明暗是最典型的品味。

## 硬约束

- ⚠️ **附件 A 与正文双向 ID 绑定**：第四章每功能末尾写「验收标准：见附件A · FR-031~033」，附件 A 每条反标「所属 F-03」。**只做单向绑定的附件必然变成孤儿**——正文改了没人同步，下游按孤儿附件生成用例全是错的。
- ⚠️ **文案是硬约束的一部分，不是装饰**。控件有字数上限就写进规格。
  📌 真实教训：一处 Toast 组件硬上限 18 字，而 PRD 规定的错误提示 30 字——直到设计阶段才发现装不下，PRD 正文与实际文案长期打架。**凡有长度限制的控件，规格里必须写上限，并检查所有要塞进去的文案**。
- ⚠️ **双端必须逐功能回答三选一**：两端同一套交互 / 降级版 / 只在一端存在。不回答＝到 S7 必然返工。
- ⚠️ **有设计基线时，基线是「用户给的那份」**，不是我从别处找的同名文件。锚点（模版链接 / node-id / 截图）以用户提供的为准，**不得自作主张换锚点**。
  📌 真实教训：把模版锚点换成"看起来更合适"的另一处，导致整轮返工；另一次只读规格文字没看截图，二轮返工。**规格文字与实际截图都要看**。

# S6 · 可交互 HTML demo

## S6.0 先定保真度：这一轮要做到哪一档

**不许默认直奔高保真。** 先答一句：这一轮的 demo 是用来回答什么问题的？

| 档 | 长什么样 | 回答什么问题 | 什么时候用 |
|---|---|---|---|
| **线框** | 灰块 + 真实文案，无颜色无图 | 信息架构对不对？关键路径几步？ | 功能清单刚定、还在争「放哪儿」时 |
| **骨架** | 真令牌 + 真布局，占位内容 | 布局撑不撑得住所有状态？断点对不对？ | 令牌定了、开始排页面时 |
| **高保真** | 真令牌 + 真内容 + 全状态 + 微交互 | 这个方案能不能给老板看、给研发照着做？ | 方案基本定了、要交接了 |

⚠️ **档位选错的代价是不对称的**：方向还没定就上高保真，被否时扔掉的是整份；
而线框阶段被否，扔掉的只是半小时。**方向没定 → 一律先线框。**

### ⭐⭐ 保真度是**两个轴**，不是一个（2026-09-02 补）

上面那张表只说了**视觉**保真度。它答不了「点不点得动」——
实测一份「视觉高保真」的 S6 产物，**71 个控件里 66 个点了毫无反应**。
⛔ 只报视觉档位，等于把「好看的静态图」和「能走通的原型」说成同一件事。

| 行为档 | 含义 | 判据（可机器验） |
|---|---|---|
| **B0 静态** | 只能看 | —— |
| **B1 可导航** | 页面之间能走 | 路由能通 |
| **B2 可操作** | 表单能填能校验，列表能增删改 | `dead-click-gate.mjs` 死按钮 ≤5% 且控制台零报错 |
| **B3 闭环** | 全流程从头走到底，状态跨页保留，失败能重试 | 关键路径脚本走得完 + 跨页状态持久 |
| **B4 拟真** | 时延 / 失败 / 无权限 / 极值都能**注入**触发 | 场景矩阵每个状态都有 `scn=` 能触发 |

**声明档位时两个轴都要写**，例如「视觉：骨架 × 行为：B3」。
- 给老板看 ≈ 视觉高保真 × **B3**
- 给研发交接 ≈ 视觉骨架 × **B4** 就够（研发要的是行为与契约，不是配色）
- ⛔ **「视觉高保真 × B0」是最贵也最没用的组合** —— 画了最多的图，回答不了任何问题。

## 定位

**可执行 UX 基准（executable UX baseline），不是「演示品」也不是视觉创作。**
它证明产品的操作、状态转换、反馈、恢复、输入方式与端行为**真实可运行**；
研发后的最终应用必须能用同一份 flow 契约回放，并在用户可感知层面与它一致。
⭐ 交互稿与 demo 是**同一件东西**（用户 2026-09-07 拍板）：同一套交互逻辑的 HTML 形式——
目录版（`templates/proto/`）是开发态，bundle 出的单文件是分发态，⛔ 不得出现第二套手写实现。
演示外壳（场景切换器等）与产品 UI 隔离：它不进产品 DOM 的键盘顺序，也不出现在截图基准里。
「换掉 mock 即接真接口」只承诺 **adapter 语义稳定**（`operations.json`），
不承诺工程沿用同一 store/网络库/HTTP 形态（那些是工程决定）。
⭐ S9.3 产品验收会**用同一份 `flows.json` 在最终应用上回放**（s9-quality-gates 执行合同）——
所以这里的 flow 契约不是 demo 的私产，是贯穿到验收的行为合同。

**从 `templates/proto/` 起步**（四层可运行原型：① 数据/场景 → ② `api.js` 唯一调用面 →
③ store + router → ④ 视图）。⛔ **不要从 `demo-scaffold.html` 起步** ——
那份是最小锚点示例，它示范的「一个状态一个 `<section>`」会把 demo 钉死成幻灯片。

⭐ 为什么必须是这个形态：**状态要跑出来，不能画出来。**
`?scn=empty` 不是另画一屏，它只是把 fixture 换成空数组，界面自己走到空态；
`?scn=api-500` 只是让接口抛错。这样「操作与真实实现保持一致」才第一次成为可检验的事 ——
把 `api.js` 整体换成真 `fetch`，其余三层一行都不用改（借自 MSW 的 Deviation-free）。

内置 `modules/prototyping/MODULE.md` 负责场景编排 / 交互可达性 / 自包含分发 / 几何自测门禁 / 诚实占位，
以及把目录版合成零外链单文件（`modules/prototyping/scripts/bundle.mjs`，随套件安装，不需要另装 demo-html）。
**HTML 工作流内部**顺序不能反：先行为骨架，后视觉皮（反过来会得到好看但点不动的东西）。
⚠️ 这说的是 HTML 自己内部的次序——**跨工作流与 Figma 是三锁并行协同**（架构正本 §四），不再互相等锁定。

## S6.1 编码前必答六项（不答就动手，返工的是整份）

1. 这个 demo 要回答什么问题？（对应上面的档位）
2. 谁会看它？（老板 / 研发 / 用户走查——三者要的东西不同）
3. 覆盖哪些场景？哪些**明确不覆盖**？
4. 数据从哪来？真实的、样例的、还是占位的？
5. 哪些交互是真的能点通的，哪些只是静态展示？
6. 交付形态是什么？（单文件 / 一组文件 / 需不需要起服务）

## S6.2 状态表用四列，不用列举

⚠️ 「空态 / 加载 / 失败 / 无权限」这样的**列举不是规格**——它没说清楚状态怎么进、怎么出、
进去以后用户能干什么。改用四列：

| 状态 | 触发条件 | 可见结果 | 此时可用的动作 |
|---|---|---|---|
| 空 | 库里 0 张照片 | 引导文案 + 主 CTA「导入」 | 导入 · 打开设置 |
| 加载中 | 已发起导入 | 骨架网格 + 进度条 + 已完成计数 | **后台运行** · 取消 |
| 部分失败 | 导入完成但有读取失败 | 完成提示 + 失败计数 + 可展开清单 | 查看失败项 · 知道了 |

**末尾必须显式列一行「不在本轮范围内」**，写清这一轮故意不做的状态与理由。
没有这一行，读的人无法区分「漏了」和「故意不做」。

## 交付契约

1. **分发态 bundle 后单文件、零外链、双击即开**（可直接发给他人，不依赖本机服务；开发态是目录版，正本唯一，见上「双态」）。
2. **场景导航**：附件 A 的每个 `FR/AC` 要么有对应场景，要么显式标注「不演示 · 理由」。
3. **真实可点**：关键路径必须能点通，不是静态截图拼接。
4. **诚实占位**：假数据标成假数据，未实现的功能标明，不做出「已经能用」的假象。

## 硬约束

- ⚠️ **demo 的价值在于被眼睛检验，所以必须真的打开看**。只读代码判断 demo 对不对是无效的。
⚠️ **静态截图看不见的东西**：Tweaks 面板、动效、按钮切换态——这些只能录屏或人工点。
  「截了图」不等于「验了动效」。
⚠️ **不要用合成事件去验按需渲染的内容**。IntersectionObserver 不理会合成 scroll、
  lazy 图在视口外根本不去取——**探针假设渲染是急切的，而产品是按需的**，
  于是断言对正确实现也给不出绿。正解是**读产品自己挂的就绪标记**（如引擎初始化完挂 `.ready` 类），
  而不是猜渲染时机。
  📌 真实教训：某项目连续 67 轮读代码零发现，一旦在真实渲染环境里打开走查，两轮挖出 12 条问题。**渲染层的问题读代码看不出来**。
- ⚠️ **字符串替换生成 HTML 时，替换值里的 `$$` 会被静默改写成 `$`**（多数语言的 `replace` 把 `$` 当捕获组转义符）。这会制造「代码看着对、产物是错的」的假绿。含 `$` 的内容用函数式替换或先转义。
- ⚠️ **几何自测**：断点、侧栏宽度、溢出这类问题肉眼扫容易漏，用脚本量。历史上栽过「断点算错」和「侧栏空白」两次。
- ⚠️ 自测别在 CSS 过渡动画中途量尺寸，会量到中间态得出错误结论。
