# S3 · 产品定义（名字叫「收敛」，做的是定义）

> ⚠️ **正名（用户 2026-08-31）**：这一阶段名叫「定义收敛」，
> 但它做的**不是把 S1 的粗定义打磨一遍**，而是——
>
> ## 〇之前 · 收口时必跑两件事（2026-08-31 补）

1. **互换测试**：把产品名换成同品类竞品，愿景与差异化还成立吗？成立＝这两节没有信息。
2. **RAT Top-5**：假设表按**「错了整个产品就不成立」**排序，每条写明**用什么最小动作能证伪**。
3. ⭐⭐ **填证据等级表**（`definition-final.md` 十一之二，判据见 `references/evidence-levels.md`）：
   每条关键结论一行，写**等级 · 证据在哪 · 与本决策的相关性 · 不够怎么补 · 停止线**。
   ⛔ **S3 拍板最低 E2**（和真实目标用户谈过）；内部工具可降 E1 但要写明豁免理由。
   ⛔ **写 E0 不违规，写了 E0 却把停止线留空才违规**——那等于承认没证据然后照常往前走。
   ⚠️ **停止线不是提醒，是拦截**：它会被抄进 `state.md`，成为对应阶段的入场条件（铁律 48）。
   ⛔ 写不出证伪动作的假设等于没登记——它只会在上线后自己爆。

判据与五类风险见 **`references/substance-over-theater.md`**。

## **从 S1 的用户需求 + S2 的调研与分析中，给出产品的定义。**
>
> 它是一个**综合**阶段，不是一个润色阶段。
> 此前它只有 52 行，混在 `s3-s4-product.md` 里当作 S4 的前戏——
> 而它是**全流程最贵的一个决定**。

---

## 〇、为什么它最贵

**WHAT 错了，要到六七个阶段之后才知道。**
设计做得再好、交互打磨得再细、代码写得再干净——如果定义错了，全是沉没成本。
这也是本流水线唯一把「人拍板」放在这么前面的原因。

### ⭐⭐ 「不做这个」是合法且高价值的结论
> **一个把每个想法都验证通过的产品负责人是没用的。**
> 最有价值的产出有时候就是**「别做这个」+ 理由**。

如果 S2 的证据不支持做，S3 的正确产出是 **`no-build.md`**（写清为什么不做、什么条件下会重新考虑），
**而不是硬凑一份定义**。⛔ 流水线在这里停下是成功，不是失败。

### ⚠️ 拍板的诚实边界
没有被人拍板的定义**不一定更差**，但——
**声称拿到了签字而其实没有，是后面每个阶段都赖以为基的谎言。**
拍没拍板必须如实写在 `definition-final.md` 首行。

## 一、输入契约（两个来源，缺一不可）

| 来源 | 具体是什么 | 缺了会怎样 |
|---|---|---|
| **S1 用户需求** | 用户给的方向、粗颗粒功能、硬约束、不可协商项 | 定义会漂成「我觉得该做什么」 |
| **S2 调研与分析** | `insights.md` 的**机会**与**核心范畴** · 三份定向报告 · `competitor-landscape.md` · `matrix.md` · `key-flows.md` · `downstream-coverage.md` · ⭐**「竞品有而我们没有的」** | 定义会退回拍脑袋，S2 白做 |

四个结构物各有独立职责：全景决定“比谁”，矩阵决定“比什么”，关键流程决定“同一任务差在哪”，
双向覆盖表决定“哪些 PRD/Figma/HTML 问题已有证据、哪些仍是明确未知”。S3 不得只读报告摘要后跳过结构物。

⛔ **只有其中一个就动笔 = 违规**：
- 只有 S1 → 那是把用户的话抄一遍，不是定义
- 只有 S2 → 那是竞品综述，不是**我们的**产品

⭐ **先读过去的教训**（`lessons.md` 与历史 `no-build.md`）：
别重新争论已经定过的事，也别把一个已经被否掉的想法重新提一遍。

## 二、⭐⭐ 定义必须覆盖下游（用户要求，这张表是本阶段的骨架）

**判据**：下游每一处需要「产品层决定」的地方，定义里都要有答案。
**答不上来的，下游只能自己发挥**——而那部分不在任何需求文档里。

| 定义项 | 下游谁在用 | 缺了会怎样 |
|---|---|---|
| **一句话定位** | PRD 〇摘要 · 六章价值 · 设计的情绪基调 | 摘要写不出「这是什么」 |
| **目标用户 + ⭐不服务谁** | PRD 6.0 · 设计的人群假设 · 交互的五人格 | 做一个谁都能用但谁都不爱用的东西 |
| **核心价值一句话** | PRD 摘要 · 价值论证 · 落地页的 memorable-thing | 设计找不到「要让人记住的唯一一件事」 |
| **产品边界（做/不做）** | PRD 3.2「明确不做」· 功能清单的范围 | 范围蔓延，评审时反复重开 |
| **功能集合 + 优先级依据** | PRD 3.2 功能清单 | 优先级没有依据 = 拍脑袋 |
| **⭐ 载体（web/移动/两端）** | PRD 载体列 · 设计出几套稿 · **双端三选一** | **复发率最高的返工** |
| **⭐ 是否 AI 驱动** | PRD `AI?` 列 · 附件 B.2 算法能力边界 | AI 功能没有能力边界表 |
| **⭐ 成本/规模量级** | PRD 成本列 · CEO 视角的投入产出 | 没有成本的优先级就是拍脑袋 |
| **成功长什么样（可量化）** | PRD 5.2 目标 · 7.1 埋点 · S10 复盘 | 上线后无法判断成没成 |
| **护栏指标（不能变坏的）** | PRD 摘要 · 7.2 回滚条件 | 优化一个指标搞坏另一个 |
| **关键路径（用户走一遍）** | PRD 6.3 · 交互稿的场景 · demo 的 happy path | demo 不知道该演什么 |
| **状态与数据边界** | 附件 C 安全合规 · 附件 E 状态机 | 安全与权限无依据（本流水线的老伤） |
| **产品调性 / 情绪基调** | 设计的 Trust/Excitement/Professional/Creative | 设计只能猜 |
| **硬约束与不可协商项** | 全流程 | 到 S7 才发现某条根本做不了 |
| **⭐ 单向门清单** | S4 优先拍板项 | 见第五节 |

⚠️ **这张表就是 `definition-final.md` 的目录**。模板：`templates/definition-final.md`。

## 三、从「需求 + 调研」到「定义」的四步（是生成，不只是评审）

原来的 S3 只有「4 视角轮换评审」——**评审只能改进已有的那一个方案，不能产生更好的**。

```
① 框定问题     从 S2 的核心范畴出发，写出「我们到底在解决什么」
      ▼
② 生成候选     ⭐ 至少 3 个**互不相同**的产品定义候选
      ▼
③ 多视角辩论   让候选互相攻击（4 视角，见第七节）
      ▼
④ 综合成一个   不是选一个，是取各自成立的部分合成
```

### ⭐ 三个候选的硬要求
- **必须互不相同**：不是同一个定义的三种措辞。
  判据（借自设计侧的反收敛）：**如果把三个候选的产品名互换，读者看不出差别，那就是一个候选。**
- 三者应当在**不同的轴**上分歧：服务谁不同 / 边界不同 / 赢的方式不同
- ⛔ **只给一个候选 = 从第一个想法倒推理由**。第一个想法通常是品类默认。

### 每个候选要写清
「它赌的是什么」·「它放弃了什么」·「什么证据会证明它错」

## 四、定义要经过的三道拷问

### 4.1 前提挑战
1. **这是不是正确的问题？** 换个框法会不会有明显更简单或更有影响力的解？
2. **这是不是最直接的路径**，还是在解决一个**代理问题**？
3. **什么都不做会怎样？** 真痛点还是假想痛点？

### 4.2 ⭐ 逆向思维（问了怎么赢，就要问怎么输）
> 「我们怎么赢」问完之后，必须问：**「什么会让我们失败？」**

把失败路径写下来，逐条对应到定义里的某个决定。**写不出失败路径，说明还没想清楚。**

### 4.3 理想态映射
```
  现状              这个定义带来的变化           12 个月后的理想态
  <描述>     --->   <差量>              --->    <目标>
```
⚠️ 如果这个定义**不指向**那个理想态，它要么是错的，要么理想态是错的。二者必居其一。

## 五、⭐⭐ 单向门 vs 双向门（决定哪些必须现在拍板）

按 **可逆性 × 量级** 给每个决定分类：

| 类型 | 含义 | 处理 |
|---|---|---|
| **单向门** | 走过去就回不来（或代价极高） | **必须在 S3 拍板**，且要慢、要充分 |
| **双向门** | 错了可以改回来 | **快速决定**，边做边调，不要在这里耗 |

### 典型的单向门（定义阶段必须点名）
- **服务谁 / 不服务谁**（改了等于换产品）
- **载体**（两端 vs 单端 —— 改了设计与研发全重做）
- **数据模型与对外接口的形状**（用户已有数据之后就改不动）
- **埋点 schema**（改了历史数据断裂，而报表依赖它）
- **品类定位与命名**（对外说过就收不回）
- **是否依赖模型能力**（AI 与规则是两条不同的工程路径）

⭐ **绝大多数决定是双向门**——**在双向门上追求完美，是定义阶段最常见的浪费**。

### 收敛判据
> **70% 的信息就足以做决定。**
> 等到 90% 通常已经太晚，而且那多出来的 20% 常常来自「做了才知道」。

⚠️ 但这条**只适用于双向门**。单向门要等到证据足够，或者把它**转化成双向门**
（例：先只做一端 + 预留结构，而不是承诺两端）。

| 提案 | 类型 | 对象 | **依据（S2 具体发现，带来源）** | 影响 | 单/双向门 | 建议 |
|---|---|---|---|---|---|---|
| P-01 | 增 | 批量重命名 | 8 家中 7 家有，缺失会被当基线缺陷 `[查证·链接·日期]` | +1 功能 | 双向 | 建议加 |

### ⚠️ 门禁验不了的（必须人读）
- [ ] 三个候选**真的在不同的轴上分歧**，不是同一个定义的三种措辞
- [ ] 每条提案的证据**真的支持那个结论**（门禁只能看有没有链接）
- [ ] 单向门**真的都被识别出来了**（漏掉一个的代价在半年后才出现）
- [ ] **用户已拍板**（未拍板不得进 S4）

## 九、诚实边界

- 本阶段的产出是**决定**，不是**方案**。「怎么做」在 S4，不在这里。
- ⭐ **「不做」是合法结论**，产出 `no-build.md` 并在此停下，是成功不是失败。
- 定义会错。**错了要回到这里改，而不是在 S4/S5 打补丁**——
  在下游打补丁的定义，会变成一份自相矛盾的 PRD。

### ⭐ 读者分区（交付物给谁看）

**正文给人看；附件给人 + AI 编程看；⛔ 过程日志两边都不进**

- 正文：给**人**（产品总监 / 评审 / 业务方）—— 结论先行、自足，图表证据直接放正文

### 格式硬要求（⭐ 这些是**跑门禁才发现**的，光读判据代码看不出来）
