# 设计规则集：先分类，再用对应的那套规则

> ⚠️ **本文件补的是一个「声称有、实际没有」的洞。**
> `review-perspectives.md` 视角 2 第一句就是「**① 先分类——营销页 / 应用 UI / 混合。
> 分类不同，规则集不同，用错规则集的评审等于没评**」，
> 然后……只给了一套通用的 12 问。**分类器在，分支不在。**
>
> 来源：gstack `plan-design-review` / `design-review` 的 Design Hard Rules（2026-08-31 精读），
> 其上游是 OpenAI「Designing Delightful Frontends」(2026-03) + gstack 自有方法论。

---

## 一、分类器（评之前先定这一步，不许跳）

| 类型 | 特征 | 用哪套规则 |
|---|---|---|
| **MARKETING / 落地页** | hero 驱动、品牌前置、以转化为目标 | 落地页规则 + 通用规则 |
| **APP UI** | 工作区驱动、数据密集、以完成任务为目标（仪表盘/后台/设置） | 应用 UI 规则 + 通用规则 |
| **HYBRID 混合** | 营销外壳里嵌功能区 | **分区适用**：hero/营销段用落地页规则，功能段用应用 UI 规则 |

⚠️ **最常见的误用**：拿落地页规则去评一个后台系统，于是要求它「有强视觉锚点、有 2–3 处动效、
首屏像海报」——而一个每天用八小时的工作台，正确答案恰恰是**安静、密集、少颜色**。
反过来，拿应用 UI 规则去评落地页，会评出一个正确但没人记得住的东西。

---

## 二、落地页规则（分类 = MARKETING 时适用）

- **首屏读成一幅完整构图，不是一个仪表盘**
- **品牌优先的层级**：品牌 > 标题 > 正文 > CTA
- 排版要有表达力和目的性——**不许用默认字体栈**（Inter / Roboto / Arial / system）
- **不用纯色平铺背景**，用渐变、图像或细微肌理
- Hero **满幅出血**，不要内缩/平铺/圆角变体
- **Hero 预算**：品牌 + 一个标题 + 一句支撑句 + 一组 CTA + 一张图。**就这些**
- **Hero 里不放卡片**。卡片只在「卡片本身就是那个交互」时才出现
- **一节一个任务**：一个目的、一个标题、一句短支撑句
- **动效至少 2–3 处且是有意的**（入场 / 滚动联动 / hover 揭示）
- 颜色：定义 CSS 变量，避开紫配白的默认长相，**默认只用一个强调色**
- 文案用产品语言，不是设计解说。**「删掉 30% 还更好，就继续删」**
- **默认的漂亮**：构图优先 · 品牌是最响的那行字 · 最多两款字体 · 默认无卡片 ·
  **首屏当海报，不当文档**

## 三、应用 UI 规则（分类 = APP UI 时适用）

- **安静的表面层级、强排版、少颜色**
- **密集但可读**，界面装饰降到最低
- 组织成四块：**主工作区 · 导航 · 次级上下文 · 一个强调色**
- **要避免的**：仪表盘卡片马赛克 · 粗边框 · 装饰性渐变 · 观赏性图标
- 文案用**功用语言**——定位、状态、动作。不是情绪、品牌、愿景
- 卡片只在「卡片本身就是那个交互」时才用
- **节标题要说明这块是什么、或用户能在这做什么**（「已选指标」「套餐状态」），
  不是「概览」「数据」这种什么都没说的词

⭐ **一句话记法**：落地页要**被记住**，应用 UI 要**被忘记**。
Jony Ive 的判据在这里最好用——**「注意不到」就是对的**。

## ⭐⭐⭐ 三之二、规则分四层（2026-08-31 补，外部评审揪出）

> ⚠️ **此前所有规则混在一起，都写成「无例外」的口气**——
> 于是「对比度 ≥4.5」和「不许用 system-ui」享受同一级强制力。
> **后果不是啰嗦，是把「与默认风格不同」误判成「设计质量不合格」**：
> 数据可视化、金融终端、开发工具、企业后台、无品牌内部系统，
> 合理地违反其中好几条。

| 层 | 是什么 | 强制力 | 违反时 |
|---|---|---|---|
| **A · 无障碍与安全硬门** | 对比度 · 焦点可见 · 键盘可达 · 触控目标 · reduced-motion · **错误不能只靠颜色** | ⛔ **无例外，任何产品类型都不许违反** | 门禁报红，必须修 |
| **B · 产品类型默认值** | 落地页正文 ≥16px · 导航 ≤5 项 · 一组字段 ≤4 个 · 下拉 ≤7 项 · 工作区首屏留白 ≥40% | ✅ **可以覆盖，但要在设计说明里写一句为什么** | 记一条「已知偏离 + 理由」，不报红 |
| **C · 品牌与设计方向** | 字体族 · 强调色数量 · 非灰色数量 · 纯黑纯白 · Hero 满幅出血 · Hero 不放卡片 · 标题/正文比例 · 落地页动效数量 | ⚠️ **项目自己定，定了就锁**（Taste Memory 的品味轴） | 与本项目自己的声明不符才算问题 |
| **D · 评审启发式** | 「删掉 30% 文案还更好就继续删」· 「卡片要挣得它的存在」· 一节一个任务 | 💡 **不是判据，是评审时的提问角度** | 不进门禁 |

⛔ **不许把 C/D 层的东西写成「绝不 / 无例外」**——
⭐ **一条规则如果换个产品类型就该被推翻，它就不是硬门。**
⚠️ 判断方法：**问「金融终端 / 开发者工具 / 内部后台 违反它是不是合理的？」**
答「是」→ 它最多是 B 层。

## 四、通用规则（按上表分层，**不是全部无例外**）

- **[A]** 为色彩系统定义 CSS 变量（否则无法做对比度与主题的机械校验）
- **[C]** 不用默认字体栈（Inter / Roboto / Arial / system-ui）
  ⚠️ **这是品牌方向不是硬门**：无品牌的内部工具用 system-ui 是**正确选择**（省一次字体加载、跟随系统）
- **[D]** 一节一个任务
- **[D]** 「删掉 30% 的文案还更好，就继续删」
- **[D]** **卡片要挣得它的存在**——没有装饰性卡片网格
- **[A]** ⛔ **绝不**用低对比正文（对比度 <4.5:1）——**这一半是硬门**
- **[B]** 落地页正文 **≥16px**。⚠️ **只对落地页**；
  应用 UI 的下限见 `visual-spec.md` 分载体表（Web ≥14px · 桌面客户端 ≥13px，信息密集可到 12px）。
  ⭐ **此前本行写成「正文 <16px 一律硬否决 · 无例外」，与 `visual-spec.md` 直接对冲**——
  执行时必然得出相反结论。**无障碍的硬门是对比度，不是字号。**
- ⛔ **绝不**把 placeholder 当唯一的 label（有内容时 label 必须还看得见）
- ⛔ **始终**保留链接的已访问/未访问区别
- ⛔ **绝不**让标题浮在两段之间（标题必须**在视觉上更靠近它所引导的那一节**，
  而不是更靠近上一节）

## 五、七条硬否决（命中任一即打回，不进入打分）

1. 通用 SaaS 卡片网格作第一印象
2. 漂亮图片但品牌很弱
3. 强标题但没有明确动作
4. 文字后面压着杂乱图像
5. 多个 section 重复同一句情绪陈述
6. 没有叙事目的的轮播
7. **App UI 由堆叠卡片构成，而不是由布局构成**

## 六、Litmus 七问（YES/NO，用于跨模型一致性打分）

1. 首屏里品牌/产品是不是毫无疑义？
2. 有没有一个强视觉锚点？
3. 只扫标题能不能读懂这一页？
4. 每一节是不是只有一个任务？
5. 这些卡片真的必要吗？
6. 动效有没有改善层级或氛围？
7. **把装饰性阴影全部去掉之后，它还高级吗？**

## 七、⭐⭐ 可辩护的品味（这条是整份文件的地基）

> **Taste is debuggable, not subjective.**
> 「这感觉不对」**必须能追溯到一条被打破的原则**。追不到，就不是发现，是情绪。

本 skill 长期只有两端：**可量化门禁**（对比度、间距倍数、令牌绕过率）与
**「好不好看归评审」**。中间是空的——于是评审意见要么是能量化的那几条，
要么是「感觉有点乱」这种没法执行的话。

**这条规则就是那座桥**：
- 评审提出任何主观判断时，**必须同时点名它违反了哪一条**（本文件的规则、
  `visual-spec.md` 的节号、或下面 12 条认知模式之一）
- 点不出来 → 这条发现降级为「待验证的直觉」，不进结构性发现
- ⚠️ 反过来也成立：**规则挡不住的难看，仍然是难看**。
  规则是让判断可复核，不是让判断变成打勾。

### 12 条认知模式 —— 优秀设计师是怎么「看」的

不是检查表，是**看东西的方式**。评审时让它们自动运行。

| # | 模式 | 一句话 |
|---|---|---|
| 1 | **看系统，不看单屏** | 永远不孤立评价一屏：它前面是什么、后面是什么、崩坏时什么样 |
| 2 | **共情即模拟** | 不是「我理解用户」，是真的跑心理模拟：信号差 / 只有一只手 / 老板在旁边 / 第一次用 vs 第一千次 |
| 3 | **层级即服务** | 每个决定都在回答「用户该先看到什么、再看什么」。这是在尊重他的时间，不是在美化像素 |
| 4 | **崇拜约束** | 限制逼出清晰。「如果只能显示 3 样，哪 3 样最重要？」 |
| 5 | **提问反射** | 第一反应是问题不是意见：「这给谁用？他在这之前试过什么？」 |
| 6 | **边界偏执** | 名字 47 个字怎么办？零结果？断网？色盲？RTL？ |
| 7 | **「我会注意到吗」测试** | **看不见即完美**。最高的评价是没注意到设计 |
| 8 | **可辩护的品味** | 见上。「这感觉不对」要能追溯到被打破的原则 |
| 9 | **减法默认** | 「尽可能少的设计」(Rams)。「减去显然的，加上有意义的」(Maeda) |
| 10 | **时间尺度设计** | 前 5 秒（本能）· 5 分钟（行为）· 5 年（反思）——**三个同时设计**（Norman） |
| 11 | **为信任而设计** | 每个决定都在积累或消耗信任。陌生人之间的托付，要求像素级的用意（Gebbia） |
| 12 | **给旅程画分镜** | 动像素之前先画完整的情绪弧线。**每个时刻是一个有情绪的镜头，不只是一个有布局的屏幕** |

参考谱系：Rams 十原则 · Norman 三层次 · Nielsen 十启发 · 格式塔 ·
Krug（三秒扫描 / trunk test / satisficing / 善意水库）· Redish（为扫描而写）·
Jarrett（无脑表单）· Ira Glass（品味是你不满意自己作品的原因）·
Jony Ive（**「人能感觉到用心，也能感觉到敷衍。不同和新颖相对容易，真正做得更好非常难。」**）· Gebbia。

## 八、0–10 评分法（比「有问题/没问题」有用得多）

对每个设计维度打 0–10 分。**不是 10 分，就说清楚 10 分长什么样，然后把它做到那儿。**

```
1. 评分：「信息架构：4/10」
2. 差距：「4 分是因为方案没有定义内容层级。10 分会给出每一屏的主/次/三级。」
3. 修：直接改方案，把缺的补上
4. 重评：「现在 8/10——还差移动端导航层级」
5. 真正的设计选择 → 交人拍板（不是我替他选）
6. 再修 → 直到 10 分，或用户说「够了，往下走」
```

⭐ **「让我看看 10 分长什么样」**：任一维度低于 7 分时，**直接产出那个 10 分的样子**
（Figma 稿 / 交互稿片段），而不是用文字描述。
**它让「现在」和「应该」之间的差距变得可见，而不是抽象。**

⚠️ 复跑时：8 分以上的维度快速过一遍，**8 分以下的走完整流程**。

## 九、结构化评审语法（把意见变成可讨论的东西）

不许只写「感觉不对」。用四种句式：

| 句式 | 用途 | 例 |
|---|---|---|
| **「我注意到…」** | 观察（不带判断） | 「我注意到主 CTA 和次级操作在抢注意力」 |
| **「我好奇…」** | 疑问 | 「我好奇用户能不能看懂这里的『处理』是什么意思」 |
| **「如果…会怎样」** | 建议 | 「如果把搜索放到更显眼的位置会怎样」 |
| **「我认为…因为…」** | 有理由的判断 | 「我认为节与节的间距太均匀了，**因为**它没有制造层级」 |

**每条都要挂回用户目标或产品目标**，并且**给出具体改法**，不只是指出问题。

## 十、诚实边界

- 本文件解决「**这一类产品该长什么样**」，解决不了「**这个具体决定对不对**」
- 三套规则集是**默认值不是律法**：项目值与本文件冲突时以项目为准，
  但**必须在 `decisions.md` 写明为什么偏离**（与 `visual-spec.md` 同一条纪律）
- 12 条认知模式**不可自动验**，它们进报告的形态是
  「已按 N 条模式走查，发现 N 处」，**不是「认知模式 ✅」**
