# 从证据到细致报告：S2 / S4 写作循环

本文件规定如何写出来，不重定义模板目录、证据等级或阶段批准。读者报告沿用现有模板；功能账本、事件账、洞察账本和 `state.md` 继续各管原来的职责，不另建重复正本。

## 1. 先分清正在写什么

| 任务 | 写作单元 | 单元成立的依据 | 不得冒充 |
|---|---|---|---|
| teardown / competitive-pack / full-research 的产品拆解 | 同一角色对同一对象的一项可独立验收行为，包含适用分支 | 真实操作、结果、截图及明确的未测边界 | 官网介绍不能冒充实测；父模块不能代替最细功能 |
| tech-approach | 一个会改变输出、失败处理或代价的策略决策点 | 锁定版本的源码、调用路径、输入、分支、数据结构与出处；运行结果另行取证 | 读过代码不能冒充跑过；三段摘录不能代替机制解释 |
| S4 PRD | 我方已作出选择的一项功能及其产品规则 | 研究证据 + S3 产品决定 + 我方约束，或明确标注的用户需求/待决策项 | 竞品事实不能自动成为我方要求；草案不能冒充批准 |

最细不是固定四级，也不是每个点击单独成项。创建、编辑、归档改变不同结果，应分开；创建中的必填校验是分支，不为增加功能数再造一个功能。并列动作只有在权限、对象、规则和结果确实一致时才能共用说明。

## 2. 先保证分母，再准备本批材料

按约定范围逐项检查导航、旅程、对象生命周期、设置、权限和条件入口。操作中出现的新菜单、弹窗或状态入口回填现有表面清单，保留发现来源和待访问状态；“已发现项全部归类”不等于产品没有遗漏。技术模式以入口/调用链/策略分支代替 UI 表面。

先完成粗盘点，再选代表功能域做样章；该域取证齐即可开始写作，不必等全部竞品完成。每一批只加载：任务范围与版本、该批完整路径/对象、相关事件或源码、真实配图、待证问题、已通过的同类样章及本次模板片段。不得只把前一轮摘要交给写作者。

发现队列中的每一项最终都应已访问、明确受阻或经范围决定排除。无法补测的限制写清对结论的影响；可以补测但尚未执行的项仍是待办，不得用“诚实缺口”宣布完成。范围变更更新版本与理由，不能通过缩小分母抬高覆盖率。

## 3. 写一个功能域样章，再分批展开

1. 选能体现普通操作、条件分支、失败恢复及相邻功能关系的代表域；不是专挑最简单的按钮。先读 `templates/examples/report-writing/research-domain.md` 的成稿及反例，学习说明方法，不复制教学应用的限制值。
2. 先写该域用户目标与端到端旅程，再逐个最细功能写自然语言：为何使用 → 入口/前置 → 输入和规则 → 操作前后态 → 精确反馈 → 异常与恢复 → 限制与下游意义。字段/状态表是查阅工具，不代替解释。
3. 边写边放本功能的真实截图，说明图中哪里支持哪条结论、它不能证明什么；成功图不证明失败分支，静态图不证明动效。技术模式放由真实机制提炼并渲染的图，源码定位不能换成 UI 截图。
4. 用现有 `research-quality-review.md` 记录样章版次、产品/UX/测试意见和修正，标明其只是该域评审，不是整份最终批准。由未参与撰写的读者仅根据成稿回答下面的消费题。若只有 Agent 评审，明确记录，不能冒充用户确认。
5. 样章通过才展开同类功能。后续出现明显不同的机制，例如批处理或权限审批，再校准该类写法；不要求每段都等用户批准。保留原有产品决策与任务范围的人工批准点。

消费题：从哪里进入？什么输入合法？满足什么条件才执行？结果、数据及界面怎样变化？失败、取消后保留什么、怎样恢复？结论能支持什么决定、尚不能支持什么？评审答案须指出正文和证据位置；需要猜的关键规则就是问题。

每批围绕一个能完整讲清的域/旅程展开，规模按复杂度调整，不设通用字数或固定功能数。每批循环“取证 → 正文与图 → 消费检查 → 补测/修正”。写到一半的功能保持草稿，不能以一段概述把整批标成完成。

在 `state.md` 的写作续跑表记录范围版本、当前批、样章位置/审核依据、本批单元 ID、成稿位置、未解决问题、下一步。功能事实仍从账本读取；跨会话从这些路径继续，不靠聊天摘要重写已有内容。

## 4. 从详解到比较，再到我方 PRD

比较按共同用户任务逐层进行：域/父节点的边界和模型 → 子能力的实现路径 → 最细行为的规则、状态、恢复与代价。公共节点映射到各产品原生路径，不强行统一原生树；缺失、仅观察和阻断分开，不能把 UNKNOWN 写成 ABSENT。每个结论引用已验收的单品正文与证据，不能只消费一句话矩阵。

PRD 起稿时，先给研究输入作 adopt/adapt/reject/defer/watch 处置，沿用洞察账本和下游映射。每个我方功能说明“研究事实是什么 → 我们选择什么 → 为什么 → 谁批准或在哪一阶段待决”。用户直接给定的要求可以成为独立来源，不强行为它寻找竞品背书。

按一个 F 功能垂直写完第七章与适用附件 A/C/D/E/F 的对应片段，而不是先写全书概述、最后才想字段和异常。正文保留读者理解行为所需规则，精确字段/文案/状态正本仍在各自附件，以明确编号回指，不复制多份可编辑值。示例见 `templates/examples/report-writing/prd-slice.md`。

交给独立消费者检查：产品经理能否说明选择与不做项；设计能否列出所需页面/状态；测试能否写出无需猜测预期值的用例；研发是否还被迫作未授权业务决定。发现产品范围改变回 S3；证据不足回 S2；不影响范围的细节在本功能卡修正。设计尚未产出时遵守 S4/S5 的 OPEN 规则，不能伪造 S7 稿或批准。

## 5. 组装不再摘要化

生成顺序是“事实与逐项详解 → 比较 → 决策 → 摘要”；阅读顺序仍是模板中的“摘要 → 全景 → 详解”。模板章节顺序不是让模型从第一章起一次性填完的指令。

保留每个已验收单元的完整行为、限制、否定词、数值、来源与邻接图片。组装只统一术语、编号、导航、重复职责和段落衔接，不能把多个详解压回模块介绍。共用规则只在权威位置维护，功能处解释适用方式并精确回指；拆成分册时全部分册同版交付与验收，不甩给读者内部底稿。

范围内单元、正文小节、配图和证据逐项对账；全文改写会让旧样章/批次评审失效，需要重审受影响内容。未测项目仍保留未知，不因排版收尾悄悄变成支持。原生平台分批发布时标“进行中”；先回读检测远端新增编辑，再更新同一正本，不能盲目覆盖。最终按 `delivery-quality-contract.md` 验完整同版正文、图片和原生页面。

## 6. 验“生成效果”，不只验检查脚本

维护本 Skill 时把两种测试分开：

- 固定证据写作：相同任务、证据包、模型/运行条件，分别运行变更前后版本，检查详解是否漏规则、过度声称、图文错配，及转化后的 PRD 是否把未知伪装成决定。保存产物，不只保存分数。
- 从零研究：另用获准真实产品走发现、遍历、写作与原生发布全链路；前一种测试不能证明这一种已经通过。技术模式改验真实源码与机制，不强加 GUI。

评审至少检查功能/决策点覆盖、事实正确性、规则可复述性、适用异常、图文邻接、下游可消费性和人工返工。结构数量只作底线，不作满分保证；关键规则错误不得被平均分掩盖。逐项记录 PASS/FAIL/UNABLE，公布阻断范围；单次样例或同一 Agent 的自评不足以声称模型稳定达标。需要验证 Claude 时单独记录 Claude 的实际运行，其他模型不能代报。
