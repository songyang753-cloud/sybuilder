# S3（S3A 业务梳理 + S3B 产品定义）　S4（S4A 产品结构 + S4B PRD v0.9）

这两阶段是**唯一**能决定「做什么」的地方。后面所有阶段都只是把这里的决定执行出去——这里错了，后面做得越好损失越大。

## 子阶段边界（2026-09-07 按 Codex 外审拆分；架构正本见 `delivery-pipeline.md` §二）

拆子阶段防两个常见错误：**把业务流程当功能列表**；**结构未清就填 PRD 模板**。

| 子阶段 | 回答什么 | 产出 | 不许做什么 |
|---|---|---|---|
| **S3A 业务梳理** | 角色/现状流程/价值成本/规则/指标如何成立 | `templates/business-map.md` | 不擅自定完整产品方案 |
| **S3B 产品定义** | 为谁做什么、不做什么、为什么现在；**Go/No-build** | `definition-final.md` 或 `no-build.md` | 不替代 PRD 与设计；⛔ 未作 Go 决策不得进 S4A |
| **S4A 产品结构** | 功能/IA/任务/对象/权限/状态如何组织 | `templates/product-structure.md` | ⛔ 不写技术架构（换技术栈答案就变的不属于这里） |
| **S4B PRD v0.9** | 哪些产品事实必须在设计前锁定 | PRD 一~五章 + **OPEN 项清单**（设计相关项合法 OPEN，每项带 owner/决策阶段/回灌位置） | ⛔ 结构缺失时 PRD 的文字完备度不算过（S4A 是先决条件） |

回路：`S3B ⇄ S4A ⇄ S4B` —— 结构暴露范围/权限/规则冲突时回产品定义重议，记 `DEC-xxx`。

# S3 · 产品定义（正文已独立成篇）

> ⚠️ **正名**：这一阶段名叫「定义收敛」，但它做的**不是打磨 S1 的粗定义**，而是
> **从 S1 的用户需求 + S2 的调研分析中，给出产品的定义**。它是一个**综合**阶段。
>
> **正文见 `references/s3-definition.md`**（206 行）——
> 覆盖下游 18 项 · 三候选生成 · 单向门/双向门 · 逆向思维 · 前提挑战 ·
> 增删提案表 · 5 视角轮换 · 出场门禁。
>
> 模板 `templates/definition-final.md` · 门禁 `scripts/definition-gate.py`

**为什么它插在研究之后**：用户给的 S1 定义是方向确定、功能粗颗粒。
先定义再研究会白跑一轮——研究结论多半推翻拍脑袋定的边界。
先研究再定义，S4 直接站在证据上开工。

⚠️ **它是全流程最贵的一个决定**：WHAT 错了，要到六七个阶段之后才知道。

# S4 · 产品方案迭代

写作执行入口：`evidence-first-writing.md`。先在既有洞察账本/下游映射中明确研究结论的处置与我方决定，再逐功能同步写正文、字段/状态/权限和验收；独立消费者应能据此设计与测试，不靠猜补。不要先输出整份粗稿再声称九章齐全等于完成。

## 交付契约

PRD 第一~五章（结构见 SKILL.md「PRD 结构」）。核心是三样：

1. **功能清单**：`F-xx`｜简介｜优先级｜载体｜负责人｜上线时间，**末尾必有「明确不做」**。
2. **功能详细说明**：每个 `F-xx` 写功能介绍 / 设计说明 / 交互说明 / 异常场景。
3. **架构图 / 流程图**：`fireworks-tech-graph`，降级 Mermaid。

## 硬约束

- ⚠️ **异常场景不是可选项**。只写 happy path 的功能说明，到 S8 必然返工——测试用例的一半在异常分支上，那里没写就是没需求，没需求就没人测。
- ⚠️ **字段级规格必须在这里落地**：凡涉及输入的功能，写清字段、类型、必填性、长度/取值范围、校验规则、错误文案。
  📌 这是本流程最贵的一条教训：历史上一份登录 PRD 通篇没有字段级规格，到测试阶段**根本生成不出用例**，整条链路卡死。写 PRD 时省下的 20 分钟，在下游要付十倍。
- ⚠️ **数字必须有出处**。「支持 1000 并发」「3 秒内返回」若非用户给定或查证所得，一律登记 `ASM-###`，不许直接写成结论。
- ⚠️ **模糊量词一律不合格**（借自 gstack `spec` skill 的量化门槛）：**「若干文件」不可接受——去数出确切数量；「提升性能」不可接受——给出指标与目标值**。写不出数字，说明这条还没想清楚，登记 `TBD-###` 带 owner，不要用形容词蒙混过去。
- ⚠️ **异常场景用固定六问穷举**，不要靠临场想（同样借自 `spec`）：输入为**空** / 为 **null** / **超大** / **重复提交** / 被**错误角色**调用 / 被**调用两次**。六问逐条问过，写不出的那条就是缺口。
- ⚠️ **安全与合规需求必须在这一步采集，写进 PRD 附件 C**（数据清单 / 角色权限矩阵 / 产品级安全规则 / 合规约束），并把其中的规则写成 `FR` 进附件 A。
  📌 **不写会导致整条链路"合规地"漏掉安全**：附件 A 没有安全 `FR` → S8 用例工程按铁律不许猜补 → 一条安全用例都没有，而每一步都守了规矩。
  ⚠️ 权限矩阵里**每个"不允许"都要有 `FR`**——「不能做什么」才是越权测试的依据，只写「能做什么」等于没定义安全边界。
  ⚠️ 通用工程基线（无硬编码密钥、参数化查询、XSS/CSRF、限流）**不进 PRD**，那是工程标准默认执行，见 `s9-quality-gates.md`。这里只写产品级规则。
- ⚠️ **功能拆分要垂直切片，不要水平分层**（借自社区综述，2026-08-16 查证）：拆成「贯穿数据层+服务层+界面的一条窄链路」（tracer bullet），不要拆成「先做完所有后端、再做所有前端」。
  📌 **这是 AI 协作的系统性偏误**——模型天然倾向水平分层，结果端到端反馈被推迟到最后一个阶段才出现，而那时改设计已经最贵。每个 `F-xx` 应该能独立走通一条完整链路。
- 编号只增不改（M1）；砍掉的功能标 `F-xx [已取消] 理由`。

## ⭐ 歧义扫描（S3 出场 / S4 入场前跑一遍，**先扫再问**）

**不要一上来就问问题。** 先按 10 类逐类打 **Clear / Partial / Missing**，得出覆盖图，
再从缺口里挑最值钱的问。完整分类表与问问题的纪律见 **`references/requirements-quality.md`** 第五节。

| 类别 | 一句话 |
|---|---|
| 功能范围与行为 | 核心目标、成功判据、**显式的不做**、角色区分 |
| 领域与数据模型 | 实体/属性/关系、唯一性、状态迁移、**数据量级假设** |
| 交互与 UX 流 | 关键旅程、错误/空/加载态、无障碍与本地化 |
| 非功能质量 | 性能 · 伸缩 · 可靠性 · **可观测性** · 安全隐私 · 合规 |
| 集成与外部依赖 | 外部服务与**失败模式**、导入导出格式、协议版本 |
| 边界与失败处理 | 负向场景、限流、**并发冲突** |
| 约束与取舍 | 技术约束、**显式记录被否决的替代方案** |
| 术语一致性 | 词表、被禁用的同义词 |
| 完成信号 | 验收可测性、可度量的完成定义 |
| 占位与残留 | TODO、**没有量化的形容词** |

**问问题的四条纪律**（这是本条最值钱的部分）：
1. **一轮最多 5 个问题**（全流程，不是每类 5 个）
2. 每个问题能用 **2–5 个互斥选项** 或 **≤5 个字** 回答
3. 只问**会改变架构 / 数据模型 / 任务拆分 / 测试设计 / UX 行为 / 合规**的问题
4. 排序按 **影响 × 不确定性**，不按顺手程度；**答案必须回写进文档**

⚠️ 某类的澄清「不会改变实现或验证策略」→ **不问，记 N/A**。
⚠️ 允许跳过澄清直接进 S4（探索性冲刺），但**必须写明「跳过澄清，下游返工风险上升」**。

## 入场门（S4 开跑前必过，不过就退回 S3）

回答两题，答案要能写进 PRD：

1. **现状与痛点**：谁、在什么场景、遇到什么问题？有数据或来源吗？
2. **做完之后什么变了**：可观测的变化是什么？（不是「体验更好」）

| 情况 | 怎么办 |
|---|---|
| **两题全空** | **不许动笔。** 退回 S3 做需求澄清——这时候写 PRD 只会把混乱固化成文档，产出必然是一份没有价值论证的功能清单 |
| 一题空 | 可以写，但必须在第一章摘要顶部标注 `⚠️ 价值论证不完整，评审需重点质疑`，并把空缺登记为 `ASM-xxx` |
| 都不空 | 正常开跑 |

📌 真实教训：一份线上 PRD 两题全空——通篇功能清单，评审时无从判断该不该做。

## 视角轮换（M3）

> 下表是 S4 的**必跑子集**；完整视角库（11 个，含典型发现）见 `references/review-perspectives.md`，终审必须跑满。

| 轮 | 视角 | 专问什么 |
|---|---|---|
| 1 | 产品总监 | 功能与定义是否一致？有没有偷偷长出定义外的东西 |
| 2 | 竞品对标 | 每个功能对比竞品是持平/领先/落后，落后的认不认 |
| 3 | 用户旅程完整性 | 串起来走一遍，空态/首次使用/失败/中断态齐不齐 |
| 4 | 研发可行性 | 哪个功能的成本会突然爆炸？有没有藏着的强依赖 |
| 5 | 商业化与运营成本 | 谁来维护内容/审核/客服？运营成本算过吗 |
| 6 | 合规与数据边界 | 收了什么数据、存哪、给谁看、能不能删 |

**留痕**（`reviews/rN-<视角>.md`）必须含：本轮视角 / 提了什么 / 改了什么 / 为什么 / **提了但没采纳的及理由**。最后一栏防的是同一条建议在后面几轮反复出现、被当成新发现。

## 写入协作文档（可选，取决于项目）

用 `dws` 写钉钉文档时：
- 单次内容过长会失败，**分块写**；`create` 与 `update` 的入参形态不同（一个走内容参数、一个走文件），用前先看 `--help`，不要凭记忆。
- ⚠️ **写完必须回读校验**，会静默失败——写入返回成功不等于内容进去了。
- ⚠️ **多列表格会被静默压列**：4 列表格可能落地成 2 列。判完整不能靠肉眼看渲染，要查底层结构里的列宽定义与单元格数。
- 链接一旦发给别人就**原地更新**，不要新建文档换链接。
