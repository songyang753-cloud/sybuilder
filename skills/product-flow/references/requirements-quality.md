# 需求质量：把 PRD 当代码，把检查清单当它的单元测试

> **核心比喻**：如果 PRD 是用中文写的代码，那么这份检查表就是它的**单元测试套件**。
> 你测的是「需求写得好不好、全不全、含不含糊、能不能验收」——
> **不是「实现对不对」**。
>
> 来源：`github/spec-kit`（★132318，2026-08-31 查证）的 `checklist` / `clarify` / `analyze` 三个命令。
> 采纳理由见文末。

---

## 〇、它填的是哪个空

product-flow 原本只有两层，中间是断的：

| 层 | 谁在管 | 回答什么 |
|---|---|---|
| 填没填 | `prd_completeness_check.py` | 每个 `F-xx` 在各附件里有没有对应内容 |
| **写得好不好** | **← 这一层原本是空的** | 需求本身完不完整、含不含糊、能不能测 |
| 内容对不对 | 11 视角评审 | 该不该做、做得对不对 |

中间这层的特征是：**可以逐条问、答案是「是/否」、而且大部分能机械查**。
它比「填没填」贵一点，比「对不对」便宜得多，而**下游返工大半出在这一层**。

## 一、五个质量维度（每条检查项必须归到其中一个）

| 维度 | 问什么 | 反例 → 正例 |
|---|---|---|
| **完整性** Completeness | 该有的需求都写了吗 | 「所有 API 失败模式的错误处理需求都定义了吗？[Gap]」 |
| **清晰性** Clarity | 有没有含糊到没法执行 | 「『显著展示』是否被量化成具体尺寸/位置？[Clarity, §4.2]」 |
| **一致性** Consistency | 几处需求互相打架吗 | 「hover 态需求在所有交互元素上一致吗？[Consistency]」 |
| **可测性** Measurability | 能被客观验证吗 | 「『视觉平衡』能被客观验证吗？[Measurability, §FR-2]」 |
| **覆盖度** Coverage | 场景与边界都想过了吗 | 「零结果场景的需求定义了吗？[Coverage, Edge Case]」 |

## 二、⛔ 措辞黑白名单（这条决定了检查表是不是跑偏）

**最常见的跑偏**：把「需求质量检查」写成了「功能测试」。两者长得像，作用完全不同。

### 🚫 绝对禁止（写成这样就变成了测试用例，不是需求检查）
- 任何以 **「验证 / 测试 / 确认 / 检查」+ 实现行为** 开头的条目
- 出现 **点击 / 跳转 / 渲染 / 加载 / 执行 / 显示正常 / 工作正常 / 符合预期**
- 引用具体框架、接口、算法
- ❌「验证落地页显示 3 张卡片」 ❌「测试桌面端 hover 生效」 ❌「确认点 logo 回首页」

### ✅ 必须的句式
- 「**是否定义/指定/写明了** <某类需求>（针对 <某场景>）？」
- 「**<含糊词> 是否被量化** 成具体判据？」
- 「<A 节> 与 <B 节> 的需求**一致吗**？」
- 「<某需求> 能被**客观测量/验证**吗？」
- 「<边界场景> 在需求里被**覆盖**了吗？」

⚠️ **判据**：一条检查项如果要读代码或跑程序才能回答，它就不属于这里——
它属于 `s8-testcases.md`。**这里只读文档。**

## 三、条目结构与可追溯性

每条写成：`- [ ] CHK### <问句> [维度, 出处]`

- **出处三选一**：引用章节 `[§4.2]` / `[Gap]` 表示查的是「缺不缺」/ `[Ambiguity]`、`[Conflict]`、`[Assumption]`
- **可追溯率 ≥80%**：至少 80% 的条目要带出处标记。没有出处的条目**没人能复核**
- **软上限 40 条**：超了按风险合并；「≥5 条低影响边界」合并成一条

## 四、⛔ 生成者不许勾自己的框

**`[x]` 的含义是「评审人判定这条需求质量达标」，不是「这件事做完了」。**

- 生成检查表的人/工具**只许生成条目，绝不许勾选**
- 只有在评审人明确要求时，才可协助评估某条
- 📌 这与本 skill 的老教训同源：*「模板末尾那份自检清单是人勾的……清单挡不住任何东西」*——
  而**自己勾自己的清单**比人勾还弱一档。

## 五、S3/S4 入场：歧义扫描（先扫，再决定问什么）

**不要一上来就问问题。** 先按下表逐类打分，得出覆盖图，再从缺口里挑最值钱的问。

| 类别 | 扫什么 |
|---|---|
| **功能范围与行为** | 核心目标与成功判据 · **显式的不做** · 角色/人群区分 |
| **领域与数据模型** | 实体、属性、关系 · 唯一性规则 · 生命周期与状态迁移 · 数据量级假设 |
| **交互与 UX 流** | 关键旅程 · 错误/空/加载态 · 无障碍与本地化 |
| **非功能质量** | 性能 · 伸缩 · 可靠性 · **可观测性** · 安全隐私 · 合规 |
| **集成与外部依赖** | 外部服务与失败模式 · 导入导出格式 · 协议与版本 |
| **边界与失败处理** | 负向场景 · 限流 · 冲突解决（并发编辑） |
| **约束与取舍** | 技术约束 · **显式记录被否决的替代方案** |
| **术语一致性** | 词表 · 被禁用的同义词 |
| **完成信号** | 验收标准可测性 · 可度量的完成定义 |
| **占位与残留** | TODO 标记 · **「健壮/直观/流畅」这类没有量化的形容词** |

每类打 **Clear / Partial / Missing**。

### 问问题的纪律
1. **一轮最多 5 个问题**（全流程，不是每类 5 个）
2. 每个问题必须能用 **2–5 个互斥选项** 或 **≤5 个字** 回答
3. 只问**会改变架构、数据模型、任务拆分、测试设计、UX 行为或合规**的问题
4. 排序用 **影响 × 不确定性**，不按顺手程度
5. **答案必须回写进文档**，不许只留在对话里
6. 若某类的澄清「不会改变实现或验证策略」→ **不问**，记 N/A

⚠️ 跳过澄清直接进 S4 是允许的（探索性冲刺），但**必须写明「跳过澄清，下游返工风险上升」**。

## 六、机器能查的部分：`scripts/requirements-quality-gate.py`

```bash
python3 scripts/requirements-quality-gate.py <PRD.md> [--json]
# 0=通过 1=有问题 2=跑不了
```

它查六类（都属于「读文档就能判」）：

| 规则 | 查什么 | 为什么可机械查 |
|---|---|---|
| `vague-adjective` | 快/稳定/健壮/直观/流畅/友好/高效/丰富/海量/极致 + fast/robust/scalable/intuitive 等**没有邻近数字或阈值** | 形容词是有限集 |
| `placeholder` | TODO / TKTK / ??? / `<占位>` / 待定 / 待补 / xxx | 字面量 |
| `untestable-verb` | 「应该 / 合理 / 正常情况下 / 尽量 / 视情况」出现在验收标准里 | 无判据词是有限集 |
| `term-drift` | 同一概念多种叫法（按术语表核） | 集合比对 |
| `duplicate-req` | 近重复 FR（去停用词后高相似） | 字符串相似度 |
| `traceability` | 检查表条目带出处的占比 <80% | 计数 |

⚠️ **诚实边界**：它查得出「有含糊词」，**查不出「这条需求对不对」**。
它也查不出**缺失**——「PRD 里压根没有这条需求」没有字面痕迹，
那要靠第五节的歧义扫描（人做）与 11 视角评审。

## 七、为什么采纳 spec-kit 这套（以及不采纳什么）

**采纳**：
- 「检查表 = 需求的单元测试」这个定位——它一句话解决了「检查表到底该写什么」的长期含糊
- 五维度 + 措辞黑白名单——**可以直接判一条检查项写得对不对**，这在别处没见过
- 歧义扫描分类法 + 影响×不确定性排队 + 最多 5 问——**把「多问几句」变成了有预算的动作**
- 生成者不许勾自己的框

**不采纳**：
- `.specify/extensions.yml` 的 hook 机制（那是 spec-kit 自己的运行时约定，与本流水线正交）
- 它的目录结构与命令名（`/speckit.*`）——本流水线用自己的阶段编号
- 「constitution」的完整治理体系过重；只取「**产品级不可违背原则，违反即 CRITICAL**」这一条，
  落成 `.product-flow/constitution.md`（可选，5–10 条即可）
