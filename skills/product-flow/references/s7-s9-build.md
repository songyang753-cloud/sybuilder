# S7 · Figma 高精度设计稿

## 定位

产出**研发可以照着写码**的稿子。判据不是"好看"，是「研发看着它能不能不问人就写出来」。

## 交付契约

1. 每个 demo 场景都有对应画面（含各状态，不只 happy path）。
2. 图层命名带 ID：`F-03/锁定态`——ID 链在设计稿里断掉，S8 方案与 S9 实现都无法对账。
3. 标注齐全：尺寸、间距、字号、色值、圆角、状态变化。
4. 复用既有设计系统的令牌/组件（项目有基线规格就按基线，不新造）。
5. ⭐ **资源清单**（2026-08-31 联合评审补——原来四条里一条都不讲资源）：

| 资源 | 交付形态 | 命名规则 |
|---|---|---|
| 图标 | **SVG**（优先）· 需位图时 @2x/@3x | `icon-<语义名>-<尺寸>` |
| 插图 / 空态图 | SVG 或 @2x/@3x PNG | `illus-<场景>` |
| 字体 | 字体文件 + **授权说明**（可商用与否） | — |
| 位图素材 | WebP/AVIF + 兜底 | `img-<用途>` |

⛔ **没有资源清单，研发只能自己找或自己切**——于是**实现出来的东西和稿子不是一个东西**，
而设计以为交付完成了。

6. ⭐ **版本冻结点**：稿子会改。必须写明**研发按哪一版做**（版本号 + 日期 + Figma 链接），
   冻结之后的改动走变更流程（附件 I），**不许直接改稿而不通知**。
7. ⭐ **暗色稿与断点稿**：
   - 产品支持深色 → **必须出暗色稿**（`visual-spec.md` 3.4「暗色不是反色」——不出稿研发就会反色）
   - 一端内有断点 → **每个断点至少出一张关键页**，不能只出最宽的那张

## 硬约束（MCP 直写踩过的坑，全是静默失败型）

- ⚠️ **换页必须用异步的设置当前页 API**，直接给 `currentPage` 赋值不生效。
- ⚠️ **写文本前必须先加载字体**，否则整段脚本失败。
- ⚠️ **中文字体要用服务端真实存在的那个**（实测 `Noto Sans SC` 可用；`PingFang SC` 在服务端不存在，回退后会渲染成豆腐块）。**字体名不要凭本机装了什么就写什么**——脚本跑在远端。
- ⚠️ **脚本是原子的**：中间报错则整段不执行，不会留下半成品，但也意味着一个小错会让你以为"什么都没发生"。
- ⚠️ **结果靠 `return` 回传**，打印日志不会回来。要验证做没做成，必须 return 出可核对的值（新建节点 id、数量等）。
- ⚠️ **MCP 复制不了也删不了文件**——需要新文件用建文件的工具，不要指望脚本搬运。
- ⚠️ **有基线模版时，链接里给的 node-id 就是模版本体**，不要自作主张换成别的锚点。

## 对账（M4 · S6→S7）

demo 每个场景是否都有 Figma 画面？缺的那些就是「研发拿到的稿子缺状态」——研发到时候会自己编，编出来的东西没有需求依据，也不会被测。

## 出场条件

- [ ] 每个 demo 场景有对应画面，含全部状态
- [ ] 图层命名带 `F-xx` ID
- [ ] 标注齐全，研发无需追问即可实现
- [ ] 中文实际渲染正常（不是豆腐块）——**看导出图确认，不是看脚本返回成功**
- [ ] **用户定稿**

# S9 · 研发 · 审计 · 验收 · 上线

## ⭐⭐ 范围：两种模式，开工前必须先定是哪一种

> 2026-08-31 修正（Codex 评审揪出）：原文写的是「**两块都做，不是二选一**」。
> ⚠️ **那是错的**——Handoff 与 Build 是**两种不同的授权和责任边界**，不是一件事的两半。
> 2026-09-13 进一步拆段：Handoff 的技术/算法/测试文档归独立 S8；只有 Build 才进入 S9。

| | **Handoff 模式（默认）** | **Build 模式** |
|---|---|---|
| 我交付什么 | S8 飞书技术/算法/测试方案 + 接口/用例/评测锚点；**到此停** | S8 全部 **＋ S9 仓库代码、执行证据、验收与上线记录** |
| 谁写实现代码 | **研发团队** | 我 |
| 需要什么授权 | 无（产出的是文档） | ⛔ **用户明确说「你直接在仓库里做」** |
| 需要什么访问 | 无 | 仓库写权限 · CI · （若涉及上线）部署权限 |
| 出场判据 | S8 联合方案门禁、原生回读与三专业批准 | S8 已批准 **＋ S9 各段门禁全绿 + 终审流水线跑满** |

### ⛔ 默认是 Handoff
**没有用户的明确授权，一律 Handoff。**
S2–S7 全程是产品与设计主导的（铁律 35），完成 S8 方案也不会自动获得工程侧写入或上线授权——
**阶段推进不等于权限扩大；没有 Build 授权就停在 S8。**

### 进入 Build 之前必须先说清的三件事
1. **改哪个仓库、哪个分支**（⛔ 默认分支上不直接改）
2. **上线由谁按下按钮**——⚠️ 授权写代码 ≠ 授权上线，这是两次授权
3. **回滚谁来做**

⚠️ **强制「两块都做」还有一个成本**：Handoff 场景下我会写出一份注定没人看的
技术方案（因为团队有自己的），或者在 Build 场景下重复产出交接物料。
**先定模式，再干活。**

## S9 执行顺序

1. **S8 联合方案与接口契约已批准**——接口定下来前端、后端、算法与测试才能按同一事实并行。
2. **S9.1 开发与持续验证**：按 S8 的纵向切片执行；从附件 A 的 `FR/AC` 顺 ID 链消费测试用例，执行契约见 **`s8-testcases.md`**（也可单跑后导入 S8）。开发走 TDD：先写测试看它为正确原因失败，再实现。
3. **S9.2 工程测试与审计**：执行 S8 风险/覆盖计划；测试工程师须对同一候选构建从真实 GUI 入口完整实走主流程、关键分支、失败与恢复，再完成工程测试与 `four-node-review` 终审；不够写用例就回 S8/S4/S5 报缺口，**不要靠猜把用例补齐**。Web 用真实浏览器，macOS/移动端先获授权再操作真实应用；API/DOM 只可辅助诊断，不能代替 GUI。
4. **安全机械层**：`python3 scripts/sec-scan.py <代码目录>` —— SEC-1/3/8/9 四条。
   ⚠️ 其余 6 条只能人工与专项审查，合法结论是「已人工审查，发现 N 处」，不是 ✅。
5. **工程标准与门禁**：`engineering-standards`（假绿门禁识别、可复现构建、棘轮式收紧）。
   ⚠️ **放行判据见 `s9-quality-gates.md`**——安全清单 SEC-1~10、编码规范、测试标准（TDD＋≥80%＋单元/集成/E2E 三层）、Review 严重度分级。**功能跑通不等于可以放行。**
6. **终审**：`four-node-review` 六道检查节点（entry/gates/security/review/qa/bench），按风险定档（S/A/B/C）。
7. **S9.3 产品经理 GUI 走查与四方验收**：只有 S9.2 对**同一构建**得出 `PASS` 才能开始。产品经理依据冻结 PRD 与产品经验另开会话，亲自从 GUI 真实入口跑同一批主流程、分支和失败恢复，并做开放探索；分别核 PRD↔应用、HTML↔应用、Figma↔应用。测试报告、Node qa、自动化录像和截图摘要均不能顶替本次走查。
8. **S9.4 灰度与正式上线**：S9.3 只有 `APPROVED` 才可进入；上线和回滚仍由有授权的人拍板。

## 硬约束

- ⚠️ **门禁必须反向测试**：写完门禁要故意造一个应该被拦的用例，确认它真的拦得住。
  📌 真实教训：一条检查规则因退出码处理有误而永远返回通过（fail-open），CI 一路绿灯，直到第三轮外部审核才被揪出。**只见过门禁变绿、没见过它变红，等于没有门禁**。
- ⚠️ **门禁三态契约**（取自本机 `four-node-review`）：门禁必须分清「我测出了什么」与「我能不能测」。**三个方向都会错**——
  ①**假绿**：跳过了却打勾；②**假红**：依赖没装报成"正确率 0"、服务没起报成"防护失效"；③**误导性红**：机器上有无关负载就判性能不达标。
  所以状态码至少三态：`PASS` / `FAIL` / `CANNOT_RUN`，**第三态绝不能折叠进前两态**。
- ⚠️ **实现按垂直切片推进**：一次做通「数据→服务→界面」的一条窄链路，而不是先写完所有后端再写前端。水平分层会把端到端反馈推迟到最后，那时改设计最贵。
- ⚠️ **grep / 计数 / 退出码不是证据**。「搜了没搜到所以没问题」这类推断历史上一轮内连出三个错误结论。要判断内容，就真的读内容。
- ⚠️ **工具的发现可采信，工具的沉默不可采信**。低召回工具没报问题 ≠ 干净。
- ⚠️ **没真跑的记 SKIPPED，绝不并进通过率**。环境没就绪 ≠ 跑了合格。
- ⚠️ **表结构是契约**：已约定的字段/列不许擅自删减，缺数据就补全或先问。
- ⚠️ **不可逆操作与上线由用户拍板**，不代劳。
