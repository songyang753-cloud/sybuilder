### 正文九章（从「一」开始编号）

**章节顺序按推导链排**：为什么做 → 给谁做、他怎么走完一件事 → 这件事在组织里怎么流转 → 要建哪些模块和功能 → 每个功能的细节。
（⚠️ 被取代的旧原则是「**按打开频率排**：开发最常翻的详细设计在前、价值论证在后」——
它优化的是开发查阅效率，代价是**前向引用**：四章功能卡要引用五/六章才定义的 `OBJ-xx` 与优先级。
取代理由与代价见 `templates/prd-complete.md` 目录一节，⛔ 不要直接改回去。）

### 🔴 PRD 完备度门禁（S4 出场前必跑，不过不许进评审）

```bash
python3 scripts/prd_completeness_check.py <PRD.md>
# 0=达标  2=有缺口  3=输入无效
```

**为什么必须有它**：模板末尾那份「PRD 自检清单」是**人勾的**。真实案例——一份自检清单全打 ✅ 的 PRD，
机器一量：第四章达标 5/25、附件 A 覆盖 6/25、附件 D 3/25。**清单挡不住任何东西，门禁才挡得住。**

它查这 8 类：
1. 第四章每个 `F-xx` 的颗粒度（默认 ≥4 行且 ≥12 条要点，可用 `--min-rows/--min-bullets` 调）
2-5. 附件 A / D / E / F 是否覆盖了功能清单里的每个 `F-xx`
6. **AI 功能是否有附件 B.2 算法能力边界与 NFR-AI**（按功能名/简介自动识别 AI 功能，宁可多报）
7. 全局 NFR 是否覆盖**六类**：性能 / 并发 / 存储 / 兼容 / 无障碍 / 可观测性
8. **优先级列是否还挂着 `ASM-###` 未拍板**——挂着就不许宣告可评审

⚠️ **诚实边界（报覆盖率必须连这句一起报）**：它只回答「填没填」，**不回答「填得对不对」**。
内容是否正确、是否可实现，仍然要靠 11 视角评审。只贴「覆盖率 100%」等同谎报。

⚠️ **改这个脚本后必须重跑自证**（M8）：`--self-test` 的五个用例——正例绿、四类反例各自变红、
无效输入返 3 不返绿。**没见过它变红，就等于没有这道门。**
📌 真实教训：我第一版度量脚本把含「设计稿」的行全过滤掉，得出「25 个功能全是 0 行」的荒谬结论——
门禁自己就是软件，一样会坏。

        （功能清单齐、四章逻辑列齐、附件 A/D/E/F 齐）

S5/S7   以这份 PRD 为唯一输入，同步产出
        ① Figma 高精度设计稿    ② 交互稿 interaction-spec
           │
           ▼
        把设计稿链接回灌到 PRD 第四章「设计稿」列（每行都要有）

⚠️ **反过来做（先画稿再补 PRD）必然出现「稿子里有的功能 PRD 里没有」**——那部分不在任何需求文档里，永远不会被验收和测试覆盖，就是 M4 说的反向漏。
⚠️ **「绝大部分完成」的判据＝功能清单表不再增删行。** 还在增删说明范围没定，这时候画稿是白画。

### 附件 I 的变更 delta 协议(文档轨=锚定真源,变更走 delta+归档)

> 借鉴 openspec 的"当前真源 + 变更提案 delta + 归档合并"。**PRD 是文档轨的锚定真源**(见 architecture.md 二·B),
> ⛔ 不是可丢弃派生物——所以它的变更**不是就地覆盖大文档**(那正是"飞书大文档重同步"反复踩坑的根),
> 而是**一条条增量 delta**,冻结(G7.5)时才合并回正本并归档。

每次评审/需求变更,在附件 I 记一条 delta,只用三种操作:

| 操作 | 必含 | 判据(⛔ 缺即不合格) |
|---|---|---|
| **ADDED** `FR/NFR-###` | 新增条目全文 | 有 ID、有验收锚点 |
| **MODIFIED** `FR/NFR-###` | ⭐**整条更新后的完整内容**(不是"把 X 改成 Y") | ⛔ 不许只写差异——防"改一条却悄悄丢掉它的验收标准"(表结构是契约不许删列) |
| **REMOVED** `FR/NFR-###` | **`Reason`(为什么废)** + **`Migration`(依赖它的怎么办)** | ⛔ 无 Reason/Migration 的删除=不可追溯 |

**归档(G7.5 冻结时)**:delta 合并回 PRD 正本;把本轮所有 delta 连同"为什么/影响判断/做了哪些"整段存进 `.product-flow/prd-archive/<date>/`(或附件 I 的归档段)。
⭐ **S10 复盘直接读归档 = 完整决策轨迹**,不靠事后回忆(治"缺陷数必带测量时间戳""事后回忆决策不可信")。

### 三条硬约束

**正文可读，附件可执行**：领导和产品同事看正文，研发测试翻附件，AI 按附件生成下游产物。

⚠️ **附件 A 必须与正文双向绑定**：第四章每功能末尾写「验收标准：见附件A · FR-031~033」，附件 A 每条反标「所属 F-03」。否则附件会变成没人看、改了正文不同步的孤儿。

⚠️ **双端产品**：功能清单必须有载体列；每个功能必须回答「两端同一套交互 / 降级版 / 只在一端存在」三选一。不回答＝到设计阶段必然返工（评审视角 9 专查这条）。

|---|---|---|---|
| **功能清单** | 思维导图（中心放射）· 平铺分组卡片 | **能力分层地图**：按「谁给谁供能」分 3-5 层，层内横排功能卡，P0 加粗描边 | 放射图拉得又高又空；平铺分组则**所有模块看起来一样重**，看不出产品的架构逻辑。分层能直接答「砍哪层产品还立得住」 |
| **页面结构** | 方框 + 箭头的流程图 | **信息架构树（IA sitemap）**：导航段 → 页面 → 可下钻详情，左→右展开，正交连线 | 页面一多，跨层箭头必然交叉成一团；而且流程图**只画得出跳转，画不出每个页面里有什么**。IA 树能把「这页包含哪些子内容」一并说清 |
| 用户走一遍的路径 | IA 树 | Flowchart / Process Flow | 路径是时序，才需要箭头 |

⚠️ **页面结构图和体验路径图是两张图，别合并**：前者答「产品有哪些页面、怎么组织」，后者答「用户怎么走完一件事」。塞进一张图的结果就是箭头满天飞还两头都没说清。

#### ⚠️ 两条画图硬规矩（吃过亏的）

**1. 功能清单不要画成思维导图。**
默认的 mind map（中心节点 + 放射线 + 一行一个叶子）在功能多时会拉成又高又空的一条，
**大片留白、看不出分组权重、也没法下钻**。改用**分组容器式架构图**：
- 每个模块 M 是一个**带底色的容器框**，功能 F-xx 作为**小卡片排在容器内**（横向 2-3 列，不是纵向一条）
- 容器按业务重要性排布，核心模块放大、放在视觉中心
- **要能下钻**：功能多于 15 个时分两层——顶层只画模块 + 每个模块的功能数量徽标，
  再对核心模块单独出一张展开图，而不是把 25 个功能全塞进一张

**2. 页面结构图要有层级和分区，不要一条条方框加箭头。**
- 按**层级分区**（入口层 / 主界面层 / 详情层 / 面板层），同层的页面横向对齐，用**背景色带**区分层
- 箭头只画**主路径**，次要跳转用虚线或省略；箭头上的触发条件要短（≤6 字）
- 孤立页面（如独立窗口、小组件）单独放一个区，**不要硬连线到主流程上制造假关系**

**颗粒度自检**：一张图如果占满一屏还看不出「哪几块最重要」，就是颗粒度错了——
要么该分层下钻，要么该合并同类项。

**导出**：SVG → PNG 用 `rsvg-convert`（**别用 cairosvg，中文会变豆腐块**）→ 上传协作文档。

**飞书插图**（2026-08-29 实测，⚠️ 与旧记录不同）：
- markdown 里的 `![](路径)` 会在**正确位置**生成空图片块，`write` 不会填内容（`images_processed: 0`）
- 用 `upload-image --index <n>` 插到该位置，**`<n>` 是「文档根的直接子块」序号**，不是 `docx blocks` 列表下标
- 🚨🚨 **绝对不要用 `delete-blocks --start N` 去删「图片占位」**。我这么干过一次，**25 张表格被删光**：
  `upload-image --index N` 之后删 `N+1`，前提是那里真的是空占位；**占位不存在时 `N+1` 就是紧随其后的表格**。
  更阴的是——图片位置校验会全绿（图确实插对了），被删的是它后面的东西，**盯着图去验永远发现不了**。
  ✅ **正确做法：源 markdown 里根本不要写 `![](…)`**，不产生占位就不需要删除，全程零删除。
  图片位置由「功能小节标题之后」这个语义位算，插入按**升序**做，第 i 次插入目标 = 基准 + i。
- 🚨 **每次 `write` 之后必须验文本完整性，不能只验图**。飞书 `write` 会**静默失败**：返回 `success`、
  `blocks_added` 数字正常，内容却缺一大块（实测同一份输入，第一次丢了 24 张表、重写一次就对）。
  判据不能只看「有没有报错」，要抽查各章的**独有字符串**（例：F-01 表里的「资产模式选择弹窗」、
  F-25 表里的「离线授权证」、竞品表的「功能维度」）。
- 🚨 **偏移会在同一篇文档内漂移，不许全文套一个推算值**：markdown 顶层块序号与飞书根子块序号的差，
  取决于中间有多少「多行 `>` 引用」被飞书合并成一个块。**实测同一篇 PRD 里，图表段偏移 -2、功能段偏移 -8。**
  正确做法＝**先插一张探针 → 回读确认落点 → 按实测偏移批量**。我按推算值批量插过一次，5 张图整齐地偏后两节。
- `docx blocks` 封顶 500 块且无翻页，大文档后半段够不到 ID，只能靠探针法定位
- 填完再 `delete-block` 删掉那个空占位；`--parent` 指向空图片块会报 `block not support create children`
- 全文覆写会清掉已上传的图片，覆写后必须重传

**一致性校验**：功能全景图的叶子 = 功能清单表 F-xx = 第四章小节，三者一一对应；页面结构图 = 页面清单。

### ⭐ 特例：给「已上线产品」补写 PRD（反向提取型）

**这是常见场景**（产品先跑起来了、文档欠着），但**整条流水线要倒过来走**。
不要按 S1→S10 的进度条评判它——那样前三个阶段会永远挂红，而它们其实**已经存在于产品里，只是没被文档化**。

#### 反向模式的阶段映射

| 正向阶段 | 反向怎么做 | 判据 |
|---|---|---|
| **S1 产品定义** | **从产品反推**：跑起来用一遍，写出「它到底是什么、给谁、边界在哪」。**必须交用户确认**——你反推的定义和他心里的定义常常不是一回事 | 用户签字，否则后面全是空中楼阁 |
| **S2 行业研究** | 只做**差异化定位**这一段：现有产品 vs 竞品，哪里领先/持平/落后。不必做全量竞品档案 | 每条对比 `[查证·来源·日期]` |
| **S3 定义收敛** | 变成**「明确不做」的追认**：把产品**事实上没做**的东西列出来，逐条问「是有意不做，还是没来得及」。前者进「明确不做」+ 触发条件，后者进 backlog | 「明确不做」非空且每条有归类 |
| **S4 产品方案** | 见下表逐项反推 | 完备度门禁退出码 0 |
| S5 设计交互 | 交互规格从真实程序抓（下表）；**每个适用状态要逐个在程序里触发出来截图**，不能只写文字 | 每个 `F-xx` 状态按四类三段式写全 |
| S6 demo | **不适用——真实程序就是 demo，而且比 demo 更强**。跳过，在报告里注明「已上线，以真实程序替代」。⚠️ **但必须补机器契约，见下** | 显式注明，不是默默跳过 + **基线清单已锁** |
| S7 Figma | 照常，但设计稿是**还原**而非创作，规格全部量自真实程序 | 同正向 |
| **S9.2 工程测试终审** | **最容易被忽略的一步**，见下方「研发测试反向对账」 | 需求↔用例双向对账通过 |

#### ⭐⭐ S6 被跳过时，S7 的入场条件怎么算（2026-08-31 补，Codex 评审揪出）

**问题**（历史语境：旧串行模型时 S7 入场曾写「S6 已锁定」，现为 A 锁+并行协同——本节讲的替代契约仍然必需）：出场门禁 `reconcile-gate G3` 对账的是
**demo 场景 ↔ Figma 画面**，而 demo 的锚点是 `data-scene` / `data-fr` 这类专用 HTML 属性。
⚠️ **真实程序没有这些属性**，桌面端和原生 App 甚至**没有 DOM**。
于是「真实程序替代 demo」在人理解上成立，**在机器契约上是断的**——
G2/G3 会直接进 UNABLE，而 UNABLE 不是通过。

**替代契约：`.product-flow/baseline.md`（真实程序基线清单）**

| 项 | 要求 |
|---|---|
| **载体** | 一份 `baseline.md` + 一个截图目录，**不是 HTML** |
| **锁定的是什么** | **版本号 + 构建号 + 抓取日期**三者同时记；换版本必须重抓，不许沿用旧截图 |
| **每个场景一行** | ⛔ **`场景ID` 必须是 `fNN-<状态>`**（如 `f01-empty` / `f01-loading`）——不合这个命名，G3 无法逐场景对账，会直接报 UNABLE · 对应 `FR-xx`/`AC-xx` · **进入路径**（菜单路径 / URL / 深链，逐级写全）· 截图文件名 · 抓取时的版本号 |
| **三元键必须完全一致** | ⛔ `功能 + 端 + 状态` 三段都要对上：`f01-pc-empty` ↔ `F-01 \| pc \| empty`。
**端可省略**（单端产品写 `f01-empty` 即可，按 `*` 匹配任意端）；**状态段用英文 slug**，写「空态」对不上 |
| **元素身份怎么给** | 有 DOM → 按元素标识表补 `id`（改不了线上就在 `baseline.md` 里登记**选择器**）；<br>**无 DOM（原生/桌面）→ 用「截图 + 框选坐标 + 元素名」三元组**，元素名沿用标识表的命名规则 |
| **什么叫「锁定」** | 每个 FR/AC 都能指到一行；**指不到的显式写 `不演示·理由`**，与 G2 的口径一致 |

**门禁怎么切**：
- `reconcile-gate.py G2`：输入从 `demo.html` 换成 `baseline.md`，判据不变（每个 FR/AC 有场景或「不演示·理由」）
- `reconcile-gate.py G3`：对账 **`baseline.md` 场景 ↔ Figma 画面**，锚点用场景 ID 而不是 `data-scene`
- `browser-audit.mjs`：**无 DOM 时诚实报 N/A**，⛔ 不许因为跑不了就当通过
- `element-identity-gate.py`：`--html` 换成 `--baseline`，无 DOM 时只校验命名规则与需求回指

⛔ **「跑不了」必须留成 N/A 或 UNABLE，不许折叠成 PASS。**
⚠️ 这一节此前完全缺失——**特例路径在人这里说得通，在机器契约上是断的**，
而断的地方不会报错，只会安静地变成 UNABLE 然后被当成「没问题」。

#### S8 反向对账：给已有测试挂上需求编号

已上线产品通常**测试很多、需求编号没有**。这时「591 条测试全绿」**证明不了需求被覆盖**——
因为没有编号，就无法回答 M4 的两个问题：**哪个需求没测**（正向漏）、**测了哪些没人要的东西**（反向漏）。

补救顺序：
1. 先写附件 A 的 `FR-###`（可从现有测试反推——**已有测试就是已实现行为的规格**）
2. 给每条测试挂上它验证的 `FR`（测试名或注释里写 `FR-031`）
3. 跑 `scripts/coverage_check.py <PRD.md> <cases目录>` 做双向对账
4. **反向漏尤其要看**：有测试却没有对应需求 → 要么补需求，要么这个测试在测没人要的东西

⚠️ **不要反过来做**（先挂编号再写 FR）——那样 FR 会退化成测试的复述，失去「需求」的意义。

#### 反向提取各产物的来源



| 要写什么 | 从哪反推（不要凭空写） |
|---|---|
| 第四章交互规格 | **真实程序**：`scripts/capture-live-ui.js` 抓 `getComputedStyle` + `getBoundingClientRect` + 逐视图截图，再对照代码补参数 |
| 附件 D 字段规格 | 代码里的 IPC/接口定义与数据结构 |
| 附件 A 验收标准 | **现有测试用例反推**——已有测试就是已实现行为的规格 |
| 附件 B.2 算法能力边界 | ⚠️ **代码里没有评测数据，必须找算法侧要真数**。要不到就登记 `TBD-###`，**绝不编** |
| 附件 E 状态机 | 代码里的状态枚举 + 真实程序逐态截图 |

⚠️ **反向提取最容易漏的是「非功能」**：性能预算、并发、存储上限这些代码里没有显式声明，
必须单独找人确认或登记 TBD。
⚠️ 反向提取的 PRD 要在附件 H.4 注明**哪些章节是 AI 直出未经人复核**——它和反复确认过的内容看起来一模一样。

### 逐条重复块

- **标题格式**：`### M: <模块名> / F-NNN: <功能名称>`
- **每块下限**：表格数据行 ≥ 4 · 要点 ≥ 12
- 🚨 标题格式**逐字**如此：`### M: ` 开头、` / ` 分隔、`F-数字: ` 后接名称。⛔ 少一个空格或用 `##`/`####` 都会让这一条功能**整块对门禁不可见**（而文档看起来是写了的）。
- 每条功能的第四章块里，**表格数据行 ≥4**（表头与分隔行不算）且**逻辑列要点 ≥12 条**。数字可用 `--min-rows` / `--min-bullets` 调，但默认就是验收口径。 ⚠️ 行数统计会剔除分隔行与含 `| 页面 |` 的表头行；且**只算第一个下级标题之前**的内容。
- 🚨 **「要点」不是独立的 `- ` 列表行**，是数**表格单元格内**的条目：`<br>-` 每出现一次算一条，另外单元格以 `| - ` 开头也算一条。⇒ 要点要写在逻辑列里，⛔ 写在表外不算。（2026-09-17 靠脚手架跑门禁才发现：我生成了 12 个独立 `- ` 行，ch4_ok 仍是 0/3。）
- ⚠️ 设计稿列要真链接（`[名](url)` 形态）；`- / — / 待补 / TBD / <占位>` 都算空。

### ⭐ 读者分区（交付物给谁看）

**正文给人看；附件给人 + AI 编程看；⛔ 过程日志两边都不进**

- 正文：给**人**（产品总监 / 评审 / 业务方）—— 结论先行、自足，图表证据直接放正文
- 附件：给**人 + AI 编程**（研发按它写代码）—— 字段规格、状态机、ID 映射、内部锚点
- ⛔ **过程日志两边都不进**：门禁条数 / 收敛轨迹 / 第几轮 / 我犯了什么错 ⇒ 去 `.proposals/` 与 commit message

**门禁**：`audience-gate.py <交付文档.md>`　⚠️ 只拦机械可判的混入（内部路径/过程数字/自检编号/把读者支出去），拦不住「写得好不好读」

### 格式硬要求（⭐ 这些是**跑门禁才发现**的，光读判据代码看不出来）

- **功能块标题**：`### M: <模块> / F-NNN: <名称>` —— ⛔ 空格与分隔符逐字一致，否则整块不可见
- **占位识别**：`- / — / 待补 / TBD / <任意尖括号内容> / 空` 都被当作**没填**
- **设计稿链接**：必须是 `[文字](链接)` 形态才算数
- **要点计数**：`<br>-` 的出现次数 + 单元格以 `| - ` 开头的行数；⛔ 表外的 `- ` 列表一条都不算
- **退出码语义与 research-gate 不同**：⚠️ 本门禁：**0=OK / 2=有缺口 / 3=跑不了**；而 `research-gate.py` 是 **1=有发现 / 2=跑不了**。⛔ 跨门禁复用「2 就是跑不了」的判断会把**有缺口误读成环境问题**。每个门禁的退出码要各自查。
- **七个必填附件**：A 验收标准 · C 安全与合规（唯一不许省略）· D 字段规格 · E 状态机边界 · F 文案规格 · P 范围边界与路径规划 · Q 依赖与风险。⚠️ P/Q 判据原话：**外移不等于变可选，仍必填**。
- **功能清单表五列**：`ID` · `功能名称` · `AI?` · `载体` · `成本/规模`。⛔ 少一列就报表头缺口；`AI?` 不能靠关键词自动识别（实测漏报 100%，门禁已不再回退）。
- **全局 NFR 六类**：性能 · 并发 · 存储 · 兼容 · 无障碍 · 可观测性 —— 缺哪类报哪类。
