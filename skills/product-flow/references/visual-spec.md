# 视觉规格库（S5.1 用）

> 前面的 `design-quality-gates.md` 回答「怎么判断做错了」，本文件回答「**怎么做对**」。
> 分两部分：**可量化的**（第一至五节，能验）与**不可自动验的**（第六节，只能靠人看）。
> **两部分不许混为一谈**——把定性原则写成判据，会让报告出现「已验证：有质感」这种假绿。

---

## 一、排版

### 1.1 字号下限（按载体）
| 载体 | 正文下限 |
|---|---|
| Web | ≥14px（面向年长用户 ≥16px） |
| 移动端 | **≥16px**（低于会触发 iOS 自动缩放） |
| 桌面客户端 | ≥13px（信息密集型可到 12px，但注解不得低于 11px） |
| 演示稿 | ≥24px（理想 28–36） |
| 印刷 | ≥10pt |

### 1.2 层级
- **标题 : 正文 ≥2.5×**，理想 3×。**低于 2.5 判不合格**
- **全页字号最大/最小比必须 ≥2.0**——低于此即「字阶扁平」，层级形同虚设
- 字阶步进比：**品牌向 ≥1.25**（Major Third），**产品向 1.125–1.2**
- **字号总数 ≤7 个**

### 1.3 行高

⚠️ **行高必须按它所修饰的字号分档判定，不能一刀切。** 标题本来就该比正文紧——
拿一个「所有行高 ≥1.5」的规则去扫，会把 `h1{font-size:28px;line-height:1.25}` 误判为不合格。
📌 这条是 `visual-spec-gate` 拿正例 fixture 跑出来才发现的：门禁首版只收集所有 `line-height`
一刀切，**规格这里原本也没写清「≥1.5」是只对正文还是对全部文本**。

| 字号档 | 拉丁 | **中文/CJK** |
|---|---|---|
| ≥48px（大展示字） | 1.1–1.25 | 1.15–1.3 |
| 24–48px（标题） | 1.2–1.35 | 1.25–1.4 |
| 21–23px（小标题） | 1.3–1.6 | 1.35–1.65 |
| 16–20px（**正文**） | **≥1.5** | **≥1.6** |
| ≤15px（正文/注解） | 1.6–1.7 | **≥1.7** |

⭐ **中文/CJK 在拉丁基础上 +0.1**（汉字字面率高，同样行高下更挤）。
**中文正文行高 <1.4 即判拥挤，无论字号。**

⚠️ 判定时要**在同一条 CSS 规则块内把 `font-size` 与 `line-height` 配对**。
分散在两处、或行高继承自父级的，门禁判 **N/A（无法配对）**——**不许当作通过**。

⚠️ **光看字号分不出角色**：20px 既可能是正文也可能是小标题，卡在档位边界上必然误判。
判定顺序应是：**先从选择器判角色**（`h1`–`h6`，或类名含 `title`/`heading`/`display`）
→ 字号 ≥24px 时即便无语义也可安全判为标题
→ **仍判不出角色的，单列为「角色不明」并弃权，既不计通过也不计失败**。

⭐ **推论：语义命名是这条判据能工作的前提。**
把类名写成 `.t` / `.b`，门禁只能弃权——**命名不是风格问题，它决定了后面还能不能自动验。**
这与组件命名规范（每个节点斜杠层级语义命名，绝不留 `Frame 12`）是同一条要求的两面。

### 1.4 行长
**45–75 个字符**（理想 66），实现用 `max-width: 65ch`。
中文按 **25–40 字/行**（印刷 25–35，屏幕 30–40）。

### 1.5 字重与字体族
- 字重最多 **2–3 个**；**相邻档必须 ≥200 的差值**才有可感层级（Weber 定律）——
  400 与 500 并排，用户看不出区别
- 字体族 **≤2 个核心 + 1 个 mono**
- **中文禁用 italic**：浏览器与 Figma 的合成斜体是低级错误，强调用字重或颜色
- 中英混排：**英文字体声明在前，中文在后**

### 1.6 排印细节（低成本高回报）
- 标题加 `text-wrap: balance`
- 用弯引号，不用直引号
- 用 `…` 不用 `...`
- 数字列用 `font-variant-numeric: tabular-nums`
- 小写文本不加字距；展示字 letter-spacing 不低于 **-0.04em**

## 二、间距与留白

### 2.1 阶梯
只用 **4 · 8 · 12 · 16 · 24 · 32 · 48 · 64 · 96 · 128**。
**所有垂直间距必须是 8 的倍数。**

### 2.2 关系（比绝对值更重要）
| 关系 | 值 |
|---|---|
| 标题 → 正文 | 12–16 |
| 段 → 段 | 16–24 |
| 文 → 图 | 24–32 |
| 图 → 图注 | 12–16 |
| section → section | **≥48**（48–64） |

⭐ **组间间距必须是组内的 2–3 倍。** 这一条比任何绝对值都重要——
分组是靠间距**对比**读出来的，不是靠间距大小。

### 2.3 留白占比
一般 **≥40%**，极简风 **≥60%**。

### 2.4 两个方向都要查
- **太少**：≥10 个间距值中最高频值占比 >60% 且唯一值 ≤3 种 → **单调**
- **太多**：间距值出现 10 个以上互不成比例的数（3/5/7/9/10/14…）→ **无规律**

📌 真实教训：某产品的 CSS 文件头写着「间距只用 3 级 8/16/32」，
而它自己的代码用了 14 个不同值，**恰好包含它声称消除掉的 10/12/14/24**。
**注释里的设计哲学不等于代码里的事实**，要用脚本统计，不要读注释。

## 三、色彩

### 3.1 对比度（这是硬线，不是建议）
| 对象 | 最低 |
|---|---|
| 正文 | **4.5:1** |
| 大字（≥18px 或 ≥14px bold） | 3:1 |
| UI 组件 / 图标 / **承载信息的边框** | 3:1 |
| 长文阅读 | 建议 7:1 |

- **正文色对其所在背景的对比度 ≥ 4.5:1**（WCAG AA）。
  ⚠️ 本条 2026-08-31 修正：原文写「白底正文不得浅于 `#525252`（`#666` 只有 3.8:1）」——
  **那个数是错的**，`#666666` 对白实测 **5.74:1**，而 `#525252` 本身要求 **7.81:1**，
  比这里援引的 AA 标准严了近一倍，会把合规颜色判成不合格。
  ⭐ 无障碍硬门的判据是**对比度**，不是「颜色够不够深」——
  用明度代理近似一个本来就能精确计算的量，只会两头都错（`visual-spec-gate.py` 已按真实对比度重写）。
- **颜色不得是唯一的信息载体**：链接要有下划线，错误要有图标+文字

### 3.2 分配
- 主色 **≤3** + 中性色；调色板 **≤12 个非灰色**
- 比例：中性 **70–80%** / 结构 15–20% / **强调 5–10%**
- 品牌色只占界面的 **10–15%**

### 3.3 禁纯黑纯白
用 `#171717` / `#fafafa` 一类，不用 `#000000` / `#FFFFFF` 作页面级底色或正文色。

### 3.4 暗色模式不是反色
- **surface 用「高度」表达层级**，而不是单纯把亮度取反
- 文字用 off-white（约 `#E0E0E0`），**不用纯白**
- **主强调色去饱和 10–20%**
- `html` 上设 `color-scheme`
- ⚠️ **不要把浅色模式的阴影逻辑直接搬进深色模式**（见第六节）

### 3.5 色彩空间
用 **OKLCH**（同 L 即同感知亮度），并为不支持的目标提供 hex 兜底。

## 四、圆角与形状

- **内圆角 = 外圆角 − 间隙**（嵌套时不这么算，视觉上会「不同心」）
- **圆角值集合 ≤4 个**——全站一个大圆角是 AI 默认长相
- 圆角要有层级：缩略图 < 控件 < 卡片 < 浮层

## 五、组件像素规格（研发照着建，不许目测）

### 5.1 三档尺寸
| 组件 | sm | md | lg |
|---|---|---|---|
| Button 高 | 32 | 40 | 48 |
| Button padding（横/纵） | 12/6 | 16/8 | 24/12 |
| Button 字号 | 14 | 14 | 16 |
| Button 图标 | 16 | 18 | 20 |
| Input 高 | 32 | 40 | 48 |
| Input padding | 8/12 | 8/12 | 12/16 |
| Table 行高 | 40 | 48 | 56 |
| Badge padding/字号/高 | 4·8/11/20 | 4·10/12/24 | 6·12/14/28 |

Card：header `24 24 0` · content `24` · footer `0 24 24` · 内部 gap `16`
Dialog 最大宽五档：`384 / 512 / 640 / 768 / 100%-32px`
Table 单元格 padding `12 16`；文本左对齐、**数字右对齐**、状态居中、操作列右对齐

### 5.2 状态优先级（固定，不许改）
`disabled > loading > active > focus > hover > default`

### 5.3 关键状态的精确值
- **Focus ring**：宽 2px · 外偏移 2px · **对比度 ≥3:1**
- **Disabled**：`opacity .5` + `pointer-events:none` + `cursor:not-allowed`，
  且**对比度仍需 ≥3:1**（看得见但不能用，不是看不见）
- **Loading**：子元素 `opacity .7`，骨架形状必须匹配真实内容布局

### 5.4 过渡时长矩阵
| 属性 | 时长 | 缓动 |
|---|---|---|
| 颜色 | 150ms | ease-in-out |
| 背景 | 150ms | ease-in-out |
| transform | 200ms | **ease-out** |
| 透明度 | 150ms | ease |
| 阴影 | 200ms | ease-out |

（动效的完整判据见 `motion-spec.md`，此处只给组件级默认值。）

## 六、⚠️ 质感、景深与光影（**本节不可自动验**）

> 这一节没有一个数字。它全部靠人看。
> **不许在报告里写「已验证：有质感」**——本节只能写「已按此节走查，发现 N 处」。

### 6.1 核心立场
**把景深当作表达空间层级的结构语言，不是装饰性的抛光。**

### 6.2 统一光照模型
- 整个界面假设**一个统一的全局光照逻辑**
- 不许每个组件各有各的光照行为——那会让系统显得是「拼起来的」而不是「设计出来的」

### 6.3 表面层级
- **底层表面基本保持平的**，靠间距、色调、轻结构边界区分
- **升起的表面必须挣得它的分离**：菜单、浮层、吸顶区、模态内容
- ⭐ **如果很多相邻模块看起来一样「浮」，说明堆叠逻辑已经塌了**

### 6.4 两族阴影，不要一坨模糊
| 族 | 特征 | 用于 |
|---|---|---|
| **接地阴影** | 更紧、更安静 | 让浮起的表面感觉附着在它所在的平面上 |
| **升起阴影** | 更柔、更宽 | 菜单、浮层、模态等确有理由的覆盖层 |

- **用分层阴影逻辑，不要一坨糊掉的模糊**
- **绝不用阴影替代间距、边框或层级**
- **如果阴影成了画面的主要视觉纹理，它就太强了**

### 6.5 高光
用来定义边缘清晰度与材质厚度，不是用来装饰一切。
**高光必须比文字和内容更安静。读起来先像「镀铬/油亮」就是太强了。**

### 6.6 辉光是稀缺资源
- 只留给**罕见的、高价值的、强语义**的信号
- 普通按钮、卡片、表单控件、结构容器上**不许有常驻辉光**
- **不许用彩色辉光去补救弱层级或弱构图**
- 如果很多元素同时发光，它就不再传达优先级了

### 6.7 什么时候才配用更强的升起
**配**：脱离文档流的浮层 · 上下文菜单 · 模态 · Tooltip · 需要与滚动内容分离的吸顶区
**不配**：密集网格里的普通内容卡 · 常规表单字段 · 静态看板块 · **每一个主按钮**

### 6.8 浅色与深色的景深逻辑不同
- **浅色**：景深主要靠阴影在亮画布上读出来
- **深色**：景深主要靠**更亮的表面平面 + 更清晰的边缘 + 受控的高光**；
  阴影仍有帮助但很少能独自撑起层级
- **共同规则**：**先用表面层级建立高度，再考虑加阴影**

### 6.9 失败信号（看到即有问题）
太多元素下面糊着一层模糊阴影 · 深色表面之间明度差太小撑不起层级 ·
辉光被当成普通组件的常驻强调 · 高光读起来像镀铬而非边缘 ·
不同模块看起来被不同方向的光照着 · 用「高级感模糊」代替真正的构图

### 6.10 ⭐ 唯一一条能当判据的
> **把所有阴影与辉光全部去掉之后，这个界面还有没有清晰的分组与层级？**

没有 → 说明层级本来就是靠阴影糊出来的，**先修构图，不要调阴影**。

## 五之补 · ⭐ 令牌绕过率（查的是「有没有人不用令牌」）

**令牌干净 ≠ 使用干净。** 这是两件事，而只查前者的门禁看不见后者。

📌 真实教训：某项目的 `tokens.json` 间距是干净的 7 阶（全为 4 的倍数），
来源门禁全绿；而同一批产物的 CSS 里照样手写 `padding:5px 10px` / `3px 9px`，
**11 个唯一值里 7 个是离群值**。令牌被完整地定义了，然后被完整地绕过了。

**判据**：视觉属性（间距 / 圆角 / 字号 / 色值 / 背景）的声明中，
**引用令牌（`var(--…)`）的占比 ≥80%**。

**为什么是 80% 而不是 100%**：极少数确实该硬编码的场景存在（1px 描边、
`transform` 的具体位移量、与系统控件对齐的魔法值）。但**超过 20% 就说明令牌形同虚设**。

⚠️ 这条与 `token-provenance-gate` 是**互补而非重复**：
- `token-provenance-gate` 查「令牌的来源可不可追」——**令牌自身的质量**
- `token-bypass` 查「令牌有没有被真的用起来」——**令牌的落地率**
两道都绿，令牌体系才算成立。**只跑前者，会得到一份来源完美但没人用的令牌表。**

## 六之三 · 工艺层在哪

本文件管**做对没有**（对比度、间距倍数、圆角集合）。
**做好了没有**——构图与栅格 · 光学对齐 · 排印工艺 · 色彩科学 · 情绪基调 · Delight ·
旋钮怎么动一档 · 锚点配方取什么 · 构图层 slop —— 在 **`references/craft-layer.md`**。

⚠️ **两者不可互替**：一个页面可以每条数值判据全绿，同时平庸得没人记得住。

## 七、这份规格的诚实边界

- 第一至五节**能验**，且大部分已做成门禁（对比度、间距倍数、字体黑名单、圆角集合大小…）
- 第六节**验不了**，只能人看。它进报告的形态是「已按 6.x 逐条走查，发现 N 处」，
  **不是「质感 ✅」**
- 本文件给的是**通用基线**。具体项目的值以 `design/DESIGN.md` 为准——
  当项目值与本文件冲突时，**以项目值为准，但必须在 `decisions.md` 里写明为什么偏离**
