# 逐组件键盘契约（可执行）

> **来源**：W3C ARIA Authoring Practices Guide（`w3c/aria-practices`，29 个模式）·
> `microsoft/sonder-ui`（**做过可用性研究的**无障碍组件，7 个模式带实测发现）。
> 2026-09-03 引入。

## 为什么单独立一份

`interaction-criteria.md` 里的键盘条目是**通用**的（Enter 提交、焦点移到第一个错误、
Tab 顺序）。而真正出事的地方是**逐组件**的：
下拉框 `Esc` 该不该回滚选择、对话框关掉后焦点回哪里、标签页用箭头还是 Tab 切换 ——
这些**每个组件的答案都不同**，通用条目一条也覆盖不到。

⛔ 此前这一层完全没有：规格里写「支持键盘操作」，
**没有任何东西说得清「支持」具体指哪几个键**，于是研发各做各的、用例也无从写起。

⭐ 现在它是**可执行的**：`flow-walk-gate.mjs` 支持 `key` / `tab` 步骤，
下表每一行都能写成一条 flow，被真的按一遍。

## 一、契约表（只收「按错了会出事」的那些键）

### 对话框 / 模态（`dialog`）
| 键 | 必须发生什么 | 漏了会怎样 |
|---|---|---|
| 打开时 | 焦点移入对话框（通常是第一个可聚焦元素或标题） | 键盘用户还留在背景页，按 Tab 在看不见的地方乱走 |
| `Esc` | 关闭对话框 | 没有鼠标的人被困住 |
| `Tab` / `Shift+Tab` | **焦点在对话框内循环**（焦点陷阱） | Tab 会走到背景内容上，读屏用户完全迷失 |
| 关闭后 | 焦点**回到触发它的那个元素** | 焦点回到 `<body>`，用户丢失上下文位置 |

⛔ 破坏性确认框：**默认焦点不要放在破坏性按钮上**（回车误触）。

⭐⭐ **同意/授权类弹窗还要多一条：`Enter` 不许绑定到任何「允许」项。**
默认焦点放在「拒绝」是**焦点位置**，`Enter` 不绑允许项是**按键绑定** —— 这是两件事：
一个弹窗完全可能焦点在「拒绝」，却还挂着一个全局 `Enter` 处理器直接同意。
⛔ 用户在别处连按回车时，弹窗一弹出来就被"同意"掉了，而他根本没看见内容。

> 来源：本机 `agent-workbench` 的真实交互规格（授权弹窗一节写着
> 「默认焦点在 `拒绝` · `Esc` = 拒绝 · ⛔ **`Enter` 不绑定任何允许项**」）。
> 📌 这一条是**拿新写的 `keyboard-covered` 规则去真实规格上对照时捡到的** ——
> 那份规格的键盘**散文**比我的契约想得更细，缺的只是**可执行形式**。
> ⭐ 这也正好说明这条规则抓的是什么：**不是「你没想过键盘」，
> 而是「你想过、写下来了、但没有任何东西会去按一遍」。**

### 下拉选择 / 组合框（`combobox` / `listbox`）
| 键 | 必须发生什么 |
|---|---|
| `↓` / `↑`（收起时） | 展开，焦点落在**上次高亮项**或第一项 |
| `↓` / `↑`（展开时） | 上下移动高亮；**到头不循环**（APG 默认） |
| `Home` / `End` | 跳到第一 / 最后一项 |
| `Enter` | 选中当前项并收起 |
| `Esc` | 收起，**并把选择回滚到打开前的值** |
| `Tab` | 选中当前项、收起、焦点走到下一个元素 |
| 可打印字符 | 跳到以该串开头的第一项 |

📌 **sonder-ui 的实测发现（我推不出来的）**：他们做用户研究时发现
**相当多的人被「筛选」行为搞糊涂** —— 尤其是拼错时返回空结果、
以及选中之后其余选项全被滤掉的那一刻。
⇒ **选项不多时不要做筛选**，只把焦点移到最接近的匹配项即可。

### 标签页（`tabs`）
| 键 | 必须发生什么 |
|---|---|
| `←` / `→`（水平） | 在标签之间移动 |
| `Home` / `End` | 第一个 / 最后一个标签 |
| `Tab` | **跳出标签条，进入面板内容**（⛔ 不是切换标签） |

⛔ 最常见的错误：用 `Tab` 切标签。那样有 12 个标签就要按 12 次才能到内容区。
⚠️ 自动激活（移动即切换）vs 手动激活（移动后按 Enter）：
**面板内容加载慢时必须用手动激活**，否则箭头划过会触发一串请求。

### 展开/折叠（`disclosure` / `accordion`）
| 键 | 必须发生什么 |
|---|---|
| `Enter` / `Space` | 切换展开状态，且 `aria-expanded` 同步 |

⛔ 用 `<div>` 做触发器 → `Enter`/`Space` 都不响应。用 `<button>`。

### 菜单（`menu` / `menu-button`）
| 键 | 必须发生什么 |
|---|---|
| `Enter` / `Space` / `↓` | 打开菜单，焦点到第一项 |
| `↑` / `↓` | 在菜单项间移动（**循环**，与 listbox 相反） |
| `Esc` | 关闭并把焦点还给触发按钮 |

### 表单（通用，`interaction-criteria.md` 的键盘部分在这里落地）
| 键 | 必须发生什么 |
|---|---|
| `Enter`（在单行输入框里） | **提交表单** |
| `⌘/Ctrl + Enter`（在 `textarea` 里） | 提交 |
| 提交后校验不通过 | 焦点移到**第一个错误字段** |

## 二、怎么把它变成可执行的

每一行都能写成 `spec/flows.json` 里的一步。示例（Esc 回滚选择）：

```json
{ "id": "KB-combobox-esc", "name": "下拉框按 Esc 回滚到打开前的值",
  "widget": "combobox", "fr": ["FR-0xx"], "start": "#/page",
  "steps": [
    { "do": "click", "role": "combobox", "name": "所属项目" },
    { "do": "key", "key": "ArrowDown" },
    { "do": "key", "key": "Escape" },
    { "do": "expect", "textContains": "<打开前的值>" } ] }
```

现成模板见 `templates/spec/keyboard-flows.json`，按项目改 `name` / `start` / `fr` 即可。

## 三、门禁怎么守

`spec-sync-gate.py` 的 `keyboard-covered` 规则：
**`elements.json` 里出现了有键盘契约的 role（dialog / combobox / listbox / tabs /
disclosure / menu），`flows.json` 里就必须有对应 `widget` 的键盘 flow。**

⛔ 它**不检查**你写的那条 flow 对不对（那归 `flow-walk` 真跑一遍），
只检查**你有没有为这个组件写键盘用例**。
⭐ 这一条挡的是最常见的那种漏：组件做出来了、鼠标能用、**没人想过键盘**。

## 四、诚实边界

- 本表**只收「按错了会出事」的键**，不是 APG 的完整复述。
  完整规范以 W3C APG 为准，本表是**摘要 + 落地形式**。
- 合成 `KeyboardEvent` 不触发浏览器的默认交互链（如原生 `<select>` 的弹层）。
  ⇒ 门禁能验「你的处理器有没有响应」，验不了「原生控件的行为对不对」。
- 焦点陷阱（Tab 在对话框内循环）**合成 Tab 验不了**（合成事件不移动焦点）——
  `flow-walk` 的 `tab` 步骤是按文档序近似，**只能证伪不能证真**，真人仍要按一遍。
