# 输入适配器

PRD 形态不同，抽取方式不同，但**就绪度判定的标准完全一样**——文档格式好看不等于内容够用。

## A · 结构化附件（product-flow / 带附件 A 的 PRD）

**最省事的形态。** 附件 A 已经是 `FR-###` + Given/When/Then + `AC-#`，末尾还有可追溯矩阵。

抽取：
1. 附件 A 每条 `FR` → 一个需求项；每个 `AC` → 至少一条用例。
2. 正文第四章的字段规格表 → R2 材料。
3. 正文异常场景表 → R3 材料。
4. 可追溯矩阵 → 直接作为覆盖对账的基准清单。

⚠️ **仍要核双向 ID 绑定**：正文标了 `见附件A · FR-011~013`，附件 A 也要反标 `所属 F-01`。只有单向绑定说明附件可能已经和正文脱节——**按脱节的附件生成用例，测的是旧需求**。

## B · 六章制 PRD（正文含验收标准）

验收标准散在各功能段里而非集中附件。

抽取：
1. 逐功能扫「验收标准 / 验收条件」小节，**自建** `FR` 编号（记录来源章节行号，便于回溯）。
2. 自建编号要写进产出的 `requirements.md`，并注明「本编号为测试侧自建，PRD 无原生编号」。
3. ⚠️ **自建编号只在本次产出内有效**，不要回头去改 PRD——那是产品的文档。

## C · 裸文档（无验收标准，只有功能描述）

最常见，也最危险：读起来很完整，实际撑不起用例。

抽取：
1. 把每段功能描述拆成可判定的断言候选。
2. **凡拆不出可判定断言的，直接进缺口清单**，不要硬拆。
3. 典型撑不起来的表述：「支持批量操作」（批量上限多少？部分失败怎么办？）、「快速响应」（多快？）、「智能推荐」（凭什么推？错了怎么办？）。

⚠️ 这类文档的就绪度判定结论通常是「不可生成」或「部分可生成」。**这是正确结论，不是我没努力**。

## D · 用户故事 / Epic

`作为<角色>，我想<做什么>，以便<价值>` + 验收条件列表。

抽取：
1. 每个 Story → 一个需求项；每条验收条件 → 至少一条用例。
2. 角色信息直接喂给权限矩阵（见 `testcases-design.md`）。
3. ⚠️ 用户故事的验收条件常写成"能成功 XX"的 happy path 单行——**异常与边界基本都缺**，R3/R6 大概率不合格。

## 通用硬约束

- ⚠️ **抽取结果必须可回溯**：每个需求项标明出处（章节/页/行）。做不到回溯，后面没人能判断用例对不对。
- ⚠️ **抽取不是改写**。原文说得含糊，抽取结果就应该含糊并被判为不可测；**不要在抽取阶段"顺手把话说清楚"**——那一步就是编造的入口，且极难被发现，因为产物读起来非常专业。
- ⚠️ **多份文档冲突时不许自行裁决**：列出冲突项进缺口清单，指明两处出处，让人来定。
  📌 真实教训：同一产品的 PRD 正文与实际组件约束打架（文案 30 字 vs 控件上限 18 字），谁对谁错不是测试侧能定的。
