## Z1 · 性能的权威阈值（补上 G 组唯一的空缺）

G4 给的是**相对**判据（「设在实测中位的 10–30 倍」），它防的是数量级回归，**但答不了「多少算好」**。
绝对目标取自 Google 的网页体验指标——**数字直接来自 `GoogleChrome/web-vitals` 的源码常量，不是转述**。
⚠️ **两处措辞要精确**（2026-09-10 外部评审纠正）：**Core Web Vitals 只有 LCP / INP / CLS 三项**，
下表的 **FCP / TTFB 是补充诊断指标，不叫 CWV**；且**页面或站点的判级看的是真实用户 page views 的 p75**，
不是单次测量的值。

| 指标 | good（≤） | poor（>） | 量的是什么 |
|---|---|---|---|
| **LCP** 最大内容绘制 | **2500 ms** | 4000 ms | 主内容多久可见 |
| **INP** 交互到下次绘制 | **200 ms** | 500 ms | 点下去多久有反应（已取代 FID） |
| **CLS** 累积布局偏移 | **0.1** | 0.25 | 页面跳不跳 |
| **FCP** 首次内容绘制 | 1800 ms | 3000 ms | 第一个像素多久出来 |
| **TTFB** 首字节 | 800 ms | 1800 ms | 服务端 + 网络的下限 |

判级语义（README 原文）：**`≤[0]` = good，`>[0]` 且 `≤[1]` = needs improvement，`>[1]` = poor。**
判级对象是**真实用户的 p75**（一次本机 Lighthouse 跑分不构成判级）。

⛔ **本节只适用于网页真实用户体验。** API / CLI / 后台任务必须定义自己的端到端 SLO
（通常看 p95/p99、错误率与业务预算），**不能拿 LCP 的 2500 ms 去判一个接口**。

**怎么和 G4 配合**（两者不是替代关系）：

- **Z1 是「达标线」**——面向用户的体验目标，绝对值，跨项目可比。
- **G4 是「回归线」**——设在**本项目实测中位的 10–30 倍**，防的是某次改动让热路径慢一个数量级。
- ⚠️ **只有 Z1 没有 G4**：一个本来 400ms 的页面交互劣化到 2400ms，仍在 LCP 的「good」里，没人发现。
  （此处此前举的是「30ms 的接口」——那正是上面禁止的用法：接口不该用 CWV 判级。2026-09-10 改。）
- ⚠️ **只有 G4 没有 Z1**：基线本身就很烂时，「没有回归」是在为一个不达标的现状背书（同 G5「地板要设在退化值之上」）。

⚠️ **这些数字会变**：Google 改过若干次（FID 已被 INP 取代）。同 J1：事实性数据要有外部权威源。

> ✅ **2026-09-05 已逐条复核，五项全部一致、零偏差**。

## Z2 · API 安全必查表（OWASP API Security Top 10 · 2023）

> **本节许可：CC BY-SA 4.0。** 来源为 OWASP API Security Top 10（2023）及 ASVS，
> 作者归属各 OWASP 项目贡献者。SYBuilder 做了中文转述、条款映射与解释补充；
> 从本 Z2 标题至下一个 Z3 标题之前的完整章节（含本地补充）均保留同一许可。
> 原创部分的 Apache-2.0 不替代本节条款。来源、固定复核版本及完整许可见
> [第三方清单](../../../THIRD_PARTY.md)；这不是 OWASP 官方译本或背书。

> ✅ **2026-09-05 已逐条复核，10 条与官方 2023 版一一对应**。
> 核法：`gh api "repos/OWASP/API-Security/contents/editions/2023/en/0x11-t10.md" --jq .content | base64 -d`

K15 给的是「AI 高发漏洞」的经验清单；这一张是**正式条目**，两者互补——**K15 说哪些容易被 AI 写出来，Z2 说这一类的完整边界在哪**。

| 条目 | 一句话 | 本文对应 |
|---|---|---|
| **API1** 对象级授权失效 | 每个用 ID 取数据的地方都要判归属 | **I1** 按全端点+聚合面穷举 |
| **API2** 认证失效 | 认证实现不当，令牌可被冒用 | K15 |
| **API3** 对象**属性**级授权失效 | 合并了「过度暴露」与 **mass assignment** | K15 |
| **API4** 资源消耗无限制 | 带宽/CPU/内存/短信/账单类资源没有上界 | **G2** 无界即缺陷 |
| **API5** 功能级授权失效 | 管理功能与普通功能边界不清 | **I1** |
| **API6** 敏感业务流无限制 | 不是实现 bug——是**自动化滥用**没有代价（抢票、刷评论） | **G2** + 业务侧限流 |
| **API7** SSRF | 服务端被诱导去请求内网 | K15 |
| **API8** 安全配置错误 | 配置复杂，容易漏 | **I2** 配置单源 |
| **API9** 资产管理不当 | 废弃版本、调试端点还开着 | **E5** 声明侧对账 |
| **API10** 不安全地消费第三方 API | **对第三方返回的数据比对用户输入更信任** | **A2** 外部调用三态 |

⭐ **API6 和 API10 是这张表里最容易被漏掉的两条**，因为它们**都不是「代码写错了」**：
API6 是功能被按设计使用、只是次数太多；API10 是把「对方是服务不是用户」当成了可以放松校验的理由。

⚠️ 另有一根**正交的轴**：`OWASP/ASVS`（应用安全验证标准，官方稳定版 **5.0.0**）的 **L1/L2/L3** 定的是**安全验证该做到多深**（**L1**＝低保证 / 第一步 / 可自动化的组合视图；**L2**＝**多数应用的推荐基线**，尤其是处理需要保护的数据的应用；**L3**＝高价值、高保证、高安全关键。⚠️ 2026-09-10 外部评审纠正：此前这里写的是「普通应用 L1」——**比 OWASP 自己的推荐低了一档**。最终等级由威胁模型、数据敏感度和业务影响定），**不是条款的强制力等级**。别对所有项目上同一档。引用固定版本：<https://owasp.org/www-project-application-security-verification-standard/>

## Z3 · 强制力分级 —— 一份没有分级的规范，执行时所有条款都会被当成建议

这是**研发总监视角**该管的事，也是本文此前的结构缺口：**99 条并列摆着，读的人无从判断哪条不能让步。**

制度取自两处：`alibaba/p3c` 的**强制 / 推荐 / 参考**三档、
`isocpp/CppCoreGuidelines` 的**逐条 Enforcement**（每条规则都带一个 Enforcement 小节，写明**该怎么检查**——可能是静态分析、代码评审、运行期检查，官方也明说**有一部分不可机械执行**。⚠️ 2026-09-10 外部评审纠正：此前写成「411 条规则每条都写明怎么机械检查」，**两处都不准**——规则总数会漂，而 Enforcement ≠ 机械可判。本文借的是**「逐条声明检查方式」这个结构**，不是「都能机械检查」这个结论）。
（`OWASP/ASVS` 的 L1/L2/L3 **不在此列**——它定的是**安全验证深度**、不是条款强制力，见 Z2 末尾那条。
把两者并列会诱使人以为「L1 项目可以调低条款强制力」；实则**强制力由 p3c 三档定、验证深度由 ASVS 定，两根轴独立**。）

### 三档的定义

| 档 | 含义 | 违反时怎么处理 |
|---|---|---|
| **【必须】** | 违反**必然**产生一个不会报错的缺陷 | **阻断**。不接受「下次再说」，也不接受「这次赶时间」 |
| **【应当】** | 违反**通常**是缺陷，但存在正当例外 | **要写理由**，理由进代码注释或 PR 描述，可被复核 |
| **【参考】** | 因项目 / 语言 / 团队而异 | 项目自己定，定了就写下来 |

**未标注的一律按【应当】。** 下面只列【必须】档——**因为只有这一档需要所有人记住。**

#### 定档理由（可被复核，可被反对）——【必须】档为什么是这些条

分级是**管理授权**，不是技术偏好——所以定档理由要写出来让人能反对。**下表只列有争议或新升档的条款**（其余各条无异议，直接看上面的清单）：

| 条款 | 争议 | 处置 |
|---|---|---|
| **C5** 缺陷类改动先红后绿 | 「改个明显的一行也要写测试」太重 | **保留**，但给出口：**5 分钟内写得出复现测试的必须写**；写不出的（竞态 / 环境相关 / 需要真设备）**记 Open Item 带到期日**（H5），不许无声跳过 |
| **K1** 引用 API 前先确认存在 | 老手觉得多余 | **保留**。它对 AI 写码是最高频的真缺陷（「名字合理、位置合理、读起来像真的」，而语法/类型/测试无一会报错），**成本只是一次 grep** —— 多余时浪费 2 秒，漏掉时是一个恒 `undefined` 的静默降级 |
| **M4** 回滚必须真跑过 | 成本最高，小项目扛不住 | **降为「条件必须」**：**触及生产数据面**（迁移 / 回填 / 删列 / 改类型）时是红线，其余按【应当】。这是按影响面分档，不是放水 |
| **A8** 算出来了≠送达了 | 原本只在【应当】 | **升为【必须】**。实证：删两个字符（模板里一处插值）让**三轮才消灭的缺陷全部复活，而全套判据照绿** —— 这比 M4 更该是红线 |
| **B20** 一处改动不得让全部门禁同时失效 | 新升档：「这不是编码准则，是 CI 配置问题」 | **保留为红线**。它的后果是**全部**门禁一起失去拦截力，而每一道门自己都还在正确工作、报告里也照写失败 —— 没有任何一道门会因此变红。红线的定义就是「违反它之后，其余所有检查都不再作数」，这条正命中 |
| **D31** 新建判据必须见它红过一次 | 新升档：「跑一次不算验证」 | **保留为红线**，且成本极低。一道从不执行的门和一道不存在的门，在结果里完全一样；而「判据算得对」这件事再怎么自证也答不了「它会不会被跑」。与 **D3**（两向都要有反例）配套：D3 管判据对不对，D31 管它在不在线上 |
| **A19** 不合格不许洗成没能测 | 新升档：「UNABLE 又不是绿，有什么要紧」 | **保留为红线**。要紧在**处置**：现实中很多流水线把 UNABLE 当「告警不阻断」⇒ 一条真实的不合格被降级成告警，是一次迟到的假绿；且它同时把人引向查环境而不是查被测物。⚠️ **这是在描述现状不是认可它** —— 必检/参考两档的统一处置表在 **A19** 正文（单源，此处不复述）：**必检项的 `UNABLE` 一律阻断**。与 **A1** 成对：A1 防 UNABLE 混进 PASS/FAIL，A19 防 FAIL 被写成 UNABLE |
| **D34** 判据必须先证明它取到了被测对象 | 新升档：「这是测试技巧，不是红线」 | **保留为红线**，与已在档的 **D31** 是同一件事的两半：D31 问「这道判据跑了吗」，D34 问「它读到的是被测对象吗」。任一不成立，判据的所有结论都不指向被测对象 —— 而失败症状与「一切正常」完全一致。本文作者同日自犯两次（空文件列表让指纹「相等」、命令替换覆盖 `$?`），成本只是给「取到了多少」配一条下限断言 |

### 每条规则要标注「怎么检查」（借 C++ Core Guidelines 的 Enforcement）

三类，写下来比写不下来强：

| 类 | 含义 | 本文的例子 |
|---|---|---|
| **机械可判** | linter / 类型检查 / 脚本能确定性判定 | P0 全部（formatter / linter / 类型检查 / 依赖漏洞扫描） |
| **行为可判** | 要真跑起来才知道（本文推荐的形态） | A1 三态、D3 两向反例、K9 门禁能不能红；**G2 的「无界」**——2026-09-10 从「机械可判」挪来：「缺 LIMIT」grep 得出来，但**它不等于无界**（完整聚合 / 流式 cursor / 唯一键限定都合法无 LIMIT），要看会不会把不受信输入完整物化 |
| **只能人判** | 需要理解意图 | E1/E2 承诺对账、H1 诚实边界、C1 最小 diff |

⚠️ **别把「只能人判」的条款硬做成源码正则**——按 **B4**，那类判据两头都不承重（100+ 变异实测：**14 次假绿 + 5 次误红**）。
**写不出机械判据不是失败，把它诚实标成「只能人判」才是。**
