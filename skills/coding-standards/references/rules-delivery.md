## M · 交付与运行期

### M1 · 健康检查必须证明依赖真的可达 ⭐⭐

一个只返回 `200 OK` 的 `/health`，证明的是**这个进程还在**，不是**这个服务还能干活**。
数据库连不上、缓存挂了、下游超时——它照样 200。

⇒ 健康检查要**真的碰一下每个关键依赖**（一次轻量查询 / ping），并按 **A1 三态**报告：
`PASS`（全部可达）/ `FAIL`（某依赖不可达，**说清是哪个**）/ `UNABLE`（自己都没起来）。

> ⚠️ **和 A1 的示例（「目标不可达 ⇒ UNABLE」）不是矛盾，是命题不同**（2026-09-10 外部评审提出，
> 此处补清）：状态由**你在证什么**决定。
> - **readiness 探针跑成功了，并确认某个必需依赖不可用** ⇒ 这是**测出来的结论**：`FAIL`。
> - **观察者自己没能完成探测**（探针起不来、协议解析不了、证据不足）⇒ `UNABLE`。
> - **被测进程根本没起来**：它自己不可能返回任何状态 —— 由**外部编排器**报 availability `FAIL`；
>   只有当编排器也判断不了进程状态时才是 `UNABLE`。
> ⇒ 一句话：`FAIL` 说的是「我测到了，不合格」，`UNABLE` 说的是「我没测成」。A1 的示例是探针
> **自己**够不到目标（没测成），M1 这里是探针**测到了**依赖不可用。

> ⚠️ **但要分清三种探针——碰依赖的程度和失败后动作完全不同**（Kubernetes 官方；2026-09-09 codex 评审）：
> - **readiness（能否接流量）**：查完成请求**必需**的依赖，不可达就摘流量。上面「碰每个关键依赖」指的是它。
> - **liveness（要不要重启）**：**只查进程自己是否卡死到「重启能恢复」的状态，绝不碰外部依赖**——依赖抖动时若 liveness 跟着挂 ⇒ **无效重启 + 放大故障**（依赖没好，整群重启一圈更糟，级联）。
> - **startup（初始化完成没）**：避免慢启动被 liveness 误判杀掉。
>
> 三者**别合成一个** PASS/FAIL 接口。本条要求的「碰依赖」属 readiness；liveness 反而要**克制**。

⚠️ 这是 **A1 的运行期形态**——把「我还活着」和「我还能服务」折叠成一个 200，就是二态冒充三态。

⭐⭐ **它的适用面比「HTTP /health」宽得多：任何自称能报告可用性的东西都算**
—— CLI 的 `--doctor` / `--check` / `--status`、安装脚本末尾的「安装完成」、
IDE 插件的「已连接」、脚手架的 `preflight`。

⭐ **实证（第十次外部实战，2026-09-05，一个多引擎抓取工具的 `--doctor`）**：
它对某个浏览器驱动引擎的可用性判据是
```bash
crawl4ai) [ -x "$VENV/crwl" ];;      # 只看二进制在不在
```
而那个引擎真正干活靠的是 playwright chromium。
**受控实验**：造一个只会 `echo fake` 的假 `crwl` 放进临时 venv ⇒ 体检照报「**✅ 可用**」。
链条是完整的：安装脚本里 `playwright install … | tail -1 || true`
（**pipeline 退出码是 tail 的**）让装失败不留标志 ⇒ `--doctor` 说可用 ⇒ **真抓取时才炸**。

> **判据量的是「文件存在且可执行」，声称的却是「引擎可用」** ——
> 中间隔着「依赖装全 / 能启动 / 能抓到内容」三层（同 **B12**）。

⇒ **自检一句**：**把这个东西的依赖删掉一个，我的健康检查会变色吗？**
不变 ⇒ 它检查的不是可用性，是存在性。
⇒ 修法不必推翻重来：照它已有的 ⚠️ 档（本例里 `fc-tencent`/`fc-cloud` 早就有）补一格，
   并**双向验证**（依赖在 ⇒ 仍报可用**不误伤**；藏掉依赖 ⇒ 报 ⚠️）。

> ⭐⭐ **懒加载让「活着」和「能服务」的裂缝更深**（第 18 次外部实战，2026-09-06 bailian-tts-proxy）：
> 常驻代理启动时**不读**凭据（`loadKey()` 每次请求才调），凭据文件早已不存在 ⇒
> **进程正常起、`launchctl list` 报 last exit 0、每个请求 502**。调度器眼里它健康，调用方眼里它全坏。
> 这比「/health 只返 200」更隐蔽：这里连 health 端点都没撒谎——它根本没被要求碰凭据。
> ⇒ **启动时就 fail-fast 校验凭据可读**（M6），或让 health 真的取一次 key；
> 「懒加载省一次磁盘读」换来的是「坏了没有任何调度信号」。

### M2 · 写操作的重试必须幂等 ⭐⭐⭐

重试是默认存在的：网关会重试、客户端会重试、消息队列会重投、用户会**再点一次**。

⇒ 每一个**写**操作都要回答：**这个请求被执行两次，结果和一次一样吗？**

- 不一样 ⇒ 必须有幂等键（业务唯一键 / 请求 ID / 去重表），**并且服务端据此判重**——
  「客户端不会重发」不是理由，那不由你控制。
- **job / webhook handler / 定时任务同样算写操作。**

⚠️ 后果不对称：读操作重试多花一次查询，**写操作重试可能扣两次钱、发两条短信、建两个订单**。

> **适用条件(2026-09-09 codex 评审)**:本条针对**可重试或可能被重复投递**的写。不是所有写业务上都能「两次=一次字节相同」——审计、计量、事件追加天然每次都写一条;它们的幂等是用**请求 ID 去重**保证「同一请求只追加一次」,而不是强求结果相同。重复语义按业务选:**幂等键 / 去重表 / 幂等消费 / 单调序列号 / 明确拒绝重放**。⚠️ 去重检查与副作用提交必须**原子**(否则查重通过后崩溃、重试又执行一遍)。

> **重试的另一面:只在一层重试 + 配重试预算**(借自 SRE Book / Nygard《Release It!》)。M2 管重试的**正确性**(幂等);这条管重试的**量**:调用链每一层都自己重试 ⇒ 次数是**乘积**(A→B→C 各 3 次 = 27 次打到 C),而它恰好在**下游已经过载**时引爆(过载→超时→各层重试→放大过载)。规则:**每一类失败只能有一个明确的「重试 owner」**(通常最接近用户的那层,或最了解幂等性的那层),其余层对**这一类**失败快速失败上抛。⚠️ 2026-09-10 外部评审收窄:**不是「全局只准一层重试」**——不同层可以重试**互不重叠**的失败类别(客户端重连接建立、业务层重幂等事务冲突),真正不许的是**同一类失败在多层各自重试**造成乘积放大;跨层时必须共享端到端 deadline、总尝试预算与退避抖动,并**算得出最坏放大倍数**;并给重试配**预算**(如「重试量 < 请求量的 10%」),超了就停——把「局部各自正确、聚合成灾难」这类(同 B20)挡在放大之前。

### M3 · 验签必须在解析之前 ⭐⭐

webhook / 回调 / 跨服务消息：**先用未验证的载荷取出字段来做判断，再去验签，等于没验签。**

⇒ 顺序固定：**取原始字节（带大小上限）→ 验签 → 才允许解析和使用任何字段。**

⚠️ **一个必要的例外**（2026-09-10 外部评审提出）：JWS、多租户签名等协议**必须先看一眼 header**
才知道用哪个 `kid` / 算法 / 租户密钥 —— 一刀切「验签前不许解析」会让这些协议无法实现。
边界是：可以**最小解析不可信信封**，且**只能用于挑密钥**（`kid` 须对照**已知密钥集**校验），
**不得据此授权、路由到业务、或执行任何副作用**；随后仍然对**确切的原始字节**验签。
⛔ **算法不在此列——算法不许由 header 决定**（2026-09-15 收窄）：须来自服务端**固定 allowlist 并与密钥绑定**
（如 JWK 的 `alg` 字段，RFC 8725 §3.1）。否则 `alg=none` / RS256→HS256 混淆攻击下，
**「随后对原始字节验签」这一步本身就会成功**——攻击者自造的签名验的正是他给的字节，后置验签兜不住。
（真正要禁的不是「解析」，是**验签前信任业务语义**。）

同族三条一起做（都来自真实的重复投递）：**重放**（同一条被再投一次）、**重复投递**（至少一次语义的常态）、
**乱序**（后发的先到）。⇒ **三件事要三种机制，别指望一个「已处理」记录全包**：
重放靠**时间戳 + nonce**，重复投递靠 **M2 的幂等键**，
而**乱序靠去重是接不住的** —— 去重只认「这条见过没有」，拦不住**旧事件覆盖新状态**；
它需要**单调版本号 / 状态机前置条件 / 条件写入**（compare-and-set）。

⚠️ **测试模式与生产模式的凭据必须分离**——用测试密钥验生产签名会一直失败，反过来更糟。

### M4 · 回滚路径必须被真正走过 ⭐⭐⭐

**一条从没被执行过的回滚脚本，和一条不存在的回滚脚本，在平时完全一样。**

⇒ 每个**破坏性变更**（数据库迁移、数据回填、schema 变更、配置切换）交付前回答三句：

1. **前滚**在干净环境里跑得通吗？
2. **回滚**跑过吗——**不是「写了」，是「在有数据的环境里真跑过一次」**？
3. 破坏性的那一步（删列 / 改类型 / 清数据）**分阶段**了吗（先兼容双写、再切读、最后删）？

> **收窄(2026-09-09 codex 评审):恢复策略不限于回滚**。删敏感数据、不可逆格式转换等**没有安全回滚**——强求「回滚必须走过」会逼出并不可靠的**伪回滚**。要求改为:**必须有一条经过验证的恢复策略**——回滚 / 前滚修复 / 备份恢复 / 双写切换 / 分阶段兼容,任选其一;**不可逆步骤显式标注**,并在**执行前验证恢复点**(备份可用、快照存在)。回滚只是其中一种,不是唯一。

⚠️ 这是 **D20 的运行期形态**：防假绿的门可能从没开过火；回滚路径同理，而它开火的那天是最糟的一天。

> **泛化(权威背书,Google SRE / Nygard):不只回滚——所有「你从不走的路」都是未知非安全**。降级分支、熔断打开后的路径、故障切换到备用、限流触发后的行为——这些**平时不执行**的路径,和「不存在」在平时完全一样,而它们执行的那一刻正是系统已经出事的时刻。**未诱发过的降级/熔断/failover 路径 = 未验证 = 假定坏的**。做法:用故障注入(杀依赖/断网/塞满队列)**主动触发**每条降级路径至少一次,别等真事故当第一次运行。

### M5 · 日志要有用，且不泄密 ⭐⭐

两个方向同时是缺陷（同 B7）：

| 方向 | 后果 |
|---|---|
| **说得太少** | 出事时查不出来。错误日志只有 `error` 没有**上下文**（哪个用户、哪条记录、哪次请求）＝ 等于没记 |
| **说得太多** | 密钥、令牌、身份证、手机号、完整请求体进了日志 —— **日志通常比数据库更难做访问控制，也更容易被导出** |

⇒ 固定做法：**结构化日志 + 显式脱敏白名单**（列出允许打的字段，而不是列出禁止打的——
禁止清单是 **B5 的枚举**，新增一个敏感字段就漏一个）。

⚠️ 密钥纪律的正本在**基础层 P1**（`references/foundation.md`），此处不复述（I2 单源；此前这里写的是「按 **F1 组**」——F 组是活性与降级，那是 2026-09-05 把基础层从旧的 F 系编号改名成 `P` 系时的残留错引）。一句话版：**按长度决定打不打印是错的判据（短值恰恰是人设密码）**，需要关联时用带密钥的 HMAC，不用截断的裸哈希。

⭐⭐⭐ **「有用」这一半比「不泄密」更常出事：记了，不等于记下来了**
（第六次外部实战，2026-09-05，一个常驻 HTTP 中转服务）：
它在上游返回 4xx/5xx 时把错误响应体写进日志 —— 而那个响应体带 `content-encoding: gzip/br`，
代码直接 `Buffer.concat(chunks).toString()`。
**321 条错误记录，全部是压缩字节的乱码。** 日志里看起来「有在记录错误」，实际一个字读不出来。

⭐⭐⭐ **而更贵的是第二层：一处二进制污染，让整个日志对默认文本工具不可见**
```bash
$ printf 'a =>\n'          >  t.log
$ printf '\xff\xfe b =>\n' >> t.log     # 一行非法字节
$ grep  -c "=>" t.log            # 1   ← 含非法字节的那行被**静默跳过**，不报错不告警
$ grep -ac "=>" t.log            # 1   ← `-a` 不管用：这不是「二进制抑制」，是多字节解码
$ LC_ALL=C grep -c "=>" t.log    # 2   ← locale 才是那个开关
```
⚠️ **诚实边界**：当时那次的原始日志已轮转，**现场那两条命令的确切输出无法复跑**（此前这里写的
`-ac` 能数出全量，在本机 BSD grep 上复跑不出来 —— `-c` 也不可能「无输出」，它总会打一个数）。
上面这组是**在本机可复跑**的最小复现：结论不变（一处污染让 grep 数不到），**但修法不是 `-a`，是 `LC_ALL=C`**。

**排查时你 grep 不到，不是因为没有，是因为工具根本不看。**
一处污染让整条观测链失效，而每一行都还老老实实躺在文件里 ——
这与 **B20**（一处改动让全部门禁同时失效）是同一个形状，只是发生在观测面上。

> 后果叠起来才是完整的故事：7 天 **3054 次转发失败 + 308 次上游错误**，
> 错误详情全记成乱码，乱码又让正常记录也 grep 不到，而没有告警 ——
> **所以没有任何人看过这些错误**。

⇒ **两条做法**：
1. 写进日志前**先还原成人能读的形式**（解压 / 解码 / 反序列化），失败就记摘要
   （`<解压失败 encoding=br bytes=812>`），**绝不把原始字节倒进去**。
2. 最后一道兜底闸是**按目标格式转义**，不是无差别删除（2026-09-10 外部评审收窄）：
   用**结构化 logger**，在序列化边界对 `CR`/`LF`/分隔符/不可打印字节按该格式转义
   （JSON logger 本来就能安全编码换行）；实在编不了的数据，记**长度 + 摘要 + 解码错误**。
   ⛔ **别在业务值上全局删字符之后还声称「保留了原始证据」** —— 堆栈、协议报文、
   带换行的用户输入都会被改掉，而 OWASP 要求的是防日志注入（`CR`/`LF`/分隔符），不是清洗全部控制字符。
   （⚠️ 本 skill 自己的门禁扫脚本里的控制字符是另一回事：那是**检测**不可见字节，不是删它们。）
   这一条挡的不是内容错误，是**观测面被整体污染**。

⭐⭐ **它还有一个几乎没人算进来的面：排查动作本身会泄密**（实测 2026-09-05）。
审一个 launchd 任务时，我用 `cat` 读了它的 plist —— 那里面有一个明文的 app secret，
于是这份凭据被原样复制进了终端回滚、会话记录和上下文。
**程序的日志有人做脱敏，而排查过程没有任何东西替你把关**，
何况排查往往发生在最紧急、最不容易注意这件事的时刻。
⇒ 读任何**可能含凭据**的配置时，默认用「只看结构不看值」的方式：**结构化解析 + 字段级脱敏**
（`plutil -p | sed 's/=.*/= <redacted>/'`、`jq 'walk(...)' ` 把叶子值统一替换）。
⚠️ **别拿字段名过滤当护栏**：`grep -v -iE 'secret|token|password|key'` 不可靠——敏感值未必用这些名字
（`dsn`、`cred`、`auth`、`pat`、裸 URL 里的 `user:pass@` 都躲过它）；**也别拿文件权限（是不是 600）当「可以看原值」的依据**。默认脱敏，需要某个具体值时单独、显式地取。
⚠️ 同源的一条：验证「凭据已经清掉了」时，**判据要量的是「值还在不在」，不是「变量名还在不在」**。
我第一次验就 grep 了变量名，命中的是自己刚写下的那行说明文字 —— 量错了对象（同 **A17**）。

### M6 · 干净检出必须能起来，缺配置要 fail-fast

⇒ 两条硬要求：

1. **从一个干净的 clone 出发，照文档写的命令能把它跑起来**——跑不起来说明有一步只存在于某人的机器上（同 G3）。
   ⭐ **「干净检出能起来」还欠一半：起来的那份是不是你以为的那份**（2026-09-10 外部评审补的供应链维度，并入本条）：
   **锁文件 + frozen/immutable 安装**（`npm ci` / `pip install --require-hashes` / `cargo --locked`，
   不是每次自由解析）；**校验来源与完整性**（registry + 校验和）；发布时**留下 provenance**
   （构建器、源码 revision、依赖锁、制品摘要，能出 SBOM 更好）；
   **新增依赖与其 install script 要过一次「有必要吗、它拿到什么权限」**；
   ⛔ **供应链校验失败不许被普通的网络重试或 warning 放行** —— 那正是 A16 的形状。
2. **必需的环境变量要在启动时校验并 fail-fast**，带上「缺的是哪一个、去哪拿」。
   ⛔ 最坏的写法是 `process.env.X || '默认值'`：**缺配置被静默兜底成一个能跑但是错的状态**（同 A2）。

> ⭐⭐ **fail-fast 遇上无脑重启的 supervisor = 重启风暴，且危害会悄悄累积**（第 20 次外部实战，2026-09-06 openclaw gateway）：
> 服务因「配置 mode 未设」正确地拒绝启动（fail-fast 做对了），但 launchd `KeepAlive=true` + `ThrottleInterval=1`
> **每秒重启一次、每次同样失败** ⇒ 服务从没起来（端口无 LISTEN），而错误日志**悄悄涨到 809MB** 无人察觉。
>
> ⭐ **反向极端同样致命**（第 21 次外部实战，2026-09-09 VPS firecrawl）：restart policy=`no`，
> 宿主机一次重启让整栈静默退出 **3-4 周无人察觉**——上游探测只把它当「暂时不可用，跳过」。
> 风暴与死寂是 supervisor 设计空间的两端：瞬时失败该重启（`unless-stopped`），永久失败该停下告警，两头都要配。
> 同轮另一面：**换机迁移把整套工具链蒸发**（`~/.crawlstack` venv + `~/bin` 软链指向旧机用户名悬空 17 天），
> 而依赖它的管线因写死仓内绝对路径侥幸活着——**文档承诺的命令接口死了，没有任何东西会报**。
>
> ⭐⭐⭐ **复活一个停摆的服务，等于把它停摆期间被冻结的配置缺陷一起解冻**（第 25 次实战，2026-09-09，
> **我自己在同一场里制造又发现的**）：VPS 上自建 Firecrawl 整栈死了 3-4 周，我按 M6 把它拉起来 ——
> 它的 compose 里 `"3002:3002"` 绑的是 `0.0.0.0`，而该服务 `USE_DB_AUTHENTICATION=false`
> **完全无鉴权**（Bearer 是 `self-hosted` 占位符），即一个任人调用的 SSRF 代理。
> 服务死着的三周里这个配置是无害的（端口不可达）；**复活动作把可用性和暴露面一起带了回来**，
> 而我当时的注意力全在「它起来了没有」。
> ⚠️ 诚实边界：实测公网不可达（`nc` 超时，对照 443 通），唯一防线是云安全组 —— 是纵深防御缺口，
> 不是「正在被利用」。收窄绑定后同型普查：VPS 其余 22 个服务**全部**绑 `127.0.0.1`，它是唯一例外。
> ⇒ **恢复任何停摆服务后，立刻查它的暴露面（绑定 / 鉴权 / 权限），别只查它活没活**；
> 且不要把「另一层拦住了」当作可以不修 —— 那一层不归你管，改动时没人会通知你。
> ⚠️ **续（第 29 次实战 tick 12 复核抓到）：`docker update --restart` 改的是运行时状态，
> 会被下一次 `docker compose up -d` 用 compose 文件里的原值覆盖回去**。tick 8 我用 `docker update`
> 设了 `unless-stopped`，同一 tick 后面为改绑定面跑了 `up -d`，重启策略当场被打回 `no` —— 四个 tick 后复核才发现。
> **改配置要改真源（compose / 声明文件），不是运行时**；这正是「同一事实在两处、只改一处必漂移」的运维形态。
> 教训延伸：**一次修复里若同时用了「改运行时」和「重新声明」两种手段，后者会静默回滚前者**。
>
> ⭐ **「能装上」也在被生态静默改写**（第 22 次实战，2026-09-09 morph）：install 脚本**被拦掉**
> （只留一条 warn），Electron 的二进制于是没下载，`npm ci` 照样 rc=0；
> ⚠️ **归因未复核**（2026-09-10 外部评审提出，本机复核也没能确认）：此前这里写的是「**新版 npm 默认**拦截 postinstall」，
> 而本机 `npm 11.19.0` 实测 `npm config get ignore-scripts` = `false`。**被拦是事实，「默认」是推测**——
> 也可能来自项目 `.npmrc` / CI 配置 / 某个具体版本的行为。按 H2：**现象照记，机制标未查明**（复核法：`npm config get ignore-scripts` + `npm config ls -l | grep ignore`）。
> 而 electron 的 `install.js` 在半截产物上 **rc=0 且什么都不做**（`isInstalled()` 误判已装）——
> 两层工具各自「成功」，叠出一个装不上也不报错的状态。⇒ 依赖装完后要验的是**产物**
> （二进制能 `--version`）不是安装命令的退出码；npm 的 install-scripts 拦截警告不能当噪音划掉。
> `launchctl list` 只显示「上次退出码 1」，让人以为是偶发。**根因还叠了一层版本降级**：配置由新版写、当前是旧版，
> 旧版读不了新配置（K1 的运维形态：运行时版本 ≠ 配置版本）。
> ⇒ **区分「瞬时失败」（网络抖动，该重启）与「永久失败」（配置错 / 版本不兼容 / 端口占，重启一万次也没用）**：
> 后者的正确响应是**停下来告警**，不是无脑重启。supervisor 配置（`ThrottleInterval` 要够大、
> `KeepAlive` 对永久失败要能识别）和被托管服务的 fail-fast **必须一起设计**，否则一个做对了另一个照样酿成风暴。
> ⚠️ 与 M1 同源：`launchctl`/`systemctl` 的「上次退出码」是**历史值**，进程可能此刻正在跑（rerank 那次）或正每秒重启（这次）——
> 判活性只能端到端，不能读 supervisor 的状态字段。

> **「能构建」是会随时间与机器漂移的，而没有任何东西替它报警**（2026-09-06 实证）：
> DiskBar 在旧机上以 Swift 6.0 工具链定稿，换机后 CLT 只有 5.9——整个包在现用机器上
> **构建不了**，被发现是因为一次审计顺手想跑测试，距换机已 14 天。发布路径本身兜底
> （构建脚本第一步跑测试），但**两次构建之间这件事对所有人不可见**——与 D33
> 「长期跑不起来的检查 = 不存在的检查」同族，周期性重验「干净检出能起来」才算数。
