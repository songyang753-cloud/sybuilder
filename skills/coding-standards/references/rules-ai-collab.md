## K · AI 协作写码的特有失效

### K1 · 引用任何 API 前先确认它存在

**幻觉 API 与编造签名是 AI 写码的头号失效。**

- 生成任何第三方调用前，先在项目**已安装的版本**里确认该符号存在。
  ⚠️ **查 manifest 是查错了对象**（2026-09-10 外部评审纠正）：`package.json` / `requirements.txt` /
  `go.mod` / `Cargo.toml` 只说明**依赖名和版本约束**，说明不了某个**符号、签名、参数**存不存在
  （lockfile 与实际安装物才是事实源，而它们常常和约束不是同一个版本）。
  ⇒ 认账的四种证据：**实际安装产物**（`node_modules` / site-packages / `go doc` / `cargo doc`）、
  **类型声明**（`.d.ts` / `.pyi` / 头文件）、**钉死版本的官方文档**、**一个最小编译或运行探针**。
- 确认不了 ⇒ 就地标注 `// VERIFY: <lib>.<symbol> against version X`，**并在回答里点出这处不确定**。
- 需要的库不在项目里 ⇒ **提议安装（带具体版本）**，不要先写依赖它的代码。

> **静默打桩比拒绝更糟**——一个假装能跑的 stub 会一路流到测试和评审，而拒绝会当场暴露问题。

⭐⭐⭐ **更难防的一半：API 存在，但它的语义随运行时版本变了**
（第九次外部实战，2026-09-05，`except TimeoutError` 接不住读超时）。

```python
except TimeoutError:            # Python 3.10+：完全正确（socket.timeout 就是它的别名）
    ...                         # Python 3.9-：socket.timeout 是另一个类 ⇒ 异常从这里穿过去
```

三个特征让它比幻觉 API 更难发现：
1. **它不是编的** —— `TimeoutError` 真实存在，是现代、推荐、正确的写法；
2. **静态检查全过** —— 语法、类型、lint 一个都不会响；
3. **失效方式是「穿过去」而不是「报错说不支持」** —— 你看到的是一屏无关的调用栈
   （实测那次是整屏 `ssl.py`），指向的位置离真因很远。

⚠️ AI 写码在这一条上有**结构性偏向**：训练语料里的写法偏新，
而项目实际跑的解释器/运行时经常偏旧 —— **两边都"对"，只是不在同一个版本上**。
> 那份文件开头还写着「零第三方依赖，仅用标准库，**任何环境开箱即用**」——
> 承诺是真心的，只是没在旧解释器上跑过一次。

**做法**：
1. K1 的检查要**多问一句版本**：不只是「这个符号存在吗」，而是
   **「在这个项目实际运行的那个版本上，它是这个意思吗」**（`python3 -V` / `node -v` / go 版本）。
2. 涉及**异常类型、内置别名、默认参数值**这三类时尤其要查 —— 它们最常在小版本间悄悄合并或改名。
3. 写成**兼容式捕获**（`except (TimeoutError, socket.timeout)`）比写成"最新正确"更值：
   代价是一行，收益是不必假设运行时版本。

> **运行时数据孪生:传给下游的 id / 引用必须来自上游真实返回**(接地 / provenance,借自 agent-eval)。K1 治**代码符号**幻觉(编译期:这个 API 存在吗);这条治**运行期数据引用**幻觉:把一个 id / 句柄喂给下游操作(删除 / 收藏 / 跳转)时,它必须是某个上游调用**真实返回过**的,不能是「格式正确、看起来合理、其实没人产出过」的捏造值。校验查**来源**不查**格式**——工具调用 / RAG / agent 代码高发。

### K2 · 「编译通过」≠「正确」；「我写完了」≠「我验过了」 ⭐⭐

两句必须分开说：

- **编译/类型通过只说明语法对。** 要确认这个函数做的是它**名字承诺**的事，而不只是「返回了个东西」。
- **诚实状态汇报**：被问「X 做完了吗」，按**已验证的**答，不按**尝试过的**答。
  > 「我写了代码，但没跑测试」——当事实就是这样时，这就是正确答案。

⚠️ 这条与承重层 **A1（三态）** 同构：`已验证` / `已验证不合格` / **`写了但没验`** 是三种状态，说成两种就是假绿。

### K3 · 验证强度要匹配风险

| 改动类型 | 最低验证 |
|---|---|
| 琐碎（改字符串、格式） | 语法检查 |
| 逻辑改动 | 手工把执行路径走一遍 |
| 并发 / 状态 / 事务 | **写出具体场景**（谁先谁后、中间失败会怎样）；具体要求见 **F3**（唯一所有者 / check-act 同一原子边界 / 不跨外部等待持锁 / 多锁全局序 / 取消传播 / outbox） |

**按风险跳过验证，本身就是那个失效模式。**

### K4 · 没有证据不许说「看起来没问题」

- 被问「这对吗 / 这能跑吗」，**先主动列几种失败模式再回答**：空输入、边界值、状态与并发假设是常见起点（重点是别只给笼统结论,不是凑够某个固定数字）。
- 评不全 ⇒ 说清**查了哪些、没查哪些**，不要给一个笼统的结论。
- 没有规格可对照时，**要一份规格，或者拒绝下判断**——不要凭"读起来合理"背书。

⚠️ 与承重层 **H1/H2** 同源：不知道就说「我需要验证 X」，**不要编一个听起来合理的答案**。

### K5 · 上下文腐化：会话越长，质量越低

这不是比喻，是可观测现象：**会话填满时输出质量下降**（PAUL 称之为 *context rot*）。

**做法**：

1. 长任务切成**能独立验证的薄切片**，一片一提交。
2. **状态写进文件，不靠会话记忆**——`STATE.md` / 计划文件 / 进度注记。换会话时读文件，不靠回忆。
3. **输出质量下降是「换上下文」的信号，不是「再加把劲」的信号。**

### K6 · 子代理按任务类型分工（此处有真实分歧，不假装有定论）

**两个高星 skill 直接对立**：

| 立场 | 主张 |
|---|---|
| **PAUL** | 子代理带着全新上下文回来，**实现类工作只有 ~70% 质量**，还要人收拾。开发留在主线，子代理只用于**发现与研究**（它们的活儿本来就是搜集上下文） |
| **superpowers** | 明确采用 **subagent-driven-development**，让子代理逐个啃工程任务，主代理检查与推进 |

**本文取的综合**（依据是三家独立来源在同一件事上撞了车——superpowers、alibaba/open-code-review、four-node-review 都得出「给 agent 精心裁剪过的上下文，而不是整个会话历史」）：

> **按任务类型分**：**发现 / 研究 / 审查** → 子代理（**上下文隔离是优点**，一包一 agent 覆盖可数）；
> **实现** → 主线（**上下文连续性是必需**，隔离反而制造返工）。

分歧点名即可，**别替项目选边**；选了哪边写下理由。

> ⭐⭐ **实证补一条（2026-09-09 亲历）：fork（继承父完整上下文的子代理）会延续父叙事而非执行被交付的独立任务。**
> 我在一个 /loop 自主长跑里派了个 fork 去评估另一套 skill，fork 继承了「我正在做 loop」的全部上下文，
> 最终回复复述了「两件事并行推进中」的父叙事、**只用了 3 次工具调用、零文件产出**——被交付的评估它根本没做。
> 换成**全新上下文的 general-purpose agent**（只带自包含 briefing，不带会话历史）才真执行。
> ⇒ 判据：**「继续我正在做的同类工作」用 fork；「派一个需要独立聚焦、与当前叙事不同的任务」用全新 agent。**
> 上下文连续性对前者是优点，对后者是污染源——fork 会把父的「当前在干什么」误当成自己的任务。
> 而且这个失效**静默**：fork 返回一段看起来合理的摘要，不核实产出文件是否真存在（D31/H10）就会把空转当完成。

### K7 · 计划必须闭环：把「计划的」和「实际发生的」对账 ⭐⭐

**孤儿计划是 AI 协作的常态**：计划建了、任务做了、没人回头核对做的是不是计划的那件事。

收尾时必须做一次 **reconcile**：读**实际产出**，对照任务规格与验收标准。它抓三样：

- **drift**（做着做着偏了）
- **missing requirements**（有条要求从头到尾没人碰）
- **false completion**（**报告说完成了，实际没有**）

> 这条与承重层 **H7（收尾自我对账）** 是**两个独立来源撞出的同一条**——H7 反推自 four-node-review 铁律 66，K7 来自 PAUL 的 UNIFY。
> 按 four-node-review 的「交叉命中」规则，**两源独立得出同一结论 = 最高置信度**。

### K8 · 验收标准先于实现

- **开工前定义「完成」**，用 `Given [前置] / When [动作] / Then [结果]`。
- **每个任务引用它的验收标准**；标准不是事后补的装饰。
- **完成的判据是「验收标准被验证」，不是「代码写完了」。**

### K9 · 不许为了让检查变绿而关掉检查 ⭐⭐⭐

这是 AI 写码**最高频**的失效形态，且每一种都长得像"在解决问题"：

| 形态 | 真相 |
|---|---|
| 改测试让它过 | 你改的是那道题，不是那个答案 |
| 给判据加豁免 | 见承重层 B10：整文件豁免就是弱点换个地方复现 |
| 调低阈值 | 见 G5：地板要设在退化值之上 |
| 跳过/注释掉失败的检查 | 见 A7：缺席必须留痕 |
| 删掉断言 | 见 D2：断言要能红 |
| **加 `sleep`/`Task.Delay` 让时序测试变绿** | 你把竞态**藏进了概率**——它不关任何检查,而是让本应红的时序缺陷概率性变绿;换台慢机器/CI 满载就复现。正解=确定性同步(信号量/条件变量/轮询到条件/fake clock),不是「睡够久应该就行」。合法例外只有:被测对象本身就是限流/超时/退避(借自 gstack slopwatch SW004) |

> **判据变绿的方式只有一种：让被测的那个东西真的对。**
> 有一个专门的 skill（`constraint-driven-development`）存在的理由就是**抓 agent 消音检查与跳过测试**——说明这不是个别现象。

#### 怎么挡住它（K9 是【必须】档，只写「不许」等于没写）

> `plankton-code-quality` 的原话：**LLM 会去改 `.ruff.toml` / `biome.json` 关掉规则，而不是修代码。**

三层防御，缺一层就有缝：

| 层 | 做法 | 挡住什么 |
|---|---|---|
| **事前** | 把 linter / 类型 / 门禁的**配置文件列进受保护清单**，编辑前拦下 | 直接改配置关规则 |
| **事后** | 收尾时 `git diff` 检查这些配置**有没有被动过** | 绕过事前拦截的改动 |
| **对账** | 配置真要改时，**改动必须和一条需求对得上**（同 C1），并说明**它原本挡的是什么、新写法为什么仍然挡得住** | 「合理地」放宽 |

⚠️ 受保护清单本身是 **B5 的枚举**——新增一种 linter 就漏一种。
⇒ 更承重的做法是**反过来**：把「门禁配置目录」整个列为受保护，新增文件默认在内。

⚠️ **第四层:行内/调用点抑制指令,配置文件防御完全看不见它**(三源撞车:gstack slopwatch SW002 + claude-code-harness PreToolUse guard + contravis4 CLAUDE.md)。`eslint-disable` / `#pragma warning disable` / `@ts-ignore` / `# type: ignore` / `as any` 这类**从不进配置文件**——上面三层(受保护配置清单 / git diff 查配置 / 配置改动对账)锚的全是配置文件,对写在源码行里的消音**零覆盖**。需要**不同型**的一道:扫 diff 里**新增的抑制 token**,每个都要么对得上一条需求(同对账),要么就是消音。

⚠️ 唯一的例外是**判据本身写错了**（B7 过紧 / D3 只测了一个方向）。这时改判据是对的，但必须**说明它原本要挡什么、新写法为什么仍然挡得住**。

#### 镜像面：不许为了让检查变绿而**改坏本来正确的代码**（K9 的反面，借自 gstack slop-scan，2026-09-09）

K9 治「关掉检查」；它有一个反方向的孪生失效：**不关检查，但为了迎合检查去改动一段本来正确的代码**——门禁数字变好看了，代码变差了。
gstack 的 slop-scan 把扫描发现明确分成两类（`~/.claude/skills/gstack/CLAUDE.md:490-544`）：

| 该修（真质量问题） | 不该修（迎合扫描器反而变坏） |
|---|---|
| 文件操作旁的空 `catch` ⇒ 用 `safeUnlink`（吞掉 EPERM = 静默数据丢失） | fire-and-forget 操作的 `catch {}` 是**对的**——别改成脆弱的 `err.message.includes('closed')` 字符串匹配 |
| 进程 kill 旁的空 catch ⇒ `safeKill`（吞掉 EPERM = 以为杀了其实没杀） | 扩展/插件代码 catch-and-log 是**对的**——别改成 throw（未捕获异常会整个崩） |

> 纲领一句话：**「别追数字。」** 接受「那个看起来『脏』的模式其实是正确工程选择」的发现，标注豁免理由，不改。
> 与 K9 合起来：**变绿的正当方式只有一种——让被测的东西真的对**；关掉检查、和改坏正确代码去迎合检查，是同一枚硬币的两面。

### K10 · 别在你没读过的代码上动手

AI 写码的三个典型走偏（sentrux 的原文归纳）：**幻觉出不存在的函数** / **把新代码放错位置** / **在它碰过的文件里引入 bug**。

**做法**：写新代码前先找项目里**有没有已有实现与约定**。

> 呼应承重层的一条实证：**正确写法常常已经在同一个仓库里**——同类问题在另一个目录早就做对了。

### K11 · 多方并行改同一仓库：写入锚定内容，提交锚定路径 ⭐⭐

多方（多个 agent 会话 / 多个人 / 人 + agent）同时改一个仓库时，**你读到的那一版可能已经被别人改了**。

**写入侧**：
- 编辑基于**内容锚点**（唯一匹配的原文片段），不基于行号；写入前**校验源文件新鲜度**，陈旧就重读再改。
- 打补丁必须 `assert 出现次数 == 1`，替换后再确认落点（同 A14、D8）。

**提交侧**（下面这套是 2026-09-04 五个会话同仓协作实跑验证过的）：

| 规则 | 为什么 |
|---|---|
| **只 `git add <自己的路径>`，绝不 `-A`** | `-A` 会把别人未提交的改动一起卷走 |
| ⭐⭐ **提交也要带路径：`git commit -- <自己的路径>`** | **只 `add` 自己的路径是不够的**——`git commit` 提交的是**整个索引**，别人**先 stage** 的文件会被一起带走。受控实验确认：`git add mine && git commit` ⇒ 提交了 mine + theirs；`git commit -- mine` ⇒ 只提交 mine，别人的仍留在暂存区 |
| ⚠️⚠️ **带路径提交的第二个语义：它提交的是那些路径的「工作区当前内容」，不是你刚验过的暂存内容** | 2026-09-10 受控实验：`a.txt` 暂存版=`STAGED`、工作区版=`WORKTREE-NEWER`，`git commit -- a.txt` 提交进去的是 **WORKTREE-NEWER**。⇒ 隔离作用成立（别人的 `b.txt` 仍留在索引），但「我验的是暂存快照」这个假设**不成立**。**前置条件：提交前必须先验「工作区 == 暂存」**（本 skill 的 `precommit-guard.sh` 就是这么做的：不一致直接 UNABLE 逼你 `git add`）。缺了这一步，带路径提交会把该路径下**未暂存、未验证**的半成品一起带进去 |
| ⚠️ **未跟踪文件是第三个洞**：门禁读得到它，提交带不走它 | `git ls-files -com` 会把未跟踪文件纳入被测范围，而 `git diff` 不看它们、带路径提交也不会自动收它们 ⇒ **门禁可以依赖一个未跟踪文件而通过，最终提交里却没有它**。守卫已补这道检查 |
| **提交前看一眼 `git diff --cached --name-only`** | 这是上一条的兜底：索引里有没有不是你的东西，一眼就知道 |
| **提交前先 `stat` 看 mtime + `ps` 确认没人正在写** | 判断依据是**时间**，不是猜 |
| **正在飞的改动一律不碰** | 半成品被提交后，对方再 `git checkout -- file` 拿回的是**你提交的中间态**——这个坑不容易被发现 |
| **代提交他人改动的门槛：静置足够久 + 双向真跑验证** | 关键是**给对方留出收尾/提交窗口**(经验值 ≥30 分钟,按团队节奏调,不是硬数字);验证不只 `py_compile`:坏输入必须被拒且点名,合法输入不许被误杀(同 D3、B16) |
| **一次一组，提交信息与 diff 一一对应** | 任一方回退自己那部分不牵连其他人 |
| **push 前 `fetch` 并用远端指针比对，不看退出码** | `git push \| tail; echo $?` 取的是 `tail` 的退出码，证明不了任何事 |

> **本文自身的事故（2026-09-04）**：我用 `git add skills/coding-standards/ && git commit`，
> 结果**卷走了另一会话已 stage 的 10 个 product-flow 文件 + 一份 COORDINATION.md**。
> 对方推测起因是 `git add -A` ——**不是**，我用的是显式路径。
> 真因是 `git commit` 吃整个索引，受控实验复现确认。
> ⚠️ **归因错了，修法就会错**：按「别用 -A」去修，这个洞一个字都堵不上（我本来就没用 -A）。

⛔⛔ **上面全是「提交侧」。回退侧是另一个洞，而且更狠：不进 reflog，git 找不回来**
（2026-09-10 实录，同一棵共享工作树）：在仓库根上跑一次**不带路径**的
`git checkout .` / `git restore .` / `git clean`，会把**所有「工作区与 index 不一致」的文件**一次性重写
（⚠️ 2026-09-15 受控实验修正：此前写「每一个被跟踪文件」——实测干净文件**一个都不碰、mtime 不动**，
`git checkout -- .` 与 `git checkout HEAD -- .` 都只重写脏文件）——
而**脏文件恰恰就是别人尚未提交的在飞改动，它们就此消失**。它不动 HEAD、不写 reflog、也没有 stash，
`git reflog` 里什么都看不到，**没有任何 git 命令能找回来**（这次是靠另一个会话早前的
工作树全量拷贝才抢救出 9 个文件、共 200+ 行）。
⇒ **规则**：共享工作树里，`checkout` / `restore` / `clean` **一律带路径**，
和 `add` / `commit` 同一条纪律；要「清干净重来」就先确认整棵树是你一个人的。

⭐ **配套取证法（下次不必互相猜疑，两句话定性）**：
1. **「被回退」还是「被提交」**：看 `mtime` 与该文件**最后一次提交的日期**——
   mtime 是今天、最后提交停在几天前 ⇒ **被回退**（被提交的话，提交时间会跟上）。
2. **「全仓操作」还是「按路径操作」**：看这一批 mtime **有没有横跨无关目录**——
   按路径的提交**根本不碰工作区文件的 mtime**；一批 mtime 横跨无关目录同一秒
   ⇒ 是**某种全树写盘操作**（这次现场：约 350 个文件、横跨 10 个不相干的子项目），
   可以**排除掉一切按路径的操作**，不用再逐个会话对质。
   ⚠️ **但这条判据只能单向用**（2026-09-15 受控实验修正）：全仓 checkout **只重写脏文件**，
   在大部分干净的树上留下的 mtime 痕迹与按路径操作**一模一样**——
   「没看到无关目录同秒」洗脱不了它。这也意味着 09-10 那次「350 个文件同秒」的**机制未查明**：
   干净树上的裸 `git checkout .` 造不出这个现场——要么那 350 个文件当时确实都脏，
   要么是另一种全树写盘操作（备份恢复 / rsync / 分支切换……）。结论「全树写盘发生过、
   在飞改动因此丢失、按路径提交可排除」不受影响，**具体是哪条命令干的，证据不支持指认**（H2）。
> ⚠️ 这次差点又栽在**同一秒的巧合**上：有人的三笔按路径提交恰好落在 15:50:14，
> 与回退同一秒 —— 时间相邻**不是**因果，用上面第 2 条一测就分开了（同 **H11**：
> 一个能解释全部症状的结论，正因为哪儿都对得上而最难被推翻）。

**协作侧**（这一条今天产出最大）：
- **先声明边界**：我动哪些目录、不动哪些，一句话说清，比事后解释便宜得多。
- ⭐ **发现别人的约定不统一时，不要去「统一」它** —— 那会动到正在飞的文件。
  正确做法：**只在自己新写的部分照新约定来，并在 `.proposals/` 留一条建议**，由作者自己决定何时收敛
  （实测：退出码约定 `0/1/2/3/4` 就是这么落地的——提议方没有去改任何一个已有脚本）。
- **把踩到的坑回赠给写规范的那一方**——别人的门禁失效，就是你规范条款的来源。
  ⚠️ 但**拿不准的外部实证，先问出处方怎么概括，不要先写进规范**：写进去之后就没人会再去核了
  （实测挡下过一条错误条款——对方主动更正说那是他扫描器的 bug，不是缺陷类型）。

### K12 · 注释不许复述代码，也不许引用任务

- **不写复述型注释**：`// 把 x 加一` 这类零信息。注释只解释**非显然的 WHY**：隐藏约束、针对某个 bug 的绕法、会让读者意外的行为。
- **不写自指注释**：`// 用于 X 流程`、`// 为 issue Y 添加`、`// review 提的 TODO`——这些属于 commit message 与 PR 描述，**留在代码里会随演化而腐烂**。

⚠️ 与承重层 **E1** 配合：注释要么解释非显然的 WHY，要么不写；**写下的每一句保证都要能对账**。

### K13 · 隐藏的取舍要说出来

生成的代码里有用户没问、但影响架构的决定时——**引入一个依赖 / 选了某种异步模式 / 挑了复杂度不同的数据结构**——在回答里**点名这个取舍**，不要埋在代码里。

### K14 · 不因压力改变技术结论

- **紧迫感不是论据**（「先上再说」）：把代价**说一次**（"不做 X 会怎样"），然后照做。**不重复警告，也不道歉。**
- **权威不是论据**（「CTO 要的」「法务说没事」）：代码的对错与谁提的无关。
- **拒绝把真实风险说轻**。风险确实小就照做并说明为什么小。
- **被反驳不等于要改口**：只在**新证据**面前更新结论，不在情绪或重复施压面前更新。

### K15 · AI 会自信地把漏洞和功能一起交付 —— 固定必查清单

> 安全缺口在被人利用之前都不明显。没有明确指引时，**AI 会把有漏洞的模式和功能一起自信地交付**。

**每次涉及以下面时逐条过**（合并 VibeSec 的 bug bounty 清单与 CoSAI CodeGuard 的 AI 高发项）：

| 面 | 必查 |
|---|---|
| 密钥 | 硬编码凭据;**尤其别进前端 bundle**;**不进日志**(随机初始密码打进 journal = 把强口令降级成日志明文;正解写**仅属主可读的一次性文件**,POSIX 上创建时原子指定 `0600`、父目录 `0700`,**写后回读实际权限**再确认——别指望默认 mode 或 umask,Windows 用只授予目标账户的 ACL;⚠️ **stdout 不算「不落盘」**:服务与 CI 里它被 journald/launchd/容器运行时/流水线日志原样采集,只有能确认它连的是**交互式 TTY**时才可显示一次,并同时提示立即轮换);**落盘即 0600**(open 默认 644=全局可读);凭据进 .gitignore 要在**创建那次提交之前**;**权限主动全机普查**而非撞见才修(一次 `find` 曾 chmod 修掉 4 个 644 真机密,并顺藤发现私钥/token 已进 private git 仓历史——644→进 git→进远端);**private ≠ 安全**,凭据不该进 git 哪怕私有仓;**命中要甄别**(名字含 key/token ≠ 机密,B13) |
| PII | 手机号/身份证等明文落库（实证同上：`users.phone` 存明文手机号；公开版不保留个人号码）——至少与业务解耦评估是否该加密或脱敏存储；日志与导出同样不带。⭐ **加密只答了「存得安不安全」,答不了「为什么收、收多久、谁能看、怎么删」**（2026-09-10 外部评审补）：每类个人数据要能说出**用途 / 最小字段集 / 责任人 / 可访问角色 / 保留期限 / 删除方式**；**删除必须传播到派生面**——主存储、索引、缓存、导出、派生表，以及按既定周期到期的备份；导出与删除两条路径都要有授权、审计和端到端测试。**说不出用途和保留期的字段，默认不采集。** |

> ⭐ **同一作者同一批服务，安全习惯不会自动从做对的那个传染到做错的那个**（第 27-28 次实战，2026-09-09）：
> 同一人写的 algo-survey 是模范（`.env` 0600 + bcrypt + ConstantTime + `X-App-Key`/`media_sig` 签名 + 密码不入日志），
> 而 feedback 同目录 `.env` 是 0644、初始密码打进 journal。**审计不能因为「作者显然懂安全」就跳过任何一个服务** ——
> C11 的另一个投影：「已经有一个做对了」最容易让人省掉对旁边那个的检查，而它们常常不一致。
| 鉴权 | 敏感页/接口有没有认证；水平与垂直越权；**IDOR** |
| 参数 | **mass assignment**（整个请求体直灌模型）；token 撤销与会话生命周期 |
| 输入 | 跳过输入校验；SQL 注入；XXE；路径穿越；不安全上传；**采集回来的内容再变成命令参数时，它就是攻击者输入**（实证 2026-09-09 webgrab：批量 URL 来自页面抽链接，经单引号内插进 ssh 远程命令——恶意页面放一条含 `'` 的链接即可在采集服务器上执行任意命令。修法：RFC3986 等价编码 `'`→`%27` 或 body 走 stdin `-d @-`，**别信任何一层引号**） |
| 出网 | **SSRF**；**open redirect** |
| 命令白名单 | **按二进制名放行的白名单挡不住参数里的能力**（实证 2026-09-09 dingclaw：「只读」命令族里 `find -exec/-delete`、`rg --pre`、`sort -o`、`git config 键值` 全是执行/写盘通道，`{} +` 形态连复合符都不带）；**换行/回车也是命令分隔符**——复合符集漏了 `\n` 则 `ls\ncurl evil` 按首词判只读放行整段 |
| 加密 | 弱算法；密钥管理；证书校验 |
| 本地服务 | **`listen(PORT)` 不带 host = 全接口**(多数框架默认)——「本地」是假设不是事实;绑回环还不够:**浏览器是桥**,跨站页面能 POST 到 localhost、DNS rebinding 能顶着攻击域名连进来。三道门:**绑回环 + 验 Host(剥端口别 split 冒号,拆坏 IPv6)+ 验 Origin**。⚠️ 后果不止「执行任务/读数据」:**经手付费凭据的本地代理 `CORS: *` = 额度盗用**(恶意网页 `fetch` 它、用你的 key 花你的钱;不设 CORS 则浏览器发得出读不到)——「只是个 TTS 代理」也有值钱攻击面 |
| 其他 | 不安全函数；弱口令策略；JWT 配置 |
| 防泄漏验证 | 光有 redaction/打码**不够**——要有**泄漏哈网 + 正对照**证明它真拦得住（播种密钥→捕获 stdout/stderr/落盘/日志全通道→断言缺席→一条故意泄漏断言被抓到），且扫的必须是**将发送的确切字节**不是渲染前的串（承重层 B2 scan-at-sink 细则 + D34 哈网范式） |

**CodeGuard 的生命周期框架**（三个时机都要，不只事后）：

- **生成前**：规划/写规格时就把安全模式定下来（steer，而不是事后 review）
- **生成中**：写的当下按上表逐条过
- **生成后**：作为 review 清单
