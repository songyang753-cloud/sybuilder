### A1 · 检查类函数返回三态，不返回布尔

任何「检查 / 校验 / 探测 / 验证 / 健康检查」类函数，返回值必须能区分三种终态：

| 终态 | 含义 |
|---|---|
| `PASS` | 测了，合格 |
| `FAIL` | 测了，不合格 |
| `UNABLE` | **没能测**，必须附可操作的原因（依赖未装 / 目标不可达 / 前置条件缺失） |

**二态即缺陷**：`UNABLE` 混进 `PASS` 是假绿，混进 `FAIL` 是假红。它必须是第三种东西。

```
✗  function check() { return failures.length === 0 }      // 没测也返回 true
✓  function check() {
     if (!canReach(target)) return { status:'UNABLE', reason:'目标不可达: '+target }
     ...
     return { status: failures.length ? 'FAIL':'PASS', checked: items.length, failures }
   }
```

**自检问句**：调用方能不能分辨「它说没问题」和「它没能测」？分辨不了就还是二态。

⭐⭐ **三态最常在「验收侧」被塌回二态 —— 而症状是 flaky**（2026-09-10，peer 会话 `case-5c` 回流的实证）：
一套浏览器门在**生产路径上把三态做对了** —— 基建类错误（CDP 端口没起来）被映射成 `rc=2`「没能测」。
**而它自己的自证 harness 那一层没做同样的区分**：

```js
try { got = (await check(dir, '用例甲')).rc } catch { got = 2 }   // 基建失败 → 2
// …随后 got 直接与「期望值」比对 ⇒ 期望 0 的用例被判红
```

⇒ **基建起不来产生的 2，被当成「被测物给出的结论」**，于是整道门进 `failedScripts`。
实证形态：两道门**各偶发失败一次**，单独跑和重跑都绿（真因是端口 `9300+random(600)` 无冲突检测、
CDP 就绪预算固定 20s，本机多会话同时跑时会撞）。

**为什么这个位置特别贵**：它表现为 **flaky**，而 flaky 的下一个读者会**去查一个不存在的产品缺陷**。
⚠️ **只加重试／端口探测是不够的** —— 那只降低概率，不改变分类；撞上的那一次照样把基建失败报成缺陷。
**分类必须先对**：`实得 == 「没能测」而期望不是` ⇒ 本例不判红、整体退「没能测」，重试可以叠加在这之上。

⇒ **自检问句**：我的三态，**传到验收/自证那一层还是三态吗**？
（同族：**A15** 把期望值写死成 `0` 会逼人删掉诚实的 UNABLE；**A19** 不合格不许洗成没能测——这条是它的镜像：**没能测不许洗成不合格**。）

> **适用条件(2026-09-09 codex 评审)**:三态是给**依赖外部资源 / 采集过程 / 可失败前置**的检查用的——它们才有「没能测」这个合法终态。**纯内存、确定性的全函数**(`isValidEmail(s)`、`isSorted(xs)`、`isEven(n)`)**没有 UNABLE 态,返回布尔更简单准确**,别硬套三态。判据:问「这个检查存在『我没法判定』的合法情形吗」——有(网络/文件/外部命令)才要三态,没有就是布尔。异常是否作为第三通道,由项目错误模型定。

### A2 · 外部调用有三态，第三态最容易被吞

任何跨进程 / 跨网络的调用，失败有三种形状，**第三种最危险**：

1. 进程失败 / 连接失败 —— 会抛，容易接住
2. 输出不可解析 —— 会抛，容易接住
3. **能解析，但没有预期字段** —— **不抛**，于是走进成功分支

```
✗  const n = (JSON.parse(out).metadata || {}).vulnerabilities ?? 0   // 错误体被洗成「0 漏洞」
✗  if (!r.metadata?.vulnerabilities) return UNABLE(...)               // 合法的 0 也为真 ⇒ 把「0 漏洞」洗成 UNABLE
✓  const r = JSON.parse(out)
   if (!r.metadata || !('vulnerabilities' in r.metadata))            // 查**存在性**,不是真假值
     return UNABLE('响应缺 metadata.vulnerabilities，可能是镜像源不支持该接口')
   if (!Number.isSafeInteger(r.metadata.vulnerabilities))                // 「数量」必须是非负安全整数
     return UNABLE('vulnerabilities 字段格式非法')                       // typeof==='number' 会放过 1.5/NaN/Infinity
   if (r.metadata.vulnerabilities < 0) return UNABLE('vulnerabilities 为负')
   const n = r.metadata.vulnerabilities                              // 0 是有效结果
```
> ⚠️ **本示例自身踩过坑(2026-09-09 codex 评审抓到)**:原 `✓` 写的是 `if (!r.metadata?.vulnerabilities)`——**合法的 `0` 漏洞会让它为真,把「检查完成、零漏洞」洗成「未能检查」**,恰恰违反本条要守的三态区分(A19)。校验外部字段一律**查存在性 + 查类型**,绝不用 `!value` / `?? 0` 兜底,因为 `0`/`''`/`false` 都是合法值。

实证（第 21 次外部实战，2026-09-09 crawl-stack/webgrab）：jina 返 HTTP 401，错误 JSON 体 370+ 字符——
比 MIN_CHARS=200 长、不匹配任何毒页面正则，于是产出校验放行、报 `engine=jina`、exit 0，
**认证错误被当正文交付**给日报管线。根因一个字符：`curl -s` 没带 `-f`——
HTTP 状态码是区分「正文」和「错误说明书」的第一信号，被丢弃后**内容层判据只能靠猜**。

`|| {}` / `?? 0` / `|| []` 出现在**解析外部响应**的位置时，默认它是个缺陷，除非你能说清「这个默认值代表的真实世界状态是什么」。

⚠️ **同一形态在命令行工具上：错误也是输出**。
> 实证（本文自身，2026-09-05）：逐个核实来源仓库是否存在，判据写成「`$out` 非空就算 OK」——
> 而 `gh api repos/<不存在的仓库>` 把 `{"message":"Not Found","status":"404"}` 打在 **stdout** 上。
> 于是一个 404 被记成 `OK`，**101 个全 OK 的报告里藏着 2 个根本不存在的名字**。
> 更糟的是我还写了 `2>/dev/null`：真要有 stderr 也被我自己捂掉了。
>
> ⇒ 对外部命令，**「有输出」不是判据**。判据必须是**内容层面的正例**：
> 这里正确的写法是断言返回的 `full_name` 与请求的名字相等（顺带还抓到一个上游改名）。

⚠️ **同一形态在对象属性上**：你取的那个字段，**可能是你刚编出来的**。
> 实证：给一条诊断加身份，写了 `spec.__name`——**这个字段整个仓库里不存在**，恒为 `undefined`，
> 标签永远只剩冒号后半截。语法检查、类型检查、全套测试**没有任何一环会报错**。
> 这是 AI 写码最典型的幻觉形态：**名字合理、位置合理、读起来像真的**（同 K1）。

⇒ 凡是从一个对象上取**自己没亲眼见过**的属性，先 `/usr/bin/grep` 一次这个名字在仓库里是否存在；
**取不到时不要静默降级成空串**——那正是它能长期不被发现的原因。

**自检问句**：如果对方返回的是一个**格式合法的错误**，我这段代码会怎么走？

⚠️ **同型不止出现在外部调用上——任何「两种不同状态」被兜底折叠成一种，都是这个缺陷。**
> 实证：`prompt()` 取消返回 `null`、留空返回 `''`，用 `|| 默认值` 兜底会把两者折叠——
> 而用户意图**完全相反**（「我不做了」vs「我不填」）。实测后果是**按取消后满屏部件当场消失**。

> **测试面孪生:失败夹具必须含「协议以下」的故障,不只「格式合法的错误」**(借自 Nygard《Release It!》Test Harness)。mock/夹具通常只造你**想象得到**的失败(4xx/5xx/超时返回),但真实世界还有一整类**协议以下**的故障:连接挂起不返回、字节一滴一滴流(slow drip)、返回半截/乱码/超大响应、TCP 连上但永不发数据。A2 第三态(能解析但没预期字段)在测试里的对应就是:**夹具要主动造这些 out-of-spec 故障**,否则「有超时/有错误处理」(F1/A2)只在你想象的失败上被验过,真出这类时代码从没走过那条路。

### A3 · 「零失败即通过」必须配下限断言

`failures.length === 0` 在**检查项集合为空**时恒真。空集合有两种来源——真的没问题，和**根本没收集到东西**。

⚠️ **这两件事要分开量**（2026-09-10 外部评审收窄）：下限断言真正要证的是**采集成功**，
不是「域里一定有东西」。若业务上确实允许零个对象，空集上的 `PASS checked=0` 就是正确结论，
硬报 UNABLE 反而是**把合法零值洗成没能测**（A19 的镜像面）。
⇒ 判据分两步：①采集失败 / 无法判断空集是否真实 ⇒ `UNABLE`；
②只有当业务契约规定「至少存在 N 个」时，才对**数量**设下限，不足是 `FAIL` 而不是 UNABLE。
本条的 `MIN_EXPECTED` 属于第 ② 种；第 ① 种要断言的是采集器自己有没有跑完。

```
✗  return { ok: failures.length === 0 }
✓  if (checked.length < MIN_EXPECTED) return UNABLE(`只收集到 ${checked.length} 项，少于下限 ${MIN_EXPECTED}`)
   return { ok: failures.length === 0, checked: checked.length }
```

**上报体必须带真实计数**——没有计数就无法证明它验过什么。

**自检问句**：如果收集环节整个失败了，这个函数返回什么？

⭐ **「空但合法」的输入必须被显式验一次**（`case-05` 实证）：
「每个 X 都满足 P」在**没有 X 时恒真** —— 这样的判据会**在最该出声的时候报绿**。
> 他普查 12 道门在「空但合法」输入上的行为：**11 道正确报 UNABLE，无一假绿**。
> 结果是好消息，但**它值得被显式验一次** —— 因为**一旦有一道假绿，你永远不会从正常使用中发现它**。
⇒ 条款类判据（「所有函数都…」「每个错误都…」「每处调用都…」）尤其容易中招。
⭐ **下限断言要盖两个数，而不是一个**（本文自身实录，2026-09-05）：
一个是「**被测对象有几个**」，另一个是「**判据自己筛完还剩几个**」——后者更容易漏。

> 实测：一道「十组必须在场景索引里可达」的判据，循环体前有一句
> `grep '^### J[0-9]+ ·' SKILL.md || continue`（判断该组是否存在）。
> 而条款根本不在那个文件里 ⇒ **每一组都被 continue 掉，循环体一次都没执行**。
> 它照常输出 `PASS 十组均可达`、照常占一个检查条数、在报告里和真检查完全一样。
> **把索引表里全部十个组级入口删光，它仍然报 PASS。**
>
> ⇒ 判据内部任何 `continue` / `filter` / `if not match: skip`，都要问一句
> **「全被跳过时，我这条会说什么？」** 答案若是「说没问题」，就缺一条 `剩余数 < 下限 ⇒ UNABLE`。

⚠️ 它和 **D31**（判据会不会被执行）是同一句话的两个层级：
D31 问「这道判据跑了吗」，这一条问「**它跑了，但它判了吗**」。
两者的症状完全一致 —— 报告里一行漂亮的 PASS。


### A4 · 截断标志必须跟着数据走到消费方

有界资源（前 N 行 / 前 N 个分块 / 第一个匹配项 / 一次探测）被裁剪之后，如果结果通过一个**断言完整性的接口**报出去，就是在说谎。

```
✗  读前 5000 行求和 → 返回 { sum: 5000 }        // 真值 6000，读的人以为是全表
✓  返回 { sum: 5000, truncated: true, limit: 5000 }
   且 truncated 要写进落盘对象 —— 只放在返回值里等于没有（读磁盘的那一方看不见你的返回值）
   消费方据此改措辞：「只统计了前 5000 行，这个数字不是全表的」
```

⭐⭐⭐ **一个反直觉的方向性观察：越是「我要全部」，标志越容易缺失**
（第九次外部实战，2026-09-05，一个给 AI 当工具用的只读查询 CLI）：

```python
if not args.all and total > returned:      # ← 用 --limit 截断：有提示
    out["_hint"] = "仅返回前 N/total 条…"   #    用 --all 被上限截断：一个字都没有
```

写的人的心理很自然：「`--limit` 是用户自己限的，要提醒他还有更多；
`--all` 已经是全部了，还提醒什么？」——**而 `--all` 恰恰有一条安全阀（翻页上限）会让它拿不全**。
于是**意图最强的那条路径，反而没有标志**。

⚠️ 两个加重因素：
- 输出里只给了 `total` 和 `returned` 两个数字，**要消费方自己去比** —— 而它多半不会比；
- 唯一的警告写在 **stderr**，而 AI 工具调用常常只取 stdout。**警告在，通道不对。**

> 该工具**已因同型问题出过两次生产事故**（AI 日报静默少拉 191 条；另一份日报丢过 74%）。
> 当时修的是 `--limit` 那条路 —— **同后果的另一条路留到了今天**（**C6**）。

⇒ **自检两句**：
1. **「全部 / 完整 / 所有」这类语义的路径，有没有安全阀会让它其实不完整？**
2. **标志走的是数据通道还是日志通道？** 消费方只读 stdout 时，stderr 里的警告等于不存在。

**截断点通常是一个有注释的命名常量——限制是有意的，缺的不是限制，是标志。**

⚠️ 措辞要诚实：源总量若在裁剪时已经丢掉，就说「原表更长」，**不要编一个 sourceRows**——编一个数字正是你在修的那类缺陷。

**自检问句**：这个数字的读者，会不会以为它是全量的？

### A5 · 新增诊断字段必须有人读并断言

加一个计数桶 / 日志字段 / 诊断标记之后，如果没有任何一处**读它并据此判断**，它只会让判据**更容易过**（未预期的东西被并进「已见集合」）。

**自检问句**：把这个字段的消费方删掉，有哪条断言会红？一条都没有 ⇒ 别加这个字段，或者补上消费方。

⚠️ **配置字段同样适用，而且后果更重**（`case-05` 实证）：
> 某门禁**从来没读过配置里的 `end` 字段**，恒定跑桌面视口 ⇒ **移动端路径根本走不了**。
> 实况：6 条关键路径全是 PC，移动端一条都没有，**而用户明确要求了双端**。

⛔ **一个声明了但没人消费的字段，比没有这个字段更糟 —— 它让人以为覆盖到了。**

### A6 · 「为什么失败」只能断言代码真验证过的因果

向人陈述原因的文案（错误信息、失败横幅、告警正文），断言的因果必须是代码真的判别过的。

```
✗  const timedOut = status === null && (signal != null || err?.code === 'ETIMEDOUT')
   // 任何信号致死都走进超时分支 → 段错误 / OOM / 外部 kill 全被告知「墙钟 300s 到点」
✓  超时：err?.code === 'ETIMEDOUT'；信号致死：signal != null 且 err === undefined —— 分开报
```

**没有诊断，人会去查；错的诊断，人会去查错的地方。** 后者更糟。

⚠️ 分类做细之后必须补一条「**分类变细不等于放行**」的兜底断言（本例是 `code !== 0` 仍成立），否则「区分」很容易在下一次改动里被写成「豁免」。

**自检问句**：这句话断言的因果，代码真的验证过吗？

### A7 · 缺席必须留痕

计划做五项、实际做了三项、剩下两项静默跳过——跑了的三项证据完全合格，缺席的两项**不留任何痕迹**，于是它和「做了且没问题」长得一模一样。

**做法**：开始前把计划项列出来，结束时逐项标 `done` / `UNABLE + 原因`。任何一项 UNABLE，整体就不是「通过」。

**自检问句**：这段逻辑如果**整块没跑到**，输出会有什么不同？没有不同就是缺陷。


### A8 · 「算出来了」不等于「送达了」 ⭐⭐

凡是「A 算出来的值要进 B」的结构，断言必须落在 **B 的输出**上，不能落在「A 被调用了几次」。

> 实证：截断提醒被抽成纯函数、四个分支都调用了它，守它的断言是「调用出现 4 次」。**删掉模板里的一处插值**（那行调用一字不动）——调用数仍是 4、全套判据照绿，而被截断的表在下游重新变回「完整的表」。三轮才消灭的缺陷，删两个字符全部复活。

**警觉信号**：判据里出现 `.match(...).length === N` 或 `includes(...)` 时，它测的多半是**形状**，不是**行为**。

> **制品层的同型(A8 上抬,借自 gstack review/plan-eng-review)**:「能**处理** X 的代码」不是「X 本身」,「**描述**这份工作的散文」不是「结构化交付物」。写了 markdown 抽取库 ≠ 交付了那份 markdown;把评审结论写进计划正文 ≠ 产出了评审报告。A8 是值层面(算出没送达),这是制品层面(**会做 X 的东西 ≠ X**)——收尾时问的不是「我做了能产出它的东西吗」,是「它本身在不在交付物里」。

### A9 · 证明你的检查真的跑了（元判据） ⭐⭐⭐

「声称的 ≠ 实际的」最彻底的形态：**代码在、断言写得很好、文件报绿，而它们从未运行**。

> 实证：一个判据文件在 `try {}` 里写了 `return (async () => {…})()`；**CJS 模块顶层的 `return` 会终止整个模块体**，它后面四个块从提交那天起一次都没执行过，文件仍然 exit 0、仍被计进「N 套 / M 条断言」的统计。在那四块开头各植一个 `assert(1===2)` 毒丸，跑它依旧 **EXIT=0**。

**做法**：给「检查集合」本身加一条**元检查**——证明每个检查块真的被执行了（执行计数 / 毒丸测试 / 按脚本而非模块体编译来判顶层 `return`）。⚠️ **别用正则**判「顶层」——本例就藏在 `try{}` 里，正则判不准。

⚠️⚠️ **元判据必须长在被监督对象之外**（`case-c0` 实证）：
> 元判据第一版写在 `run()` 末尾，而它要抓的正是「提前 `return` 让后面的块跑不到」——
> **提前 return 会把元判据自己一起跳过 ⇒ 恒绿**。移到 `report()` 才生效，反向测试确认会红。

⇒ **一个检查若与它要抓的故障共享同一条执行路径，那条故障它永远抓不到。**

⚠️ 另两个同源的坑（同一会话，加元判据时连撞三个）：
- **元判据把自己算进了它要数的那个集合** ⇒ declared 恒比 actual 多 1 ⇒ **恒红**
- **反例的锚点字符串出现在用来找它的那行代码里** ⇒ `count == 1` 当场失败
  ⇒ 在自己身上做变异测试时，**锚点必须拼出来**（`'ABC'+'DEF'`），别写成字面量

**元判据会抓住你自己，那正是它值钱的时候**：上面那条元判据落地几小时后，作者写新判据时原样写了一个顶层 `return`，被当场点名。**别在这种时候给自己开豁免。**


### A10 · 「没跑起来」和「跑了，答案是没有」必须长得不一样 ⭐⭐⭐

这是 A1 三态在**消费方**的样子。底层往往已经把两者分开了，**而调用方全都塌成同一个业务结论**。

> 实证：底层已生成准确诊断（「git 不可用（未找到可执行的 git）」）并用 `status === null` 区分「没跑起来」与真实失败。**15 个消费方里只有 1 处读它**——其余丢弃 stderr、只看 `status`/`stdout`。后果：**边界审计返回空数组 ＝「边界守住了」**（越权写入既不上报也不回滚）；每次操作都被判成「这次没改动任何东西」而改动已落盘。

⭐ **镜像错误同样坏：把环境失败折叠成「产品缺陷」**（`case-05` 实测，2026-09-05）
> 一道门把 `evalInPage` 的**所有**异常 catch 成 `rc:1`，文案写「换上真接口后页面直接崩了」——
> 而这个 catch 同时接住了 `CDP 端口没起来` / `找不到 Chrome` / `ETIMEDOUT`。
> 症状：连跑 30 道门时出现一次不可复现的红（当时本机 12 个 Chrome、别的会话在用），单跑 5/5 绿。
> **信了那句文案，就会去查一个根本不存在的缺陷。**
>
> 同仓的基建模块早写着契约「基建失败要冒泡成 2，不许 catch 成通过」——
> 这一处犯的是它的**镜像**：不是折叠成 PASS，是折叠成 FAIL。
> **一个漏报，一个把人指向不存在的病，一样坏**（**A6**：指错方向的诊断比没有诊断更糟）。
>
> ⭐ 普查同型副本后发现：其余 5 道同类门都已是 `catch → UNABLE exit(2)`，只有这一处走偏，
> **因为它把调用包在了「按用例返回 rc 的函数」里，而不是顶层**。
> ⇒ **循环内 / 按条目的 catch，是这类错误的高发形状** —— 值得单独扫一遍：
> 那一层 catch 天然倾向于「给这一条一个结论」，而正确做法是让基建失败**穿透**到顶层。

**降级要分三类，第三类最坏**：

| 类 | 表现 | 危害 |
|---|---|---|
| ① 正确降级并**如实说明** | 「没跑起来，因为 X」 | 可接受 |
| ② 静默失败 | 什么都不说 | 坏 |
| ③ **给出自信而错误的结论** | 「边界守住了」 | **最坏——它还会附赠一条错误建议** |

**做法**：在底层加共用判据（`isUnavailable(r)` + `reasonOf(r)`），让**每个消费方**都能问出「这是没跑起来，还是跑了但答案是否定的」；**把底层已经写好的诊断透出去，不要各自编一个原因**。

⭐ **比「加 isUnavailable」更早一步、成本也更低的自问**（`case-c0` 实测，2026-09-04）：
> **每一个 `if os.path.isfile(...)` / `if (fs.existsSync(...))` 都要问：「文件不在时，这条判据还算跑过吗？」
> 答案是否，就必须有 `else`。**
> 他扫了 14 处外部文件读取：**13 处是对的，1 处塌了** —— 三方对账那处**只有 if 没有 else**，
> 文件不在时整段不跑，而报告显示 ✅ 通过。
> ⚠️ **漏的那一处恰恰是最晚加的那个** —— 自问一旦形成就很稳，**新增的代码是它的盲区**。
> ⛔ 而四态（PASS/FAIL/N-A/UNABLE）**是那个项目自己文档里写的**——H10 又一例。

### A11 · 上游写得诚实，下游要把这份诚实说出口 ⭐⭐

一层写得很诚实，**不代表下一层会把这份诚实说出口**。

> 实证：内核侧被打磨得很好——写不下时拒绝并给出可读原因、失败带 `stoppedReason`、截断带标志。**而渲染层几乎从不消费这些返回值**：`await api.storage.set(...)` 丢弃返回值 ⇒ 实测 80 次点击落盘 52、**静默丢失 28**，条目出现在卡片上、下次开 app 全没了；四处变更型 IPC 的 `{ok:false,error}` 无人展示。

**自检问句**：我这个函数辛苦返回的失败信息，**有人读吗**？`await f()` 后面不接任何判断，等于 `f()` 白写。

⚠️ 与 A5 同构：A5 说「加了字段要有人读」，这条说「**已经有的字段也要有人读**」——后者更常见，因为没人觉得自己在删信息。

### A12 · 「能拿到绿灯的坏东西」是一类独立的审计单位 ⭐⭐

当一轮里每条发现的证据都带着同一句「**而自动校验是绿的**」时，那不是巧合——
**说明校验的裁决面本身有系统性缺口，而它往往是唯一的把关。**

⇒ 把**校验器本身**当被审对象跑一轮，穷举三件事：

1. 它**到底检查什么**——从代码读，**别信注释**（注释常比实现乐观）
2. 它**明确不检查什么**——写下来，别让它留白
3. 每一格「不检查」对应的**用户可见后果**——区分「看起来正常但功能是死的」（最坏）与「肉眼可见的坏」（用户自己会发现）

**反向也要问：它有没有误杀**（把好的判成坏的）——那会让人为一次假失败白付一次代价（同 B7）。

### A13 · UNABLE 如果成了常态，它就退化成 PASS ⭐⭐⭐

A1 要求三态。但**三态里的 UNABLE 如果每次都出现，人就会去关掉它**——关掉之后，它和 PASS 没有区别。

> 实证（`case-e9` @ sample-xiangce，2026-09-04）：供应链扫描的超时写了 **60s**，
> 而 `npm audit` 实测要 **81~312s**。于是**每次构建都报「没扫成」**，
> 人只能用 `AUDIT_ALLOW_SKIP=1` 绕过 —— **一道逼人用逃生门的门禁，最终会变成没人跑的门禁。**

⇒ 引入 UNABLE 之后要**跟踪它的出现率**：偶发正常，**常态就是设计错了**。
两条出路：把前提修好（此例是按实测分布定超时），或把这项检查**移出阻断路径**并明说它是尽力而为。

⚠️ 与 B7 同族：**会逼人加豁免的门，最终一定会被加豁免。**

### A14 · 打印了 ✗ 却仍然 exit 0 ⭐⭐

> 实证（`case-54` @ 某验证项目，2026-09-04）：一道门禁把失败收进累加器，
> 但**插退出码那几行时锚点被前一步改名，`str.replace` 静默失配** —— 于是它会打印 ✗，退出码却是 0。
> 正向全绿，是另做一次独立性检查时顺带撞上的。

**自查问句**：**「这一节如果全部失败，整个脚本的退出码会是几？」**

⇒ 可做成元判据：**凡名字带 `fail` / `error` 的累加器，必须能追到某条 `exit` / `raise`。**

⚠️ 配套（同源）：**没断言的替换 = 可能什么都没发生。** 每次 `str.replace` 打补丁必须先
`assert s.count(old) == 1`，替换后再确认落点（同 D8）。

### A15 · 「门禁必须绿」≠「退出码必须是 0」；退出码语义不统一会把 FAIL 伪装成 UNABLE ⭐⭐⭐

**三态门的合法结论不止一个。** 把期望值写死成 `0`，会逼人去删掉诚实的 `SKIPPED` / `UNABLE`。

> 实证（`case-05` @ product-flow，2026-09-04）：覆盖率检查对某份**填写正确**的夹具，
> **正确结论是退出码 3**（有诚实的 SKIPPED）。夹具对里若把期望写成 0，
> **逼出来的「修复」是把那三条 SKIPPED 删掉** —— 判据反过来奖励说谎。

⚠️ **更坏的一层：退出码语义在脚本之间并不统一。**
> 同仓 22 道门禁里 **20 道是 `2 = 跑不了`**，而另一道的 `2 = 有缺口`（真失败）、`3 = 输入无效`。
> 任何按「2 就是跑不了」写的汇总器，会把**真失败标成跑不了** ——
> **把 FAIL 伪装成 UNABLE 是最坏的一种误标**（比反过来更坏：它让人以为「没测到」，于是不去修）。

⭐⭐ **另一端同样致命：把 UNABLE 当成「本轮不适用」放行。**

| 状态 | 含义 | 该不该挡 |
|---|---|---|
| **NOT-RUN** | **你没跑它**（可能不适用） | 必检项：**未经批准即阻断**；有批准记录的 N/A 才放行（正本＝ **A19** 统一表；2026-09-15 修正——此行原写「不挡」，与 A19 正好相反，先读到这张表的人会照「不挡」实现） |
| **UNABLE** | **你跑了，它说「我查不了」** | **必须挡** —— 你以为有信息的地方其实是空的 |

> 实证（`case-05`，两次）：①给门禁加阻断时**刻意把 UNABLE 排除在阻断集合外**（想着「跑不了可能是不适用」）
> ⇒ 空文件跑出 UNABLE，门**放行了**；②更早一次，某对账门的集合恒为空、报 UNABLE，
> 而**「UNABLE」与「通过」在他眼里没有区别**，就那样往下走了，直到另一个会话指出来。

⛔ **「本轮不适用」的正确表达是不跑它（NOT-RUN），不是跑了拿一个 UNABLE。**
⭐ **UNABLE 被当成 N/A，和 FAIL 被伪装成 UNABLE，是同一个洞的两端。**

⇒ 五条：

1. **每个脚本在文件头声明自己的退出码语义**，一句话，写死。
2. **汇总多个脚本的结果之前，先摸一遍它们的语义**（`grep -h "退出码" *.py`，三十秒）——
   别假设通用约定。
3. **夹具对里的期望退出码要按「这份输入的正确结论」写**，不是一律写 0。
4. **NOT-RUN 与 UNABLE 必须是两个不同的码/状态**，且 UNABLE 进阻断集合。
5. **两道正交的检查都要有**（`case-05` 的划分）：
   **「单个脚本自述 vs 它自己实际用的码」**（否则登记表可能登记了脚本自己都没在用的码）
   ＋ **「汇总方能不能正确读懂每个脚本的码」**（否则 22 个脚本各自自洽却互相打架）。

### A16 · 门禁不阻断，就只是一条建议 —— 结论必须串在退出码上 ⭐⭐⭐

A14 治的是**门禁自己**打印 ✗ 却 `exit 0`。这一条治的是**调用方**：
门禁**正确地红了**，而流程照走。

> **本文自身的实录（2026-09-04）**：我把门禁自述写成「20 条」而实际 19 条，
> **[8] 当场报了 FAIL** —— 但我的 `selfcheck` 和 `git commit` 是两条独立命令，
> **红了照样提交并推送**。门禁抓到了，是我把它的结论绕过去了。

⇒ **一道会红但不阻断的门，和一道不存在的门，差别只在于它给了你一个「我看到了」的错觉。**

**做法**：把门禁和它要守的那个动作**串在同一条退出码链上**。

```bash
✗  bash gate.sh;  git commit -m "..."          # 两条独立命令，红了照走
✗  bash gate.sh | tail -3                      # 管道把退出码换成了 tail 的
✓  bash gate.sh && git add <路径> && git commit -- <路径>
✓  pre-commit / CI job：门禁非零即中断后续 step
```

**自检问句**：**这道门红的时候，会有什么动作被真的挡住？** 答不出具体动作 = 它只是一条建议。

⚠️ 同源三种绕过（都实测踩过）：**管道吃掉退出码**（`cmd | tail`）／
**`;` 而不是 `&&`** ／**结果只写进报告没人读**（同 A5）。

⭐ **给阻断本身写三条自证**（`case-05` 实测，第一版就漏了第二条）：

| 自证 | 为什么 |
|---|---|
| **FAIL 必挡** | 基本要求 |
| **UNABLE 必挡** | 他第一版**刻意把 UNABLE 排除在阻断集合外**（想着「跑不了可能是不适用」）⇒ 空文件跑出 UNABLE，门放行了。见 A15 |
| **在案无红时必须放行** | **一道永远红的门会被加豁免，然后就没人跑它了**（同 B7、A13）——恒红的门和不存在的门一样没用 |

> 他给报告工具加阻断时的原话很值得记：`--status` 恒返 0 ⇒ 按本条的自检问句一问，
> **「它就是一份报告」** —— 这个判断只花了一句话。

⚠️ **怎么正确地「量」一个退出码**（本文作者同日栽三次，故给可直接抄的写法，而不是再写一条纪律）：

```bash
cmd | tail -5; echo "rc=$?"        # ⛔ 拿到的是 tail 的退出码，不是 cmd 的
cmd 2>&1 | grep -c X; echo "$?"    # ⛔ 同上；且 grep 无匹配时**既输出 0 又退出 1**
cmd >/dev/null 2>&1; echo "rc=$?"  # ✅ 不经管道
o=$(mktemp); cmd > "$o" 2>&1; rc=$?; tail -5 "$o"  # ✅ 先取码，再看输出（mktemp——固定 /tmp 路径会被并发会话互相覆盖，C12/[10k]）
set -o pipefail                     # ✅ 另一解，但必须显式开，且只在 bash/zsh
```

> 三次实录都长得一样：**我据此报了一个不存在的缺陷，然后去查被测物**。
> 错误诊断比漏报更贵 —— 漏报只是没发现，错误诊断会让人去修没坏的东西。

⭐⭐ **另一面：退出码对了，不等于该发生的事发生了**（本文作者现犯，2026-09-05）。
给一个无人值守任务补三态退出码后，我按 `rc=3` 验「没能执行」这一态 —— **rc 确实是 3，看起来通过**。
但那条路径只写了日志、**没有发告警**：它长这样

```bash
[ -x "$BIN" ] || { log "找不到 $BIN"; exit 3; }   # rc 对了，人永远不会知道
```

而我在**同一个文件往上 20 行**的注释里刚写下「沉默会让这个任务永久静默失效」。
⇒ **门的验证必须同时断言两件事：退出码，和这一态该产生的副作用**（告警发了吗、台账写了吗）。
只断言 rc 的测试，会把「静默失败」原样放行 —— 而静默失败正是它要防的东西。
⚠️ 别忘了**负向那半**：健康态必须断言「**没有**告警」，否则「逢跑必告警」也会一路绿灯（同 B16）。

### A17 · 量具本身可能在骗你 —— 拿一个已知答案的输入验它 ⭐⭐⭐

A15/A16 治的是「门禁的结论有没有被正确表达 / 接住」。这一条更底层：
**判据可以是对的、门禁可以是绿的，而量具在骗你。**

> 实证（`case-05`，2026-09-04）：用 `--window-size` 设浏览器视口 ——
> ```
> 请求 390x844  → innerWidth = 500   ⛔
> 请求 414x900  → innerWidth = 500   ⛔
> 请求 1440x900 → innerWidth = 1440  ✅
> ```
> **macOS 上 `--window-size` 有最小宽度限制（实测约 500px），Chrome 悄悄把 390 撑到 500 且不报任何错。**
> 后果：**整个会话所有「移动端」测量都跑在 500px 上** —— 端形态门、视口审计、移动端路径全部如此。

⇒ **自检问句：这个数字，我拿一个已知答案的输入验过吗？**

⭐ 他是靠**「请求 390 应该得 390」这种废话式断言**验出来的 ——
**正因为它是废话，才从来没人想过要写。** 这类断言性价比极高：一行、零维护，
而它守的是**所有下游结论的地基**。

⚠️ **第一次修可能更错**：改用 `mobile: true` 后，页面没有 viewport meta 时 CSS 宽退回 **980**
（请求 390 实得 980）—— **换量具也要重新验一次已知答案**。

⭐ **诚实处理的范本**：重测后结论没变，但他**显式写明「此前那批数字不该被引用」**，
没有假装「重测了所以之前也没问题」（同 H2、D13）。

### A18 · 截断 / 跳过 / 豁免 / 不适用 —— 本身通常合理，不合理的是不说 ⭐⭐⭐

**这是 A 组的母题**，A4（截断标志）、A7（缺席留痕）、A15（UNABLE vs NOT-RUN）都是它的分支：

> **「没查」与「查过没问题」在输出上必须可分辨，否则前者会被读成后者。**

> 实证（`case-05`，十轮 review 收敛后归纳，**一天之内同一形态命中六处**，形态各异而病根一个）：

| 处 | 文案说的 | 真相 |
|---|---|---|
| 扫描器 `limit=6` | 「6 处」 | 实际 **20 处** |
| 遍历 `MAX_BYTES` | 该规则报绿 | **2.5MB 文件整个没扫** |
| slug 豁免 | 「19 个都出现」 | 18 个出现，**1 个被豁免** |
| 裸文件名跳过 | 「N 处都指得到」 | 另有 **2 处未查** |
| 空页面 | 「你没做端形态」 | **没得判**（传错文件的人会去修一个不存在的问题） |
| 坏 JSON | 退出码 1 ＝「有缺口」 | **输入读不了** |

⚠️ **这条目前没有可靠的机器判据，如实标注**：判断「某个 `continue` 有没有被计入某条成功文案」
本质上要理解数据流。按 **B17**「不可靠的检测器比没有检测器更糟」（制造噪声然后被关掉），
**不硬做**。

⇒ 但有一条**可执行**的替代要求，先把它做上：

> **凡是有跳过分支的扫描，自证里必须有一条让那个分支触发的用例，并断言输出提到了它。**

**自检问句**：**我这段输出，读的人能分辨「查过了没问题」和「这部分我没查」吗？**

### A19 · `UNABLE` 只留给「真的没能测」——**不合格不许洗成没能测** ⭐⭐⭐

**A1** 防的是一个方向：`UNABLE` 混进 `PASS`（假绿）或混进 `FAIL`（假红）。
**反方向没人防**：把「测了、不合格」报成「没能测」。

它看起来无害，因为 `UNABLE` 也不是绿。**而现实中很多流水线把 `UNABLE` 处置成「告警、不阻断」** ——
于是一条真实的不合格被悄悄降级成一条告警，**这就是一次迟到的假绿**。

⚠️ **这是在描述现状，不是在认可它**（2026-09-10 外部评审指出这句与 A15「UNABLE 必须挡」并排放着
会被读成「放行也行」）。**统一表如下，必检项（required check）一律以此为准**：

| 状态 | 必检项（required） | 参考项（advisory） |
|---|---|---|
| `PASS` | 放行 | 放行 |
| `FAIL` | **阻断** | 按事先声明的策略 |
| `UNABLE` | **阻断**（没能测 ≠ 通过） | 告警，但**不许计进通过率** |
| 根本没跑（NOT-RUN） | **未经批准即阻断** | 留痕 |
| 已批准的 N/A | 放行（要有批准记录） | 放行 |

⇒ 一句话：**流水线历史上怎么处置 `UNABLE` 不改变它的语义**。必检项的 `UNABLE` 放行，
是那条流水线配置本身的缺陷。
而且它同时毁掉诊断：人看到「没能测」会去查环境、查依赖、查网络，
**没有人会去查被测物本身** —— 而问题恰恰在那儿。

实测（本文自身，2026-09-05）：用 D20 的办法把每个文件整段清空跑门禁 ——
`SKILL.md` 清空报 `UNABLE 找不到 MUST 标记块`、`sources.md` 清空报 `UNABLE 找不到三表分界`，
整套 `rc=3` 而不是 `1`。两处的被测物**都读到了**，只是内容没了。

⭐ **真正的根因：解析失败有两种成因，而它们共用同一个分支**
—— ①**被测物缺了那个结构**（是缺陷，判 FAIL）；②**解析器自己坏了 / 依赖没装 / 文件读不到**（判 UNABLE）。
写判据时 `UNABLE` 常常是 `except` / `if not match` 的顺手兜底，**两种成因一起掉进去，必然错一半**
（与 **D21** 「变异存活有两种成因」同构）。

**判别口径，一句话**：
> **我拿到被测物了吗？** 拿到了、读完了、发现它不满足要求 ⇒ **FAIL**。
> 压根没拿到（依赖缺失 / 目标不可达 / 权限不足 / 解析器异常）⇒ **UNABLE**，并附可操作原因。

> **实证二（外部代码，2026-09-05）**：本规范第一次拿去审**不是照它写的**真实脚本
> （`claude_auth_keepwarm.sh`，一个每天跑的无人值守任务）。它有一句兜底：
> 「探测失败但非认证类（网络/超时），不告警」。
> 这一句同时吞掉了**三层互相独立的故障**——旧机的 HOME 路径、macOS 没有 `timeout`、
> `claude` 不在写死的那个路径 —— 每一层都让探针 `rc=127`，**探针从来没有真正执行过一次**，
> 而任务已经这样静默失败了整整一个迁移周期。
> **告警路径不是「没触发」，是「不可能触发」。**
> ⇒ 单列「探针没能执行」这一态并让它告警之后，反向测试立刻变红（rc=3 且发出告警）。

⭐⭐ **一个高频具体形态：拿「数量」当状态码**（第八次外部实战，2026-09-05）。
`process.exit(failed.length)` 看起来很方便 —— 调用方还能顺手知道错了几条。
但状态码空间是**共享**的：那份代码里 `2` 已经被「没能测」占用
（用法错 / 文件不存在 / 找不到 Chrome / 零断言）⇒
**「恰好 2 条断言失败」与「Chrome 没装」返回同一个数字**，调用方无从分辨。
> **失败条数属于报告内容，不属于状态码。** 状态码只回答三个问题之一：
> 过了吗（0）／不合格（1）／没能测（3）。数量放 stdout。

⭐⭐ **折叠最贵的形态：被折叠的一态会武装后续的破坏动作**（第 22 次外部实战，2026-09-09 morph）。
`commitFeature()` 用同一个 `null` 表示「没有改动」和「git commit 失败」。前者是圆满收尾；
后者意味着**已通过内核验证的功能还躺在工作树里没提交** —— 任务被标成 done，
而下一个任务失败时的 `discardUserland()` 会把它**静默销毁**，日志里两个任务各自都「正常」。
⇒ 判断一次折叠值不值得拆，别只问「两态语义差多远」，要问：
**「系统里有没有哪个后续动作，对这两态该做的事截然相反？」** 有，就必须拆。
⚠️ 同类还有 `exit(len(errors))`、`exit(warnCount)`、`return errno` 混用自定义码 —— 都是同一个洞。

**两条做法**：
1. 每个 `UNABLE` 分支都要能回答「**是什么东西没拿到**」。答不上来的，它其实是 FAIL。
2. 把「读取」和「校验」分成两步写：读取失败 → UNABLE；读到了再校验 → PASS/FAIL。
   一步写完的判据，天然分不开这两种成因。

⭐⭐ **另一半：`UNABLE` 说得出「没能执行」，也别去猜「为什么」**
（本文自身实录，2026-09-05）：把一个条款文件设成不可读，四道判据齐声报
**「缺 python3 或它自己崩了」** —— 而真因是那个文件读不到，
`PermissionError` 连同完整路径**就在几行之上的 stderr 里**。
> **证据在场，而摘要说谎。人读的是摘要。**
兜底分支当初写死这句猜测时，确实穷举了当时想得到的两种原因；
第三种（输入文件不可读）不在其中，于是它把一个**没想到的原因**说成了**想到的那两个之一**。
⇒ 兜底诊断的正确写法是**指向证据**（「真因见上方 stderr」），不是复述一个猜测清单。
⚠️ 猜错原因比不给原因更贵：不给原因的人会去翻日志，给错原因的人会照着去查 python3。

⭐⭐ **再一半：前置检查的文件集合，必须盖住下游真正会读的每一个文件**
上面那四处误诊的根因不在兜底文案，而在更前面 —— **前置检查只列了六个文件，
漏掉了下游确实在读的另外两个**。于是缺文件时不在前置干净地 UNABLE，
而是一路走到下游**变成别的形状**。
⇒ 自检一句：**把判据里所有 `open(` / 读文件的路径列出来，和前置清单对一遍。**
（这是 **C11** 的普查动作用在自己身上：判据够不着的那处，往往是判据自己的输入。）

### A20 · 判据只报**第一个**问题 ⇒ 有 N 类缺陷就要跑 N 轮才知道 ⭐⭐⭐

`if 问题甲 … elif 问题乙 … else 通过` —— 甲和乙如果是**两个独立缺陷**，
这条链只会报排在前面的那个，另一个被完全吞掉。
症状不是假绿（它确实红了），而是**红得不完整**：
修的人只会去修被报出来的那一个，修完再跑，第二个才浮出来。
**门禁需要跑几轮才报完，就等于把「还剩几个问题」这件事对使用者隐藏了几轮。**

⚠️ 它和 elif 的**正当用法**长得一模一样，只能靠问一句区分：

> **这两个分支，是同一个量的不同取值，还是两件独立会坏的事？**

| 形态 | 例 | 判定 |
|---|---|---|
| 同一个量的不同取值 | 「声明缺失」→「声明与实现不一致」→「超限」 | ✅ elif 正当（后者以前者成立为前提） |
| 两件独立会坏的事 | 「标题格式不合规」与「标题把上一条截断」 | ⛔ 必须并列收集后一起报 |

⭐ **实测（本文自身，2026-09-05，一轮内两处）**：
| 处 | 症状 |
|---|---|
| `[3a]` 条款标题 | 删掉一条标题的 `·`，格式与截断两类同时成立，门禁**只说截断，一个字没提格式** |
| `10l` 闭环契约三档 | 上一行注释白纸黑字写着「每档报**不同**的诊断」，而实现是 elif 链 —— **设计写对了，实现没守住** |

**做法**：把诊断**收集进一个列表**，最后一次报完（`FAIL a | b | c`）。
代价只有几行，收益是「一轮看全」。

⚠️ 与 **A18**（截断/跳过要说出来）的分工：A18 管**没做的事要说**，
本条管**做了、也发现了，却只说出其中一件**。后者更隐蔽，因为它红了，看起来门禁正在工作。

⇒ 普查动作很便宜：**把门禁里所有 `elif` 列出来，逐个问上面那一句。**

## B · 守卫的承重性 —— 你写的检查能不能被绕过

<!-- IDX:B:BEGIN 组内索引：本组每条都必须在此出现（门禁校验闭世界）-->

**守卫放在哪** — **B1** 执行点放特权方 · **B2** 守危险能力的出口，不守守卫本身 · **B3** 执法器不得比注册器松 · **B8** 运行期加固比判据便宜

**判据钉什么** — **B18** 承诺型判据要写成条件式 · **B17** 「有时能抓到」比「从来抓不到」更危险 · **B4** 断言「系统做了什么」，不断言「源码长什么样」 · **B7** 过紧与过松同样是缺陷 · **B9** 连续两轮同型缺陷 ⇒ 停止打补丁，换判据的种类 · **B11** 两条判据正面冲突时，多半是各对一半——合并，别放宽 · **B12** 判据的默认倾向是「挑一个最容易观测的量来代表要守的那件事」 · **B13** 谓词只能看见它那种形态的谎

**判据的观测面够不够** — **B5** 观测域是枚举 + 被观测域自由 ⇒ 差集恒非空 · **B6** 判据强度 = min(观测面, 输入驱动)，两半都要抬 · **B10** 全集对账必须闭世界；豁免按「行为」列，不按「文件」列 · **B14** 一道「不许手抄清单」的门，自己就是一份手抄清单 · **B15** 判据与被测实现共用同一个定义 ⇒ 门禁永远绿 · **B16** 一条规则有几条合法路径，判据就得认几条 · **B19** 判据必须驱动生产的那一份，不是自己声明的同名拷贝 · **B20** 一处改动可以让全部门禁同时失效

<!-- IDX:B:END -->

> 本组来自 four-node-review 中最痛的一批实证：某项目连续 **14 轮**加固判据，每一轮的修法都对，而下一轮总能在**相邻一格**找到同型缺口。
> 结论不是「再写一条判据」，是**换判据的种类**。

### B1 · 执行点放特权方 ⭐

**判定问句：这条规则的执行点，能不能只靠改发起方的代码就绕过？**

能 ⇒ 你写的不是守卫，是补丁。

```
✗  白名单校验写在渲染层 / 客户端 / 调用方，而执行方的接口不带身份：
   ipcMain.handle('data:fetch', (_e, service, params) => fetch(service, params))
   ⇒ 给内存里的声明对象投毒、加一条同义通道、动态拼属性名……任一行改动都能整条还原
✓  执行点挪到特权方，且特权方**自己从权威来源（磁盘 / 数据库）推导规则**，
   不采信发起方传来的任何声明
```

⚠️ 挪的时候必踩两个坑：①**照抄发起方的写法**（对方拿到的是已解析的对象，磁盘上是文件名字符串）⇒ 规则算成空集 ⇒ 合法请求被拒；②只测了裁决函数，**没人守特权方真的调用它**（改成 `if (false)` 后全绿）。

### B2 · 守危险能力的出口，不守守卫本身

找到那个唯一的 sink（取数 / 写盘 / 出网 / 记分 / 提权），要求它的**每一处出现**都在守卫的放行分支里。这样新增任何绕过路径，都必然新增一个未被守护的出口——藏不住。

反面：守「守卫有没有被调用」。守卫可以被绕过去，出口不行。

**细则:scan-at-sink —— 扫「将要发送的那份确切字节」,不扫发送前的中间串**（借自 gstack，`~/.claude/skills/gstack/CLAUDE.md:457-459`，2026-09-09）。当出口是「把内容发给外部 sink」（codex / gh issue / push / 上报），泄漏检查必须扫**序列化后、即将交给 `gh`/`git`/HTTP 的那份字节**——写进临时文件、扫那个文件、把**同一个文件**交出去。**绝不「扫一个字符串、再重新渲染发出去」**:那会重开一个 scan-vs-send 缺口——你扫的和你发的不是同一份,中间任何编码/拼接都可能把已过检的内容变回带密钥的。这与 [[feedback_fixed_in_copy_not_in_source]] 同型:检查的对象必须**就是**被消费的对象,不是它的副本。

### B3 · 执法器不得比注册器松

注册器（准入 / 校验 / schema）拒绝的形态，执法器（运行期裁决）绝不能判为「合法」或「不设限」。

> 实证：目录里只放一个 `{"main":"nope.js"}`，注册器拒、裁决器判「不设限」⇒ **造一把主钥只需要一个 JSON 文件**。

**要么直接复用注册器的校验函数，要么比它更严。** 且「不设限」这一档的前提本身必须被验证。

### B4 · 断言「系统做了什么」，不断言「源码长什么样」 ⭐⭐

对源码做正则/字符串匹配的判据**两头都不承重**：改个变量名就绕过，而正确的重构反而会把它判红。

实测被绕过的写法（每一种都全套门禁绿）：`const alias = sink;` 后调 `alias(...)`；解构改名；换 `.on` 而非 `.handle`；`'sv'+'c:x'` 动态拼名；`Object.defineProperty` 而非赋值；`obj?.off?.()` / `obj['off']()` 让 `\.off\s*\(` 失配。

**这不是主张，是量出来的**：同一批 100+ 个定向变异下，**靠正则 / 计数 / 字符窗口的判据累计 14 次假绿 + 5 次误红；真跑行为的判据 0 次错判**。

⭐ **三个独立仓库的同期实测（2026-09-04，peer 会话回流）都指向同一结论**：

| 来源 | 实测 |
|---|---|
| `case-e9` | lint 规则的正则一撞上模板里第一个引号就断，于是模板字符串里带引号的写法**完全看不见**。该形状**实存 100 处，只报出 15 处**；补规则后浮出 58 条。**它给的不是假绿，是虚假的安心。** |
| `case-b8` | 一条 slice 判据对**五种真实写法全漏**（map 后 slice / 常量上限 / 变量上限 / 多空格 / 成员表达式），**而它的正例恰好是会被匹配到的那种，所以一直绿**。另一条同类判据只认 ASCII 文件名，而那个仓到处是中文名 |
| `case-54` | 门禁钉死了 `time.time()-last_crit>30` 这个写法，后来把冷却统一改走 `config.cooled()`（治墙钟向后跳）⇒ 正则失配，**一个正确的改进被判红**。改用 **AST 找分支 + 断言引用了哪个计时器**后才稳 |

⭐ **另两种「判据看错那一格」的具体坏法**（`case-55` 第 9、10 例）：
> ⑨ **只验「fail-closed 写法存在」** —— 变异**在它前面插一个 fail-open 分支**，
>   原写法还在 ⇒ 判据照常绿。**修：同时验「没有反向放行分支」。**
> ⑩ **全文计数 `>= 1`** —— 目标符号全仓 8 处，删掉关键那处照样绿；
>   收窄到专用变量名后**仍然绿**，因为那条路径有**两个**独立失败出口各一处，删其一计数还是 1。
>   **修：棘轮下限设 2，并注明「新增出口时同步上调」。**

⇒ **「正例恰好是能被匹配到的那一种」是这类判据最常见的自欺形态**——它证明的是「我能匹配我写的例子」，不是「我能覆盖这一类」。
且假绿**全部**落在渲染 / 接缝层，被抓的**全部**落在有真跑用例的模块——**接缝没有主人，所以没人守**。
绕过一条正则判据简单到令人不安：把 `n.empty` 写成 `n?.empty`、把豁免串粘成行尾注释、把被查的标识符挪进一个对象字面量。
⚠️ **误红比漏判更坏**：它会让人给判据加豁免，然后就没人跑它了（同 B7）。
⚠️ 真跑**不一定要重型环境**——一个 80 行的 DOM 垫片就够把整个 UI 层跑起来，一次裁决 1.2 秒。

**三种承重做法**：

1. **运行期普查**——stub 掉宿主框架、加载真实入口，记录它**真实注册/导出/暴露**了什么，与已知清单比对。观测的是「注册这个动作」，改名换 API 都逃不掉。
2. **喂受控输入看真实裁决**——把夹具喂进去，断言它真的按那个输入判。
3. **属性式反例**——几十个随机的、不存在的标识符，逐个断言拿不到授权。写死一张名字表只能测到你想到的那几个。

⚠️ **凡是「渲染成什么样 / 输出什么文本 / 点了会怎样」这类保证，判据必须执行它**——
源码断言只能证明「那行代码在」，**证明不了它生效**。实证：给组件加了「缺列时从首行推列名」的兜底，
判据用正则断言那行代码在 ⇒ **全绿**；而实参是数组、被当对象读了属性 ⇒ 恒空，
**那段推断从来没生效过**——用最小 DOM 垫片真跑一遍、断言**输出的文本**才抓住。
⚠️ **真跑的判据要配反向保护**：否则一个「把所有分支都改成显示 `—`」的错误实现同样能过
（正确写法是同时断言「绑不到数显示 `—`」**和**「`value=70` 仍显示 70」）。
⚠️ 垫片的作用域要覆盖**渲染期间**而不只是构造期间。

⚠️ **实在只能扫源码时，钉那条跨越多个环节的数据链**（`A 成立 → B 被设置 → C 二选一`），**断哪一环都要红**。只钉链条一端的判据，改另一端时照绿。
⚠️ 反向的危害同样真实：钉实现形状的判据，**会把当时那种写法固化成规范**——下一轮把实现收敛成更好的形式，它双双报红而行为完全正确，甚至把一个后来被判为 HIGH 的写法钉成了标准。

### B5 · 观测域是枚举 + 被观测域自由 ⇒ 差集恒非空 ⭐⭐

判据的观测域常常是**作者写死的一份枚举**（一个文件名、一张豁免表、一个目录、一批测试标识符），而被观测的东西是**自由给定的**。这时无论你把枚举做多大，差集永远非空——加固只是把差集挪个地方。

> 实证：同一条判据改了三版都没堵住。40 个随机名 ⇒ 漏 `zzz-helper`；100+ 个从磁盘真实名变形 ⇒ 漏 `totally-made-up-xyz`；加了全称断言但探针名仍是我列的 ⇒ 漏 `q7x-random-name-9`。

**正解不是把枚举做大，是换承重物——找一个被观测方无法回避的物理事实**：

- **切断物理依赖做全称断言**：把 `fs.readFileSync` / 网络 / 时钟 / 随机源换成恒抛，断言此时对**任意**输入都必须拒绝。授权若能凭空产生，说明有一条不读权威来源就发放的分支。
- **探针输入从被测源码自己提取**：按名字开的后门**必须把那个键写进源码**，于是它一定在「源码里的字符串字面量」这个集合里。
- **组合关系断言**：`f(x)` 恒等于 `g(h(x))`，断言在一大片输入上——加任何独立分支都会打破它。
- **差分对账**：期望值从权威来源**独立重算**，不写死表。⚠️ 固有边界是「两份实现同源就会同时错」，写清楚。

### B6 · 判据强度 = min(观测面, 输入驱动)，两半都要抬

**观测面再宽，没喂到那个输入就一次观测都不产生。**

> 实证：服务名维度已升成权威全集（175 个），而 `params` 维度还是 20 个手写形状 ⇒ 一个 `params.__zz9` 即万能放行、全套绿。

- **输入侧别猜键**：把可疑入参换成 `Proxy`，观测「被测代码读了它的哪些属性」。裁决路径本就不该读它——读了就是把它当成了裁决输入。
- **观测侧别只盯一个点**：一个模块往往有多个等价出口。与其在出口侧追，不如在**依赖侧**断言：决策模块不许出现裸网络模块 / `fetch` / `Date.now` / `Math.random` / `process.env` / 模块级可变状态——时间引信与高阈值计数器正是靠它们躲过「同一输入结果恒定」。

### B7 · 过紧与过松同样是缺陷

一条会误报的判据早晚被人删掉或加豁免，**而红色会把维护者指向错误诊断**。

> 实证：把三元改成语义完全相同的 `if/else`，判据红了并报「`|| true` 之类的短路…可取任意服务」——事实上什么都没被短路。

**钉语义要点**（拒绝分支必须存在），**不钉字面形状**。

### B8 · 运行期加固比判据便宜

两条几乎零成本、比任何判据都强：

- 安全关键文件加 `'use strict'`（切断 `arguments` 与形参的双向映射——非严格模式下 `arguments[4] = x` 等价于改写第 5 个形参）
- **把交出去的白名单 / 配置冻成只读**（`Object.freeze`）：后门从静默生效变成响亮的 `TypeError`
  ⚠️ **两条适用条件**（2026-09-10 外部评审实测纠正）：①`Object.freeze` **只冻自身属性，是浅的** ——
  `Object.freeze({nested:{allow:false}})` 之后 `x.nested.allow = true` **照样生效**；
  ②**只有严格模式才抛** `TypeError`，非严格模式下写入是**静默失败**（那正是本条想消灭的形态）。
  ⇒ 安全关键配置：校验后**复制成内部不可变表示**；需要冻嵌套结构时用能处理循环引用的 `deepFreeze`；
  并确保这段代码真在严格模式下跑。别把浅冻结当成完整的运行期边界。

### B9 · 连续两轮同型缺陷 ⇒ 停止打补丁，换判据的种类

打补丁只会让判据**更具体**，不会让它**更承重**——它把判据收紧到上一轮攻击的那个字节周围，而把**紧邻的自由度**留着（兄弟行、调用方、第二个参数、操作数、下一条语句）。

| 不承重的判据 | 换成 | 为什么承重 |
|---|---|---|
| 「这一行还在」 | 写入点/调用点的**完整集合**（计数 == N） | 加任何一行都会改变计数 |
| 「参数位第一个」 | 从 import / 依赖声明取**全集** | 新增实现必然要声明依赖 |
| 源码正则钉操作数 | 抽成**纯函数 + 行为断言** | 与写法无关，只与行为有关 |
| 行首锚定 | 锚定 **+ 禁止撤销动作** | 锚定管位置，禁令管后续语句 |

**反向自检**：**「在不违反这条判据的前提下，我能不能达到同样效果？」** 想得出一种，就还没守住。

⚠️ 另：**一条永假的断言不是防御，是误导读者**（`x.length >= 1` 而 `x` 由一个已断言非空的集合 map 出来）。


### B10 · 全集对账必须闭世界；豁免按「行为」列，不按「文件」列

**闭世界**：一条判据自称「做全集对账」，实现却是一个硬编码的两元素列表——它在结构上**不可能发现缺席的成员**。真正的全集对账长这样：

1. **枚举出这一类的所有实例**（扫全部源文件里每一处该动作）
2. **每一处都必须落进一个已分类的桶**（合规 / 登记为例外并写明理由）
3. **新增一处未分类的 ⇒ 红**

> 写它的时候它当场抓出两处作者没想到的成员——这就是闭世界与点名的区别。

**豁免按行为列**：给两个文件开整文件豁免之后，往被豁免的文件里新加一处裸写，判据照绿。**整文件豁免就是「文件级匹配器」弱点换个地方复现。** 豁免要落到**具体的操作目标**，文件里新出现的任何一处仍要被对账。
⭐ **第三条：豁免/出口一旦加了，就必须在计数里体现出来**（`case-05` 实测，2026-09-05）：
> 一道判据只查 `data-el="X"` 这个**字面量**在页面里出现没出现，
> 而底部 tab 的 slug 是运行时拼的（`data-el="tab-" + n.path`），静态永远扫不到。
> 他为此加了个 `runtimeSlug` 出口 —— **然后证据文案立刻开始说谎**：
> 「19 个 slug 都在 demo 里以 `data-el` 出现」，而其中 1 个根本没出现。
>
> ⇒ **出口本身会变成新的谎**，除非报告里把它拆开说：
> 「19 个中 18 个静态命中、1 个走运行时出口（已单独核验方式：X）」。
> 判据加豁免的同时**必须改它的自述**，否则你只是把一个红移进了绿里。

⚠️ 这与 **A19** 是同一件事的两种形态：A19 是把「没能测」洗成「不合格」的反向，
这一条是把「没测到」洗成「测过且合格」。**两者都让读者拿到一个比事实更好看的读数。**


⚠️ 同源的两个旁路：「行内出现 `.tmp` 就整行跳过」（写个 `// x.tmp` 注释即可绕过）、「只匹配 `fs.writeFileSync(`」（解构出来的、`require('fs').writeFileSync(…)`、`appendFileSync`、`fs.promises.writeFile` 全在面外）。**扫描面要按「动作」穷举，不是按一种写法。**

### B11 · 两条判据正面冲突时，多半是各对一半——合并，别放宽 ⭐⭐

> 实证：老判据要求「遍历触顶的痕迹**必须到达** `breaches`，否则停在内部函数上等于没人看得见」；新发现要求「**不许作为** `breaches` 的元素，否则会被 `length` 判成越界」。看起来必须二选一，实际是**同一个要求的两个侧面**——痕迹留在**返回对象**上（老判据要的「对用户接口」）但**不作为元素**（新判据要的「不判失败」）。

**做法**：写成**并存的两条断言**，并**各自反向测试**（去掉标记 → 老那条红；重新混进元素 → 新那条红）。

⚠️ **任何时候「为了让新代码通过而放宽老判据」，都要先证明老判据守的那件事已经由别处守住**——否则那是在拆防线（同 K9）。

### B12 · 判据的默认倾向是「挑一个最容易观测的量来代表要守的那件事」 ⭐⭐⭐

这是 B4/B5/B6 背后的母题。它**换层复发六次**，每次换一张皮：

| # | 守住了 | 没守住 |
|---|---|---|
| ① | 实现在不在 | **谁在消费它** |
| ② | 那段文本长什么样 | **跑起来会怎样** |
| ③ | 组件名（逐到了） | **调用点**（共享 helper 让 3 条夹具替 16 个组件作证） |
| ④ | 注入点在**链首** | **链尾从没被任何断言执行过**（一抛错整条链就断） |
| ⑤ | 夹具描述的世界 | **产品真实的世界**（对一个虚构元素作证，绿了两个月） |
| ⑥ | **契约里最好数的那一半** | **契约本身**（见下） |

⭐⭐ **第 ⑥ 种最隐蔽，因为判据看起来完全对口**
（第十一次外部实战，2026-09-05，一个「把 demo 打包成零外链单文件」的工具）：

```js
const remaining = (html.match(/["'(](https?:)?\/\/[^"')]+/g) || []).length;  // 只数远程链接
process.exit(remaining === 0 ? 0 : 1);
```
交付契约叫「**零外链单文件**」，而判据只数了 `http://`。
素材文件不存在时，内联失败、原样保留相对路径 —— 不是远程链接，**不计数** ⇒
打印「**✅ 零外链**」并 **exit 0**，而产物里躺着一个断链的 `<img>`。

> **契约不是「没有 http:// 链接」，是「这个文件双击打开是完整的」。**
> 判据挑走了契约里**最好数的那一半**，剩下那一半没有任何东西守。

⇒ 识别它的问法与前五种不同：不是「隔了几层」，而是
> **「把我这条判据全部满足，交付契约就一定达成了吗？」**
> 答案是「不一定」⇒ 差额就是没人守的那部分，**而它通常正是不好数的那部分**。

⇒ **每写一条判据都问：「我观测的这个量，和我要守的那件事，中间隔了几层？每一层都可能是它的逃生口。」**

⚠️ 尤其警惕「**数一数有几处**」这类判据——**计数守不住「这一处到底对不对」**。

### B13 · 谓词只能看见它那种形态的谎 ⭐⭐

> 实证：「渲染出来不许含数字」这条谓词，覆盖了所有**把读数写成文字**的组件——
> 而**把读数画成图形**的那一类（五个点亮几个、五颗星亮几颗、一个天气图标）**一个字符都不打印**，
> 结构上落在谓词的量程之外。
> 同源：通用夹具只设 `value` 字段，于是读 `n.a`/`n.b`/`n.code` 的组件从没被渲染过——
> **前 30 轮所有按 `value` 做的普查，一个都没扫过这些字段名。**

⇒ 写完谓词先问：**「哪一类正确的东西，会因为形态不同而天然满足我这条谓词？」**
那一类就是它的盲区，需要**另一种观测方式**（例如让图形类组件也产出一个诚实的文字占位，把它拉进谓词的量程）。

> ⭐ **同一根还有假阳性那一面**（2026-09-06 shell 广扫实证）：用 `grep '$var（'` 初筛「变量紧跟全角括号会崩」，
> 在 13 处命中、**真危险 0 处** —— 命中全是双引号字符串**内部**的合法插值（`echo "…（$code）"`），
> 而真正会崩的是字符串**外**、且只在 bash 3.2 上。文本谓词看得见「有没有这串字符」，
> 看不见「在不在引号内 / 什么解释器」——那正是决定它是不是缺陷的语义。
> ⇒ **文本模式初筛的命中是「待甄别」不是「缺陷」**；报之前逐个看上下文，否则给出的是**虚假的警报**
> （与 B12 那条「虚假的安心」正好照镜子：一个漏报到让人放心，一个误报到让人麻木，都源于观测的量隔着语义）。
> 自证：初筛探针也要有**阳性对照**（造一个真危险样本证明它能命中），否则「零命中」既可能是真干净，也可能是探针瞎了。

### B14 · 一道「不许手抄清单」的门，自己就是一份手抄清单 ⭐⭐⭐

这是 B5（观测域是枚举 ⇒ 差集恒非空）**最尖锐的自指形态**。

> 实证：为「测试夹具不许凭空造元素」加了一道元门禁，它内部**手抄了一份 id 清单**——
> 而抄的时候**恰恰漏掉了触发它诞生的那个 id**，于是**它在落地的那一个提交里就放过了自己的目标**。

⇒ **门的被检物必须从「活对象」上取**：运行时注册表的键、桩对象自己的 `Object.keys`、对象自己的字段名，
再与事实源比对。**手抄一份清单 = 再造一个与被检物不同源的拷贝，正是这类门要治的病**（同 D9）。

⚠️ 同族：**门的另一半接进去了却没通电**——反向检查的参数全仓一次都没传过，那半检查在所有接入点恒不报错。
⇒ 门加完要问一句：**「它的每个分支，今天真的有人喂过数据吗？」**（同 A9）

### B15 · 判据与被测实现共用同一个定义 ⇒ 门禁永远绿 ⭐⭐⭐

> 实证（`case-55` @ fm-agent-demo，2026-09-04）：运行时给可点元素补 `tabindex` 用的是
> `querySelectorAll('div[onclick]')`，而 `el.onclick = fn` 是 **JS 属性赋值、不产生 HTML 属性**
> ⇒ **27 处 chip 全键盘不可达**；而 **a11y 门禁用的是同一个选择器**，所以一直绿。

⚠️ **它的前提断言 `total>0 && bad===0` 防住了「空集恒真」，防不住「集合定义本身是窄的」**
—— 这是 D4 正向基线的盲区：**基线证明了「有东西被检查」，没证明「该被检查的都在里面」。**

⭐ **判别口径**：门禁用选择器去**找到元素来操作** = 必要耦合，**错了会红**（安全）；
用它去**定义应被检查的全集** = 危险，**错了永远绿**。

⇒ **判据分层，后两层不与实现共享假设**：

| 层 | 做法 | 本例 |
|---|---|---|
| 同源 | 与实现同一个选择器 | `div[onclick]`（漏 27 处） |
| **换维度** | 换一个与实现无关的观测量 | `cursor:pointer` —— 不问代码怎么绑的，问「**用户看着像可点的，键盘到不到**」 |
| **行为** | 运行时注入一个用该机制绑定的元素，看它补不补 | 注入 `el.onclick=fn` 的元素 |

**反向测试时只有「换维度」那条抓到了漏网的 chip** —— 印证 B4「真跑行为判据 0 次错判」。

### B16 · 一条规则有几条合法路径，判据就得认几条 ⭐⭐⭐

**判据惩罚正确实现，是新判据第一版最常见的失效。**

> 实证（`case-c0` @ agent-workbench，2026-09-04）：一天出现 **7 次，每一次都发生在新判据的第一版**。
> 形状：无条件要求「单向门有出路」（而某类门本就不需要）／要求逐行写豁免（而豁免写在文档级）／
> 只认「用户拍板」一条解除路径（而**证据升级也合法**）。

⇒ **写判据前先枚举这条规则的全部合法实现路径，每条路径都要有一个「必须绿」的正例。**

⚠️ **扩覆盖和不误伤必须同时验**（同 D3 的两个方向）：
> 同一会话把判据的集合从「DOM 标签名」换成「元素类型」以扩覆盖，
> 第一版**无条件要求表单控件绑定** ⇒ **当场 2 处假阳性**（`type=password` 的遮罩是浏览器原生行为，不需要 JS）。

⭐ **反方向的极端：一道什么都不干的门**（`case-c0` 实测）：
> 他写普查工具时第一版是 `_census(out): return out` —— **有文档、有注释、一行事不干，注释写得比真门还长**。当场撤掉。
> **自查问句：这段代码整个删掉，任何一次运行的输出会变吗？** 不会 ⇒ 它不是门，是装饰。

⭐ **本文自身的实录**：为 B15 写「条款标题格式」检查时，**第一版当场误红了一处正当的小节标题**
（`### 怎么挡住它（K9 …）`——标题正文里提到某条款 ID 是合法写法）。收窄成「ID 必须紧跟在 `#` 之后」才对。
**写这条规则的人，在写守它的判据时立刻犯了它。**

### B17 · 「有时能抓到」比「从来抓不到」更危险 ⭐⭐

一个**间歇性有效**的检查会制造**虚假信心** —— 人会依赖它，而它在关键的那次沉默。

> 实证（`case-05`）：一处模板字面量截断，`node --check` **碰巧**抓到了。
> 但它是否报错**取决于截断后的残码是不是合法语法** —— 实测两种形态，**一种 exit 0 一种 exit 1**。
> 「`node --check` 能挡住这类问题」这个结论，是从**走运的那一次**总结出来的。

⇒ **判断一个检查能不能依赖，看它的失效条件，不看它抓到过几次。**
问：**它在什么情况下会沉默？** 答不出来 ⇒ 还不能把它当防线。

⚠️ 与 A13（UNABLE 常态化）、B7（误红被加豁免）同族但机理不同：
那两条是**噪声太多导致被绕过**，这一条是**沉默不可预测导致被误信**。

⇒ 正确做法：把间歇性检查**降级为辅助信号**，另立一条**确定性判据**守同一件事。

### B18 · 承诺型判据要写成「文案在 ⇒ 能力必须在」 ⭐⭐

> 实证（`case-55`）：产品文案说「可逐项或一键清除」，而**抽掉 6 个清除入口后 32 道门禁全绿**。

判据不能只写「入口数 ≥ 6」——那样**新增/改名入口就会误红**，而且守不住真问题。
正确形状是**条件式**：

```
文案在  ⇒ 能力必须在（逐项 + 一键各至少一条可达路径）
文案不在 ⇒ 该条 N/A
```

⭐ **否则它会奖励最坏的修法：删掉承诺文案，门就绿了。**

⚠️ 这类判据的 N/A 分支要按 **A15** 处理：**是 NOT-RUN（该条不适用），不是 UNABLE**。

### B19 · 判据必须驱动**生产的那一份**，不是自己声明的同名拷贝 ⭐⭐⭐

**比 B4 的「断言源码长相」更坏的一种**：判据**确实在跑行为**——只是跑的是它自己在测试文件里
重新声明的那份实现。它读起来像验过了生产代码，实际与生产代码**完全脱钩**。

实测（`example-app` R43-1，CRITICAL）：判据里写着

```js
// 行为验证：okName 真的挡得住路径穿越（不是只写了一行）
const okName = (n) => /^[a-z0-9][a-z0-9-]*$/.test(String(n || ''));   // ← 判据自己声明的
for (const bad of ['../../etc', '/etc/passwd', 'a/../../b']) assert.strictEqual(okName(bad), false);
```

把**生产侧**改成 `.test(String(n||'').split('/').pop())`（一次自然的 validate-vs-use 错配重构，
**正则字面量逐字节不变**）⇒ **全套 51 道门零拦截**；沙箱真跑
`plugin:remove(null,'../../victima')` 从 `{ok:false}` 变 `{ok:true}`，目录被删，
且回收站路径同样被穿越 ⇒「移进回收站所以可恢复」这个两轮专门修过的承诺**同时失效**。

⭐ **成因是拷贝按文件边界藏起来了**：同一条正则在 4 个产品文件各写一遍，判据里是第 5 份。
上一轮已经把**同一文件内**的 4 处合并成一个函数，**跨文件的 4 份却看不见**。

**三条做法**：
1. 把规则抽成**不依赖重型环境的模块**（这条正则被特意抽进一个不 require electron 的文件，
   判据才能真的把它跑起来）——**可测性是设计目标，不是事后运气**。
2. 判据 `require` 那个模块，**禁止在测试文件里重新声明同名实现**。
3. 配一条**元判据**：扫所有测试文件，任何 `const/function <被守的名字>` 声明都报错。
   （同一文件里对另一个函数已经做过「三份拷贝逐字相等」的检查——**手法就在那里，只是没对这条用**。）

⚠️ 反例要挑**能击穿它**的：见 D28。

### B20 · 一处改动可以让**全部**门禁同时失效 ⭐⭐⭐

门禁的数量给人一种错觉：49 道门，总不会一起坏。
**会的 —— 只要它们共用同一个「把结果变成非零退出码」的出口。**

实证（`example-app` 第 40 轮，CRITICAL）：测试入口那行
`if (failed.length) process.exit(1)` 被加了个 `&& !process.env.CI` ——
失败照数、结果照打印 `ok:false`、**进程退 0**，
于是 CI 认为一切正常，**49 道门同时降级为「只打印不拦截」**。
每一道门自己都还在正确工作，报告里也确实写着失败。

⭐ **这类旁路的特征**：改动**很小**、**读起来像在照顾环境差异**、
且**不会让任何一道门变红**（它取消的正是「变红」这个动作本身）。
代码评审时它长得像一行无害的兼容处理。

**三条做法**：
1. **单点出口要有自己的看守**：至少一道门断言「注入一条必失败的用例时，整套的退出码非零」。
   这道门必须**从进程外面**看退出码，不能在同一个进程里读变量。
2. **对退出路径的改动按最高等级评审**：`process.exit` / `exit code` / CI 条件分支，
   任何附加条件都要说明「它在什么情况下会吞掉失败」。
3. **环境变量不许出现在「要不要拦截」的判断里**。
   环境可以决定**跑不跑**某道门（跑不了就报 UNABLE），**不许决定失败要不要算数**（A1、A16）。

## C · 改动的副作用面 —— 改别人的代码时

<!-- IDX:C:BEGIN 组内索引：本组每条都必须在此出现（门禁校验闭世界）-->

**改动纪律** — **C1** 最小 diff · **C4** 清自己产生的孤儿，既有死代码只提不删 · **C5** 先红后绿

**抽取与搬迁** — **C2** 抽取 / 搬迁必然伴随三种静默损坏 · **C7** 「收窄」的动作里最容易夹带放宽

**修复的副作用** — **C3** 修复要覆盖「缺陷实际走的那条路」 · **C6** 修好一处，去问「同后果的另一条路补了吗」——尤其是主路径 · **C8** 修复可能比原病更重，而且同批修复会互相抵消 · **C9** 修复的「绕过口」常常是它自己新引入的输入面 · **C10** 你刚学到的那条经验，可能正是让这次修复失效的原因 · **C11** 补齐时「已经有一个的那处」最容易被跳过 · **C12** 同型普查不含你接下来要写的代码 · **C13** 传了隔离参数不等于隔离生效了

<!-- IDX:C:END -->

### C1 · 最小 diff

只碰必须碰的。不顺手优化邻近代码、不重构没坏的东西、风格跟随现有代码。

**检验标准：diff 里每一行都能追溯到那条需求或那条发现。** 做不到的行删掉。

> **姊妹纪律:结构性改动与行为改动不得混在同一步/同一提交**(Kent Beck「Tidy First」,借自 gstack plan-eng-review)。搬结构(重命名/抽取/移动/改签名)和改行为(逻辑/分支/返回值语义)混在一次 diff 里 ⇒ 分不清哪几行改了行为、哪几行只是挪位置,review 与 bisect 被噪声淹没,回退时无法只退其中一半。**先搬结构、跑测试仍绿、再改行为**,两步分开提交。这与「最小 diff」正交:最小 diff 管「别多碰」,这条管「碰的两类要分开」。

### C2 · 抽取 / 搬迁必然伴随三种静默损坏 ⭐

「把这段逻辑抽出来复用」是最被鼓励的重构，也是最容易静默损坏的操作。三种形态，**每次逐条核**：

1. **判据跟着代码搬走了，喂参数那行留在原地**——消费方仍指向旧位置，或悄悄退回文本匹配。
2. **语义静默收窄**——内联时会做的某个检查，抽出去之后某个分支不再做了。
3. **上报了不等于收下了**——新字段一路加到发送端，接收端把它丢了。

> 实证：某仓库一个会话内这三种各复发 3 次以上，且**每次都是在刚刚批评完同一形状之后**。

**自检问句**：抽出去之前，这段代码的**每一个调用点**分别做了什么？抽出去之后还都做吗？

### C3 · 修复要覆盖「缺陷实际走的那条路」 ⭐

最容易的失败不是修错，是**修在了另一条路上**。

> 实证：崩塌保护写好了，但它只从「运行期裁决文件」读上一轮——而这个缺陷的真实场景（首次运行 / 全新安装）恰恰是那个文件**不存在**，于是保护静默关闭。

**修完必问**：触发这个缺陷的**那个具体状态**，现在走进修复代码会怎样？把那个状态**当夹具真跑一遍**，而不是跑一个你顺手造的、更方便的状态。

⚠️ 同族：**判据也会守在另一条路上**——测试用例在碰到被测逻辑之前就返回了，于是删掉整条校验照样全绿。

### C4 · 清自己产生的孤儿，既有死代码只提不删

本次改动产生的不再使用的 import / 变量 / 函数要清掉。**既有死代码在报告里提一句，不删**——删它属于另一个改动，会污染这次的 diff（违反 C1）。

### C5 · 先红后绿

修之前先有一个能复现该缺陷的失败断言，**确认它红的原因正是这个缺陷**；修完转绿。

「改完看着好了」不算修好——你不知道它本来是不是就好的，也不知道下次回归时谁来拦。


### C6 · 修好一处，去问「同后果的另一条路补了吗」——尤其是主路径 ⭐

> 实证一：「文档被截断时不许说『没有相关内容』」这条修复，只加在了**检索没过下限**那条路上；而**模型判定 found=false** 才是配置正常时的**主路径**，那条路上一个字的提醒都没有。
> 实证二：加固了某个原型链命中，而唯一的生产调用方**前一行就把入参收敛成四个字面量**——那条路根本不可达；真正可达的同后果缺陷当时没被处理。
> **实证三（外部代码，2026-09-05）——病因就写在紧挨着的注释里**：某采集管线里，
> 「分层兜底」那一步的 `2>/dev/null` 造成过一次事故（一个页面把脚本打崩、stderr 被吞、
> **46 个失败渠道整天没兜底且无人发现**），事后在该行下方留了详尽注释记录教训。
> 而**紧挨着它上面那一步（全量采集）至今仍是 `2>/dev/null`** —— 同一份文件、相邻两行、
> 同样的吞错法、同样的后果。⇒ **写下教训的位置离未修的同型缺陷只有一行**，
> 这说明「记录教训」和「扫同型」是两个独立动作，前者做了不代表后者做过（同 **E6**）。

**做法**：报一条缺陷时把「**后果**」和「**触发路径**」分开写，然后问：**这个后果还有别的到达方式吗？**

- 「同一句话有多个产出点」的结构，修法是把它抽成**单一事实源**让所有产出点共用，而不是逐个去补。
- **不可达路径的加固无害，但它会让人以为这个后果已经解决了。** 加固前先确认那条路在生产中可达。

⭐⭐ **「另一条路」的第三种形状：不是分支，是**数据流的另一端**
（第十四次外部实战，2026-09-05）。前两种都在**同一个决策点**附近（另一个 `elif`、另一条调用链），
这一种跨在**生产方 ↔ 消费方**之间：

> 某采集管线的 shell（消费方）上次刚被修好：逐步记录失败、有失败就 `exit 1`、
> 只有全成功才打印「完成」。做得很干净。
> 而它调用的采集脚本（**生产方**，897 行）**没有任何 `sys.exit`** ——
> 它自己早就算出了 `report_status`（完整版 / 残缺版）却只写进 metrics，退出码一律 0。
> ⇒ 消费方那套严密的判定，**收到的输入永远是 0**。修好的那一半，被没修的那一半架空了。

⇒ 识别它要问的不是「还有别的分支吗」，而是：
> **「这条信息要经过几手才到达做决定的那个人？每一手都保留它了吗？」**

⚠️ 顺带一个容易做错的修法：这里**不该**让「结果不完整」去决定退出码 ——
那个判据要求几十个渠道**全部**成功，实践中几乎必然不满足 ⇒ 管线天天变红，
而**会随机变红的门禁只会训练人忽略红色**（同 **B7**、**A13**）。
> **分层本身是对的：退出码表达「这一步执行完了」，产物表达「结果质量」。**
> 错的是终点那句话把两者混成了一句「完成」。**要修的是措辞，不是退出码。**


### C7 · 「收窄」的动作里最容易夹带放宽 ⭐⭐

把一条判据/豁免/匹配收窄时，最容易在同一个改动里悄悄放宽另一个维度。

> 实证：把豁免从「整行子串匹配」收窄成「锚在第一个实参」时，**顺手把豁免键也缩短成 3–4 字符**（`dest`/`sig`），而比较仍是 `includes` ⇒ 任何**含**这几个字的标识符都被放行（`designPrefs`、`assignedState`、`sigStore`）。把上一版判据取出来跑同一用例 ⇒ **旧的抓得住**，所以这是净退化，不是历史遗留。

**做法**：**收窄之后，把上一版能抓住的用例重跑一遍。** 抓不住了就是退化——哪怕新写法在你关心的那个维度上更严。

### C8 · 修复可能比原病更重，而且同批修复会互相抵消 ⭐⭐⭐

> 实证：为了让「静默放行」不再和「零越界」同形，把降级诊断 `push` 进了 `breaches` 数组——**而调用方只看 `breaches.length`**，非空即判越界且不可重试。于是那台机器从「偶尔悄悄漏审」变成**每一次都硬失败**，还宣称「已回滚」。更隐蔽的是：这条修复让上游的 `agentOk` 恒假，**同一次提交里另一条修复的救援分支因此结构性不可达**——两条修复彼此抵消，修好一条另一条才开始生效。

**三条**：

1. **诊断不是业务数据**——别塞进那个「消费方按 `length` / 非空判定」的集合里。挂成不可枚举的标记，由调用方如实说出来。
2. **改一个返回值/状态的语义之前，先列出它的全部消费方**，逐个问「这个新值在这里会被读成什么」（同 A11、I3）。
3. **同一次提交里有多条修复时，逐对问「它们会不会互相抵消」**——尤其是当一条改了另一条依赖的状态时。

### C9 · 修复的「绕过口」常常是它自己新引入的输入面 ⭐⭐⭐

> 实证：上一轮把「拿不到数就显示 0」改成「显示 —」，占位文案取自组件的 `empty`/`fallback` 字段——
> 而**生成模型有很强的倾向给数值字段写 `"fallback": "0"`**（看着整齐）。
> 于是「没测到」又变回「测到的 0」，**只不过这次谎是模型写的、内核照办**。
> 同轮的变体：兜底函数收了个 `hint` 参数，调用点把用户写的值当 hint 传进去，**谎从 hint 那条路绕过了刚加的净化**。

⇒ 修完一条「**不许出现 X**」之后，立刻问：**「X 还能从哪条路进来？」**

**尤其是那些「由被约束方自己提供」的字段**：占位文案、标题、单位、fallback、示例数据、hint。
**你刚写进文档的明文契约——执行方不执行就不算数。**

### C10 · 你**刚学到**的那条经验，可能正是让这次修复失效的原因 ⭐⭐⭐

同一个仓库里刚踩过的坑，会变成下一次改动时最顺手的「模式」。
**而经验带着它的适用条件，模式不带。**

实证（`example-app` 第 39 轮，最尖锐的一次）：给子进程退出加「先 `SIGTERM`、800ms 后 `SIGKILL`」的升级，
并顺手给那个定时器加了 `unref()` —— 理由是「本仓库刚踩过定时器活引用的坑」。
而这条在别处正确的经验，**在这里正好反了**：
唯一调用方是退出钩子，其后事件循环随即结束，
`unref()` 让这个定时器**不再阻止进程退出** ⇒ **`SIGKILL` 那一步永远不会发生**。
修复的两半互相抵消，而代码读起来两半都对。

⭐ **判别口径**：一条经验是「**在什么条件下**成立」的，不是「在这个仓库里成立」的。
把它搬到新位置时，**逐条重述它依赖的条件，再看这些条件在新位置成不成立** ——
尤其是「谁调用它」「调用之后还会发生什么」这两条。

**两条做法**：
1. 凡是**为了呼应另一处经验**而加的代码，注释里写清它依赖的前提；
   前提不成立时这行就是负作用（与 E 组的「注释必须是可证伪的断言」同源）。
2. 修复由两半组成时（升级 + 兜底、重试 + 超时、加锁 + 释放），
   **必须构造一次「让第二半真的执行」的用例**。两半都写了不等于两半都会跑（D27）。

### C11 · 做「补齐」类改动时，**已经有一个的那处最容易被跳过** —— 而它常常是最重要的那处 ⭐⭐⭐

普查补齐（给每个步骤加检查、给每个入口加校验、给每个写操作加幂等键）有一个天然的坑：
**你遍历的全集，很容易变成「看起来缺的那些」，而不是「全部」。**
已经有点什么的那一处会被眼睛自动跳过 —— 它长得像「已经做过了」。

⭐ **而它恰恰最可能是最重要的那处**：它之所以已经有东西，通常是因为**那里出过事**。
出过事 ⇒ 有人打过补丁 ⇒ 补丁往往只解决了当时那个症状，不是这次要补齐的那件事。

实证（本文自身，2026-09-05）：给一条 9 步采集管线补「步骤失败必须进台账并影响退出码」，
我补了 8 步 —— **唯独漏掉第 4 步「分层兜底」**。
理由是它**原本就有** `fb_rc=${PIPESTATUS[0]}` 和一句告警，看起来已经做过了。
而它的检查只**打印**，既不进台账也不影响退出码；
更要命的是，那一步正是历史上出过「**46 个失败渠道整天没兜底且无人发现**」事故的那一步 ——
**全管线里最该被拦住的一步，恰恰是补齐后唯一没被拦住的。**
> 这条是把[「提交前自检」第 7 问](../SKILL.md)真的跑了一遍才发现的 ——
> 静态读 diff 看不出来，因为那一处的 diff 是空的。

**三条做法**：
1. **全集先枚举出来再动手**：把「全部对象」列成清单（步骤名 / 入口名 / 写操作名），
   逐个标记「补了 / 本来就有 / 确认不需要」，**不许有未标记项**（同 **B10** 闭世界对账）。
2. **「本来就有」的那些要单独验一遍**：它现有的东西**满足这次补齐的标准吗**？
   常见落差是「打印了但没有落到退出码」「记了日志但没有断言」「校验了但只在一条路上」。
3. 补齐完成后，**对每一类对象各注入一次失败**，确认全部被接住 ——
   包括那些「本来就有」的（**D3** 两向验证，此处即差集的正例）。

### C12 · 同型普查的全集里，**不包含你接下来要写的代码** ⭐⭐⭐

修完一类缺陷，你会去做同型普查（**C6**）—— 那次普查扫的是**既有代码**。
而接下来那半小时里，你正在写的新文件**不在任何普查的范围内**，
偏偏它是**用修复之前的手感写出来的**：注意力刚被那个缺陷占满，肌肉记忆却还没更新。

⭐ **实证（本文自身，2026-09-05，一天内三次，全是「刚修完就复发」）**：

| 刚修完的那类 | 转头在哪复发 |
|---|---|
| 别人脚本里的 `2>/dev/null` 吞错 | 我自己给它加的截断检查里写了 `[ … ] 2>/dev/null` |
| `precommit-guard.sh` 的固定临时路径 | 一轮后新写的 `reverse-test.sh` 里写死 `/tmp/revtest-gate.out` |
| 告警文案里 `$VAR` 紧跟全角括号 | 我为修它而加的那行注释/代码里又写了一次 `$rc（` |

三次都不是「不知道」，是**知道之后写的**。

**两条做法**：
1. **修完一类，立刻把它变成判据**（**E6**：修复 + 门禁才防回退）——
   判据不区分「既有代码」和「你五分钟后写的代码」，而人的注意力区分。
   这是唯一能覆盖「尚不存在的代码」的手段。
2. 判据一时做不出来的，就在**本次会话内**把它列进「每写一个新文件先过一遍」的短清单，
   并在收尾时**对本次新增的文件单独再扫一遍**（普查的全集要包含本次自己的产出）。

⚠️ 与 **C11** 一起，普查会漏掉的是**三个方向**（`case-05` 补的第三个）：

| 漏掉的 | 为什么看不见 |
|---|---|
| **已经有一个的那处**（C11） | 它长得像「已经做过了」，而它已有的东西通常只解决了当年那个症状 |
| **还不存在的那处**（C12） | 它在你普查之后才被你自己写出来 |
| **判据够不着的那处**（B6 的量程） | 你用来普查的那把尺子本身覆盖不全 —— **反例没红，不等于规则没问题，也可能是尺子量程盖不住** |

> 实证（`case-05`）：建一道「模板必须被读」的门时，第一版判据扫的是报错措辞，
> 逐条推演后只覆盖 5 处缺陷里的 2 处 —— 它跑起来是绿的，而绿的原因是够不着。

**三个方向合起来才是「我已经全扫过了」**；少一个，这句话就是假的。

### C13 · **传了隔离参数**不等于**隔离生效了** —— 要有 fail-closed 的前置检查 ⭐⭐⭐

任何「把破坏性操作关进沙箱」的测试，都依赖一个前提：那个隔离参数**真的**改变了程序的落点。
`--user-data-dir` / `EXAMPLE_APP_ROOT` / `HOME=` / `--prefix` / 容器挂载 / `chroot` ——
它们**通常**生效，而「通常」在一次不生效时的代价是**写坏用户的真实数据**。

⇒ **在做任何破坏性动作之前，让程序自己报出它算出来的那个路径，并断言它落在你的沙箱里；
不满足就立刻退出，绝不继续。**

实测（`example-app` N67）：被测的是打包应用的启动脚本 `boot.js`，它
`app.setName('example-app')` 之后取 `app.getPath('userData')`，而它的 `refreshCode()`
是**先 `rmSync` 再拷贝** —— 隔离一旦没生效，就会拿合成 bundle 覆盖用户真实的
`kernel/ / cli/ / docs/`（本机实测该目录**确实存在**）。
⇒ 探针的入口**不是被测脚本本身**，而是一个包装器：先核对 userData 落在临时目录内，
不满足就 `emit + quit`，**绝不 require 被测脚本**。

⭐ **这道前置在第一次运行时就拦下了自己** —— 原因良性（macOS `/var` 是 `/private/var` 的软链，
`getPath` 返回真实路径而我传的是符号链接路径），但它 **fail-closed**，方向是对的。
两边取 `realpath` 后通过。**宁可被误拦一次，也不能放过一次。**

⚠️ 隔离「大体生效」也要查干净：同一次实测里，包装器为「忠实模拟」多调了一次
`app.setName(...)`，那句让 Chromium 往**用户真实目录**写了 GPUCache / Session Storage
（要害的 `workspace/` 未被触碰）。**一道判据不该往用户目录里写任何东西** ——
删掉那句后实测该目录 mtime 不再变化。

**验收方式**：跑完之后，对沙箱**外**那个真实目录做一次 mtime / 内容比对，
并把结果写进记录。没比对过，就只是「我以为它没被碰」。

### D1 · 测试夹具必须来自生产路径 ⭐

手工构造的对象字面量，要能在生产代码里找到**「谁产出这个形状」**。找不到 ⇒ 你的断言在测一个不存在的世界。

> 实证：某同步模块的 `stamp()` 只认 `updatedAt||ts||time`，而条目真正写的是 `updated`——两台设备改同一条时旧版覆盖新版并回推云端。守它的断言喂的是 `{id, text, updatedAt}`，而**整个仓库没有任何代码产生这个形状**。这条藏了 36 轮才被抓到。

**根治写法**：让测试**用生产路径产出的数据**当输入（先调页面的新建方法拿到条目，再喂给被测函数），形状就不可能对不上。

⚠️ 这类缺陷**覆盖率、变异测试、覆盖面探测全都看不见**——那三样只问「这行代码跑到了吗」，不问「跑它的那个输入像不像真的」。

⭐ **更彻底的形态：判据夹具描述的世界，可能和产品真实的世界不是一回事。**
> 实证：产品 HTML 里的一个元素在某次重构里被删掉了，而 JS 引用留着；
> **5 个行为判据的夹具各自造了这个元素** ⇒ 判据一路绿灯，而那条「修复」**从未落到产品上，躺了两个月**。
> 更绕的是：我据此报了一个 HIGH 产品缺陷（「切到空场景会白屏」），而那**是夹具产物**——真实产品并不白屏。

⇒ 加一道**元门禁：夹具里出现的每一个 id / 类名 / 桥方法 / 清单字段，产品侧必须真有**（在 HTML 里，或在代码里被动态创建）。
至少查六项：**DOM id/class、插件清单形状、`window.*` 桥的方法集、服务字段表、持久化结构、CSS 类名**。
**判据可以对着一个不存在的世界永远绿着。**

> **适用条件(2026-09-09 codex 评审):夹具必须对应被测契约,「来自生产路径」只约束正常路径**。单元测试、属性测试、协议错误测试、安全测试经常要构造**生产路径不会主动产生、但系统边界必须处理**的输入(畸形包、注入载荷、边界值、协议以下故障——见 A2 测试孪生)。规则:**正常路径**至少含生产来源或生产序列化格式的样本;**异常/边界/攻击测试可人工构造**,但要写明它代表的**合同条件或攻击输入**(不是随手编一个)。

### D2 · 断言要有意义

不是「没抛异常就算过」。三种常见的假测试：

- 断言只写了「不抛异常」
- 断言是**照着实现的当前行为反向补的**（永远不会红）
- 改了实现之后顺手把断言调绿了

**自检问句**：把被测函数的返回值改掉一位，这条断言会红吗？

### D3 · 判据式两个方向都要有反例 ⭐

写完一个判别式，分别构造「**该真而判假**」与「**该假而判真**」的输入各一个。

> 实证：用 `sum(chunk.length) < text.length` 判「文档被截断」——chunk 是**重叠**的、`text.length` 含会被折叠的空白，于是**漏报**（真截断标 false）与**误报**（没截断被标截断）同时存在。而正确的信号 `chunks.length >= MAX_CHUNKS` 就在同一个函数里。

**只测了一个方向的判据式，另一个方向几乎总是错的。**

⭐ **验收要「零误杀」和「有命中」同时报，只报一侧等于没验收。**
> 实证：给「空白部件」加门禁，跑完绿基线报告「13 个真实部件零误杀」——看着很好，
> **但同一次运行里那个已知的空夹具也没被抓到**。判据数的是 `querySelectorAll('*')`，
> 而一个空容器仍会产出它自己那个元素 ⇒ 计数恒 ≥ 1，**门是哑的，却看着像在干活**。

⚠️ **「零误杀」这一侧尤其容易给人虚假的安心**——它读起来像好消息。

### D4 · 对比型断言必须先有正向基线

「两边一致」可能是**两个空集合在比较**。先证明载荷确实会被命中，再断言一致。

> 实证：给函数加可选参数前，测试喂的目录根本没被读，三条比较全在空集合上绿。

⚠️ **基线数字是一条需要跟着代码一起维护的断言**，不是一次性的常量。修改让命中数从 6 降到 5 时它报红——**这不是误报，是它在正常工作**。调整时把新数字的**含义**写进注释（「5 = 改成标记后剩下的真实写入点」），**而不是改成一个更松的阈值了事**。

⭐ **推广到「普查」：任何普查的输出里必须含一个已知阳性，否则量具作废**
（`case-05` 实测 + 本文同日独立复现，2026-09-05）

> 他查「哪些门禁提示语写了 `--help` 而自己拒绝 `--help`」，循环里写了
> `timeout 60 python3 …` —— **macOS 没有 GNU `timeout`** ⇒ 每次调用都没执行 ⇒
> 日志空 ⇒ grep 零命中 ⇒ **报「全部干净」**。
> 而他几分钟前刚亲手复现过其中一处 —— **救回来只因为结论与已知事实矛盾**。
> 去掉 timeout 并**强制带一个已知必然命中的对照组**后重跑：**命中 3 处**，
> 第一版会放走另外两处。
>
> 本文同日独立踩到同一个 `timeout` 坑（见 **D32** 的日报实证），
> 并在扫 `~/bin` 有无硬编码凭据时用上了这条：先拿一段**含假凭据的对照样本**过一遍模式，
> 确认「模式命中 2/5 类 ⇒ 有效」，再采信「45 个文件 0 命中」这个结论。
> **没有那一步，「0 命中」和「模式根本没跑」不可分辨。**

⇒ 固化成一句：**普查报「零命中」之前，先证明它抓得到你已知的那一个。**


### D5 · 否定型结论需要比肯定型更强的证据

「它没做」「它没红」和「**我没看到**」长得一模一样。常见误判：探针文件未 `git add` 所以工具看不见、匹配只命中了注释、被查对象用了另一个字段名。

### D6 · 变异测试三条

1. **默认在一次性副本 / 独立 worktree / 容器里变异，真实工作区零写入** —— 这样就**不要求先提交**
   （2026-09-10 外部评审收窄：强制提交 WIP 会污染历史，而且保护不了共享仓里别人的改动）。
   本 skill 的 `reverse-test.sh` 已是副本模式，**那个「变异态被 SIGKILL 卡住」的窗口从根上不存在**。
   ⛔ 只有在**确实无法隔离、必须原地变异**时，才回退到旧要求：已知干净基线 + 唯一锚点 +
   可验证的恢复副本 + 退出后精确 diff 核对（`git checkout <BASE> -- <file>` 会连带抹掉该文件
   **尚未提交**的改动，所以那条路才需要「先提交」）。**不许用宽范围 checkout 恢复。**
2. **确认变异真的落到目标位置**——同一模式常有多份副本，「替换了第一处」会让你把好判据判成坏的。替换后再确认落点。
3. **反例要真的制造出那个缺口**——「受害对象本来就满足条件」的反例两边恒等，把判据改回错误实现照样绿。

### D7 · 重载下的红先复现再采信

整机负载会制造假红，而**摘要层分辨不出来**。

> 实证：一次变异测试报「3 条判据变红」，逐条翻输出才发现只有 1 条是变异抓到的——另两条一条在做真实 DNS 查询、一条有 300s 墙钟，都是并发进程导致（15 分钟 load 均值 8.21，单独跑只要 0 秒）。

**做法**：runner 必须把「环境不洁」与「断言失败」在**结果结构里**分开（`timedOut` / `killedBySignal` 字段），不能只在正文写一行字。

### D8 · 非 ASCII 源码不用 `perl -pi` 改写

中文注释的仓库里 `perl -pi` 的风险**不是响亮报错，是无声损坏**（2026-09-15 实测修正——此前这里写「会因编码报错」，
本机默认环境实测：ASCII 与中文模式的替换都 rc=0 正常完成，**默认的 perl 是字节导向的，根本不报错**；
只有显式置入解码模式（`-C` / `PERL_UNICODE` / `use utf8`）才可能报 Malformed UTF-8）。
真实风险：字节级模式（如 `s/.//`）会**切开多字节字符产出乱码**——没有任何报错，坏的是文件（同 A6：错的机制描述会让人去查错的地方）。

⚠️ **要件是编码契约，不是工具品牌**（2026-09-10 外部评审收窄）：perl 配好编码契约也能用；
而下面紧接着的反例说明 **python 一样会写坏文件**。四条缺一不可，满足了用什么工具都行：
**①显式声明输入/输出编码**（别让进程 locale 决定）**②锚点唯一**（先断言出现次数为 1 再替换）
**③原子写入** **④写后验证**（字节级扫控制字符 + 让目标文件的解析器/语法检查跑一遍）。
本文的默认选择仍是 `python3` + `encoding='utf-8'`，因为它把 ① 写在了明面上。
⚠️ **换成 python 只解决了一半 —— 另一半是「你写的替换串自己被转义吃掉」**。
> 实证（本文自身，2026-09-05）：用 python **普通字符串**往门禁里写一段带正则的 shell 代码，
> 其中正则的词边界 `\b` 被 python 解释成**退格字符 0x08** 写进了文件。
> 后果：两个词边界消失、判据的正则语义被静默改变，
> 而**退格字符在编辑器、`cat`、`grep` 输出里完全看不见** —— 从外面看那行代码一切正常。
> 它是被那道判据的**正向基线**（命中数从 3 掉到 1 ⇒ 报 UNABLE）抓出来的，不是被眼睛看出来的。
>
> 同日第二次：为了把上面这段写进文档，我的编辑脚本里出现了 `r'''`，
> **提前闭合了外层的三引号** —— 同一个坑，换了个形状，当场再犯一次。

**三条做法**：
1. 含反斜杠的替换串一律用 **raw 字符串**或 `chr(92)` 拼接；**含引号的长文本走文件**，不要内联。
2. 改写完**立刻回读并断言新内容确实是你想要的形状**（不只是「替换发生了」）。
3. **给判据配正向基线** —— 上面那处如果没有基线断言，它会直接报 PASS：
   一把被悄悄改坏的尺子量出来的「合格」。这条比前两条都重要（同 **D4**）。



### D9 · 判据必须消费生产代码本身，不能消费它的副本 ⭐⭐⭐

> 实证（记录者称为「本会话最贵的一次」）：生产代码在主进程文件里算 `sourceChars = raw.length > cap ? raw.length : undefined`；该文件需要 electron、判据驱动不了它，于是判据在自己内部**照抄了一遍这行逻辑**再去断言。结果：把生产代码改回缺陷写法，**判据纹丝不动 EXIT=0**——它测的一直是它自己那份副本。

遇到「被测逻辑困在一个加载不了的模块里」，正确解法是**把那段逻辑抽成一个不需要重依赖的纯函数**，生产与判据共用它。**抄一份到判据里等于没测。**

⚠️ 这条和 A4 是一体两面：**副本会和本体分叉，而判据永远绿。**

> **LLM-as-judge / 评分器时代的孪生:判官能看见「标准答案」就会照答案打分**(借自 agent-eval)。B15 是「判据与被测实现同源」,D9 是「判据消费的是副本不是本体」;这条是**判官与答案键同源**——LLM 评分器若在判定时读得到期望输出/用例断言值,它会向答案回归打分而非独立判断证据,评分虚高且察觉不到。做法:把判官的输入**限制为待判证据本身**(终答 + 工具序列),答案键对它不可见。

### D10 · 反向测试没红，先怀疑你测的是另一条路 ⭐⭐

> 实证：给「模型判定 found=false 时要带截断提醒」写行为判据：桩掉模型、真跑问答、断言提醒在。基线绿、变异……**也绿**。原因是那个问题过不了检索下限，请求走进了 `miss()` 分支——而 `miss()` 也会加同一句提醒，于是断言在**错误的路径上**照样通过，判据从头到尾没碰过它要守的那条路。

**行为判据必须钉住「我走的是哪条路」**：断言只有目标路径才有的字段、断言返回值正是桩返回的那个。

**写完先做一次「让目标路径失效」的变异——没红就说明你测的不是它。**

⚠️ **一个恒定返回成功的桩，会让它下游那道门结构上不可能开火。**
> 实证：为「查询规格无效」写反例时发现，夹具里的数据桩恒返回 `{ok:true}` ⇒ 无论反例怎么写，
> 那条失败分支都到不了——**门不是没抓到，是根本没被执行过**。

⇒ 写反例前先确认「**这条路径真的会被走到**」：**桩的返回值必须能覆盖失败侧**，否则你写的是一条永远绿的用例。
（与 D4「正向基线」是同一件事的两面：前提防的是空转的绿，桩的失败侧防的是**结构上不可达**。）

### D11 · 测试不要绑在外部服务的延迟上

一条判据真跑带外部模型的路径：30s + 60s×2，逼近 runner 的 300s 墙钟。**这种红既不是缺陷、也不可复现，最后的结局通常是这条判据被加豁免、再被删掉**（同 B7）。

**做法**：把超时做成**可注入**（生产不设 ⇒ 行为逐字不变；判据设一个极小值），让判据**确定性地**落到它真正要守的那条降级臂上。改完该判据从可能 300s 降到 1 秒。

⚠️ 附带收益：降级臂（没有 key / 没有本地模型）**往往正是新装用户的默认状态**，本来就更该被守住。

### D12 · 模块在加载时定死的东西，清缓存要连着清

`const ROOT = process.env.X ? ... : ...` 写在模块顶层 ⇒ 它在**第一次加载时**就固化了。测试里改了 env 再删被测模块的缓存**是不够的**——被测模块依赖的**那个读 env 的模块**也在缓存里，值仍是旧的，于是探针扫了一个空目录、拿到 `undefined`。

**清缓存要清整条依赖链上读 env 的那些；写完探针先验它在「应该为真」的输入上确实为真**（同 D4）。


### D13 · 报告里的「全绿」必须是可复现的绿 ⭐⭐

> 实证：多轮报告写下「全套 37/37」，而其中一个判据有 **37.5% 的概率随机变红**（单跑 8 次红 3 次）——那些「全绿」结论建立在走运的那几次上。

**第一顺位是把测试确定化**（能消掉随机性就别去采样它）。确实随机时再谈次数：

- **先说清你想检出多大的故障率 `p`、要多少把握 `c`**，次数至少 `ceil(log(1-c)/log(1-p))`。
  举例：想以 95% 把握发现 10% 的偶发，需要 **≈29 次**；跑 8 次只能覆盖到约 31% 的故障率。
- **整套 ≥3 次 / 新改的单个判据 ≥8 次**是本文的**经验下限**（够抓 37.5% 那种高频抖动），
  **不是统计保证**——2026-09-10 外部评审提醒：故障率 1% 时跑 8 次只有约 7.7% 的机会看到它。
- 报告里要带上：**跑了几次、失败几次、随机种子、机器负载**。没有这些，「全绿」不可复算。

**任何一次红都要先归因**（断言失败 / 超时 / 信号致死 / 整机负载）**再决定能不能说「绿」**。

⚠️ 发现自己此前报错了，要**明确更正**，不要在新报告里悄悄换成正确数字。

> **被测对象本身非确定时(真模型/并发/外部时序),功能判定要「多跑取最严 + 抖动单列」**(借自 agent-eval)。D13 治「可复现的绿」;这条治另一半:绿是**非确定的、被平均掩盖了失败**。规则:多跑 N 次,聚合**取最严**(任一次失败即该维失败,不许多数/平均掉),并把「抖动」当独立信号单列暴露。**单次运行的结论等于抛硬币**——它有 2/3 概率看不见偶发问题。(与 G4 的性能采样取最小值同源:非确定性只能让观测偏乐观,所以取最严的那次。)

### D14 · 写测试时被迫的每一次「只好绕一下」，都是一条生产缺陷线索 ⭐⭐

**「绕过」不是「修复」。**

> 实证：给一个 IPC 写行为探针时发现被测程序不认环境变量（用 `__dirname/..` 拼根），**只好把整棵树拷进临时目录**才能隔离。当时以为这只是「测试麻烦」——实际后果是**判据会去读写用户真实的运行期状态**。修掉被测代码之后，隔离从「拷贝整棵树」变成「设一个环境变量」，同时消除了污染风险。

**自检问句**：这是**测试**的问题，还是**被测代码**的问题？

**每一次变通都记下来**，回头逐条问一遍。可测试性差，通常是设计问题的症状而非测试的宿命。

### D15 · 判据的取值范围错了，不是代码错了

> 实证：`indexOf('\nasync function ', i)` 在「它之后没有同类声明」时找不到，**退回 `i + 9000` 的固定长度** ⇒ 切进了后面的代码，把另一个函数里的合法写法算成违规。

- **切函数体不要用固定字符窗口**，用**结束锚点**（下一个同类声明的起点，或该函数尾部一句独有的文本）。
- 大括号配平也不行（字符串/正则里的括号会干扰）。
- 判断「守卫在不在某处附近」时，窗口要**跳过注释与空行**再看紧随的两条代码——守卫常隔着几行解释性注释。

**报红之前先问一句：是被测的东西错了，还是我取的那段根本不是它？**

### D16 · 扫源码的判据会被它要守的那段代码的注释喂饱 ⭐⭐

> 实证：写元判据扫某个调用的实参形状，第一版直接在源码上跑——**命中了上一轮写在注释里的那个反例**（那条注释正是在解释「不许这么写」）。

**同理**：数标识符出现次数、检查某个字面量在不在、确认某个词有没有出现，**全都会被注释、字符串、甚至你解释这条判据本身的那句注释满足**。

**做法**：扫源码前**先剥注释行**；更强的做法是**只在目标函数体内扫**（配合 D15 的结束锚点）。

⚠️ 如果一个仓库里已经有三处各写各的剥注释、能力还不一致（有的只剥 `//`、有的连 `*` 一起剥、都不处理行尾与块注释），**那本身就是个信号**——至少要知道自己用的是哪一档。

⭐ **「看紧邻几行」这类判据还有第二个坑：只认一种写法。**
> 实证：判据要求「每个 `prompt()` 的返回值必须在紧邻几行内判过 null」，第一版**误红三处正确代码**，
> 两个原因各占一半：①窗口只看 4 行，而其中一处的检查被一段**解释性注释**推到了第 6 行；
> ②正则只认 `== null`，而 `if (x != null) { … }` 这种**反过来写**同样正确。

⇒ 凡「附近有没有某个检查」这类判据：**先过滤注释行再看**，并把**等价写法**（`!=` / `!==` / 早返回 / 卫语句）一并纳入。

⚠️ **剥注释和锚点会互相干掉**（`case-e9` 实测）：判据的**锚点本身被写在了注释里**，而判据又剥注释
⇒ `indexOf` 恒 `-1`。**「找不到要守的东西」被当成了「没问题」**——这正是 A1 把 UNABLE 混进 PASS 的形态。
⇒ **锚点找不到时必须判 UNABLE 并报出来**，不许静默跳过。

⭐ **同族的算术陷阱**（`example-app` R43-1 实测）：`assert.ok(src.indexOf(A) < src.indexOf(B))`
用来断言「A 定义在 B 之前」。把 A 抽成模块后该串消失 ⇒ `indexOf` 返回 **-1**，
而 **`-1 < 正数` 恒真** ⇒ 这条断言变成**恒绿且什么都没验**，输出与「一切正常」完全一样。
⇒ 凡是拿 `indexOf` / `search` / `match` 的结果参与比较的，**必须先断言它 >= 0（或非 null）**。

### D17 · 把「多条路」压成「一根串」，任何一条路的失效都能被另一条顶包 ⭐⭐⭐

> 实证：断言 `!/\b0\b/.test(全部输出拼成的串)` 看起来很严——而**同时**让两条路失效时，
> 两处输出会**粘连**（`"0"` 与 `"0 items"` 粘成 `"00"`），词边界不成立 ⇒ 判据绿。
> **只坏一条抓得住，同时坏两条抓不住**——而真实回归从来不是一条一条来的。
> 正向断言 `/—/.test(串)` 得同一种病：任何一处满足即过，于是「某一路的诚实占位被删掉」被别路顶包。

⇒ **每条路单独渲染、单独断言**；**断言的作用域要和它守护的那件事一样窄。**

⚠️ 修这类问题有**硬顺序**：两处缺陷会互相掩盖——只收紧断言不修地基会当场误红正当重构，只修地基不收紧断言仍然假绿。

### D18 · 一个洞能同时封死「发现它」和「守住它」两条路 ⭐⭐

> 实证：测试垫片的 `innerHTML` 写入器是空操作。一方面让「多帧文本累加」类缺陷照绿（**发现不了**），
> 另一方面让任何依赖它的正确代码恒红（**守不住**）——于是「只修垫片」原假绿仍全绿，
> 「只写判据」正确代码恒红，**两条路各自走都走不通，只有同时做才行**。这解释了它为什么能活 31 轮。

⇒ 遇到一个**长期没被发现**的缺陷，先问：**「是不是有什么东西同时挡住了发现它和守住它？」**

**那个东西通常在测试基础设施里，而不是在产品代码里。**

### D19 · 「测试红了」不等于「判据检出了缺陷」 ⭐⭐⭐

> 实证：逐门普查时唯二的两次红**都不是检出**——一次是性能基线擦着阈值过（140ms vs 120ms），
> 一次是外部服务初始化超时（idle 复测 3/3、10/10 全过）。
> **它们和真检出在 `failed=1` 那一行长得一模一样**——只看这一行，会把 5 道无人看守的门记成「已覆盖」。

反过来同样成立：**一次抖动的红，会让你误以为某条判据守住了那段代码。**

> 实证二（`case-55`，同族第 11 例）：给性能门做「注入 O(n²) 必须变红」的验证，
> 第一次**只拿到「退出码非零」却取不到曲线行** —— **差点把门禁崩溃当成判据抓到**。
> 重跑读完整日志才确认红的是「dedup 规模≈线性」那条断言（倍率 23.8× > 20×）。

⇒ 判读变异/普查结果时，**红必须验到「是哪条断言、为什么红」**，不是只看退出码；
含时间阈值或外部依赖的用例，**复测 3 次以上**再下结论（同 D7、D13）。

⚠️ **追溯后果**：凡是靠「全套红不红」下过的结论，**都要重读一遍**。

> 实证三（2026-09-05，两个会话同日各撞一次）：对方写了一组新判据，跑变异时看到红就以为生效了 ——
> **实际报红的是另一道元门禁在告发它那组断言本身**（那 6 条断言把双参数写成单参数，
> 条件被语言静默丢弃，跑起来「全部通过 27 项」什么都没验）。
>
> ⇒ **「谁在报红」和「有没有红」一样重要**。读红时先确认**报红的是不是你要验的那道门**。

### D20 · 防假绿的门，自己可能从来没有过正例 ⭐⭐⭐

> 实证：把校验期的每一道门**整段删掉**再跑全套 —— **10 道里 9 道全绿**。
> 原因很朴素：正例集里的样本全都合规，那些门的**命中集恒空**，**它们从上线那天起就没开过火**。
> **一道从没开过火的门，和一道被删掉的门，在测试结果里完全一样。**

⇒ **每道门必须有一个「只有它能接住」的独占反例，并断言是哪道门抓的。**
否则一个反例被别的门顺手接住，那道门等于仍没被测过（实测就有一对 1-of-2 冗余的门，单拆任一仍绿）。

⚠️ **做这件事时先自查方法**：把门的**文案**改掉再跑，5/5 全红——**但红的是「文案白名单」那条判据，
是「文本变了」冒充「行为被守住」**。必须**整段删除**才看得见真相。

⭐ **「门禁能红」与「门禁对正确输入必须绿」是两个方向，承重的是后者**（`case-05` 实测）：
> 他给 22 道门禁建「门禁 ↔ 模板」夹具对时的四个设计点，每个都是踩出来的：
> 1. **承重的断言是「填对了就必须绿」，不是「空模板红不红」** —— 空模板里全是占位符，
>    门禁**应该**红，那种红**没有信息量**。
> 2. 扫措辞只配做**辅助信号**（空模板上不许出现「整节缺失 / 解析不出」这类**定位器失败**）。
>    🚨 他第一版**只做了这一半**，反向测试当场证伪：退回一处真实修复它**纹丝不动**，
>    因为那处报的是「不是合法标识符」、不在词表里；逐条推演 5 处**只覆盖 2 处** ——
>    而他**差点带着「它替代了人工审计」这个说法交付**。
> 3. ⭐ **夹具必须忠实于模板的结构，不能只做到「让门禁通过」** —— 更普适的说法是
>    **「遵守的样本」必须能独立于判据成立**：它要是「照规范真写出来的东西」，
>    不是「刚好让判据匹配上的东西」。后者在判据一改时**静默失效**，而你不会收到任何提示。 —— 他的夹具把官方模板里的
>    一张映射表写成了散文，门禁于是不红；补上那张表才红。
> 4. ⭐ **期望退出码不是一律 0**（见 A15）。

⭐ **「能变红」与「在真实产物上真的检查过东西」是两件事**（`case-c0` 实测）：
> 他做了一个**命中集普查**（`census`）——每一类判据**在真实产物上到底检查了多少个东西**。
> 17 类可计数的**恒空 0 类**（如「105 个按钮」「70 处文案」「138 条教训」这三类计数 —— 原文用的是它自己那套编号，此处刻意改写成中文描述，避免与本文条款号撞形）。
> **D20 问「它开过火没有」用的是删门；普查问的是「它在真货上碰到过几个东西」——后者更直接。**
⚠️ **普查只报不判**：命中集为 0 **有时是合法的**（那一类真的不存在），做成阻断门会立刻产生假阳性（同 B16）。

⭐ **一次「假收敛被当场打破」的外部验证**（`case-55` @ fm-agent，本方法最硬的一次）：
> 他此前用**静态审查**跑到「连续两轮零发现 ＝ 收敛」。换成**对产品代码做真实契约变异**后，
> **收敛当场被打破：连续 8 轮都有发现（2/1/2/4/7/3/2/2），共补上 25 处无人守的契约**，
> 某道门的断言从 21 条涨到 **73 条**。
⇒ 同 **H8**：**收敛的判据不能是「本轮没发现」，要是「换一个不自我指涉的问法也没发现」。**

⭐ **更大样本的同期复现**（`case-54` @ 某验证项目）：做了 **52 条变异，34 条全套门禁无一抓到（约 65%）**，
与本条 9/10 的量级一致。他的三条补充各堵一个本条原来没写的洞：

1. **每批必须放对照组**（一条**预期会被抓住**的变异）。5 个对照组里 **2 个给出意外结果**：
   一个揭示预测错了；另一个揭示**变异装置自己只跑了 21 道门禁里的 15 道**——
   它少跑 6 道而**输出读起来完全正常**，导致整天的结果被报成「全套无一抓到」，并推翻一条已发布结论。
   **对照组是唯一能发现「装置本身坏了」的东西**（同 A9、D19）。

   ⚠️ **对照组必须真的是「改造前」**（`example-app` 实测栽过）：我做「改造前 / 改造后」A/B 时，
   「改造前」的快照是在**第一个、也是最关键的那处改造完成之后**才拍的 ⇒ 那一臂无效，
   两边跑出完全一样的数字，差点让我得出「这轮改造没有收益」的结论。
   **拍快照的时刻要写下来，并与第一处改动的时刻比对。**
2. 每条「全套漏掉」都要**先实测那个变异真的改变了行为**（见 D21）。
3. 「没红」时**先怀疑变异有没有生效，再怀疑门禁**（见 D21）。

### D21 · 变异存活有两种成因，不区分会各错一半 ⭐⭐⭐

一条变异跑完门禁**没红**，只有两种可能：

| 成因 | 真相 | 不区分的后果 |
|---|---|---|
| **门禁瞎了** | 缺口造出来了，没人接住 | 漏报——放过一道瞎门禁 |
| **缺口没造出来** | 变异根本没改变行为 | 误报——**冤枉一道好门禁** |

⇒ **顺序固定：先确认变异真的改变了被测行为，再看门禁反应。**
⭐ **实际是三种成因** —— 第三种最容易被误判成第一种（`case-05` 实测，2026-09-05）：

| 成因 | 现象 | 误判成什么 |
|---|---|---|
| 门禁瞎了 | 缺口造出来了，没人接住 | —— |
| 缺口没造出来 | 变异没改变行为 | 冤枉一道好门禁 |
| **⭐ 判据承重，但另一条兜底路径接住了** | 变异确实生效，行为却没变 | **看起来和「门禁瞎了」一模一样** |

> 实证：一个「判端形态」的函数有两个来源互为兜底（URL 的 `end=` 参数、`innerWidth<=560`）。
> **只改视口** ⇒ 9 条路径全走通、没红；**只去掉 URL 参数** ⇒ 9 条全走通、没红；
> **两个同时打掉** ⇒ 走通 7 断掉 2，才红。
> 单点变异永远红不了，而单看结果，它和「这道门不承重」不可分辨。
>
> ⇒ 修法不是接受「它测不出来」，而是让**每一条兜底路径各有一个只有它能接住的用例**
> （把两个来源分开渲染、各立一条断言），任一半失效就立刻红，不必等双重变异。
> ⇒ **统计「变异后没红的门」时，要多记一列「它有几条冗余路径」** ——
> 否则冗余度高的门会被系统性地误判成「判据不承重」。


> 实证一（`case-b8`）：一道判据花了**三次变异**才造出真缺口——前两次分别被**运行时回填**与**静态属性**掩盖，
> 差点把一道好门禁判成摆设。
> 实证二（`case-54`）：52 条变异里抓到 **4 条无效变异**，最典型的是「某判据的两种写法对现有配置表的
> 全部 4 个后端给出完全相同的结果」——**改了等于没改**。不验的话报出去的是假缺口。
> 实证三（`case-54`）：三次表象是「门禁漏了」，实际都是**测量动作没发生**
> （锚点缩进 12 vs 8 / 裸 `urllib` 未绑定 / `pass` 插在 `remove` 之前）。

**「反向测试没红」的排查顺序：变异生效了吗 → 走的是那条路吗（D10）→ 才轮到门禁。**

⚠️ **这个顺序不能只是建议，它是防循环论证的**（`case-b8` 的实操核心）：
必须**先拿到「变异改变了被测行为」的直接证据**（观察产物 / 日志 / 返回值），**拿到之后**再去看门禁。
**倒过来做的时候，人会不自觉地把「门禁没红」当成对变异有效性的旁证 —— 而那正好是循环论证。**

### D22 · 断言函数吞掉条件参数 —— 假断言不会让任何门禁变红 ⭐⭐

> 实证（`case-55`）：`const ok = m => console.log('✓ ' + m)` 是**单参**的，
> 而调用写成 `ok('元判据…', X.test(bad))` —— **第二个实参被 JS 静默丢弃**。
> 这条断言**什么都没验证，却永远打印 ✓**。全仓扫出 **7 条**（5 条是作者自己写的），
> 而这个坑在同仓另外两个文件里**栽过、修好过、还留了警示注释**（同 K10、I3）。
>
> ⭐ 最值得记的是反向测试结果：**给一个门禁种入一条假断言，它自己仍然 8/8 全绿。**

⚠️ 与 **D20 同族但机制不同，检测手段也不同**：

| | 机制 | 怎么检测 |
|---|---|---|
| **D20** | 命中**集合恒空**（门从没开过火） | **整段删掉**再跑，看红不红 |
| **D22** | **条件被丢弃**（断言恒真） | 比对断言函数的**形参数与实参数** |

⇒ 断言辅助函数一律**显式接收布尔并在内部判**；并加一条元判据扫「实参数 > 形参数」的调用点。

### D23 · 累计量的判据，跑在累计完成之前 ⭐⭐⭐

**机理**：判据断言的是一个**累加量**（已执行的断言条数、已扫描的文件数、已注册的处理器数），
而判据自己**是一条普通语句、受位置支配** —— 它一旦排在「还有贡献者」的位置上，那个量就还没加完。

⇒ **判据的定义域悄悄缩成「本行之前跑过的那些」**，而**没有任何东西守着这个位置**：
棘轮守的是「断言有没有全跑」，**谁守「棘轮站得够不够后」？没有。**

> 实证（`case-b8` @ fm-agent-demo，2026-09-04）：一处棘轮执行在三条断言之前，**只守着前 6 条**，
> 而加断言的人不会想到要同时挪棘轮，**症状是安静的**。
> 同日他在自己身上也犯过一次：往 `const pass = T.filter(...)` **之后**插断言 ⇒
> **8 条全部打 ✓，汇总却说「5/8 通过，3 项失败」**。

**指纹**：**输出与汇总互相矛盾**。⚠️ 但**不矛盾的时候更隐蔽**——它只是安静地少守着几条。

**检测法（比扫行序可靠得多）**：**断言「判据读到的那个数」等于「门禁自报的总数」。**
一行元检查，不依赖静态分析。
> 对照：他第一版用正则扫行序，**9 处候选误报 5 处**（正则定位到的是 `MIN_ASSERTIONS = 40` 这类
> **定义行**、通常在文件顶部，于是「其后仍有 37 处断言」纯属误报）。

⚠️ **口径要数对对象**：数**门禁自报的集合长度**，不是**输出里带 ✓ 的行数**。
> 他因此**两次**把棘轮设到实际值之上（永远红），且**两次都发生在「修复棘轮低于满额」的过程中**——
> 量错了对象，方向相反，病根同一个。第二次是把汇总行「✓ PASS 17/17 条断言」也数成了一条断言。

### D24 · 一个「全都缺」的扫描结果，先怀疑自己解析错了 ⭐⭐

> 实证（`case-c0`）：建并排比对工具时**按位置猜列**，把 4 条技术债的「观测手段」**全判空**——
> 而守它的门禁明明是绿的。**真实产物很少整齐地全缺同一样东西。**

⇒ **扫描结果呈现「整齐的全缺 / 全有 / 全为零」时，第一嫌疑是解析器，不是被扫对象。**
先拿一条**你亲眼确认存在**的样本过一遍解析器（正向基线，同 D4），再采信整体结论。

⚠️ 同族：**环境问题会伪装成门禁缺陷。**
> 同一会话的变异扫描判 `good = (base==0 and after!=0)`，**基线偶发失败时直接报「门禁没抓到」**。
⇒ 基线不绿时这一轮是 **UNABLE**，不是 FAIL（同 A1、M6）。

### D25 · 变异测试证明「定义域内它能红」，证不了「定义域够不够宽」 ⭐⭐⭐

**变异全部取自门禁自己的取景框**——你改的是它**已经在看**的那些东西。
**盲区里的东西，任何从它框内设计出来的变异都碰不到。**

> 实证（`case-b8` @ fm-agent-demo，2026-09-04，一个被当场推翻的 CLEAN 结论）：
> 对一道 a11y 门禁做了三次变异并**按 D21 的顺序做对了**（先确认缺口真的造出来，再看门禁反应）——
> 第三次 FAIL 且诊断精确（38/38 缺 role、Enter 按不动），据此判定它承重、该轮记 CLEAN。
> **但结论仍然是错的**：它的选择器是 `div[onclick],span[onclick]`，而 `el.onclick = fn`
> 是 JS 属性赋值、不产生 HTML 属性 ⇒ **27 处 `.chip`（用户回答的主要方式）根本不在它的集合里**，
> 键盘完全不可达，而门禁一直绿。**实现侧用同一个选择器 —— 门禁与实现共用同一个盲区。**

⭐ **三个问题正交，前两个都答完了仍可能全绿而漏一整类**：

| 问题 | 谁答 |
|---|---|
| 这道门**开过火没有**？ | **D20**（整段删门再跑） |
| 这次变异**有没有造出缺口**？ | **D21**（两种成因） |
| **这道门看的那片地方，够不够？** | **本条**（换维度取集合 → 行为探针） |

⚠️ **最难被发现的形态：反空转断言在场、在跑、而且真的在起作用。**
> 那道门**有**前提断言 `inv.total > 0 && inv.bad === 0`，而且它**正是为了防「空集恒真」而写的**——它防住了。
> **它防不住「集合定义本身是窄的」：集合非空，只是装错了东西。**
> 它守的是「有没有东西」，不是「是不是该有的那些东西」（同 D4、B15）。

⇒ **解药就是 B15 的判据分层**：**共享假设是这类盲区的唯一来源**——
门禁与实现只要从同一个前提取景，它就永远看不见那个前提之外的东西。
换维度判据（不问代码怎么绑的，问 `cursor:pointer`「用户看着像可点的，键盘到不到」）+ 行为探针（真按一次）。

### D26 · 命中数异常（全中或全不中）先怀疑装置，不要先怀疑被测对象 ⭐⭐⭐

> 实证（`case-55` @ fm-agent-demo，2026-09-04）：A9 的毒丸装置第一版**把 11 道门禁全判成阳性**，
> 看起来是个大发现。真因是**装置错了**——毒丸 `throw` 被追加到门禁文件**末尾**，
> 而那 11 道**全部以 `process.exit(bad?1:0)` 结尾**，毒丸在它之后，**永远执行不到**。
> **零缺陷被伪装成了 11 条缺陷。** 修正后（毒丸植在最后一个 `process.exit` 之前）32 道扫下来 **0 命中**。

⇒ **「0 命中」同样不能直接采信**，必须两条自证都过：

| 自证 | 做法 | 证明什么 |
|---|---|---|
| **正例** | 造一个真缺陷（顶层 `return` + 其后毒丸）⇒ 必须被抓到 | 装置**抓得到** |
| **对照组** | 同一位置**只放毒丸不放缺陷** ⇒ 必须报错 | **该位置本来可达**，所以上一条的「没抓到」才有意义 |

**两条都过了，「0 命中」才敢当结论。**

⚠️ **造反例时「位置对不对」和「反例本身对不对」一样重要**：同一会话第一次自证把 `return`
插在文件中点**没抓到**——不是装置瞎，是**那个位置在某个函数体内，`return` 根本不在顶层**。

⇒ 与 D24 同源（「全都缺」先怀疑解析器）：**整齐的结果——全中、全不中、全为零——第一嫌疑永远是装置。**

⭐ **一个更具体的指纹：一批命令返回整齐划一的同一个码，尤其是「文件不存在」那个码。**
> 实证（`case-05`）：普查「各门禁在损坏输入上报什么」，得到一张漂亮的表 —— **12 道门全报 UNABLE**。
> **那张表是假的**：zsh **不对未加引号的参数展开做分词**，`scripts/$x` 变成一个超长文件名 ⇒
> 文件不存在 ⇒ 全报同一个码。**门禁根本没拿到损坏输入。**
> 差一点就得出「所有门禁都正确处理损坏输入」，而它**一次都没被测过**。重做后立刻抓到一处真的。
⇒ **批量跑之前先单跑一个，确认它真的在做事**（同 D21：先证明缺口造出来了）。

⭐ **跨介质查证时，搜索式必须按目标介质的表达习惯写**（`case-55` 实测）：
> 他一度断定「PRD 完全没提大文件 5MB 阈值」并准备补写 PRD —— 实际 PRD 早就写了「大文件 ≥3 个（≥5MB）」。
> 真因：**他拿代码里的写法 `5*MB`（带星号）去搜文档，而文档写的是 `≥5MB`。**
⇒ **「没找到」于是被读成「不存在」，而这个结论看起来完全合理、毫无矛盾感**（同 D5：否定型结论需要更强证据）。

### D27 · 每加一层保护，都要问「这一层在我的执行形态下真的会被执行吗」 ⭐⭐⭐

**装置被杀时留下的不是「没结果」，是一棵污染的树 —— 而下一次测量会把它当基线。**

> ⚠️⚠️ **本条被它自己的失败推翻过两次**（`case-55` 实测，2026-09-04）。
> 每一版都是「看起来已经安全了」，而下一次超时照样把变异态留在树上。
> **一条给出虚假安心的规则，比没有这条更危险** —— 所以两次更正都保留在这里。

**三层保护，各有各的前提；而这些前提在「跑一个耗时的同步子进程」这个最常见的变异测试形态下，恰好全都不满足**：

| 层 | 它的前提 | 什么时候形同虚设 |
|---|---|---|
| `try/finally` | **正常控制流**走到 finally | **`finally` 是异常安全，不是信号安全** —— 兜不住 SIGTERM（第一版栽在这） |
| `process.on('exit')` | **自主退出** + 钩子内**全是同步代码** | 信号默认终止**不走** exit 事件；异步 restore 不会跑完 |
| `process.on('SIGTERM')` | **事件循环空闲** | ⭐ **`spawnSync` / `execSync` / 长同步循环期间，handler 排不上队 —— 注册了 ≠ 会执行**（第二版栽在这） |

⇒ **可操作的判断：每加一层保护，都要问「这一层在我的具体执行形态下真的会被执行吗」。**

**落到写法**：长任务必须**异步**，把控制权交还事件循环，信号 handler 才有机会执行。

```js
const { spawn } = require('child_process');
// ⚠️ 2026-09-10 外部评审纠正：此前这段只听 'close' —— 命令不存在时 spawn 触发的是 'error'，
//    没人接就是**未捕获异常，进程直接退出**，Promise 永远不 settle；而且没有 deadline（违反本文自己的 F1）。
const run = (cmd, args, timeoutMs = 30_000) => new Promise(res => {   // 异步，不阻塞事件循环
  const p = spawn(cmd, args); let out = ''; let settled = false;
  const finish = r => { if (settled) return; settled = true; clearTimeout(timer); res(r); };
  p.stdout.on('data', d => out += d);
  p.stderr.on('data', d => out += d);
  p.once('error', e => finish({ status: 'UNABLE', reason: e.message, out }));   // 起不来 ≠ 跑了不合格（A1）
  p.once('close', code => finish({ status: code === 0 ? 'PASS' : 'FAIL', code, out }));
  const timer = setTimeout(() => { p.kill('SIGTERM'); finish({ status: 'UNABLE', reason: `timeout ${timeoutMs}ms`, out }); }, timeoutMs);
});
const restore = () => { try { fs.writeFileSync(f, orig); } catch (_) {} };  // 必须全同步
process.on('exit',    restore);
process.on('SIGTERM', () => { restore(); process.exit(143); });
process.on('SIGINT',  () => { restore(); process.exit(130); });
try { /* 变异 + 测量 */ } finally { restore(); }
```

⛔ **而这一切仍然兜不住 `SIGKILL`。**
⇒ **唯一真正兜底的一层是：任何异常退出之后，第一件事是 `git status` + `git diff --stat HEAD`。**
> 他三次超时，**三次都是靠这一条发现的** —— 前两次是 `finally` 失效，第三次是 handler 失效。
⚠️ 精确改回，**别用 `git checkout -- .`**（会抹掉并发会话的在途改动，同 K11）。

⭐ **残留的形状会伪装成无害的改动**（同 D26）：
> 一次残留的是被删掉的 `if(ops.length) __pendingOps.unshift(...ops);` —— **刚修好的核心防线**。
> 若被提交，**等于把修复静默撤销了**，而 diff 看上去只是「一行注释缩进变了」（代码没了、注释还在）。

**分批粒度按「单批 × 单道耗时」倒算**，不是拍脑袋定条数；基线只跑一次，每条变异单独一次调用。

### D28 · 反例要按「**什么能击穿它**」挑，不是按「什么一眼就不对」挑 ⭐⭐⭐

D 组已有「正例挑得太顺手 ⇒ 判据只能过自己」。**反例那一半同样会挑顺手**，
而且更隐蔽：一串「明显不合法」的输入全被拒绝，看起来覆盖得很好，
实际**没有一个落在判据的边界上**。

一天内三次实测（`example-app`）：

| 判据 | 我挑的反例 | 漏掉的变异 | 能击穿的那个 |
|---|---|---|---|
| 重定向协议白名单 `/^https?:$/` | `ftp:` `file:` `data:` `javascript:` `ws:` `gopher:` | **去掉 `^` `$` 锚**（变 `/https?:/`）⇒ 判据照绿 | `xhttp:` —— 未锚定时 `https?:` 在偏移 1 命中 ⇒ 放行 |
| 孤儿进程回收 `/\bmimo\b/` | 命令行**压根不含** mimo 的探针 | **去掉词边界**（变 `/mimo/`）⇒ 判据照绿 | `mimolike-probe` —— 含 mimo 子串但不是独立词 |
| 「同一条正则不许有第二份副本」 | —— | 用**字符类片段**去扫，命中了另一条规则 `/^mcp-[a-z0-9][a-z0-9-]*$/` ⇒ **假阳性** | 改匹配**完整字面量**（含锚与斜杠） |

⇒ **写完反例先问一句：「如果有人把这个判据改宽一格，我这组反例里哪一个会变红？」**
答不上来，就说明反例全在安全区里。

⭐ 更省事的等价做法：**对判据本身做变异**（把 `^`/`$`/`\b`/类型检查逐个拿掉），
每拿掉一样都必须有反例变红。这比凭想象补反例可靠。

### D29 · 「写入成功」不等于「写入还在」 ⭐⭐⭐

断言守的是**写入那一刻**，守不住之后有没有别人把文件刷回去。
在有并发写者（另一个会话、变异测试装置、后台格式化、watch 进程）的树上，
**一次成功的写入可以在几十秒后被静默撤销，而覆盖回来的内容语法正确、测试全绿、看不出任何异样**。

实测（`example-app`，2026-09-05）：我的替换脚本对 3 个文件逐条断言了命中次数并写盘成功，
30 秒和 60 秒后其中 2 个文件的 mtime 被刷新，我的改动消失，内容是干净的 HEAD 版本。
真因是并发会话的变异器**备份取自 `git show <sha>:<file>` 而非工作树** ——
它在**注入变异那一步**就已经把工作树内容丢掉了，等价于 `git show <sha>:<f> > <f>`。

⭐ **两个方向的可发现性差一个量级**：
「我的提交卷走了它的变异」——它会发现并告诉我；
「它的还原吃掉了我的编辑」——**没有任何人会来告诉我**。我是靠一道恰好在找
「有没有多余副本」的新判据，撞见「旧副本根本没走」才发现的。

**四条做法**：
1. 变异 / 批量改写的备份**一律取自工作树**，不是 `git show <sha>`、不是 HEAD。
   ⚠️ **这条与另一条实证正面冲突，必须一起读**：另一次事故里，变异脚本超时被杀、文件留在变异态，
   补救时才发现「备份」是**第一次超时时存的、本身就带着变异** —— 那次的结论是
   「备份取自版本库已提交的内容（`git show HEAD:<file>`），不取工作区」。
   **两条都对，各自防的是不同的坑**：取工作树防的是「吃掉别人未提交的编辑」，
   取 HEAD 防的是「备份本身已被污染」。
   ⇒ **真正的解是让两者相等**：**动变异之前先提交**（第 3 条），此时工作树 == HEAD，两种取法等价。
   在有未提交改动的树上跑变异，无论取哪边都会踩其中一个坑 —— 那不是取法问题，是不该开跑。
2. 注入之后、跑门禁**之前**，断言「变异串确实在文件里」；跑完再验一次。
   否则**变异没落地却把绿读成「门禁没抓到」**（这正是它最贵的误读方向）。
3. 关键改动写完就提交，别让它在工作树里过夜。
4. 同一棵树上有并发写者时，改写完隔一会儿**重新读一遍**再下结论。

### D30 · 你**验的那份**和你**提交的那份**，可能不是同一份 ⭐⭐⭐

> ⚠️⚠️ **最刺眼的一种：被改的是那个正在跑的脚本自己**（2026-09-10 本文自身实测，当场撞到）。
> **shell 是边读边执行的** —— 它按字节偏移往下读，一边执行一边取下一段。
> 于是在一个长跑脚本（变异套件，数分钟）运行**期间**去编辑它，
> 正在跑的那个实例会从改动点之后**按错位的偏移继续解析**，
> 报出 `syntax error near unexpected token` 之类的错 —— 而**你去看当前文件，`bash -n` 完全干净**。
> ⇒ 这条错误信息指向的是一个**在任何一个版本里都不存在**的问题（同 A6：错的诊断把人带去错的地方）。
> **做法**：长跑脚本运行期间不许改它自己（要改先停）；这类 runner 也是「被测物在检查期间变了」
> 的一种 —— 那一次的结论一律作废重跑，别去解释那个语法错误。

判据读文件、给结论、你据此提交 —— 这三步之间文件可以被别人改。
**读取侧的这个洞，和 D29 的写入侧是同一个母题，但防法完全不同**：
D29 教你写完再读一遍；D30 说的是**判据自己读到的就是半成品**，
于是它给出的绿或红，**指的都不是你手上这份东西**。

实测（本文自身，2026-09-05）：一次 `selfcheck` 运行里同时产生**两条互相独立的错误判定** ——
报「例外 22 条 ≠ 准则 109」（真值 23，分区其实闭合）、
报「自述 13 组 20 条 ≠ 实际 14 组 21 条」（文件当时已是 14/21）。
两条都是**假红**。并发会话正在同一批文件上写入，`derivation.md` 的 mtime
与门禁启动时间相差 **不到 60 秒**。

⭐ **最危险的不是假红，是假绿**：假红会逼你去查，查到底就发现了真相；
**假绿悄悄放行，而你以为它验过了**。同一个机制两种方向，暴露概率差一个量级。

**三条做法**：
1. **指纹前后夹住**：判据开始前记录被测物的 `sha256`，出结论时再记一次；
   不一致就报 **UNABLE（被测物在检查期间变化）**，不许出 PASS 也不许出 FAIL。
2. **提交前再核一次**：`git diff --cached` 的内容指纹必须等于你跑判据时的那份。
   「跑了门禁」和「提交了跑过门禁的东西」是两件事。
3. 并发树上，**绿了不要立刻下结论**，隔几秒重读一遍再采信（与 D29 第 4 条同源）。

### D31 · 判据**算得对**，不等于判据**会被执行** ⭐⭐⭐

写一道门的注意力几乎全在「判据对不对」上：
边界、误报、漏报、在存量代码上试跑。**这些都验完了，门仍然可以是一道从没开过的门。**

实证（`example-app` 第 38 轮，我自己的门）：我为「证据必须点名测试」新建了一道门，
判据算得完全正确、在存量上准确报红 ——
**而它放在测试收集器结构上够不到的目录里，全仓没有任何调用方**。
提交信息写的却是「让今后写不进去」。
**我只自证了判据本身，没验它会不会被执行。**

⭐ 与 **D20** 是一对：D20 问「这道门**有没有过正例**」，
D31 问「这道门**有没有被跑过**」。两个都答不上来时，症状完全一样 —— 结果里一片绿。

**验它被执行的三种办法（按可信度从高到低）**：
1. **让它失败一次**：临时注入必然违反的输入，看**整套**的输出里是否出现它的名字与非零退出码。
   这同时验了「被收集到」和「结果被消费」（A16、B20）。
2. **数它**：套件报告里断言用例总数 / 门禁总数 ≥ 预期下限，新增一道就 +1（A3 的下限断言）。
3. 最弱：确认它在收集器的匹配范围内（目录、文件名模式、注册表）。
   **这条只能排除最粗的错，不能当证据** —— 匹配上了仍可能因跳过条件而不执行。

⚠️ **新建判据的验收清单里，「跑过一次并见它红」是必答项**，不是可选项。

### D32 · 「在开发目录里跑绿」不等于「在它**实际被加载的位置**跑绿」 ⭐⭐⭐

**D13** 管的是同一处**跑多次**都绿；这条管的是**换个位置**还绿不绿。
两者会同时成立又同时失效：一个东西可以在开发目录里连跑十次全绿，
**而在它真正被使用的那条路径上第一次就红**。

实证（本文自身，2026-09-05）：本 skill 的真实加载路径是 `~/.claude/skills/` 下的**软链**。
同一份门禁 —— 开发路径 `rc=0`（23 PASS），软链路径 `rc=1`（22 PASS + 1 FAIL）。
根因两层叠加：
`pwd` 默认给**逻辑路径**（软链原样保留）⇒ 后续命令都拿着软链路径跑；
而 **BSD `grep` 递归模式不跟随符号链接**（⚠️ 2026-09-15 实测修正：BSD grep 的 `-r` 与 `-R` 是**同义词**、
**都不跟随**，跟随开关是 `-S`；「`-r` 不跟 / `-R` 才跟」是 **GNU** 的语义——把 GNU 语义记到 BSD 头上，
照着改成 `-R` 会**原样复现本条描述的事故**，且这次是照着规范改的）
⇒ 递归搜索在软链目录上返回空 ⇒ 判据得出「清单没了」。

⭐ **差异来源有四类，都不是「代码写错了」**：
① **路径形态** —— 软链、相对路径、含空格 / 非 ASCII 的目录；
② **权限与挂载** —— 只读挂载、不可写的临时目录；
③ **CWD** —— 脚本假设自己在某个目录里被调用；
④ **打包 / 安装之后的布局** —— 资源被搬走，`__file__` / `BASH_SOURCE` 不再指向源码树。

**四条做法**：
1. **验收里必须包含一次「在真实加载位置跑」**。这条最便宜，也最常被跳过 —— 因为开发时
   谁都是在源码目录里跑的（同 **D31**：判据对不对，和它在不在真实路径上跑，是两件事）。
2. 脚本解析自身位置一律 `pwd -P`（物理路径），并**不依赖 CWD**：
   所有路径从脚本自身位置推出来，不从当前目录推。
3. 遍历文件用**显式清单**或 `find -L`，不依赖递归工具对软链的默认语义。
   `grep -r` / `-R`、`cp -r`、`du`、`find` 的软链行为在 GNU 与 BSD 之间**各不相同**。
4. ⚠️ **修完要反向验一次**：换形态之后判据**仍然会红**吗？
   把「跟随软链」加进去很容易顺手把判据改成恒绿 —— 修的是可达性，别把咬合力一起修掉。

> **实证二（同日，外部生产代码）——「我已经在真实路径下修好并实跑 rc=0」仍然不够**：
> 一个每天跑的 launchd 任务，我在**终端里**手动跑到 rc=0 就宣布修好了。
> 用 `launchctl kickstart` 在**它自己的运行形态**下再跑，仍然 exit 1，底下还压着两层：
> ① **macOS TCC** —— `~/Desktop` 受保护，launchd 拉起的进程写不进去（`Operation not permitted`），
>   而终端里完全正常；② 直连 API 被 403 拒绝，而 launchd 环境不带代理变量。
> **两层都只在真实形态下才出现，且失败只落在 stderr 里没人看。**
> ⇒ 判据升级：**「在真实调用形态下跑过一次」必须是由那个调度器自己拉起的一次**
> （`launchctl kickstart` / 真触发一次 CI / 真发一个 webhook），
> 不是「我在同一台机器上手敲同一条命令」。这两者之间隔着环境变量、工作目录、
> 权限授予（TCC/SELinux/容器 capability）、tty 有无 —— 每一样都足以让结论翻面。>
> **实证三（`case-05` 同日实测）——不是权限被拒，是「参数被宿主静默改写」**：
> 给无头 Chrome 传 `--window-size=390`（移动端宽度），**macOS 会把它钳到最小 500px**，
> 请求 390、实得 500，**Chrome 不报任何错**。于是那一整轮「移动端」测量其实跑在 500px 上。
> ⇒ 真实调用形态的差异有**两类**，都足以让结论翻面：
> ① **能不能做**（权限：TCC / SELinux / 容器 capability，会失败但可能只落在没人看的 stderr 里）；
> ② **做成了什么**（参数被宿主钳制或改写，**不失败、不报错，只是和你要的不一样**）。
> 第二类更阴险 —— 它不会留下任何失败痕迹，只能靠**回读实际生效值**（真实窗口宽度、
> 真实超时值、真实并发度）而不是回读你传进去的值来发现。

### D33 · 测隔离时，**回传通道不能是被隔离挡住的那一条** ⭐⭐⭐

验「这道隔离生效了吗」的判据，必须让被隔离的一方**用它仍被允许的通道**把结果说出来。
用被禁掉的通道回传，会把**两种完全不同的状态压成同一个读数**：
「里面的代码根本没跑」和「跑了但说不出话」。

实测（`example-app` N62）：验 `<iframe sandbox="allow-scripts">` 是否真的进入不透明源，
我让 iframe 里的脚本写 `parent.__ls = ...` 回传 —— **写 parent 属性本身就是跨源操作，被同一个 sandbox 挡住**。
于是探针恒返回 `NO-SCRIPT`，判据据此报出「沙箱没生效、存储不再隔离」——**指控与事实完全相反**。
⇒ 改用 `postMessage`（沙箱帧到父帧始终允许），并给「一条消息都没收到」**单列一个读数**，
不让它和「收到了、结果是拒绝」混在一起。

**通用形态**（同类替换随处可见）：
- 测网络隔离，却让被测进程「把结果 POST 回来」；
- 测只读挂载，却让被测代码「把结果写进那个目录」；
- 测权限降级，却让降权后的进程「写它已经无权写的日志文件」；
- 测超时中断，却指望被中断的那段代码「在退出前打印一行」。

⇒ 写探针时问一句：**「如果这道隔离完全生效，我这条回传路径还通吗？」**
答案是「不通」，那这个探针测不出任何东西 —— 它只会永远报「隔离生效」或永远报「没生效」，
取决于你把沉默算成哪一边。

⭐⭐ **同一形状放大一层：验证手段整体依赖了被验证对象**
（第七次外部实战，2026-09-05，一个本地 agent 评测工具）。
它有一个很好的自测：跑一组构造的负例，**断言每条都把目标维度打红 ——
没打红就说明那个 grader 是 fail-open 的假绿**。
这件事**与被测 agent 是谁完全无关**（负例自带脚本与工具返回值）。
但自测脚本硬编码了 `--adapter album`，而那个适配器所指向的项目**在这台机器上根本不存在**
（且它在**模块顶层** import，于是任何模式都直接抛错）。三个适配器全部不可用。

> ⇒ **一个「测判据自己」的测试，被迫依赖「被测系统可用」——
> 于是判据的可信度，被绑在了被测系统的可用性上。**
> 而它的文档写着「grader 自身必须先过反向测试」：那条纪律**没有任何环境能执行它**。

⚠️ 它做对了最要紧的一半：环境不可用时**明确诊断 + `exit 1`**，不是静默判过。
**所以这不是假绿，是「这道检查此刻不存在」** —— 而两者在长期效果上会趋同：
一道长期跑不起来的检查，和一道不存在的检查，对代码质量的贡献完全一样。

⇒ **自检一句**：**「被测系统整个不在，我这个自测还能跑吗？」**
跑不了 ⇒ 给它一条**不依赖任何真实系统的回放路径**（stub / 录制回放 / 纯数据夹具）。
元检查的独立性不是洁癖：它决定了**你在最需要它的时候（系统坏了）能不能用它**。

### D34 · 探针拿到的**不是被测对象的输出**时，症状与「被测对象没问题」一模一样 ⭐⭐⭐

判据分两半：**取到被测对象的输出**，和**对它下判断**。
几乎所有注意力都花在第二半，而第一半失败时，**它长得和「一切正常」完全一样**。

实证（`example-app` 第 40 轮）：想验「启动脚本设的 PATH 顺序对不对」，于是在 node 里 `require` 它再读
`process.env.PATH` —— 而那个脚本需要 Electron，第一句就抛，**读到的是宿主自己的 PATH**，变异照绿。

**本文自身同日连犯两次（2026-09-05）**：
1. 写完 **D30** 的指纹守卫立刻用它，`for f in $FILES` 因**本 shell 的 `IFS` 不含换行**
   把 20 行当成 1 个词 ⇒ 一个文件都没采到 ⇒ 「before == after」是**两个空哈希相等**，真空通过。
2. 反向测试里写 `printf '%s' "$(basename …)" "$?"` —— 命令替换先执行、把 `$?` 覆盖成 0
   ⇒ 读到「FAIL 却 rc=0」，**那是我的测量错误，不是被测对象的错误**，差点据此判门禁有缺陷。

⭐ **判别口径**：问一句「**如果被测对象根本没运行，我这个判据会说什么？**」
答案若是「说没问题」或「说不出区别」，第一半就是坏的。

**三条做法**：
1. **先验第一半**：判据必须能报出「取到了多少」（条数 / 字节数 / 进程 pid），
   并给这个数配下限断言（**A3**）。取到 0 个先判「采集这一步成功了吗」：拿不出采集成功的证据 ⇒ UNABLE；
   **采集确证成功、且业务允许空集 ⇒ `PASS checked=0` 才是正确结论**（A3 修订口径——无条件「0 即 UNABLE」会把合法零值洗成没能测，A19 的镜像面）。
2. **退出码立刻捕获**：`cmd; rc=$?` 独占一行。任何命令替换、管道、`echo` 都会覆盖 `$?`
   （同 **D5**：`| tail; echo $?` 取的是 `tail` 的退出码）。
3. **正例先跑通**：拿一个**你亲眼确认会被抓到**的样本过一遍探针（同 **D4** 正向基线），
   再采信它给出的任何否定结论。

**可复用范式:泄漏哈网(secret-sink harness)**（借自 gstack `test/helpers/secret-sink-harness.ts`，2026-09-09）——验「防泄漏本身有没有生效」这类隐蔽假绿(redaction 跑了、看着绿,但扫的是渲染前、发的是渲染后)的教科书形态,正是本条 + [[feedback_validate_detector_before_trusting]] 的落地:

> **播种 → 捕获全通道 → 断言缺席 → 正对照。** 拿一个播种的假密钥跑被测 bin,**捕获它可能泄漏的每条通道**(stdout / stderr / `$HOME` 下写的文件 / telemetry 日志),断言种子从不出现。匹配规则要四种,少一种就漏一类:①精确子串 ②URL 解码后 ③**前 12 字符前缀**(抓「我只记了一部分就拼出去」) ④base64(抓 auth-header 泄漏)。
> ⚠️ 纲领:**「静默漏报的哈网比没有哈网更糟」**——所以每个用它的套件必须含一条**故意泄漏、断言被抓到**的正对照(同上「正例先跑通」);没有正对照的哈网,它的绿只证明「没报」,不证明「会报」。

### D35 · 判据的**匹配范围**比它要守的东西宽 ⇒ 会被**邻居**喂饱 ⭐⭐⭐

D16 说的是「被它要守的那段代码的**注释**喂饱」。这条是另一种：
判据在一个**比目标更大的单位**里做匹配（整行 / 整个文件 / 整个目录），
于是**同一单位里的另一个对象**满足了它 —— 目标自己缺失也照绿。

实测（`example-app` N73）：文档一行里并排写着多个组件的定义
（`· \`progress\` {…} · \`meter\` {…}`），判据在**整行**里找属性名。
反向测试撤掉 `progress` 的 `empty` —— **不红**，因为同一行 `meter` 的括号里有 `empty`。

⭐⭐ **最反直觉的一半**：把范围从「整行」收窄到「该组件自己的 `{…}` 块」之后，
**又浮出 6 个此前没被发现的真缺口** ——
也就是说，宽范围下那个「干净」的结果**本身就是被喂饱的假象**。
> 收窄判据通常让人担心误报变多；这一次收窄**同时**修好了假绿并暴露了真缺陷。

**自检两问**：
1. 我的匹配单位，和我要守的对象，是**同一个粒度**吗？
   （行 vs 声明块、文件 vs 函数、目录 vs 模块 —— 差一级就够了。）
2. 如果目标对象整个消失，而它的邻居还在，我的判据会红吗？
   —— 这就是那条反向测试该测的东西。

⚠️ 与 B7「过紧与过松同样是缺陷」不冲突：这里收窄的是**范围**（在哪儿找），
不是**判据本身**（找什么）。范围收到与目标同粒度为止，再窄就该出误报了。

### D36 · 反向测试**没红**有三种解释，混为一谈就会去修没坏的东西 ⭐⭐⭐

写完一条判据，注入缺口，跑，**没红**。此刻脑子里通常只有一个念头：判据瞎了。
但「没红」至少有三个互斥的成因，**它们的修法完全不同**：

| # | 成因 | 现场特征 | 修哪儿 |
|---|---|---|---|
| ① | **判据真的瞎了** | 缺口确实在，判据看不见 | 判据 |
| ② | **缺口根本没造出来** | 变异没落地（替换串没命中、写到了别的文件、被格式化改回去） | 变异脚本 |
| ③ | **变异打错了靶子** | 变异**落地了**，但拆掉的不是那道闸 | 对被测物的理解 |

⭐ **③ 的一个常见成因：靶子被「兜底回退」挡住了**（本文自身实录，2026-09-05）。
门禁里有一句很好的健壮性设计：`FIND=${FIND:-/usr/bin/find}; [ -x "$FIND" ] || FIND=find`。
它让工具缺失时自动回退 —— **同时也让「工具不可用」这条分支永远走不到**。
我想给那条分支做阳性对照，`FIND=/nonexistent bash selfcheck.sh` 跑下去照样 PASS，
**连试两次**，一度以为判据坏了。真相是回退成功了，探针根本没打到靶。
> **凡是写了兜底回退的地方，「兜底被触发」这条路径就不能再靠改环境来测** ——
> 只能靠变异（把判断条件本身改掉）或依赖注入。
⇒ 处置：给这类分支**用变异证明它至少会执行**（把下限改成恒真，断言它输出预期的那句），
并在诚实边界里写明「它在正常路径上不可达，验的是分支不是场景」——
**「不可达」和「死代码」不是一回事，但不写清楚，读的人只能当它是后者。**

⭐⭐ **③ 最难识别，因为它每一项外观都正常**：脚本执行成功、文件确实变了、语法也合法、
`git diff` 看得见改动 —— 唯独改的那处**不在判据要守的那条路径上**。
> peer 实证（`case-55`，2026-09-05）：给一个「孤儿接口脱离沙箱」的判据做反向测试，没红。
> 第一反应是判据坏了。真因是变异只删掉了取索引的那个调用，
> **而真正的闸（路径归一化）还在函数体里** —— 判据没错，是缺口没造在它守的地方。
> 同一大段里这种形态撞了**至少 4 次**。

**⇒ 三条断言，一条比一条贵，但缺一层就会误判一类**：
1. **变异落地**（新串在文件里、文件确实变了）—— 排除 ②。本文的 `reverse-test.sh` 做了这层。
2. **拆掉的正是那道闸** —— 排除 ③。做法：先在**不跑判据**的前提下，
   用最小复现确认「缺口现在真的存在」（该拒绝的输入现在真的通过了）。
3. **已知阳性对照** —— 排除 ①。判据在一个**已知会红**的样本上必须红。

⚠️ **本文的套件目前只做了第 1 层和第 3 层，没有第 2 层**（这是一处写下来的缺口，不是「不需要」）：
对文档类变异 ③ 的风险低（改的就是判据读的那几个字），
但对**脚本类**变异，「文件改了」离「那道闸没了」还差一步。

⇒ 与 **D34** 是一对：D34 问「探针拿到的是不是被测对象的输出」，
本条问「**被测对象身上被拆掉的，是不是判据要守的那个东西**」。

### D37 · 探针的锚点会随代码搬家而失效，而它的表现是「**跳过**」不是「报错」 ⭐⭐⭐

任何靠**字符串锚点**定位被测物的东西（变异脚本、反向测试、打桩、断言里的选择器），
都有同一个寿命问题：**被测代码搬了家，锚点还留在原地**。
而失效那一刻它不会红 —— 它会「什么都没找到，于是跳过」。

**三种表现，一种比一种难发现**：

| 形态 | 表现 | 危险度 |
|---|---|---|
| **静默执行** | 锚点没命中却照跑，结果不作数却计入通过 | 最坏 |
| **响亮跳过** | 每次都打印 `⊘ 锚点 0 处，跳过` | 次坏 —— **见下** |
| **汇总 / 阻断** | 有一处能一次列全失效锚点；或直接判红 | 正确 |

⭐⭐⭐ **最反直觉的一条**（peer 会话 `case-55` 2026-09-05 的原话，值得原样记住）：

> **「响亮跳过」只对写脚本的当下响亮，对几十轮之后的人是安静的。**

他的实证：`archiveStamp` 那条锚点写的是 `01-core-state.js`，而该函数**早已搬到 `02-render-ui.js`**
⇒ 它一直老老实实打印「0 处，跳过」，而**他一直以为那条变异在跑**。
19 个脚本 48 条锚点，**7 条已失效**。
⇒ 那条从没跑过的变异底下压着两个真缺口（`toISOString()` 用 UTC ⇒ UTC+8 的本地 00:00–08:00
建出来的包叫前一天；预览名与真实名是两次独立的 `new Date()`，跨零点不是同一个名字），
**两条都没有门禁守**。

**同一形态的本文实证**：变异表 29 条里 4 条锚点已失效（绑在派生数字上，正本一改就死），
而套件因为太慢**故意不进门禁** ⇒ 它 FAIL 了整整一天，主门禁全程绿。
⇒ 由此得到的解耦，可以直接搬到任何「跑得贵」的检查上：
> **「执行贵」和「坏了没人知道」是两件事。** 贵的是跑，便宜的是**校验锚点还在**（一次 grep）。
> 把后者拆出来放进门禁，前者留在手动 —— 两个问题一起解决。

**做法（按强度排序，至少做到第 2 档）**：
1. ⛔ 不许静默执行：锚点匹配数 ≠ 预期 ⇒ 立刻停，别进入判读。
2. ✅ **失效锚点必须能被汇总** —— 一个入口一次列全，而不是散落在各次运行的 `⊘` 里。
3. ✅✅ 更强的一档：**让锚点失效直接判红**（本文的 `[11]` 就是这一档，它上线当天两次抓到
   「改自述打断了锚点」）。汇总要人去看，判红不用。
4. 治本：**锚点别绑在会漂移的东西上**（派生数字、行号、易改的措辞），
   或者用占位符让它跟着走（本文把锚点里的数字改成 `%d`，按 `(\d+)` 匹配实际那一处）。

**另一个方向：锚点命中「多处」——比失效更隐蔽**（peer 会话 `case-5c` 2026-09-09 回流 + 本文自身实证）：
上面整条讲的是锚点**找不到**（0 次）。反方向是锚点**命中不止一处**：
`str.index(X)` / `str.find(X)` / `grep -F X | head` 默认取**第一处**，不报错、不抛 `ValueError` ——
段落边界于是**静默错位**，判据在**错误的段落**上跑，结论读起来完全正常。
用**中文自然语言 / 标题**当定位锚点尤其危险：正文里再提一次那句话
（目录、交叉引用、另一条款引用它），第一处就换了地方。
⚠️ `try/except ValueError` 只挡「0 次找不到」，**挡不住「多处取错第一个」**——它一声不响。
- case-5c 的实证：判据用 `.find('<中文字面量>')` 定位段落，正文提到那个字面量一次就错位，
  **既会静默关掉整条判据、也会在合规文档上报假错**（通用助手 `product-flow/scripts/_section.py` 治这个）。
- 本文自身实证：`selfcheck.sh` 有 5 处用中文标题 `.index()` 切段落（来源三表 / 组表 / 场景索引 / 覆盖度）——
  当前每个锚点恰好 1 次、暂时对，但**没有任何东西拦住「将来正文再现一次」**。这正是本条的定义域：*现在对，不代表守得住*。

5. ⭐ **定位段落的锚点必须断言恰好命中一次**（`txt.count(X)==1` 否则报错），不许默默取第一处 ——
   这与反向测试要求「原串唯一存在否则 exit 4」是**同一条原理的两处应用**：锚点不唯一，定位就不可信。

⇒ 与 **A18** 的分工：A18 管「跳过了却不说」，本条管「**说了，但说的方式让人看不见**」。

## E · 承诺与实现 —— 写注释和 commit 时

> 这组抓的是一类**会骗过所有其他视角**的缺陷：读代码的人**会被注释诱导**。注释说「失败自动退回」，读的人就默认那条路存在，不会再去数它接住了几种失败。

### E1 · 每写一句承诺，当场回答「这句现在成立吗」

承诺 = 注释 / docstring / commit message / README / 错误提示文案 / 验收条件里的每一句：

> 「它会……」「失败会……」「保证……」「不会……」「自动……」

写下的**那一刻**就回代码核一遍。写的时候核最便宜——三个月后核，你已经不记得当时假设了什么。

⚠️ **反方向同样成立：一条不准确的注释能造出一条不存在的高危。**
> 实证（`case-e9`，一轮里两次）：注释**少列了两个字段** ⇒ 零上下文的评审据此报出一条**假 XSS HIGH**；
> 另一条注释被读成安全承诺 ⇒ 报出**假隔离 HIGH**。
⇒ **注释是评审者的唯一输入**——写窄了比不写更危险：不写他会去查，写窄了他会照着查错的方向。

### E2 · 承诺必须能指到实现路径

对不上就是缺陷——**要么改代码，要么改承诺**，不许两边挂着。

> 这个缺陷躲过了正确性视角（代码本身没错），也躲过了错误处理视角（它确实有错误处理），只有拿承诺清单逐条核才掉得出来。

> **最危险的形态是安全边界只存在于注释里**（2026-09-06 `~/pulse` 实证）：路由块上方写着
> 「只接受本机请求」，而下面一道检查都没有——服务还绑着全接口、能开终端执行任务。
> 注释反而**加重**危害：读代码的人看到那句就不再去核。加重项之二：校验所需的材料
> （`collectGroups().get(id)`）**当场就算出来了**，只被用来取显示名——守卫的输入都在手边，
> 差的只是那个 `if`。审计问法：**「这句注释若是真的，哪一行在兑现它？」**

### E3 · 承诺兜底要数清接住了几种失败

```
commit: 「渲染失败自动退回原封面（无人值守不能因为封面挂掉整条不发）」
实现:   只处理了子进程 returncode != 0
漏了:   TimeoutExpired（会冒泡）、FileNotFoundError（脚本缺失会冒泡）
⇒ 承诺的兜底有洞，而且外层超时常先到，是常态不是极端
```

**自检问句**：这个 `try` 接住了几种失败？我承诺的那句话覆盖了几种？

### E4 · 内外层超时不得相等

内层 180s、外层 180s ⇒ 外层常先到 ⇒ **内层的兜底永远不执行**。外层要显著大于内层与其兜底耗时之和。

---

### E5 · 从「代码」出发的对账，看不见「文档承诺了而代码里根本不存在」的东西 ⭐⭐⭐

E1/E2 的方向是**代码 → 承诺**（这句注释还成立吗）。但那个方向**在结构上看不见一整类缺陷**：

> 实证：文档声明按钮支持 `onTap`，而**全仓只有文档那一处出现过这个词**——内核从不读它，
> 点击静默 no-op，而按钮的标签、配色、hover 全部正常，自动校验全绿。
> **二十轮审计里前十九轮都碰不到这一格**：它们的起点都是代码，而这个缺陷的特征恰恰是「代码里没有」。

⇒ **至少跑一轮以「声明侧」为起点**：把提示词 / 文档 / 规格 / API 说明**告诉使用者可以写什么**逐项列出，
再回代码里找对应的**读取点**。三种缺口都要看：

| 缺口 | 表现 |
|---|---|
| ① 声明了而代码不认 | **静默失效**——写了没反应，且看起来一切正常 |
| ② 代码认而从没声明过 | 能力在产品不在——没人知道可以用 |
| ③ 两边都有但语义不一致 | **最隐蔽**——按文档写，行为却是另一回事 |

### E6 · 「修复 + 详尽注释」不防回退，「修复 + 门禁」才防 ⭐⭐⭐

E1/E2 治的是「承诺对不对得上实现」。这一条治的是**修复本身有没有人守**：

> ⭐ **「核对过 ≠ 有人守着」「注释写清 ≠ 有人守着」。**

> 实证（`case-55` @ fm-agent，八轮变异测试的贯穿母题）：最典型的一处，注释里白纸黑字记着实跑后果——
> 「把 A 移进 A/子目录 ⇒ **整棵子树从根目录消失、回收站 0 条，只有撤销能救**」。
> **修复做了、理由写得极详尽、没有任何门禁守它。**
> 量化普查：**105 处带修复标记的承重注释 → 19 处候选 → 逐个变异验证命中 17 处。**

⇒ **这个项目里「修复 + 详尽注释」是常态，「修复 + 门禁」不是。而只有后者能防回退。**

**自检问句**：**我这次修的东西，如果下一个人把它改回去，有什么会红？**
答不出来 ⇒ 这次修复只是**一次性的**，它会随时间被磨掉。

⚠️ 注释在这里甚至是**反作用**的（同 E1）：写得越详尽，读的人越觉得「这里有人管过」，
越不会去补门禁。

### E7 · **越是「讲自己是什么」的那段文字，越没人校验** ⭐⭐⭐

README 顶部的「本项目包含 N 个模块」、包清单里的 `description`、
门禁输出的那句汇总、文档里的「本文检查 M 项」、徽章上的覆盖率数字 ——
这类**自述性文字**有三个共同点，合起来让它成为漂移的重灾区：

1. **它不参与任何执行路径** —— 写错了不会让任何东西报错；
2. **它是派生量** —— 由别处的真实内容算出来，而算它的人是人，不是判据；
3. **它偏偏是读者看到的第一样东西**，很多时候还是**唯一**看到的那样。

⭐ **实测（本文自身，2026-09-05，一轮内命中五次）**：
| 处 | 症状 |
|---|---|
| 门禁自述「N 组 M 条」 | 加了一道检查却没改这个数 |
| 「全部 N 条完整条款」 | 散落 5 处手写，同时存在 127 / 108 / 120 三个不同的值 |
| 「自证门禁」整段描述 | 锚点数 / 例外数 / 【必须】数 / 分区四项**同时**过期 |
| 场景索引 | 新增的 8 条准则一条都没进去 —— **索引是唯一真正会被翻开的入口** |
| frontmatter `description` | 四个数字改成 900 / 99 / 77 / 12，**门禁一律全绿** |

每一处单独看都自洽、都不会让任何东西报错、通读也发现不了 —— 只有**机械比对**能抓。

**三条做法**：
1. **派生量不许手写第二遍**：同一个数字只允许出现在一个地方，其余处**去数字化**
   （「全部条款」而不是「全部 136 条」）。留下的那一处必须被判据对账。
2. **给自述文字配判据**，判据形态就是「重新算一遍，和文字里写的比」。
   这类判据极便宜，且几乎每次改动都会用到它。
3. **对读者零价值的派生数字，直接删掉，别再养一道门**
   —— 判据也是要维护的，为一个没人需要的数字加门是净负债。

⭐⭐ **但「手写」本身不是缺陷 —— 先分清这个数字在说什么**
（peer 会话 `case-55` 2026-09-05 按本条自查时给出的区分，两个数字症状完全一样、处置完全相反）：

| 数字在说什么 | 例 | 正确形态 |
|---|---|---|
| **描述现状** | `MIN_CHECKS = 114`，而实际已 116 | **必须可推导**，否则必漂 |
| **表达策略** | `CAP = 6`（孤儿接口棘轮上限，只许降不许升） | **必须手写** |

**把策略数字做成可推导，等于把红线改成了跟随现状的移动靶** —— 棘轮当场失效。
判断方法一句话：**这个数字变大时，是「事实变了」还是「我们让步了」？** 后者不许自动跟随。

⭐ 策略数字过期的正确处置也不同：让它**自己报告自己过期**
（实际值比下限多出一截就打印「建议上调」），但**只提醒、不判失败** ——
做成硬失败会让「多加了一条断言」这件好事本身变红，那是在惩罚正确行为（同 **B16**）。
⚠️ 而且**要验这条提醒会不会真出声**（把下限临时调低，看提醒是否打印）：
加一条「会提醒」的机制却不验它出不出声，就是又造了一条自述型死代码 —— **正是本条要治的病本身**。

⚠️ 与 **E5** 的分工：E5 管「文档承诺了功能而代码里没有」，
E7 管「文档描述自己的规模/能力，而那个描述本身已经不对了」。前者是功能面，后者是元信息面。

### E8 · 会被**复制走**的东西，必须就地自带它依赖的纪律 ⭐⭐⭐

模板、脚手架、示例代码、README 里那段"直接粘就能跑"——
它们和普通代码有一个本质区别：**它们会被复制到你看不见的地方，而它们依赖的上下文不会跟着走。**

于是一个在原处完全正确的东西，到了新家就变成了缺陷，**而外观一模一样**：

> **原处**：`continue-on-error: true` + 一句注释「起步咨询，确认后转强制」，
> 旁边的 `ratchet.md` 写着「测基线、写进章程 Open Items：存量 N，清零后转强制」。
> **抄走后**：只有 YAML 和那句注释。那条「写进 Open Items」的要求**不会跟着被复制**。
> 「起步」失去了对应的「以后」，剩下一个**永久豁免**，而它看起来和一道正常的门完全一样。

⭐ **实证（第五次外部实战，2026-09-05，`engineering-standards` 的 CI 模板）**：
三处 `continue-on-error` 都写着「确认后转强制」，**没有一处写谁、何时、记在哪**；
其中一处是**密钥扫描** —— 它同时关掉了 artifact 上传，
于是发现了密钥既不阻断、又不留证，只剩日志里一行。

**自检一句（很好用）**：

> **把这段东西单独剪下来，放进一个空仓库、给一个没读过你文档的人 —— 它还完整吗？**

**三条做法**：
1. **纪律就地嵌进模板**，不要放在旁边的文档里：把「必填项」写成占位符
   （`存量 <N> / 转强制日期 <YYYY-MM-DD> / 责任人 <@who>`），让抄走的人无法忽略。
2. **临时性必须自带到期**。没有到期日的「暂时」，在被复制的那一刻就变成了永久。
3. **两份同类模板必须给出同强度的标准** —— 同一份产物里，
   Go 模板有测试而 Node 模板没有，抄哪份就决定了你有没有测试，而使用者不会知道自己抄的是弱的那份。

⚠️ 与 **E2** 的分工：E2 管「承诺指不到实现路径」，
本条管「**承诺的实现路径在原处存在，但不会跟着复制品一起走**」——
后者更隐蔽，因为在原处怎么查都是对的。

## F · 活性与降级 —— 写长耗时 / 异步 / 后台任务时

对每一个长耗时 / 阻塞 / 可能失败的步骤，问三句：

### F1 · 卡住会怎样

有没有**墙钟超时**？还是无限等一个 native 解析 / 子进程 / 锁 / 网络？

**无超时的阻塞调用 = 缺陷**，不是「一般不会卡」。

> **适用面**（2026-09-10 外部评审收窄）：说的是**请求 / 任务 / 探针路径**上可能无限等待的
> 外部 I/O、锁、子进程。三种情形豁免：**进程生命周期本身的等待**（事件循环、主循环、
> 等关闭信号）、**已继承上游 deadline 且能被取消**的调用、**必须保证原子性的短事务**。
> 豁免不是免责：前者要有明确的关闭信号与健康契约，中者不许再叠一个与上游冲突的本地超时。

> ⭐⭐ **保活是双向的，配了一半等于没配**（第 19 次外部实战，2026-09-06 rerank SSH 反向隧道）：
> 客户端配了 `ServerAliveInterval`（检测**死服务端**），服务端 sshd 却是 `ClientAliveInterval 0`
> （不检测**死客户端**）⇒ 客户端异常断开后，服务端那个会话成僵尸、**永久持有转发端口**，
> 新隧道再也建不起来（每 10s 退 255、日志刷屏、无告警）。**launchctl 显示有 PID + 上次退出码 255，
> 让人以为它活着——实际每 10s 死一次。** 排查的坑：根因在**连接的对端配置**，不在本机服务定义（plist 完全正确）。
> ⇒ 凡「长连接 / 隧道 / 心跳」两端，问一句：**谁负责发现对面死了？两个方向都要有人管。**
> ⚠️ 我在这条里现犯「错误诊断」：先用「端口 LISTEN 但 ESTAB=0」判僵尸（错判据——ESTAB=0 只表示没人在用），
> 结论侥幸对了。**活性的唯一可靠判据是端到端走一遍它声称提供的能力**（M1），不是看端口/进程/连接数在不在。

> **防重入守卫会把一次卡死升级成永久闩锁**（第 17 次外部实战，2026-09-06 DiskBar）：
> 「一次只读一个」的守卫防住了排队，但被守的那次读永远不回来时，标志位永远是 true——
> 此后**每个周期都被自己的守卫拦掉**，而系统另一半（吞吐采样）还在动，界面看起来活着。
> 凡写 `if (inFlight) return` 都要问：**inFlight 由谁在多久之后强制清掉？** 释放阀要配
> 「旧读落地不覆盖新数据」，否则解决了冻结又引回脏写。

⭐⭐ **比「没写超时」更常见的是：超时写了，但**在后面被资源清理抵消**
（第十三次外部实战，2026-09-05，实测确认）：

```python
with ThreadPoolExecutor(max_workers=w) as ex:
    futs = [ex.submit(job, x) for x in items]
    done, pending = wait(futs, timeout=T)     # ← 看起来这里就是时间上限
    for f in pending: f.cancel()              # ← 看起来还兜了一层
# ← 真正的等待发生在这里：with 退出 = shutdown(wait=True)
```
**最小复现**：两个 `sleep(4)` 的任务 + `wait(timeout=0.5)` + `cancel()` ⇒
`wait` 确实 0.5s 返回、`cancel()` 全返回 **False**（已开始执行的取消不了），
而**离开 `with` 之后总用时 4.0s**。

⇒ 这段代码读起来有两层超时保护，实际**一层都不是上限** ——
真正的上限只能来自**任务函数自己**（它内部的 deadline / socket timeout / 子进程 timeout）。

⚠️ 同族的还有：`subprocess.run(timeout=T)` 杀的是直接子进程，**孙进程仍在跑**；
`signal.alarm` 打不断**持 GIL 不返回解释器的原生计算**与**内部自行重试 EINTR 的第三方 C 库**，且仅主线程有效
（⚠️ 2026-09-15 实测收窄：此前写「打断不了 C 扩展里的阻塞调用」过宽——`time.sleep` / 无超时 `socket.recv`
这类遵守 PEP 475 的标准库阻塞调用，alarm+handler 抛异常**恰恰打得断**，实测 1.0s 应声中断）；
`asyncio.wait_for` 取消的是协程，**它已经发出的系统调用不会回滚**。

⇒ **自检一句**：**「这个超时到点之后，谁会真的停下来？」**
答不出具体是哪个调用会返回，那它就只是「不再等结果」，不是「不再占用时间」。
⇒ 这类地方要**就地写明真正的上限在哪**（本次实战即在那行加了注释）——
否则下一个改任务函数超时的人，不会知道自己拆掉的是唯一那道闸。

### F2 · 炸了会怎样

异常 / 线程崩，是被 **检测 + 记录 + 降级 + 对用户可见**，还是被静默吞掉、后台线程无声退出、UI 冻在中间态？

**空 `catch` 吞掉用户操作失败**是这一类里最常见的形状。
⭐ **告警分支是全仓最少被执行的代码，因此 bug 存活率最高 —— 而它出错的时刻正是最需要它的时刻。**
> 实证（本文自身与关联仓库，2026-09-05，一天四次同型）：
> `$VAR` 紧跟全角标点（`exit=$CODE）`、`rc=$rc（`、`请手工检查 $F（备份在 $BAK）`）——
> bash 3.2 会把多字节字符连读进变量名，`set -u` 下**直接崩**。
> 四次里**三次落在告警/错误路径上**：日报投递失败的告警文案、保温探测失败的日志、
> 反向测试「还原失败」的提示。
> 它们平时永远不执行，所以**测多少遍正常路径都碰不到**；
> 而它们一旦被执行，恰恰是系统已经出问题、最需要有人说话的那一刻。

**两条做法**：
1. **错误分支要有一次真的执行**：注入一个必然触发它的输入，看它**说出完整那句话**
   （不是看它「没崩」—— 崩了才是常态）。这是 **D20** 用在错误路径上。
2. 能机械化的形态就做成判据（本 skill 的 `[10k]` 即此：`$VAR` 紧跟全角标点直接报红），
   因为这类 bug 靠评审看不出来 —— 那行代码读起来完全正常。

⭐ **catch 的宽窄是同一枚硬币的两面，两面都会「指错方向」**（2026-09-05，两条同日实证）：

| 形态 | 机制 | 症状 |
|---|---|---|
| **catch 太宽**（`case-05`） | 顶层 catch 把基建失败也收进来，给了一个产品语境的结论 | 文案说「页面直接崩了」，而真因是 Chrome 没起来 ⇒ **去查一个不存在的缺陷** |
| **catch 太窄**（本文自身） | 只 catch 你想到的那一个异常类，别的**漏给上层的宽 catch** | 只 catch `FileNotFoundError`，而 `PermissionError` 漏到上层 ⇒ 被折叠成「拉取失败 / 订阅凭据已失效」，**真因是文件权限 000** |

> 实证（本文自身）：一个从没被执行过的 fail-fast 路径，按本条做法 1 真跑了一遍，四种情形里
> **前三种正确、第四种把「文件不可读」报成了「订阅链接/凭据很可能已失效」** ——
> 退出码也从 4（配置问题）掉成 3（拉不到）。照它去查，会去登面板换 token，而问题在 `chmod`。

⭐⭐⭐ **「catch 太窄」的一个特别阴的子形态：异常层次不是你以为的那样**
（2026-09-05 一天内**两次独立实证**，两个不同的项目、两种不同的标准库）：

| 你写的 | 你以为它接住了 | 实际 |
|---|---|---|
| `except urllib.error.URLError` | 网络类错误，包括超时 | **`socket.timeout` 不是 URLError 子类** ⇒ 读超时穿过去，抛整屏 `ssl.py` 调用栈 |
| `except OSError`（读 PNG 头） | 文件相关错误 | **`struct.error` 不是 OSError 子类** ⇒ 截断的图片让整个门禁崩在读图这一步 |

两次都满足同样三个特征，所以特别难防：
1. **写法看起来完全正确**，而且是推荐写法；
2. **静态检查一个都不响**（语法、类型、lint）；
3. **失效方式是「穿过去」而不是「报错说不支持」** —— 你看到的调用栈离真因很远。

⚠️ 还要叠上**版本维度**：`socket.timeout` 在 **Python 3.10+ 就是 `TimeoutError` 的别名**，
所以同一行代码在新解释器上完全正确、在 3.9 上失效（详见 **K1**）。

⇒ **做法**：写 `except` 前，**用一行代码把你的假设验掉**，别靠记忆：
```python
import socket, urllib.error, struct
issubclass(socket.timeout, urllib.error.URLError)   # False —— 我原以为是 True
issubclass(struct.error, OSError)                   # False
```
> 这一行的成本，远低于「异常穿过去之后照着一屏无关调用栈去查」的成本。

⭐ **共同的判别口径**：写下每一个 catch 时问一句 ——
**「掉进这个 catch 的异常，有几种来源？我给出的那句话对每一种都成立吗？」**
只对其中一种成立，就说明这个 catch 要么该收窄、要么该按来源分叉。
⚠️ 尤其注意**上层还有一个宽 catch** 的情形：你这一层没接住的，会被它接住并**换一套说辞**。



### F3 · 顺序对不对

> ⭐⭐ **并发与事务一致性**（2026-09-10 外部评审指出这是本层的空缺；并入本条而不新增编号）：
> 「顺序对不对」在单线程里问的是步骤先后，**在并发里问的是同一件事被两个执行流看见时还成不成立**。
> 六条最小要求：
> 1. **共享可变状态要有唯一的所有者和一种同步机制**，并写出来（谁能写、拿什么锁 / 走哪个 channel / 属于哪个 actor）。
> 2. **check 与 act 必须在同一个原子边界内** —— `if (!exists) create()` 之间任何一次让出都可能让两边都创建成功。
> 3. **不得跨不受控的外部等待持锁**（拿着锁去发 HTTP / 等子进程 = 把别人的超时接到自己的临界区上）。
> 4. **多把锁必须有全局顺序**，否则就是等着发生的死锁。
> 5. **取消与 deadline 要往子任务传播** —— 父任务超时了而子任务还在跑，就是 F1 的另一种形态。
> 6. **数据库写与消息发布无法原子提交时**，用 outbox / inbox、幂等消费或等价的恢复协议；
>    并为**竞争、崩溃点、重放**写确定性测试（随机压测不算，它复现不了具体交错）。

用户可见的完成态（`done` / 结果页 / 落盘快照）是不是被排在**一串重活之后**？任一重活挂死就永远到不了终态。

**把完成态尽量前移——但只对「可以失败的收尾」**：先让状态可见，再做那些**失败了也不影响这次请求正确性**的收尾（清理 / 通知 / 缓存预热）。
> ⚠️ **必要步骤(用户请求的一部分、持久化提交)完成前不许报终态**——那是谎报，违反 A8/H7（2026-09-09 codex 评审:原文「完成态尽量前移」不加限定会诱导提前报成功）。需要降低等待感时,发**明确的中间态**(`PROCESSING` / `CORE_DONE_CLEANUP_PENDING`),而不是提前发 `done`。前移的只能是 best-effort 收尾,不是必要步骤。

### F4 · 一个坏输入不得拖死整条流程

批处理里的单条失败要能被隔离、记录、跳过，而不是让整批停在那儿。

> **适用条件(2026-09-09 codex 评审):先声明批处理语义,别默认「跳过坏输入」**。事务、账务、安全扫描、一致性迁移常必须 **fail-closed**(一条坏就整批停,绝不静默跳过)。四种语义先选一种再写:**best-effort**(尽量跑完)/ **逐项隔离**(坏的跳过、好的继续)/ **阈值停止**(坏超 N% 就停)/ **全有全无**(事务性)。「隔离跳过」只是其一,不是默认——选错会把该拦的坏数据放进下游。


### F5 · 刹车必须落在磁盘上 ⭐⭐

**内存里的超时跨不过进程消失。**

> 实证：生成用的子进程有 15 分钟硬超时，**而那个 `setTimeout` 活在父进程内存里**。父进程一消失（force quit / 崩溃 / 任何非正常退出），子进程 reparent 到 `PPID=1`，超时随之消失，无限期占 ~75% CPU；下次启动重排任务再 spawn 一个 ⇒ **每次中断累加一个孤儿**。`ps` 当场抓到一个已经跑了 4 小时 26 分的。

**三件事**：

1. **退出路径杀掉孤儿**——**仅当目标是无一致性状态的进程**（纯计算 / 无事务、无未刷盘写，如本例的生成子进程）时直接 SIGKILL：宿主随后就退出，「先温和后强硬」的升级路径结构上不可达。⚠️ **若子进程可能有未提交事务或未刷盘的写,先发 SIGTERM + 有界等待,确认不破坏一致性再强杀**;需要跨宿主生命周期回收时交给 supervisor / 进程组 / 独立 reaper,别依赖即将退出的父进程（2026-09-09 codex 评审:原文无条件 SIGKILL 会漏掉后者)。
2. **把 pid 落到磁盘**，启动时回收上次的孤儿（⚠️ 回收前校验该 pid 确实是目标进程，**pid 会被系统复用**）。
3. **同族全查一遍**（同一个 app 里的语音播报进程同样没有任何退出路径管它，app 关了声音还在念）。

⭐ 副作用值得单记：**孤儿进程会把后续所有性能类判据变成假红**——排查性能异常前先看机器上还跑着什么（同 D7）。

### F6 · 超时值不能猜一个大数 ⭐⭐

要么取**被守护路径的确定性上界**，要么**把那条路确定化**。

> 实证：给一个可能挂死的异步判据加了 15s 看门狗，数字是**从另一个判据文件原样搬来的**，没有重新测量新宿主：被守护的那段里有三次网络调用，其 DNS 兜底预算本身就是 10s ⇒ **正常最坏耗时超过看门狗**，于是它分不清「挂死」和「慢」。单跑 8 次红 3 次。

⭐ 顺带一条独立的认识：**把「静默假绿」换成「不确定的假红」，是一类独立的失败形态**——它比原状态好（问题终于可见了），但**只许作为限时过渡态存在**：停在这一步长期保留，就成了 **G4** 说的「会随机变红的门禁训练人忽略红色，比没有更糟」——两条不矛盾，分界是**过渡态 vs 稳态**。

### F7 · 周期性机制的**窗口**必须大于它自己的**周期** ⭐⭐⭐

只要一个东西是「每隔 T 跑一次」，它身上通常还挂着若干个**窗口**：
日志的保留期、告警的提前量、缓存的 TTL、重试的放弃时限、凭据的续期余量。
**任何一个窗口如果短于 T，它就会在两次执行之间悄悄关闭** —— 那一段时间里它等于不存在。

⚠️ **只对「需要连续覆盖」的窗口成立**（2026-09-10 外部评审收窄）：证据/日志保留期、
凭据续期余量、告警提前量、租约续约窗口——这些断掉就有一段真空。
而**缓存 TTL 与重试放弃时限不属于这一类**：缓存常常**故意**在下次刷新前过期并回源，
重试预算通常**就该**小于整个任务周期。它们要证的是另一件事——**到期后的 fallback 是安全的**。
⇒ 先问「这个窗口断掉的那一段时间里，有没有东西失去保护」，再决定它该不该大于 T。

⭐ **实测（外部实战，2026-09-05，`com.feishu.token-refresh`）**：
一个**每 7 天**跑一次的 launchd 任务，日志写在 `/tmp` —— 而**下一次跑之前日志已经不在了**。
（⚠️ 2026-09-10 复核：此前这里把机制写成「macOS 清理 `/tmp` 的周期约 3 天」，而本机 `/etc/periodic/daily/` 下只剩 `999.local`，**这个周期数没能证实**。**现象是实测的，机制标未查明**——本条要的结论不依赖那个数字：**别把要跨周期存活的东西放在系统会回收的目录里**。）
后果**不是「日志少了」**，是更难受的一件事：

> 排查时，「**它从未执行过**」和「**它跑过，日志被清掉了**」两种解释**都能解释现场**。
> 也就是说，「这个任务到底跑没跑」变得**不可判定** —— 而这正是你最需要知道的那件事。

同一个任务上的第二处：它每周检查一次凭据是否将过期。
若把提醒阈值设成「剩余 < 3 天」，而检查每 7 天才发生一次 ——
**凭据完全可能在两次检查之间从「剩 8 天」直接走到「已过期」，一次提醒都不会发出**。

**⇒ 一条可以直接算的判据**：
| 窗口 | 下限 |
|---|---|
| 证据（日志/审计）保留期 | **> 执行周期**，否则「跑没跑过」不可判定 |
| 预警提前量 | **≥ 执行周期**，取 **2×** 容错「错过一次」 |
| 缓存 TTL / 重试放弃时限 | **先按上面的收窄注分类**：多数缓存/重试**不属于**连续覆盖类（短于周期常是正确设计），要证的是**到期后的 fallback 安全**；确属连续覆盖的才要求 > 周期（2026-09-15 修正——此行原写「别让它在两次刷新之间失效」，与 15 行外的收窄注正好相反，是 09-10 收窄前的旧文未同步） |

⚠️ 它和 **E4**（内外层超时不得相等）是同一族：E4 管**嵌套**的两个时间，本条管**周期与窗口**这两个时间。
两者都不会让任何东西报错 —— 系统在窗口关闭的那段时间里安静地什么都不做。

⇒ 自检一句：**把这个东西身上所有的时间常数列出来，逐个和它的执行周期比一次。**

## G · 规模与真实产物 —— 写会长大的东西时

### G1 · 目标规模下是线性的吗

写的当下就回答：这段在 1× 和目标规模（10× / 100×）分别是什么复杂度？**超线性的要标出来并给上界**。

⚠️ 单函数看着 O(n) 的一串步骤，**串起来在数千条数据上仍可能挂死**——要看完整集成路径，不是单个函数。

### G2 · 无界即缺陷

无界缓冲 / 无界递归 / 无上限的外部调用 / 无上限重试——每一个都要么有界，要么写明为什么可以无界。

⚠️ **「缺 LIMIT」只是审查候选，不是判据**（2026-09-10 外部评审收窄）：完整聚合、流式 cursor、
已被唯一键限制的查询、离线迁移都可能合法地没有 `LIMIT`；反过来，**随手加一个 LIMIT 会静默截断正确结果**
（那正是 A4 治的病）。真正要判的是：**这条查询会不会把不受信输入完整物化到内存/网络/事务里**。
⇒ 结合唯一性约束、聚合语义、消费方是不是流式、调用方的资源预算一起看，而不是 grep 一个关键字。

### G3 · 代码要能在发布产物形态下跑

路径、资源定位、依赖解析**不得依赖源码树布局**。打包 / 冻结 / 容器化之后失效的写法（`__file__` 相对路径、读 `../config`、依赖 dev 目录结构）在开发机上永远不会暴露。

### G4 · 性能阈值设在实测中位的 10–30 倍

阈值防的不是「慢」，是**某次改动让热路径慢一个数量级而没人发现**。

> **适用条件(2026-09-09 codex 评审):标题的「10–30 倍 / 中位」是启发式,不是跨项目硬阈值**。① 面向**用户体验 / 服务目标**用**产品 SLO 或明确预算**,不用这个倍数;② 十倍回归很多时候**已经是严重故障**,别把阈值设这么松就当安全;③ **统计量按用途选**——在线服务常要 **p95/p99**,不是只看 p50/中位;④ 算法复杂度用**规模曲线 + 斜率**判,不用单次墙钟 `min`(min 受偶然最快样本影响);⑤ 页面体验指标(LCP/INP/CLS)**仅用于网页**,别当通用 API 延迟阈值(那是 Z1 的场景,不是这条)。下面的「断言倍率」是本条推荐的稳健做法。

**宽阈值抓数量级回归；窄阈值只抓抖动——而抖动造成的假红会让这条判据先被加豁免、再被删掉。**

必配两样：①**退化前提断言**（输入本身残缺时这轮数字不可比）；②**无累积退化**（同一操作第 1 次与第 500 次一样快）。反向验证同样必须做：注入一个数量级退化，确认它当场红。

⭐ **更彻底的做法：断言倍率，不断言绝对墙钟**（`case-e9` 实测）。
> 性能门禁阈值 2000ms 是**空闲机器上量一次 224ms** 定的；而那台机器常年并行多个会话，
> **load average 31 时同段代码实测 2971 / 7765 / 7976ms**。
⇒ 改成**同一次运行里新旧各测一遍、断言两者的倍率**，就对整机负载免疫。

⭐ **推论：时间最好只用来「等」和「算比值」，不用来「判快慢」**（2026-09-05 汇入）。
并发跑测试时，**中位数与均值都是被污染的估计量**：一道性能门取中位，同一棵干净树同一项
实测 69 / 121 / 225 / 262 / 292ms 对 120ms 阈值，**单跑十次红四次**；
而据「单跑五次全绿」判过一次抖动 —— **那是抽样运气**（同 **D13** 的采样下限）。
**会随机变红的门禁会训练人忽略红色，比没有更糟**（同 B7、A13）。

⭐ **倍率和绝对界要用不同的统计量，因为它们守的不是同一件事**（`case-55` 落地结论）：

> ⚠️ **2026-09-10 外部评审指出这张表与上面 ④ 直接打架**（上面说「复杂度不用 min」，
> 表里却写「规模倍率用 min 守复杂度」），而且「竞争只会让耗时变大」也不成立 ——
> JIT 预热、缓存命中、DVFS、计时分辨率都会让最快样本偏低。**这是同一页上的自相矛盾，按下表统一。**

| 目的 | 统计量 | 为什么 |
|---|---|---|
| **复杂度 / 规模趋势** | 多档输入规模，每档**预热后多次采样**，对**中位或稳健分位数**拟合斜率 | 要的是曲线形状；单点 min 会被偶然最快样本带偏 |
| **在线服务的延迟目标** | **p95 / p99** + 错误预算 | 尾部才是用户投诉的来源；p50 只描述中位那次请求 |
| **网页体验（CWV）** | 真实用户 page views 的 **p75** | Google 的判级方式就是 p75，不是单次测量（Z1 场景） |
| **单机诊断** | `min` 只当「最好情况」的**辅助信息** | 可以用来看「理论下限有没有变」，**不能单独证明复杂度或体验** |

⚠️ **任何放宽统计量的改动，都必须配一次「坏样本仍能红」的证明**，否则就是**悄悄降标准**。
> 他改完之后注入真正的 O(n²)，倍率 **23.8×**（阈值 20×）精确报红 —— 这一步才是改动成立的依据，
> 而不是「改完还绿」。

⭐⭐ **阈值该多宽，由它的「阻断力」决定，不是由测量精度决定**（本文作者当天现犯，2026-09-05）：
我给自己的门禁加耗时自报告，把阈值设成 **2×** —— **而上面这条 G4 白纸黑字写着 10–30×**。
当天就在真实负载下误报一次（本机 8–12 个会话并行，实测 load 22 / 8 核，
同一份代码串行单跑低负载 2s、高负载 8s，**差 3.5 倍**）。
> **我自己写的条款里已经有答案，而我在自己的门禁里没照做**（同 **H10**：引用一条规则不等于遵守它）。

但这里有一个**真实的张力**，值得写清楚而不是简单认错：

| 用途 | 阻断力 | 合理倍数 | 为什么 |
|---|---|---|---|
| **性能回归门禁** | 判失败 | **10–30×** | 假红会让判据先被豁免、再被删掉，代价极高 |
| **基线漂移提醒** | 只打印 | **2–3× 可以接受** | 假阳性代价只是一行字；而 10× 会让「4 倍劣化」完全漏掉 |

⇒ **同一个时间阈值，阻断的那个必须宽，不阻断的那个可以窄。**
把两者混为一谈，会在「漏掉真劣化」和「制造假红」之间二选一，而其实不必选。
⚠️ 前提是**它真的不阻断** —— 一旦有人把提醒改成失败，倍数必须同时改宽，否则就是给全机器的门禁埋一片假红。

⭐ **另一半：在共享机器上报告性能改进，必须把当时的负载一起写下来。**
否则那个「快了 7 倍」无法被任何人复核，也无法和下一次比较 ——
它里面混着多少是优化、多少是别人的会话刚好跑完，没有人知道。
（本文作者同日先犯：在 2.75× 过载的机器上用少次采样报了「15s→2s」，
 结构性改进是真的——90 次 `fork+exec` 确实没了——但那个倍数不是纯的。）

### G5 · 地板要设在退化值之上

> 实证：服务目录在缺一个缓存文件时从 175 掉到 19（全新 clone / CI 无网 = 正常状态），而地板写的是 `>= 15` ⇒ **静默丢掉 89% 覆盖还报绿**。

**地板数的是「够不够」，不是「有没有」。**

## H · 诚实边界与停手 —— 卡住的时候

<!-- IDX:H:BEGIN 组内索引：本组每条都必须在此出现（门禁校验闭世界）-->

**卡住时** — **H1** 「做不到」要写失败路径，不要给结论 · **H2** 归因要有证据，「未查明」就写未查明 · **H3** 认得出结构性无穷回退，到收益边界时停手 ⛔ · **H8** 收敛的判据不能是「本轮没发现」，要是「换一个不自我指涉的问法也没发现」

**交给人 / 交接** — **H4** 四种情况停下问人 · **H5** 遗留问题必须带四件套 · **H6** 别人给的诊断照单全收，修法一律自己推一遍

**收尾** — **H7** 收尾自我对账 · **H9** 长时任务的中间结论必须落在进程之外 · **H10** 引用一条规则，不等于遵守它 · **H11** 能解释全部症状的结论最难被推翻

<!-- IDX:H:END -->

### H1 · 「做不到」要写失败路径，不要给结论 ⭐

> 实证：我把「跨进程确定性触发 EPIPE 本机构造不出来」写进注释，复核者当场用 5MB 大写入做出来了。

「我试过了，做不到」长得像诚实，实际把**「我没找到方法」写成了「这件事做不到」**，而且**写进注释后就没人再去试了**——比不写更糟。

**正确形态**：说清楚**我试了什么、失败在哪一步**（「我用 `stdin.destroy()` 试的，只看到超时」——别人一眼看出漏了「写入量要撑满管道缓冲」），**而不是给出一个结论**。

凡要写「做不到」，先把失败路径写下来，再问这句结论是不是**只对你试的那一种方法成立**。

### H2 · 归因要有证据，「未查明」就写未查明

> 实证：我把一次未复现的失败写成「最可能的解释是复核者在活动工作树里跑变异」——被证伪。我写那句时手上**没有任何证据**，只是它**听起来合理**。

**一个听起来合理的归因，会让后来的人停止寻找真因。**

⚠️ **而且它会传播**：`case-05` 把一条错误归因（「起因大概率是 `git add -A`」）**写进了提交信息并推送**，
之后才被受控实验证伪。⇒ **归因一旦进了 commit message / 文档 / 事故报告，它就不再只是你的判断了。**
订正的成本远高于当初多花三十秒做个对照实验。
⇒ 他的处理值得照抄：**在原地标注「这条本身就是『归因错了修法就会错』的实例」**，而不是悄悄改掉。

### H3 · 认得出结构性无穷回退，到收益边界时停手 ⛔

识别信号（三条同时出现）：

- 每一轮的修法都对，而下一轮总能在**相邻一格**找到同型缺口；
- 每次「换承重物」之后，**新的承重物自己又是一层枚举**；
- 缺陷数不再下降，而**修复的对象从产品代码变成了判据本身**。

这时要问的不是「再写一条什么判据」，而是——

> **「这条链上所有攻击的前提是什么？那个前提由谁守？」**

如果前提是「能编辑源码」，那它由**提交边界 + 代码审查**守，**测试在原理上守不住一个能任意改源码的敌手**。继续加判据只会不断提高「改坏它需要多聪明」，而不会到达「改不坏」。

**停手时必须**：①把判断连同趋势数据写下来（不是悄悄停）；②明确移交残余风险给哪条边界；③**诚实记录未收敛且不放行**，不伪造收敛；④点清这条线**实际修掉的真实缺陷**，证明它不是白跑。

### H4 · 四种情况停下问人

不可逆操作 / 生产数据面 / 方向性二选一 / 需求真空。其余自主做完，结尾汇总。

### H5 · 遗留问题必须带四件套

`owner + 到期日 + 复审触发条件 + 当前缓解措施`。**缺任何一项 = 这不是「遗留问题」，是「未修问题」。**

**没有到期日的遗留问题 = 永久接受风险，且没人记得。**

⭐⭐ **「待改」这个状态是混装的，必须拆开**（2026-09-10，peer 会话 `case-5c` 回流）：
登记表里一条「待改 / TODO」，读的人默认理解成「**还没轮到**」；
而它常常真正的意思是「**试过了，做不到**」。**两者在表里长得一模一样，意义完全相反**——
前者是排期问题，后者是能力/设计边界，后者还携带着一份**下次不必重走的实证**。

⇒ 登记表至少要分得出三态（与 A1 同构：**别把三种状态塌成一个词**）：

| 状态 | 含义 | 必须带 |
|---|---|---|
| **未试** | 还没轮到 | 四件套（owner / 到期日 / 复审触发 / 缓解） |
| **试过做不到** | 已尝试并失败 | **失败的具体原因 + 复现方式**，以及**重开条件** |
| **决定不做** | 评估后主动放弃 | 理由 + 反对者可以拿去反驳的依据（同本文「定档理由要写出来让人能反对」） |

> **实证**（`case-5c` 那次）：某个解析器豁免项从「待改」变成「试过改不动」——
> 产物用 `---` 当分节符，而 CommonMark 里紧跟正文的 `---` 是 **setext 二级标题**，
> 正确的解析器会在那里切断，导致**正例变红**。⇒ 回退，并把这段实测理由写进豁免表。
> **「试过、失败、写清为什么」比继续挂一条「待改」诚实。**

⚠️ **同一天本文自己也栽在这个形状上**：`[11]` 判据被写成「**结构上**验不了」，
而真相是「我这个实现做不到」——换个变异对象当场就测到了（见 `references/gates.md`）。
**「做不到」和「没试过」都不该伪装成「不可能」。**


### H6 · 别人给的诊断照单全收，修法一律自己推一遍

> 实证：复核者建议把顶层 `return` 换成 `void` 并报告「四块全绿」。但那四块**没有任何环境变量管理**，而恢复 env 的 `.finally()` 是异步的——它们会同步抢跑在夹具的临时目录上，「全绿」是在**错误环境**下的巧合。

**外部复核者的诊断通常比它给的修法可靠：证据照单全收，修法一律自己推一遍。**

### H7 · 收尾自我对账 ⭐⭐

> 实证：同一个 diff 里，一半写下「纯源码文本断言是空的」并把措辞抽成纯函数，另一半守投递的却是数调用次数；同一次提交里写下「判据必须消费生产代码本身」，而自证探针在重算旧匹配器；修好了一个 fire-and-forget，同次提交编辑的另一个文件里还留着一个同型的。

**「知道」和「做到」之间没有自动通路。** 这是常态，不是意外。

**收尾时专门做一遍自我对账**：把本次提交信息里写下的每一条原则，拿去逐条核对本次 diff 的**每一处**改动——**尤其是那些不在你注意力焦点上的另一半**。

⭐⭐ **对账的粒度是「条目 × 被点名的位置」，不是「条目」**（2026-09-10 本文自身实录，同一天连栽三次）：
处理一份外部评审的 41 条意见时，我先后被问了三次「都处理了吗」，**三种问法各抓出一类不同的漏**：

| 问法 | 漏的是什么 | 成因 |
|---|---|---|
| 「都**评估**过了吗」 | 4 条**多部分建议只做了前半**（要求改 A 和 B，改完 A 就记账「这条处理完了」） | 按**条目**记账，而一条意见常常点了两处 |
| （再问一次同一句） | 1 条真漏：同一条意见**点了两个文件**，我只改了一个 | 上一轮是靠**读 + 回忆**回答的 |
| 「你**认可**的都采纳了吗」 | 2 条**认可但没落地**（其中一条我还给了个**错的理由**挡掉它） | 「认可」被当成了「做了」 |

⇒ **三条做法**：
1. **对账表按格子画**：行是意见条目、列是它点名的**每一个文件/每一个子建议**，逐格打勾——
   「这条处理过了」是**按条目**的记账方式，而漏就漏在同条的第二格。
2. **别靠读和回忆核，拿原文当锚点去 `grep` 现状**：外部意见都会引用「原文」，
   原文原样还在文件里的就是嫌疑（实测：41 条里 11 条有残留，逐个判后 10 条良性、**1 条真漏**）。
   ⚠️ 残留在自己写的「此前这里写的是……」更正注里属于良性——**要逐个看，不能只看命中数**。
3. ⚠️ **格子要看内容，不能看「这个文件动过没」** —— 那是个**弱代理**：一个文件常常是因为
   **别的条目**被改的。实测（就在写下这条之后立刻跑了一遍）：41 条 × 68 格在**文件粒度全绿**，
   逐格看内容却抓出 **3 格假 ✓**，全是同一个形状——**同一条意见点了两处，我只改了一处**：
   一处是同一个前提**有一份副本**没跟着改（I2）；另两处是内容加对了地方，
   但**从「意见指出问题的那个位置」走不到它**（可达性缺口，同 **I3**：一个规则要沿全部调用点铺开）。
4. **「认可」和「已落地」分开记两列**。尤其警惕自己给出的**结构性理由**
   （「做不到 / 需要 X 而 X 不可能」）：本轮我用「变异需要换行、TSV 放不下」挡掉一条，
   而换个锚点形状根本不需要换行 —— **那与「结构上验不了」是同一个形状：
   把「我没想到另一种做法」说成了「做不到」。**

> **本文自己的实录**：写这份规范时按 H7 做收尾对账，在**自己的产出里**连抓 3 处 E2 漂移——
> ①`derivation.md` 写「覆盖到的铁律 1–68」，实际只反推了 45 条（另 23 条是审查侧专有、被显式排除）；
> ②给门禁加了第 7 组检查后，正文仍写着「6 组 9 条」；③改成「7 组」后实际是 8 组（`[0]`–`[7]`）。
> 三处都不会让任何东西报错，也都在我刚刚写完「承诺必须能指到实现路径」之后发生。
> **这就是 H7 说的「常态，不是意外」。**


### H8 · 收敛的判据不能是「本轮没发现」，要是「换一个不自我指涉的问法也没发现」 ⭐⭐

> 实证：连续七轮「专审刚落地的修复」，发现数 12→10→5→8→6→4，第七轮比例走到 **生产缺陷 0 : 判据不承重 4**，看起来收敛了。**而它是错的**——那个框架天然只在判据面上产出，因为**每轮新写的判据就是下一轮的新审查面**，这个循环可以无限进行而生产代码的真实状态无人知晓。换成「只审生产代码、走真实用户路径」的问法后，一轮抓到 6 条真实缺陷（2 条 HIGH），**没有一条落在前七轮反复加固的点上**。

**识别信号**：本轮发现**全部落在判据层、生产代码零改动**。

**这时不要宣布收敛，也不要继续同一个循环**——换一个**只审产品行为、明确拒收判据质量类发现**的问法（走真实用户路径、边界值、并发时序、错误路径）。

⚠️ 与 H3 的区别：H3 是「攻防无穷回退，该停手移交」；这条是「**你以为收敛了，其实只是把自己的判据审干净了**」。前者要停，后者要**换问法继续**。

### H9 · 长时任务的中间结论必须落在进程之外 ⭐⭐

> 实证：复核者跑完了十次复现、建了七个夹具、五个工作树，**在写最终报告时被 502 打断，报告全丢**。
> 救回来的唯一原因是它的中间产物（每次运行的 JSON）留在了磁盘上。

⇒ 派长任务时明确要求：**每定案一条就追加写进一个文件**，最终响应只是汇总；
并**限定报告字数**——长响应本身就是挂掉的主因。

**同理适用于任何长时子任务：中间结论必须落在进程之外的地方。**

### H10 · 引用一条规则，不等于遵守它 ⭐⭐⭐

> 实证一（`case-c0`）：他写变异扫描脚本时**在注释里引用了 M6**（环境没就绪 ≠ 跑了不合格），
> 而那个脚本**恰恰违反了 M6**——基线偶发失败被直接报成「门禁没抓到」。
> 实证二（本文自身，同日）：我写下 **B15**（判据用自己的定义圈全集，圈不到的静默消失）与
> **D22**（断言函数吞掉条件参数）之后，用这两条去审**我自己的门禁**——**两条全部命中**。
> 条款是我写的，违反也是我犯的，中间隔了不到一天。

> 实证三（`case-55`，同日第三例）：他给「假断言」写的元门禁，**第一版就用了会被字符串里 `/*` 骗到的
> 纯正则剥注释**，误报了一道 —— 而那道元门禁要治的正是「判据自己不可信」。

**一天之内三个独立会话各撞一次，形状完全相同：写规则的人在写守它的判据时立刻犯了它。**

**「知道」和「做到」之间没有自动通路**（同 H7），而**引用**比「知道」还要弱一层——
它给人一种「我已经处理过这件事了」的感觉，恰恰阻止了去检查。

⇒ 两条可操作的：

1. **凡在注释 / 文档里引用了某条规则，就要能指出这段代码的哪一行在遵守它**（同 E2）。指不出来 = 只是引用。
2. **写完一条规则后，第一件事是拿它审自己已有的代码**——尤其是**守这条规则的那个判据本身**。
   本文的 B15 / D22 就是这么抓出来的。

### H11 · 一个**能解释全部症状**的结论，正因为「哪儿都对得上」而最难被推翻 ⭐⭐⭐

排查在「找到一个说得通的解释」时停止，而不是在「找到真因」时停止。
**当那个解释恰好覆盖了你观察到的每一个现象，就再也没有东西提醒你继续查了** ——
矛盾感是继续追查的唯一燃料，而完美的错误结论把燃料烧干了。

实证（`case-05`，2026-09-05，他自己发现并订正）：
后台跑一个脚本，观察到三件事 —— **退出码 0**、**产出文件 0 字节**、**父进程确已退出**。
结论「父进程退出把子进程带走了」**同时解释了这三条，没有任何一处对不上**，于是排查到此为止。
十分钟后 `pgrep` 显示那个进程**一直活着还在跑**：
真因是 **Python 重定向到文件时 stdout 全缓冲 + 任务根本还没跑完**。

> **实证二（本文自身，2026-09-05，写完这条当天就用它推翻了自己的结论）**：
> 一个订阅同步任务持续 403。观察到：四种 UA 全 403、直连与代理都 403、
> 而后端面板 API 仍 200。结论「**订阅 token 被轮换了，去面板拿新 token**」——
> 这三条它全解释得通，于是写进了给用户的报告。
>
> 按本条做法 1 反问「如果 token 真被轮换，还应该能观察到什么？」⇒
> **换一个明显错误的 token，响应应当与真 token 不同**。实测：
> 真 token / 全零 token / `deadbeef` —— **三者返回完全相同的 403 和完全相同的 6614 字节响应体**。
> ⇒ **服务端根本没读 token**；403 发生在 token 校验**之前**（Laravel 框架级 `abort(403)`，无自定义文案）。
> ⇒ 原结论被推翻：**换 token 不可能修好它**。
> 若照原结论行动，用户会去登面板、重新生成 token、粘贴回来 —— **而那什么也改变不了**。
>
> ⚠️ 注意这次「独立观测」的构造方式：不是把原来的证据再看一遍（再测十次 UA 也还是 403），
> 而是**造一个原假设必须做出预测、且预测可能落空的新场景**（换一个错 token）。
> **能被现有证据支持的观测，不算独立观测。**

⇒ 这条实证同时给出两条独立的判据（他原本只写了第一条）：
1. **「退出码 0」≠「产出存在」** —— 取产物之前先 `ls -l` 看大小。
2. **「文件是空的」≠「进程死了」** —— 断定一个进程死了之前先 `pgrep` 看一眼。
   **缓冲、还没跑完、写到了别处，长得和「被杀」一模一样。**

**三条做法**：
1. **给结论找一个它解释不了的东西**：主动去问「如果我这个解释是对的，还应该能观察到什么？」
   然后去看那一样。解释得越圆满，这一步越不能省。
2. **区分「解释了现象」和「验证了机制」**：前者是叙事，后者要有一次独立观测
   （这里就是 `pgrep`：它与 exit code、文件大小都不相关，所以它能证伪）。
3. 时间紧时至少留一句：「此结论未经独立观测证实」——比默认它成立便宜得多（同 **H2**）。

⚠️ 与 **H6**（别人的诊断要自己推一遍）互补：H6 防的是**别人**给的错结论，
这一条防的是**你自己**推出来、而且看起来无懈可击的那个。

**H11 最高频的一个具体形态：把失败归因为「既有 / 与我无关」——必须带 base 复跑的 receipts**（借自 gstack E2E blame protocol，`~/.claude/skills/gstack/CLAUDE.md:818-831`，2026-09-09）。「这是老问题」「跟我这次改动无关」是逃避追责的万能话术，而它**能解释现象、所以最难被发现是错的**（正是 H11）。把它固化成带执行步骤的边界：

> **判定一次失败是「pre-existing」之前，硬性三步：**
> 1. 在 base 分支（或改动前的 commit）跑**同一条**检查，**证明它在那儿也挂**；
> 2. 若 base 上过、你分支上挂 —— **就是你的改动**，去追，别甩；
> 3. 跑不了 base，就写「**未验证——可能相关**」并当风险列进报告，**不许写成「既有问题」**。
>
> 原话：**「'Pre-existing' without receipts is a lazy claim. Prove it or don't say it.」**
> 与终审的**反驳者-3（既有行为）**方向相反、场景不同：反驳者-3 判「一个 finding 是不是既有」用来**丢弃发现**（防误报）；这一形态判「一次失败能不能推给既有」用来**防漏修真回归**（防漏报）。同根于 [[feedback_conclusion_that_explains_is_not_verified]]。

## I · 面的穷举 —— 写权限 / 校验 / 消毒时

### I1 · 按「读写全端点 + 聚合面」穷举 ⭐

**per-item 端点收敛 ≠ 列表 / 队列 / 聚合端点收敛。**

> 实证：某社区把逐条写操作的越权全修了，而**审核队列、admin 列表、报告处理、元数据接口**整整一类仍然跨版可读可写——单线 review 挖不到，因为每个端点单独看都「按既有模式写的」。

**做法**：改一条权限规则时，先列出这个资源的**全部触达面**（单条读 / 单条写 / 列表 / 搜索 / 聚合统计 / 导出 / 队列 / 后台管理 / 通知），逐个问「这一面收口了吗」。

### I2 · 白名单 / 消毒链 / 配置必须单源

页面内复制一份白名单 = 缺陷。资源来源多口径（本地目录 / 反代 / 对象存储 / CDN）时，**白名单、渲染层、CSP、响应头是一个联动面，改一处必查其余**。

### I3 · 一个规则 / 一个兜底，要沿它的**全部调用点**铺开 ⭐

**守住的那处会替没守的背书**——读代码的人看到 A 处有校验，就默认 B 处也有。

> 实证：某个清理动作在 git 不可用时是空操作，它的 fs 兜底**早就写好了**、注释把病因写得一清二楚，**却只留在发现它的那个函数里**——10 个调用点里 6 个缺它。后果：被拒绝的候选永久留在磁盘上，并让后续同类操作**从此彻底坏掉**（残骸让差集恒为空 ⇒ 每次重试到上限再失败）。

**做法**：修完一处后，**把这个动作的全部调用点列出来逐个查**（`/usr/bin/grep -n "fnName(" file` 就够），而不是看最近改过哪一处。

⭐ **看见一个判空 / 守卫 / 归一化辅助函数时，立刻问「它的同类调用点有几个，它被用在几个」——把这个比值当缺陷密度指标。**

> 实证：判空辅助 `hasNum` 早就在，上方注释写着「0% 的仪表和无数值的仪表必须看起来不一样」——**原则完全正确**，
> 而全仓只有 2 处调用它，另外 8 个同类组件走 `num(v, 0)`：拿不到数就**强制成 0** ⇒
> 仪表渲染成「0 / 100」并染成绿色（=健康）、电量「0%」（=耗尽）、价格「$0」（=免费）。
> **用户读到的是一个被测量过的读数，而它从未被测量。**

⇒ 这类原则要加**元门禁**（「凡把某字段当数值渲染的组件必须命中该守卫」），而不是逐个补完就算完。
⚠️ 还要留意**别处的注释如何描述这个失败形态**——那道字段门的注释把它建模成「会显示破折号」，
对 2 个成立、对另外 8 个不成立，于是**没被覆盖的那部分，真实风险比注释以为的严重一档**。

⚠️ 铺开时注意**安全前置**：兜底若要删除一个来自持久化状态的名字，**先补名字校验**——否则等于把一个任意路径删除开进去。

### I4 · 缺陷藏在模块之间的接缝上 ⭐⭐⭐

**每个模块单看都对，错在它们对彼此的假设上。**

> 实证一：七轮把生产代码审到「0 生产缺陷」，换成「走真实用户路径」的问法后一轮抓到 6 条，**全部落在接缝**：意图分类器 ↔ 它的调用点（`换成深色` 被无校验的「换数据」快车道吞掉，改坏数据源还回执「成功」）。
> 实证二：「换一版」的语义是**并排候选、由用户挑**；失败后点「重试」时回传保住了 prompt / 附件，**唯独没传 opts**——而 remix 意图就在 opts 里。于是重试变成**原地改写并直接提交**，原部件当场消失，**回执照样显示「已换新版」**。

**做法**：**沿一次完整的用户动作从头走到尾**，在每个交接处问——

- 上游**以为**下游会做什么？下游**实际**做了什么？
- 这个参数/字段，是不是在某一跳被丢了？
- 界面**声称**的语义，和代码**执行**的语义，是同一个吗？

⚠️ 单元测试与单模块 review 在结构上看不见这一类：**两边都符合各自的契约**。

### I5 · 作用域限定在一个动词上，语义落在另一个动词上

> 实证：`git add` 老老实实限定了 `userland` 路径，而同一段代码里的 `git diff --cached --quiet` 与 `git commit` **都没有 pathspec**——它们走全索引。后果两重：①用户在终端手动 `git add` 的半成品被程序以自己的名义提交掉；②「有没有改动」的判定被**别处的**暂存内容顶成真，于是一次**零改动**的操作也返回了 hash，让「这次什么都没改」的诚实守卫**永远不触发**。

**自检问句**：我限定了作用域的那个动作，和**真正产生后果**的那个动作，是同一个吗？

## J · 数据即代码 —— 随代码发布事实性数据时

> 这一组抓的缺陷**没有「错误」的形态**：程序不崩、测试不红、日志不报、门禁全绿。只有真去和世界比对才掉得出来。

### J1 · 事实性数据必须有外部权威源，自洽不算数

坐标查 OSM、汇率查实时源、电话查主管部门官网、开放时间查官网。

> 实证：某 App 的四个逃逸缺陷全是数据——少女峰海拔写成峰顶 4158m（游客只能到观景台 3454m）；瑞郎符号写成 `₣`（那是 FRENCH FRANC SIGN）；出发地写成「北京」而实际是上海；同一地点在列表里出现六遍。**四条全部躲过了格式检查、类型检查、单元测试和全部门禁。**

记录格式固定为「数据里写的是 X，而 {来源} 说是 Y」。没有来源的一律标 TENTATIVE。

### J2 · 代码常量与数据文件必须做集合差集

用脚本，不用眼睛：城市 key、类型名、国家代码、时区表、类目映射。

**差集非空的每一个元素都要说清后果**——漏一个映射往往表现为**某个功能静默返回空**，而不是报错。
