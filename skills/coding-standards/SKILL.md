# 编程规范与准则（研发阶段）

**一句话**：别人的规范教你把代码写得好看；这份还要求你写的每一段**报告自己状态的代码**——返回值、日志、状态字段、健康检查、注释里的保证——都是它所声称那件事的**真实函数**。

它治的是一类**不会让任何东西报错**的缺陷：

> 代码跑得通、测试全绿、日志干净、门禁 ✅——而它报告的那件事根本没发生。

经典规范几乎不管这一层，因为它假设「只要代码正确，它的自述就正确」。**这个假设不成立。**

> **本文是薄入口**：**全部 149 条完整条款在 `references/` 下**（见下方「五层与完整条款」）。
> **主文件是薄入口，有硬上限（350 行，门禁 `[10j]` 守着）。**
> 正文只放三样最该被记住的：**【必须】30 条**、**按场景翻的索引**、**提交前自检**；
> 其余是必要的元信息（五层导航 / 落地步骤 / 与其他规范的关系 / 诚实边界 / 门禁怎么跑）。
> ⚠️ 上限不是洁癖：这份文件曾经是 1700 行，拆薄之后**没有任何判据守着它别长回去** ——
> 而「慢慢长回去」不会让任何东西报错，正是本文 **G** 组说的那种缺陷。
> 没人会通读全部条款——所以本文按「最该先看的排最前」组织。

## 怎么用：按「你现在在写什么」翻

规范失效最常见的方式不是不认同，是**想不起来去翻**。所以索引按场景组织，不按分类：

# 提交前自检（5 分钟）

不是把全部条款过一遍——**只问下面这些**。每句背后挂着一整组，答不上来就去翻那一组。

```
── 出处 coding-standards skill；右侧编号指向它的 references/rules-*.md ──
 1. 我新增的「检查/校验」函数，调用方能分辨「没问题」和「没能测」吗？        → A1
 2. 解析外部响应处，如果对方返回一个格式合法的错误，我会走进哪个分支？        → A2
 3. 我算出来的这个值，断言落在「它被送到了下游」还是「它被调用了几次」？      → A8
 4. 我新写的这组检查，怎么证明它们真的执行了（不是写在那儿没跑）？           → A9
 5. 我写的守卫，只改发起方的代码能不能绕过？                                → B1
 6. 我这条判据，改个变量名 / 加个别名 / 换种写法还成立吗？                   → B4
 7. 我抽出去/搬走的这段，每个调用点原本做的事，现在还都做吗？                → C2
 8. 触发这个 bug 的那个具体状态，我拿它当夹具真跑过吗？同后果还有别的路吗？   → C3/C6
 9. 我的测试夹具，生产代码里谁产出这个形状？判据读的是生产代码还是它的副本？   → D1/D9
10. 我的反向测试真的红过吗？「零误杀」和「有命中」两侧都报了吗？             → D3/D10
10b. 我观测的这个量，和我要守的那件事，中间隔了几层？                       → B12
10c. 我新加的这道门，有没有一个「只有它能接住」的反例？删掉它会不会仍全绿？  → D20
10d. 这道门在它**真实被加载/调用的位置**跑过吗？在那儿它还红得起来吗？    → D31/D32
11. 我这次写的注释 / commit 里每一句「会……保证……」，现在都成立吗？          → E1
11b. 反过来：文档/规格说使用者可以写的东西，代码里真有读取点吗？            → E5
12. 这段在目标规模下是线性的吗？每个阻塞点有墙钟超时吗？                     → G1/F1
13. 我写「做不到 / 大概是因为」的地方，有证据吗？没有就写「未查明」。         → H1/H2
14. 我这个函数返回的失败信息，调用方读了吗？「没跑起来」和「答案是否」分得开吗？→ A10/A11
14b. 我改了某个返回值的语义——它的**全部消费方**会把新值读成什么？         → C8
15. 沿一次完整用户动作走一遍，每个交接处上游的假设下游都兑现了吗？           → I4
```

**代码是 AI 写的、或你和 AI 一起写的，再加 5 问**：

```
16. 我调的每个第三方符号，在项目已安装的版本里确认过存在吗？             → K1
17. 我说的「做完了」，是「验过了」还是「写完了」？                        → K2
18. 这次有没有哪道检查是被我改绿的（改测试/加豁免/降阈值/跳过）？          → K9
19. 计划里写的每一条，实际都做了吗？有没有做了计划外的？                  → K7
20. 这次碰了鉴权/输入/出网/密钥吗？过 K15 那张表了吗？                    → K15
```

**这次动了写操作 / 迁移 / webhook / 健康检查 / 日志，再加 3 问**：

```
21. 这个写请求被执行两次，结果和一次一样吗？                              → M2
22. 我的验签在解析之前吗？重放和重复投递接住了吗？                          → M3
23. 这次迁移的回滚，在有数据的环境里真跑过一次吗？                          → M4
```

**最后一步（H7 收尾自我对账）**：把本次提交信息里写下的**每一条原则**，拿去逐条核对本次 diff 的**每一处**改动——
尤其是那些**不在你注意力焦点上的另一半**。「同一次提交的一半写下教训、另一半违反它」是常态，不是意外。

**diff 自检一条**：`git diff` 里每一行，都能说出它对应哪条需求或哪条缺陷吗？说不出的行删掉。（C1）

# 落地：怎么在项目里用起来

**全部条款一次全上等于没上。** 按投入从小到大分四步，每步单独产生收益：**第一天**（10 分钟）在 `CLAUDE.md`/`AGENTS.md`/PR 模板里**指向**【必须】30 条（放链接别复制正文，I2 单源）→ **第一周**上 P0 工具链并按 **A1** 核对它们真在跑 → **第一个月**按「你在写什么」挂组、AI 写码的项目 K 层整层挂上 → **持续**做逃逸缺陷回流。完整上手手册（含各步验收标准）见 [`references/adoption.md`](references/adoption.md)。

⚠️ **顺序不能反**：先上工具链再贴红线，人会以为「工具绿了就是合规」——而【必须】30 条**恰恰是工具全绿时仍成立的那些**。第一天那 10 分钟回报最高：收益来自「有人知道哪 30 条不能让步」，不是读完全部条款。

# 这份规范的诚实边界

按本文 H1（「做不到」要写失败路径，不给结论）自陈：

1. **承重层全部条款来自单一来源的实证**——four-node-review 记录的踩坑，主要来自本机若干项目（Electron/Node/Python 为主）。**它们在这些栈上被反复验证过，在别的栈上是推测**。用之前先问「这个形状在我的语言里长什么样」。
2. **基础层是文献综述，不是实证**。50 个仓库的条款我按共识度与冲突面重新编排，并核实了每个仓库的存在与星数；但**我没有逐条验证每份文档内部的每个断言**。P1 的条款可信度来自「多份独立文档一致」，不来自我的复核。
> ⭐ **第一次外部实战（2026-09-05）**：拿【必须】档去读一份**不是照本文写的**真实脚本
> （`ai-daily-briefing` 的无人值守 wrapper 与保温任务，共约 470 行），
> 读出 **5 类真缺陷**并全部修复验证：旧机硬编码路径 3 处 / macOS 无 `timeout` 致 `rc=127` /
> `claude` 路径写死 7 处 / **`rc=126|127` 被归成「网络类，不告警」**（A19）/
> **`$VAR` 紧跟全角字符 7 处，其中 5 处在告警文案里 —— 它会在正要发告警的那一刻崩掉**。
> 那个保温任务自换机以来每次退出码都是 1，而**没有任何人收到过告警**。
> 修完实跑 rc=0。⇒ 这份规范对**非自身**代码同样出活，不是只会审自己。
>
> ⭐ **第二次（同日，另一份 97 行采集管线）**：读出 4 条 ——
> **9 个步骤只有 1 个检查了失败**（脚本退出码取决于最后一条命令，且无条件打印「完成」）/
> **同一份文件里，写着「`2>/dev/null` 吞错造成 46 个渠道整天没兜底」的注释，
> 紧挨着的上一步至今仍是 `2>/dev/null`**（C6：记录教训 ≠ 扫过同型）/
> 行数数不出来时截断检查形同虚设（A3）/ 注释声明的解释器不变量与代码不一致。
> 沙箱三向验证后修复（不跑真采集）。
>
> ⭐ **第三次（同日，换语言）**：前两次审的都是 bash，本规范声称治的是**语言无关的形态** ——
> 这条此前没验过。拿【必须】档读一份 56 行的 Python（`~/bin/example-sync.py`，
> 每小时跑一次的订阅同步），读出 3 条，**其中头一条是两次 bash 审计都没出现过的类别**：
> 1. **凭据硬编码在源码里**（K15 红线）：32 位订阅 token 写在第 7 行，
>    而文件是 `-rwxr-xr-x` **全局可读** —— 任何本地进程都能读到。
>    ⇒ 按本机既有惯例外置到 `~/.config/example-sync.env`（600），取不到就 fail-fast。
> 2. **连续失败上百次而无人察觉**（**A11** 下游要读得到失败）：
>    每小时一次、日志里每次都只是又一行 403，**一眼扫过去和上一行一模一样**。
>    ⇒ 把「连续第几次」写进日志，第 3 次起附一句「凭据很可能已失效，改哪个文件」。
> 3. **「没能拉到」和「拉到了但内容不合格」共用退出码 1**（**A19**）
>    ⇒ 分成 3 / 1，人才分得清该查网络凭据还是该查上游数据。

> ⚠️ 值得记的一点：这份 Python **原本就有一条很好的下限断言**（`MIN_NODES=5`，
> 少于 5 个节点判为异常、保留旧文件）—— 它把 A3 做对了，却仍在别处栽了三跤。

# 自证门禁

```bash
# SKILL_ROOT 为本次加载的 coding-standards 目录，不能猜某个宿主的全局目录。
bash "$SKILL_ROOT/scripts/selfcheck.sh"     # 门禁本身
bash "$SKILL_ROOT/scripts/precommit-guard.sh"  # 提交前守卫（推荐入口）
bash "$SKILL_ROOT/scripts/reverse-test.sh" <文件> <原串> <新串> [期望rc] [期望诊断]
bash "$SKILL_ROOT/scripts/gate-mutations.sh"   # 门禁变异套件（数分钟，改判据后跑）
```

`reverse-test.sh` 把 **D29 做法 2**（「注入之后、跑门禁之前，断言变异串确实在文件里」）
变成一个动作，而不是一条留在脑子里的纪律（**D31**）。它保证四件事：
原串**唯一存在**否则 `exit 4` · 变异**确实落地**否则 `exit 4`（绝不进入判读）·
比对期望退出码 · **无论成败都还原并逐字节校验**（探针不许弄脏被测物）。

`gate-mutations.sh` 逐条注入一个**已知缺陷**，断言门禁变红、**且红的是预期那道判据**
（只验 rc 不验「是哪道门红了」等于没分诊 —— 同 **D19**）。
表在 `tests/gate-mutations.tsv`，它是**「哪几道判据被机器验过」的唯一真相源**：
没进表的判据，就是**只在写它的那天被人手验过一次**，此后无人守。

> ⚠️ **它会临时改动正在被使用的 skill 文件**（全表数分钟，每条变异存在几秒；实测值单源在 references/gates.md）。
> 锁只挡住**并发的变异运行**，挡不住两件事：
> ① **并发的读者** —— 别的会话若在这期间加载本 skill，读到的可能是变异态
>   （实测 2026-09-05：套件跑到一半时，另一处显示的描述里【必须】条数正是被注入的那个假值）；
> ② **你自己在旁边编辑同一个文件** —— 套件会用它开跑前的备份把你的编辑**整段覆盖掉**
>   （本文作者当场中招一次：写进这一节的说明被还原掉了，靠 `git show` 对比才发现）。
> ⇒ **跑它期间不要改这些文件，也别让别人用这份 skill**；跑完 `git status` 必须干净。
> ⇒ **它自己也有互斥锁**（套件层 + 单条变异层各一把）：实测撞到过「两个套件实例同时跑」——
>   我用 `&` 丢到后台一个没跑完、转头又启一个，两者在单条变异上串行却整体交错，
>   **一个实例的还原可能盖掉另一个实例开跑前的备份**。第二个实例现在会 `exit 4` 直接退。
> ⇒ 更彻底的做法是在 worktree 副本上跑 —— 尚未实现，这是一处**写下来的已知限制**。
> ⇒ ⚠️ **别用 `&` 把它丢到后台就走开**：它被打断时（SIGKILL / 父 shell 死掉）trap 跑不到，
>   工作区会留在变异态。跑完必须看一眼 `git status`。

> ⚠️ 它的来历：本文作者一天之内**三次**手写反向测试时变异根本没落地
> （`bash -c` 里的反引号被命令替换吃掉、`$?` 被前面的命令替换覆盖），
> 门禁照常绿 —— 而这个绿差点被读成「判据没抓到缺陷」，**最贵的误读方向**。

`precommit-guard.sh` 把三条本文条款做成一个可执行动作，而不是留在脑子里（[D31](references/rules-load-bearing.md)）：

| 它做的事 | 对应条款 |
|---|---|
| 取被测物指纹 → 跑门禁 → **再取一次**；不一致报 UNABLE | **D30** 你验的那份和你提交的那份可能不是同一份 |
| 门禁不绿就 `exit 1`，不给你继续提交的机会 | **A16** 门的结论必须落在退出码上 |
| 开发路径绿之后，**在本次宿主真实加载路径再跑一次**（可显式设 `SYBUILDER_SKILLS_DIR`） | **D32** 开发目录跑绿 ≠ 真实加载位置跑绿；不固定 Claude/Codex 目录 |
| 枚举文件不足下限报 UNABLE；`GUARD_MIN` **只能调高不能调低** | **A3** 下限断言 · **B20** 环境不得决定失败算不算数 |

⚠️ 它**不替你提交**，最后只提醒 `git commit -- <路径>`（**K11**：`git commit` 提交的是整个索引，不是你 `add` 的那些）。

**它被谁执行**（铁律 107：门要自带这份证据，否则「推荐入口」= 靠人记得 = D31）：
仓库 hook `scripts/hooks/pre-commit`（2026-09-06 接线；暂存区含本 skill 路径才运行，其它提交 0.03s 放行；
放行与**阻断**两路都端到端验过——注入红、真提交一次、rc=1 且 HEAD 未动，过程见 `references/gates.md`）。
⚠️ hook 不随 clone 走——新检出后按该文件头那行重装；`git commit --no-verify` 是显式逃生门，用它 = 对红灯自己负责。

它核的是**这份文档自己**是否自洽。**门禁本身遵守本文要求它遵守的东西**：

| 本文条款 | 门禁里的落实 |
|---|---|
| **A1** 三态 | 输出 PASS / FAIL / **UNABLE**；UNABLE 既不计绿也不计红，但让退出码非零（3） |
| **A3** 下限断言 | 解析到的锚点少于 10 个 ⇒ 判 UNABLE（「是解析坏了，不是没问题」），不判 PASS |
| **A9** 元判据 | **先做一次两向测试证明「锚点校验机制」本身有效**，无效则后续结论整体作废 |
| **D5** 否定型证据 | 一律用 `/usr/bin/grep`——`grep` 可能被 shell 函数遮蔽而静默返回空 |
