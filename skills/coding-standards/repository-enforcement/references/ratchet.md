# 棘轮原则（Ratchet）

引入新门禁的正确姿势。核心：**只许收紧，不许放松；不大爆炸打挂 CI。**

## 问题

想加一道新检查（如 `tsc`、`govulncheck`、gitleaks），但仓库里存量违例一大堆。
- 直接设强制 → CI 瞬间全红，团队被迫一次性清几十上百个存量，或干脆把门禁删了（最坏）。
- 永远不加 → 假绿继续。

## 解法：咨询门禁 → 清零 → 强制

1. **咨询起步**：CI 步骤加 `continue-on-error: true`（GitHub Actions）。检查照跑、结果可见，但**不阻断合并**。
2. **测基线**：跑一次拿存量数字（如 `tsc` 报 28 个错），写进章程 §测试/Open Items：`存量 N，清零后转强制`。
3. **守住增量**：约定**新代码不得新增违例**（评审时把关；理想情况新增文件单独强制）。
4. **逐步清零**：分批修存量，不改运行时行为。清不动的（框架级类型递归等）用最小、带原因注释的逃逸（`@ts-expect-error`/`as any as T`/`# type: ignore[code]`）。
5. **转强制**：存量到 0，删掉 `continue-on-error`，门禁转强制。同步更新章程状态。

## 判定：直接强制 还是 咨询起步？

| 情况 | 决策 |
|---|---|
| 跑一次存量为 0（多数干净仓库的 `-race`、`gofmt`、`govulncheck`） | **直接强制** |
| 存量 1~一把、且能在本次清完 | 本次清完 → 直接强制 |
| 存量多、清零是独立工程 | **咨询起步 + 棘轮计划** |
| 结果依赖外部（gitleaks 扫历史、`npm audit` 可能误报） | 咨询起步，确认无真问题后强制 |

## 反模式

- ❌ 为了"全绿"把门禁调松（降 `--max-warnings`、删检查）——破坏棘轮单向性。
- ❌ 用 `as any`/`# type: ignore` 大面积压制而不记录——把假绿从 CI 搬进代码。逃逸必须**最小 + 带原因**，且优先选会"自清理"的形式（如 `@ts-expect-error` 在问题消失后会自己报错）。
- ❌ 一次性强制打挂 CI，逼团队停下所有工作清存量。
