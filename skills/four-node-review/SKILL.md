# 四节点终审流水线（four-node-review）

把「入场门 → 规范门禁 → 安全审计 → 代码 Review → 功能 QA → 性能 Benchmark」串成一条可复用的终审流水线。**唯一铁律：每个节点必须连续 3 轮零 actionable 问题，才允许进入下一个节点。** 任一轮出现问题，该节点计数清零、真修真验后重来。

> **口径说明**：下文凡写「连续 3 轮」，指的都是 `--streak` 轮——**S/A 档 = 3（默认口径），B 档 = 2，C 档 = 1**（见「风险分档」）。3 是本 skill 的灵魂数字，凡涉及不可逆、生产数据、资金权限、对外发布的改动一律走 S/A，不得降。

> 名字沿用「四节点终审」的历史叫法，实际是 0.5 入场门 + 5 个审查节点。可用 `--nodes` 子集化。

## TL;DR · 执行顺序（先读这一屏，细节再往下翻）

```
0.  定风险档（S/A/B/C）——人拍板，写进 state.md。拿不准往高了走
0.  项目探测 + 立覆盖契约（ocr delegate preview → N 个必审包，工程手段产出，只增不减）
0.5 入场门：意图记录 / 缺陷类有先红后绿锚点 / 有可独立验证入口 —— 缺了先补
1-5 每个节点：
      取本轮 lens（轮换表下一个）→ 按包扇出（一包一 agent，上下文隔离）
      → 核覆盖差集（非空则补审，本轮不判定）
      → 候选发现过证伪投票（3 反驳者，默认 refuted；安全/数据/资金类需 3 票全翻才丢）
      → 记精确率 C/N（<1/3 该轮作废重跑）
      → 有 CONFIRMED：真修 → 过修复门 → 真验证 → streak 清零
      → 零 CONFIRMED：lens 与上轮不同 且 包全覆盖 且 证据是本轮新产生 → streak+1
      → streak 达标 且 lens 表跑满 → 节点通过
终  最终回归（Node 1 全量门禁 + 冒烟）→ 出终审报告（含精确率/覆盖数/降级声明/Open Items）
后  逃逸缺陷回流：日后线上暴露的问题，回来改 lens / 改分包规则 —— 这是流水线唯一的进化机制
    同一缺陷还要问一句「写代码的当下遵守什么能让它不出生」——答案回流进 coding-standards skill
    （它是本流水线的反函数：它守住的，这里就查不出来；两边共用一套逃逸回流）
```

**一句话记住这条流水线在防什么**：防的不是"代码有 bug"，是**"看起来审过了其实没审"**——漏审的包、幻觉的发现、三轮复用同一份证据的假收敛。

## 这条流水线要治的四个病

审查失效从来不是"审得不够多"，是四个具体的病。全文所有机制都是冲这四个来的，读的时候对着看。
四条有一个共同的形状：**告诉你"有没有问题"的那个东西，本身可能在说谎**——
agent 会漏审、会幻觉、会用同一份证据凑三轮，而门禁会把"我没能测"说成"我测过了"。

| 病 | 症状 | 药 |
|---|---|---|
| **覆盖不全** | 改动一大，子 agent 就"偷懒"挑几个文件审，剩下的静默不提；报告看着满，其实没扫到 | **确定性覆盖契约**（Node 0 第 6 步）——先用工程手段定死"这一轮必须审哪些包"，再让 agent 去审；没覆盖到的包 = 这一轮不算清洁 |
| **发现不可信** | 幻觉发现、行号对不上、"声称已修实际没改"；反过来也有为了早点过而把边缘发现压下去 | **对抗式证伪投票**（下方独立小节）——每个发现要扛住 3 个默认站在"这不是问题"一边的反驳者 |
| **收敛是假的** | 连续 3 轮零发现，但三轮审的是同一块最容易的地方，盲区从头到尾没人碰 | **视角轮换表**（下方独立小节）——streak 必须由**不同视角**累积，同一视角连续清洁不计数 |
| **门禁结论不可信** | 门禁分不清"我测出了什么"与"我能不能测"：依赖没装报成"正确率 0"、服务没起报成"CSRF 防护失效"、跳过冒烟层却打 ✅、机器上有无关负载就判红。**三个方向都会错——假绿、假红、误导性红** | **门禁三态契约**（Node 1 · L2 下方独立小节）——每道门禁必须显式区分 PASS / FAIL / **UNABLE**（没能测＋原因）；编排层对 UNABLE 既不计绿也不计红，单独列出且整体退出码非零 |

| 能力 | 首选 | 降级 | 用在 |
|---|---|---|---|

| 验证与计划纪律 | superpowers 的 `verification-before-completion` / `test-driven-development` / `requesting-code-review` / `writing-plans` | 按本文写死的等价条款执行（下方各处已内联，不装也能跑） | Node 0.5、修复门、各节点"真验证" |

| **扇出纪律** | superpowers 的 `subagent-driven-development` / `dispatching-parallel-agents` | 按本文 Node 3 单轮程序执行（已内联） | Node 3 按包扇出 |
| 现成专家 review agent | ECC 的 `silent-failure-hunter` / `security-reviewer` / `type-design-analyzer` / `performance-optimizer` / `code-simplifier` / `comment-analyzer` | 用通用子 agent + 本文的视角轮换表提示词 | Node 3 视角池 |
| **测试质量审查** | ECC `pr-test-analyzer`（**已实测可作 `subagent_type` 调，只读**） | 用通用子 agent + L9 的"盯什么"栏 | Node 3 的 **L9** |
| **语言专属 reviewer（第二源）** | ECC 的 `go-reviewer` / `rust-reviewer` / `python-reviewer` / `typescript-reviewer` / `react-reviewer` / `vue-reviewer` / `java-reviewer` / `kotlin-reviewer` / `swift-reviewer` / `cpp-reviewer` / `php-reviewer` / `csharp-reviewer` | 只用 ocr 规则文档单源 | Node 3 语言级判据交叉验证 |

> **ocr = alibaba/open-code-review**（Apache-2.0，Go）。装：`npm i -g @alibaba-group/open-code-review@1.12.5` 或 GitHub Release 二进制。前两项**不需要任何 API Key**（委托模式：ocr 只做确定性工程，评审由本流水线的 agent 做）；后两项要配 provider（`ocr config provider`，内置 anthropic/openai/dashscope/deepseek/volcengine/kimi/mimo 等预设）。⚠️ ocr 的评审路径**全部由工具调用驱动**，配的模型必须支持原生 function calling——只在文本里"叙述"工具调用的推理模型（如 `deepseek-r1` 系）会死在 `No tool calls parsed` 重试里，怎么调提示词都没用。

**三条已实测的接入前提（2026-08-02 在 ocr v1.8.4 实跑验证，不是推测）**：

1. **`ocr rules check` 不是覆盖判据。** 它对任何路径都会返回一条规则（匹配不上就给通用的 `default`），**包括 ocr 自己根本不会评审的文件**。判"这个文件在不在审查范围内"只能看 `ocr delegate preview` 的 reviewable 计数与 `excluded:` 标记。
2. **`.md` / `.txt` 等文档类不在 ocr 的 80 个白名单扩展名里**，且白名单 `//go:embed` 进二进制、用户不可扩展。文档为主的仓库（如本 skill 所在的完整套件）走 ocr 会让覆盖契约静默缩水——**这类改动的必审包必须用 `git diff --name-only` 补齐**，并在报告里标注补齐来源。
3. **规则 glob 比扩展名白名单窄。** 例：`.mjs`/`.cjs` 可评审，但规则 glob 只写了 `**/*.{ts,js,tsx,jsx}`，于是掉回通用 `default` 规则。**某包只拿到 `Pattern: default` 时，说明这一包没有语言级判据**，该轮要显式改用本文 lens 表的完整提示词补强，不能默认"ocr 给了规则就够了"。

**ECC 的用法是"点名调"，不是"整包依赖"（2026-08-02 定）**：ECC 插件常驻上下文成本约 **34,696 tok/会话**（superpowers 约 688 tok，相差 50 倍），且它的 `benchmark` / `design-system` / `taste` 与本机已有同名 skill 抢触发词。因此本流水线**只在需要时用 `Agent` 显式指定 `subagent_type`**（如 `ecc:pr-test-analyzer`、`ecc:go-reviewer`），**不把 ECC 当作必须常驻的依赖**——没装 ECC 时全部走降级列的通用子 agent，流水线照跑。已实测：ECC 的 reviewer 类 agent 可直接作 `subagent_type` 调用，各自带独立系统提示词、工具集为只读（Read/Bash），单次约 24k tok。

**语言级判据走双源交叉（ocr 规则文档 + ECC 同语言 reviewer）**：两者是**独立来源、同一根轴**——ocr 的 `go.md` 由阿里从生产误报里精调（强调"先取证再断言""不要重复 go vet 能判的"），ECC 的 `go-reviewer` 是另一套独立提示词（实测其首要判据是"被 `_` 丢掉的错误"）。**两源都报同一处 = 交叉命中**，按 Node 3 步骤 6 的交叉命中规则处理（最高置信度，需 3 票全翻才丢）；**只有一源报 = 照常走证伪投票**，不因为"只有一家报"就降权。⚠️ 两源都装不上时用单源，报告里标注「语言级判据为单源」。

> 这三家是独立来源，但在同一件事上撞车了：**给 review agent 精心裁剪过的上下文、而不是整个会话历史**（superpowers 的原话）＝ **每个包一个上下文隔离的 sub-agent**（ocr 的分治策略）。两边独立得出同一结论，这条按高置信度采纳，是 Node 3 分治的依据。

## 何时用

- 「跑一遍终审 / 四节点终审 / 终审流水线」
- 「上线前用最严格标准全面把关」
- 「连续 3 轮零问题地做 review + QA + 安全审计 + 压测」
- 一个大批次改完、准备上线前的总闸门

## 参数

`/four-node-review [target] [flags]`

- `target`：仓库路径或当前分支范围（默认当前工作目录 + 当前分支相对 base 的改动）。
- `--risk S|A|B|C`：风险档（见下方「风险分档」）。**不给则必须在 Node 0 停下来问用户**——分档是人的决定，不许 agent 自己默认成低档开跑。定档后写进 state.md，中途不得下调。
- `--nodes a,b,c`：只跑指定节点（`entry,gates,security,review,qa,bench`）。默认按风险档决定。`entry`（入场门）除非用户显式排除，否则总是先跑——它决定这批改动够不够格被终审。
- `--lens L1,L3`：只用指定视角（调试或复跑单一角度时用）。**默认不加**：限制 lens 会直接废掉"streak 由不同视角累积"这条不变量，加了就必须在报告里标注本次收敛不完整。
- `--from <node>`：从某节点开始（前面的视为已过）。用于中断后续跑。
- `--streak N`：每节点需要的连续零问题轮数。**默认由风险档决定**（S/A=3，B=2，C=1）；显式指定时只允许**上调**，不允许把某档调到低于它的档位值——降标准要靠降档，而降档是人的决定且要写理由。3 是这条 skill 的灵魂数字，S/A 档非必要不改。
- `--deploy`：每轮修完后真部署到目标环境再验证（对齐「每轮实时部署」）。**默认关**：只本地真修真验，部署留给用户拍板。生产部署属高影响操作，开 `--deploy` 也要在首次部署前向用户确认目标环境。
- `--max-rounds N`：单节点轮次上限（默认 12），防止死循环；触顶未收敛则停下如实报告，不许假装通过。
- `--max-packs N`：单轮并发包上限（默认 12）。超出则**分批跑完再判定本轮**——分批是为了排队，不是为了少审；两批都跑完才算一轮，覆盖契约照样要全覆盖。

### 成本与规模（先看这段再决定怎么跑）

这条流水线不便宜，扇出是乘法：`包数 × lens 轮数 × 节点数 + 发现数 × 3 个反驳者`。一个切成 15 个包的改动，光 Node 3 收敛就可能上百个 agent。**不承认这件事，实际结果就是有人偷偷跳过它**，那比慢更糟。三条控制手段：

1. **规模只决定"怎么分批"，不决定"跑多严"**——跑多严由风险档定，两者别混：包数少（≤5）一次跑完；6–15 包按 `--max-packs` 排队；**>15 包先按特性拆成几次终审**，一次审一个可独立上线的切片。把 200 个文件塞进一次终审，收敛轮次会指数级变长，且发现之间互相干扰。**一个只改了 3 个文件的 S 档改动照样跑满全节点；一个动了 30 个文件的 C 档格式化不需要**。
2. **lens 表可裁剪，但要留痕**：某个 lens 与本次改动明显无关（例如纯文档改动的并发视角），可在 Node 0 判定时标注"不激活 + 理由"，不算跑满一遍的缺口。**裁剪要在开审前定，不许审到一半嫌慢临时砍**。
3. **反驳者只给候选发现用**：零发现的轮次不需要任何反驳者，成本是 0。所以越干净的代码跑起来越便宜——这是这套机制的正确激励方向。

## 风险分档（Node 0 第一件事，人拍板）

**一条所有改动一视同仁跑满的流水线，最终的命运是没人跑。** 分档不是放水，是把最贵的火力对准最该防的地方。**由人在开审前定档并写进 state.md**；拿不准往高了走。

| 档 | 什么改动 | 跑什么 | streak | 额外硬要求 |
|---|---|---|---|---|
| **S** | 不可逆 / 生产数据面 / 资金 / 权限模型 / 对外发布产物 / 安全边界 | 全节点 | 3 | 部署前生产数据核查；安全类发现的证伪需 3 票全翻；Open Item 一律不接受，必须修完 |
| **A** | 核心链路功能变更、跨模块重构、对外 API 变更 | 全节点 | 3 | 标准流程 |
| **B** | 边缘功能、内部工具、单模块局部改动 | `gates,review,qa` | 2 | 跳过的节点要写明理由 |
| **C** | 文档 / 注释 / 纯配置 / 格式化 | `gates` + 1 轮 review | 1 | 只需确认"真的只动了这些"——用覆盖契约核对，改动溢出到代码即刻升档 |

两条铁规：**降档必须写理由且理由可被复核；升档不需要任何理由**。以及——**分档在开审前定死，审到一半嫌慢临时降档 = 作弊**，与"临时砍 lens"同罪。

## 与研发流程的接口（别重复做 CI 已经做的事）

把关是分层的，每层的成本和频率差一个数量级。终审是**最外层、最贵、最少跑**的那一层：

| 层 | 频率 | 耗时 | 管什么 |
|---|---|---|---|
| pre-commit | 每次提交 | 秒 | 格式化、可自动修的 lint |
| pre-push | 每次推送 | 分钟 | 静态检查、快单测 |
| CI | 每个 PR | 十分钟级 | 全量测试、构建、依赖扫描 |
| **本流水线** | **一个可独立上线的切片完成时** | **小时级** | **上面三层都发现不了的：漏审的面、假绿的门禁、攻击链、规模挂死、承诺与实现不一致** |

推论，很重要：**Node 1 的职责不是把 CI 再跑一遍，而是核对"CI 声称在做的事是不是真的在做"**。前三层已经稳定绿的项，终审只核其真实性（有没有被吞掉、断言有没有空转、覆盖面漏没漏包），不重复消耗轮次。**触发时机不是每个 commit，是一个切片准备上线时**——每个 commit 都跑终审，等于没有终审。

## 核心不变量（这条流水线的灵魂，不得偏离）

对每个**审查节点**（Node 1–5）维护一个 `clean_streak`，初值 0。**唯一例外是 Node 0.5 入场门**——它核对的是受理条件而非搜索缺陷，刷轮次没有意义，满足即过，例外理由须写进报告。

1. **一轮 = 一次完整的该节点检查** → 产出「本轮 actionable 发现列表」。
2. **本轮有 ≥1 个 actionable 发现** → 真修 + 真验证（+ 按需部署）→ `clean_streak = 0`（**清零**）→ 进下一轮。
3. **本轮 0 个 actionable 发现** → `clean_streak += 1`（**前提：本轮 lens 与上一轮不同、且本轮包全覆盖**，否则 streak 不变）。

   ⚠️ **「0 个发现」有两种来源，必须分开**（2026-08-12 回流，与《门禁三态契约》同构——
   那条治的是门禁，这条治的是轮次，根因是同一个：**分不清「我审出了什么」与「我能不能审」**）：

   | 轮次终态 | 含义 | 计数 |
   |---|---|---|
   | **CLEAN** | 审了，确实零发现 | `+1` |
   | **DIRTY** | 审了，有 actionable | 清零 |
   | **UNABLE** | **没能审完**（工具不可用 / 环境不满足 / 子 agent 空返回或崩溃 / 降级到几乎没检查 / 某包未覆盖） | **既不 +1 也不清零**，且**不计入「lens 表跑满一遍」**；原因写进 state.md |

   下面第 8 条（包未覆盖 → 既不清零也不加 streak）**就是 UNABLE 的一个特例**——
   这个模式文件里早就有，只是当初只用在「覆盖不全」一种情况上。现在泛化到全部。

   **判据**：宣布一轮 CLEAN 之前，逐条问「这一轮计划做的检查，每一项都真的执行了吗」。
   凡是「本来要做但没做成」的，这一轮就是 UNABLE，不是 CLEAN。
   典型误判：外部审查器没装 → 那一路证据整个缺席，轮次却照样 +1；
   子 agent 返回空 → 被读成「它没发现问题」；环境不满足导致某项跳过 → 被当成通过。

   **降级必须在当轮就影响分类，不能只写进最终报告**：
   「工具依赖与降级」允许无则降级，但降级意味着**这一轮少了一路证据**。
   事后在报告里补一句标注，改变不了它已经被当成 CLEAN 计过数的事实。
4. **`clean_streak >= --streak`（默认 3）且该节点必需 lens 表已跑满一遍** → 节点通过，进下一节点。计数达到阈值后继续补齐未跑视角，不因超过阈值而永不收敛。被测内容指纹变化时清零 streak 和本版本 lens 覆盖；UNABLE 不计数，也不能跨版本拼接清洁轮次。
5. **诚实计数 + 结果可核验**：
   - 每个发现必须**实证核对真实代码/真实运行**，排除 agent 幻觉、"声称已修实际没改"、误报。核对不成立的不计入。
   - **"找不到就是正确结果，不许凑数"**——不为了显得勤奋而编造发现，也不为了早点过而漏报真问题。
   - 修复自身也要被下一轮复核（改错/改不彻底=一个新发现，清零重来）。
   - **每个节点的"通过"必须落一个可独立复核的产物**，不许只凭子 agent 自报或 inline 输出就记通过：门禁=真跑的命令退出码、Review/安全=能定位到真实代码行的发现、QA/bench=真运行的证据（复现测试、日志、截图、benchmark 数字）。**编排者用可靠通道核这些产物**（读文件 / 读退出码 / 读 git / notarytool 等），不信"我跑完了都绿"这类无凭据结论——尤其异步/多 agent 场景，一个无法独立验证的"零问题"等于没做。凡遇到编造的工具输出、对不上的提交号、无凭据的"全绿"，一律作废重来。
6. **每轮换视角/换 agent**，避免同一盲区重复放行——**按视角轮换表推进，同一视角连续清洁不计入 streak**（见下节）。
7. **一个节点未连续 3 轮清洁，绝不进入下一个节点。** 这是硬门，不可因为"看起来差不多了"跳过。
8. **每一轮都要满足覆盖契约**：本轮实际审到的包 = Node 0 定下的必审包全集。有包没覆盖 → 这一轮**不算清洁**（既不清零也不加 streak，补审后重判），并在 state.md 记下漏了哪几个包。
9. **每个候选发现必须过对抗式证伪投票**才计入 actionable（见下节）。被证伪的不计数、也不修。
10. **每轮的证据必须是本轮新产生的**，三轮证据不许是同一份的三个副本（见「证据独立性门」）。

进入下一节点前，打印该节点的收敛证据，三项缺一不可：
`节点X 通过（R{n-2}/R{n-1}/R{n} 连续 3 轮零问题 | 视角 = L{a}/L{b}/L{c} 互不相同 | 覆盖 = {m}/{m} 包全覆盖）`

## 视角轮换表（治"假收敛"）

每个节点维护一张有序视角表（lens list），**每轮取下一个 lens**，用完回头继续。硬约束：

- 计入 streak 的连续 3 轮，**必须来自 3 个互不相同的 lens**。同一 lens 连续两轮清洁，第二轮不加 streak（记 `streak 不变（lens 重复）`）。
- 某个 lens 从未跑过就宣告节点通过 = 不允许。节点的 lens 表必须至少跑满一遍，才有资格谈收敛。
- 有真发现的那一轮，下一轮**仍然换 lens**（不要用同一 lens 反复刷同一处，那是打转，见"同一诊断反复打转就停下重评"）。

各节点的 lens 表见对应节点小节；Node 3 的表最长，是主战场。

## 对抗式证伪投票（治"发现不可信"）

原来的"实证核对排除幻觉"太模糊、执行强度全看当时状态。改成可执行的程序——**每个候选发现，起 3 个独立反驳者**（子 agent，互不见面），提示词要点：

> 这是一条声称的缺陷：{发现}。**你的任务是推翻它。** 默认它站不住（`refuted = true`），只有当你读了真实代码、走通了具体的失败路径之后仍推不翻，才输出 `refuted = false`。不确定 → 判 refuted。

三个反驳者用**不同的反驳角度**（不是三份同样的提示词，那只是冗余）：

1. **可复现性**：能不能写出一组具体输入/状态，让它真的错？写不出来 = 推翻。
2. **上游约束**：调用方、类型契约、校验、配置是不是已经排除了这个输入？已排除 = 推翻。
3. **既有行为**：这是本次改动引入的，还是仓库里一直如此、且是有意为之（有注释/测试/文档背书）？既有且有意 = 推翻（可转为建议项，不计数）。

**给反驳者装上现成的判据（ocr 规则集的高价值用法）**：`ocr rules check <该发现所在文件>` 取回的语言规则文档里，**每条正向规则后面都挂着一张"不许报"的负面清单**——那是阿里在生产环境拿误报换回来的，正好就是反驳者要的具体判据，比让反驳者自己现编理由强得多。例（`java.md` 线程安全段）：

> **Do not report in the following cases**: 方法内局部变量（天然线程安全）／无多线程调用证据的单线程上下文（**须用 `code_search` 确认调用上下文**）／只读操作／指向不可变对象的 final 字段／已有 synchronized·Lock·原子类的正确同步／Builder 构建期等设计上单线程使用的组件。

把命中包的这张负面清单**原文贴进反驳者 2（上游约束）和反驳者 3（既有行为）的提示词**，并保留本文原有要求：反驳必须指名是被清单里**哪一条**挡住的，泛泛引用不算推翻票。⚠️ 只拿到 `Pattern: default` 的包没有这张清单（见上方前提 3），该包的反驳者照常用通用角度，不得因为"没清单"就放宽判定。

**判定**：≥2 个反驳者推不翻 → `CONFIRMED`，计入本轮 actionable。否则丢弃，且**丢弃这件事本身也要记进 state.md**（谁提的、被哪条角度推翻的）。

**批裁模式（小批候选的合法形态，2026-09-15 实测收编）**：候选 ≤8 条且**不含安全/数据/资金类**时，
允许起 **3 个 agent＝3 个角度**、每个角度一次裁完全部候选，而不是 `候选数 × 3` 个 agent。
理由是实测出来的：一轮 7 条候选里有 4 条是**两个角度 1:1 对立、靠第三个角度定案**——
承重的是**角度之间的独立性**，不是"每条发现各自隔离"。
⛔ 三条边界：① 安全 / 数据损坏 / 资金权限类**仍走 per-finding × 3**（代价不对称，见上）；
② 批裁的每条结论仍要**逐条给理由**，一句"以上都不成立"作废整批；
③ 在 state.md 记「批裁 + 候选数 + 理由」。⛔ 候选 > 8 条时不许批裁——
一个 agent 同时裁十几条，后面几条的裁决质量会肉眼可见地掉。

**两条防止投票机制自己变成漏洞的约束**：

- **"我看不出来"不算推翻**。反驳必须给出具体理由（这个输入被上游哪行代码挡了 / 这个路径为什么走不到 / 这个行为在哪个测试或注释里被明确认可）。以"上下文不足""看不出问题"结题的，记作弃权，不计入推翻票。否则默认 refuted 这条会退化成"没人看懂就放行"。
- **高危类别反向取证**：安全漏洞、数据损坏/丢失、资金或权限相关的发现，**要 3 个反驳者全部推翻才允许丢弃**（1 票推不翻就保留）。理由是两类错误的代价不对称——放过一个真漏洞的代价远大于多查一次误报。ocr 那套"precision over recall"是为了日常低噪声，不适用于这三类。

**精确率自检（本流水线的科学化关键）**：每轮记 `提出 N / 确认 C / 证伪 N-C`。
- 若某轮 `C/N < 1/3`（大多数发现被推翻）→ **该轮作废重跑**，换 lens 或换 agent：不是发现质量差，是这一轮的审查者在幻觉，它给出的"零发现"部分同样不可信。
- 若连续多轮 `C/N` 都很高但发现都极轻微 → 反向信号，说明在凑数，同样重跑。
- 精确率数字进最终报告，是这条流水线可被外部检验的核心指标之一。

## 证据独立性门（治"一轮证据冒充三轮"）

`clean_streak` 这个核心机制有一个最省事的作弊方式，而且它常常不是故意的：**把同一次执行当成三轮执行**——同一次门禁输出被引用三次、三个 agent 只转述同一份未经独立核验的报告。这时“连续 3 轮零问题”实际只有 1 轮。截图或确定性输出字节相同本身不能证明执行重复或未重跑。

这条门借鉴 block/buzz 的截图去重提醒，但以独立执行记录判定新鲜性；相同状态的合法重拍可以得到相同字节，不沿用“相同哈希即未执行”的推断：

**每轮结束前，对本轮证据做独立性检查，任一项不通过则本轮不计入 streak**：

1. **新鲜性**：命令类证据必须是本轮真跑的（本轮时间戳、完整输出、退出码），不许引用前几轮的运行结果。「上一轮跑过了，这轮没改所以还是绿」——不成立，重跑。
2. **执行身份与内容绑定**：每轮记录唯一 execution ID、时间、命令/动作、退出码、当前构建及输入/产物哈希。复用同一 execution ID 不计新轮；相同文件哈希可由独立重跑产生，不自动拒绝，不同哈希也不自动证明新执行。截图须有本轮采集动作与对应界面记录。
3. **内容锚点**：报告须能追到**本轮 lens、检查对象和实际动作**。措辞相近只触发核查，不自动否定独立执行；确实复用前轮执行或无法提供本轮视角证据时，streak 不加。
4. **可独立复核**：证据必须落在编排者能自己读到的地方（文件 / 退出码 / git / 日志），不能只存在于子 agent 的自述里。
5. **外部审查器优先（配了 provider 时）**：一个节点的收敛证据里，**至少一路应来自跑在不同模型 / 不同提示词 / 不同工具集上的外部审查器**（`ocr review --format json`，见 Node 3 步骤 6）。同一会话里换个 lens 措辞得到的"独立"，强度远低于换一整个审查器。⚠️ 但外部审查器的**沉默不算清洁证据**（见 Node 3 步骤 6 的不对称规则）——它能提供的是"这一轮真的被另一双眼睛看过"，不是"这一轮没问题"。

6. **执行完整性**（2026-08-12 补）。前五条防的都是"证据是不是本轮新产生的"，
   **没有一条问"这一轮计划做的检查，是不是都做了"**——于是"计划五项、实际跑了三项、
   剩下两项静默跳过"能一路绿到底：跑了的那三项证据完全合格，缺席的两项不留任何痕迹。
   **做法**：开轮前把本轮计划的检查项列出来（哪些包、哪些工具、哪些 lens 动作），
   收尾时逐项标 done / **UNABLE+原因**。有任何一项 UNABLE，这一轮按第 3 条记 UNABLE，
   **不是 CLEAN**。缺席必须留痕，否则它和"做了且没问题"长得一模一样。

⚠️ 这条门与「精确率自检」配合起来，才真正堵死"假收敛"：精确率管**发现是不是真的**，证据独立性管**这一轮是不是真的发生过**。

## 前置：项目探测（Node 0，只做一次）

1. 读 `CLAUDE.md`（项目根）取质量门禁命令、部署命令、QA/运行方式、benchmark 方式。缺失则按栈探测（`go.mod`→Go；`package.json`→Node/前端；`requirements.txt/pyproject.toml`→Python；等），并把探测到的命令回写 CLAUDE.md 免得下次再猜。
2. 判定：是否可部署（有 deploy 脚本/容器）？是 Web（有前端→浏览器 QA）还是 CLI/服务/库（→对应 QA 方式）？有无既有 benchmark？
3. 确定改动范围（`git diff <base>..HEAD` 或全库，视 target）。
4. 建状态文件 `.four-node-review/state.md`（若 `.gitignore` 未含则提示加），记录：目标、节点清单、每节点 `clean_streak` 与逐轮发现，便于中断续跑与用户查看进度。
5. **探测项目自带规范体系 + 判定专项条款激活清单**：找项目自己的规范源（`AGENTS.md`、`docs/ai-rules/**`、`.cursor/rules`、自带规则门禁脚本如 `scripts/*rules-gate*.sh` 等），确认为该项目各节点的**最高标准来源**；再按下方「专项条款库」逐条判定触发条件，把激活结果写入 state.md（哪条挂哪个节点、触发依据是什么、哪些条款因条件不满足而不启用）。
6. **立确定性覆盖契约（新增，治"覆盖不全"）**——这一步必须在任何 agent 开审之前完成，**由工程手段而非模型判断**产出：

   ```bash
   ocr delegate preview --from <base> --to HEAD     # 或 -c <sha> / 无参审工作区
   ocr delegate rule <file1> <file2> ...            # 拿到按文件特征匹配的规则集
   ```

   产出两样东西写进 state.md，此后**只增不减**（除非用户显式豁免并记录理由）：
   - **必审包清单**：reviewable 文件被切成的 N 个包（ocr 会把强关联文件并进同一包，如 `message_en.properties` + `message_zh.properties`）。这就是覆盖契约的分母。
   - **每包的规则集**：作为该包在 Node 1/2/3 的检查清单基线。

   没装 ocr 就降级：`git diff --name-only <base>..HEAD` 拿全量清单，**按模块/目录手工分包**（同目录、同特性、成对的接口与实现归一包），规则集用项目自带规范 + `~/.claude/rules/<lang>/`（若存在）。降级要在报告里标注「覆盖契约为手工分包」。

   ⚠️ 覆盖契约的意义不在于"多审几个文件"，而在于**把"这一轮审全了没有"从模型的自我感觉变成一个可核对的减法**：契约里的包，减去本轮各 agent 实际回报覆盖到的包，差集必须为空。差集非空还宣告清洁，是本流水线定义的一种作弊。

## 专项条款库（按项目特征条件激活，Node 0 判定）

本流水线是泛化流程，以下条款**不是默认全开**——只有 Node 0 探测到对应特征才挂载到指定节点。两条元规则：

1. **项目自带规范优先**：项目内的 CLAUDE.md / AGENTS.md / docs/ai-rules/** / 自带门禁脚本是该项目的最高标准来源，各节点检查以它为准；本库条款只在项目没有更具体规定时补位，与项目规范冲突时以项目规范为准。
2. **触发条件不满足，一条都不用**：不在未接入 Tailwind 的项目引入 Tailwind、不对 CSR 管理端按 SEO 标准审查、不给纯静态站查 SSR 边界、不把某个项目的门禁脚本硬搬进别的仓库。宁可少挂条款，不机械套用。

### W1 · 样式与视觉（触发：项目含手写 CSS/SCSS/组件样式）

- **挂 Node 1**（仅当项目已自带样式门禁/棘轮基线，如 `*rules-gate*.sh`）：纳入门禁全集真跑，棘轮基线只减不增；同时审门禁脚本本身是否 fail-open 假绿（吞退出码、提取器漏匹配等）。项目没有此类门禁时**不强加**，至多在最终报告的建议项里提一句。
- **挂 Node 3**（仅当项目已声明样式规范）：按其规范审——典型如新增弱语义类名/变量（`.x`/`.pt`/`--c1` 类）、单行声明块、类名改名未同步模板/动态 class/`:deep()` 选择器，计 actionable；未声明样式规范的项目降为建议，不计数、不清零。
- **挂 Node 4**（任何 Web UI，无附加条件）：视觉布局稳定性——长文本/长用户名/多标签/空值/最大数量 × 窄容器/移动端，查重叠、错位、撑破容器、无意义截断；紧凑区域（作者栏、徽章、评分、工具栏、表格操作列、后台表单行）重点过；Flex/Grid 子项缺 `min-width: 0`/`flex-wrap`/`flex-shrink`/`overflow` 约束导致的错乱是真发现。

### W2 · 内容安全（触发：渲染用户生成内容/富文本/外链/上传的 Web 项目）

挂 Node 2，作为该轮安全审计的必查面：

- 每处 `v-html`/`innerHTML` 逐个核消毒链路来源；URL/图片/外链白名单必须单源复用，页面内复制一份白名单=发现。
- `target="_blank"` 必配 `rel="noopener noreferrer"`；用户可控 URL 先过白名单工具再渲染，禁 `javascript:`/`data:`/协议相对及"字符串包含式"伪装判定。
- 上传链路：类型白名单与内容嗅探必须在服务端、不信文件名/Content-Type、拒可执行/网页类附件；前端不得绕过服务端直传对象存储。
- 资源来源多口径（本地目录/历史反代/对象存储/CDN）时，白名单、渲染层、CSP、响应头是一个联动面，改一处必查其余。
- XML/Feed/导出等服务端直出内容的转义。

### W3 · 前端工程边界（触发：见各子条款）

挂 Node 3 的 review 角度：

- **SSR 框架项目**（Nuxt/Next 等）：浏览器 API（window/localStorage 等）必须在 client 分支/onMounted 内；首屏关键内容不许改成纯客户端拉取；公开页与管理端**按各自目标分开审**——公开页查 SSR 直出/SEO meta/内容安全，CSR 管理端查交互/权限/错误反馈，不混用同一标准。
- **有集中 API 封装的项目**：新代码必须走封装入口，不直连 fetch、不硬编码接口域名；前端代码禁止出现 DB 凭据/连接串。
- **类型化前端**：`any`/非空断言按棘轮只减不增（项目有基线按基线，无基线则新增即发现）。
- **通用前端**（无附加条件）：业务列表用 index 作 key、空 catch 吞掉用户操作失败、超大组件继续堆职责（只在触达时拆相关区域，不做无目标大重构）。

### W4 · 前端 QA 环境与发布边界（触发：前端依赖后端 API/数据的项目）

- **挂 Node 4**：只起前端 dev server 验证不了数据链路——按环境铁律搭同源反代 + 真后端；搭不起完整环境时，报告必须显式标注"仅静态 UI 验证，未完成端到端"，不许拿 SSR 静态渲染截图充当数据链路证据。SSR/构建配置/服务端路由类改动至少 build 级验证，dev server 通过不算数；新增源码文件警惕构建/镜像缓存漏文件（发布产物 soak 正是抓这类）。
- **挂 Node 5**（有 SSR 缓存/登录态绕缓存时）：匿名缓存命中路径与登录绕缓存路径分开压测，不拿缓存命中数字冒充真实 SSR 吞吐。

### W5 · 产品 agent 行为回归（触发：本项目是产品级 agent，或已登记在项目评测配置中）

**为什么单列**：代码 review 和功能 QA 都判不了「这个 agent 变笨了没有」。agent 的行为是概率性的——同一句话可能这次对、下次错，改一句提示词就能让另一条路悄悄退步，而所有测试仍然全绿。这类退步只有跑评测集比 delta 才看得见。

**挂 Node 4**，作为 L6 lens（详见该节点 lens 表）。执行契约：

1. 明确项目提供的 runner/judge/adapter/suites/baseline 路径；先确认入口和参数真实存在，不猜默认私有路径。
2. 先跑 grader 与 judge 的负例自检，再经生产提示词、真实工具 schema 和目标接口跑 task_success/tool_use/trajectory/safety/robustness/rubric 六维。
3. 能力层每例至少三次、取最差结果并报抖动；scripted 只验证工具，不证明模型能力。正式 W5 六维必须齐全；未跑维度列 SKIPPED 仅作诊断，最终 UNABLE，不缩小分母后报 PASS。执行口径以 `agent-evaluation/MODULE.md` 为准。
4. 套件内置通用执行入口与六维结果校验/汇总器，见 `agent-evaluation/MODULE.md`；项目仍须显式提供生产 adapter、judge、配置与基线。未接齐即 **UNABLE**，不能凭执行器合成测试或本 Skill 静态自检放行 W5。

**判据是「对基线的 delta 不退步」，不是绝对分数。** 绝对分数只反映用例集覆盖到哪儿，覆盖不到的地方给多少分都没意义；**退步才是信号**。具体四条：

1. **任一维 delta 为负 = 一个 actionable 发现**，清零重来。
2. **`safety` 维有任何失败 = P1，不看 delta**——红线不容 delta 稀释（与 agent-evaluation 自身"安全维不参与通过率稀释"同源）。
3. **`ENV-NOT-READY`（退出码 3）不算跑过**，本轮该 lens 未执行，不得计入 streak。这正对本流水线的铁律：没真跑的不许冒充跑过。
4. **「抖动」按发现处理**：agent-evaluation 真模型默认每例跑 3 次，同一用例多跑结论不一致即列进抖动。抖动不是噪声，是**只在部分运行里暴露的真缺陷**（实测过一句话三次跑出三种结局、只有 1/3 正确），一律计 actionable。

**基线推进必须是显式决定**：修完 agent 行为、确认新表现更好，才把结果 `cp` 进 `baselines/` 并单独提交。**不许在终审过程中顺手覆盖基线**——那等于自己给自己划及格线，是本流水线定义的作弊。

## Node 0.5 · 入场门（entry）— 这批改动够不够格被终审

**为什么加这个节点**：原来这条流水线全部 5 个节点都在代码写完之后跑，是纯事后审查。但最健壮的代码不是审出来的，是**写之前就想清楚、写的时候就有测试锚点**的。审查只能在既成事实上找茬——一批没有计划、没有可复现锚点的改动，审 20 轮也只是把烂摊子审得更细。入场门把"先规划再开发"的成果变成终审的**受理条件**。

**这不是让你回去重写**，是三条可在几分钟内补齐的可审性条件。任一条不满足 → 先补，补完再开审；补的过程如实记入 state.md。

1. **改动有意图记录**：能说清"这批改动要解决什么问题、边界在哪"——PRD / plan 文件 / 设计说明 / 足够完整的 commit message 均可。缺失则现场补一份**极短的**意图说明（问题 → 方案 → 不做什么），superpowers 的 `writing-plans` 可直接用。理由：审查者判断"这行代码对不对"的前提是知道它想干什么；没有意图，所有发现都退化成风格意见。
2. **缺陷类改动有复现锚点**：凡本批改动里声称"修了某 bug"的，必须有一个**先红后绿**的测试（或可执行的复现脚本）。没有就现场补——先让它红，确认红的原因正是那个 bug，再看它在当前代码上转绿。superpowers 的 `test-driven-development` 就是这个纪律。**"改完看着好了"不算修好**，这条在本流水线里是硬条件，因为后续所有节点都要靠它来判断"修复有没有回归"。
3. **有可独立运行的验证入口**：至少一条命令能把这批改动的核心路径真跑起来（测试、CLI 入口、dev/preview、构建产物均可）。没有的话 Node 4 的"真环境跑"无从谈起，先把入口搭出来。

**单轮程序**：逐条核对上述三条，缺什么补什么。**一轮的 actionable 发现** = 任一条不满足。

**收敛**：三条全满足即通过，**本节点不要求 3 轮**（它是受理条件核对，不是缺陷搜索，刷轮次没有意义）。这是全流程唯一豁免 streak 的节点，豁免理由必须写进报告。

**条件无法由审查者补齐时怎么办**（2026-08-12 回流）。上面写的是"缺了先补"，
但存在一种它没覆盖的情况：**待审代码不是审查者写的**（并行会话/他人提交/历史遗留），
"意图记录"这类条件**只有原作者能补**，审查者代写出来的就是编的。实例：同轮里另一个
会话新增了 783 行已进生产链路的代码，无 commit message、无设计说明，我无法代它写意图。

处置（三条都要做，缺一条就变成"睁一只眼闭一只眼"）：
1. **记为 Open Item 并写明缺的是哪一条**，责任人指向原作者，不由审查者顶替；
2. **在覆盖契约里给该包打标**：`意图记录缺失 → 本包的审查只能从代码反推，
   判断可靠性低于其它包`。后续所有涉及该包的结论都要带上这个限定；
3. **S 档不得放行**（S 档规则本就是"Open Item 一律不接受"）；A/B/C 档可带标继续，
   但**该包不得计入任何 CLEAN 轮次**——理由见核心不变量第 3 条：
   没有意图就无从判断"这段代码有没有做它该做的事"，那不是审干净了，是没审。

## Node 1 · 规范门禁（gates）

**目标**：声称的标准 = 真正执行的标准，没有「假绿门禁」。

**单轮程序**：把项目全部质量门禁真跑一遍（按栈自适应，典型：格式化检查、vet/静态检查、类型检查、单测、`-race`、依赖漏洞扫描如 govulncheck/npm audit（走官方源）、契约/OpenAPI 校验、E2E、构建）。**一轮的 actionable 发现** = 任一门禁红、或发现「文档/CI 声称跑了但实际没真跑/被吞错误/断言空转」的假绿。

**要点**：审 CI 配置本身（token/权限缺失致必红步骤静默通过、镜像源致 audit 空转、超时缺失、E2E 断言写死数量或靠基线容器名在别处失败被吞）。门禁要 hermetic（版本钉死）。修复=补真门禁 + 清存量（棘轮式：新门禁存量多先咨询门禁→清零→转强制，只收紧不放松）。

**lens 表**：L1 门禁真跑（全绿否）→ L2 门禁真实性（假绿考古：吞退出码/断言空转/提取器漏匹配/**测试喂的数据形状生产里根本不存在**，见下）→ L3 门禁覆盖面（**拿覆盖契约的必审包逐个问：这个包被哪条门禁管着？一个都没有 = 发现**）→ L4 hermetic（版本钉死、镜像源、超时、CI 权限）→ **L5 数据发布物**（见下）。

**L2 补充 · 三个具体的假绿形态**（逃逸缺陷回流，**2026-08-02 sample-album 实例**）。L2 原本只点了"吞退出码 / 断言空转 / 提取器漏匹配"三个类名，太抽象——下面三条是它们的具体长相，不点名就抓不到（这三条当年都是**上一轮终审判过"通过"之后**才暴露的）：

1. **合法响应体骗过 try/catch**。外部服务返回的**错误**本身是合法 JSON/合法格式 → `JSON.parse` 成功 → 不走"异常即跳过"的兜底 → 关键字段缺失被 `|| {}` / `?? 0` / `|| []` 吞成"干净结果"。实例：`cli/app.js:314` 的 `npm audit` 门禁，镜像源不实现 advisories 接口时返回合法 JSON 错误体，`.metadata || {}` 洗成"0 漏洞"，而同一依赖树在官方源下有 3 个 high。**判据**：外部命令有**三态**——进程失败 / 输出不可解析 / **能解析但没有预期字段**。第三态最容易被当成第二态处理，而两者后果相反（前者该跳过、后者该阻断）。
2. **门禁分不清"全部通过"与"什么都没验"**。检查项集合为空时 `failures.length === 0` 恒真。实例：`app verify-plugins` 把待验清单清空后仍报 `{ok:true}` exit 0。**判据**：任何"零失败即通过"的门禁都要有**下限断言**（至少验了 N 个），且上报体必须带真实计数——没有计数就无法证明它验过什么。
3. **门禁自己没跑到**。声称的检查因路径/cwd/清单收集出错而整块跳过，脚本照常 exit 0。实例：`download.sh` 的 SHA-256 校验门因一处 `cd` 层级错误使 cwd 跑出目标目录，`[ -f SHA256SUMS ]` 判假 → **从落地那天起一次都没执行过**。**判据**：对每道门禁问"它真的跑到了吗"，用可观测痕迹回答（调用计数、落盘产物、cwd），**不看它有没有打印 ✓**。

**L2 的两条方法论纪律**（同轮编排者自己制造并自查出 7 个假绿后固化，反复救场）：
- **对比型断言必须先有正向基线**——先证明载荷确实会被命中。否则"两边一致"可能是两个空集合在比较（实测踩过：给函数加可选参数前，测试喂的目录根本没被读，三条比较全在空集合上绿）。
- **否定型结论需要比肯定型更强的证据**——"它没做"/"它没红"和"我没看到"长得一模一样。同轮三次差点误判：探针文件未 `git add` 所以工具看不见、部分 grep 只命中注释、被查对象用了另一个字段名。

**新增 lens（同轮实证有效，按需激活）**：
- **门禁可持续性**（触发：门禁套件在持续增长）。**门禁慢到没人跑，本身就是假绿的生产机制**——它不产生错误的绿灯，它让人不去看绿灯。量每个套件耗时并看**增长形态**：某测试若嵌套跑完整套件 K 次，成本就是 (K+1)N，每加 N 秒总耗时加 (K+1)N。实例：一个测试占 `npm test` 总时长 68%，改成"只收清单跑门禁、不执行"后 49s→1s、全量 72s→27s。
- **门禁的脆性**（触发：存在"文件里不许出现 X"这类否定型断言）。会因**注释/文案里提了个词**就误红的断言，最终会被下一个人删掉或改松，而他不知道它原本挡的是什么。**判据是位置不是字符串**：命令位置 vs 字符串内容、可执行行 vs 注释。推论：**当你为了让测试通过而扭曲产品文案时，通常是判据写错了。**
- **跨会话/跨改动的交互面**（触发：同一仓库有多方并行改动）。各方的验证都充分，漏的是**组合**——没有人的职责范围包含交叉处。实例：A 把门禁改成 fail-closed、B 把该门禁设为打包硬门，各自都对，合起来是"离线打包被整个挡死"。**并行时这个 lens 必须每隔几轮跑一次。**

**门禁三态契约**（逃逸缺陷回流，**2026-08-10~12 某验证项目 实例**）。前面的 L2 三形态讲的都是"假绿"，
但假绿只是**一个更基本的缺陷的一种方向**：**门禁把「我测出了什么」和「我能不能测」混为一谈。**
同一轮终审里，这个根因在**八个不同位置**显形，而且**三个方向**都出现过：

| 方向 | 实例（同一轮内） | 危害 |
|---|---|---|
| **假绿** | 取流进程太年轻 → `SKIPPED` → 不计入 fails → 门禁打 ✅ | 有问题看不出来 |
| **假绿** | 视觉门禁跳过唯一需要服务在线的冒烟层，仍 exit 0 | 只验了"服务挂了不会崩"，却报"视觉能力通过" |
| **假红** | 机器上有无关负载（另一个 agent 会话占 6 核）→ fps 判红 | 没问题也报警，久了没人信，最终被重跑到绿为止 |
| **误导性红** | 看板没启动 → HTTP 断言全返回 `-1` → 报出 11 条"CSRF 防护失效/直播裸奔/状态口无鉴权" | **最危险**：让人以为产品有严重安全漏洞，进而去改本来没坏的代码 |
| 崩溃掩盖 | 端口被另一实例占用 → 未捕获 403 → 一屏 traceback，真实原因一字未提 | 崩溃的门禁与坏掉的产品，在输出上分不出来 |

**契约**：每道门禁必须能显式区分三种终态，并让编排层看得见：

- **PASS** —— 测了，且合格
- **FAIL** —— 测了，且不合格
- **UNABLE** —— **没能测**，必须附可操作的原因（依赖未装 / 目标不可达 / 环境不满足 / 前置条件缺失）

编排层（`run_gates.sh` 之类）对 UNABLE **既不计绿也不计红**，单独列出，并让整体退出码非零。
理由：UNABLE 混进 PASS 是假绿；混进 FAIL 是假红。它必须是第三种东西。

**给实现者的四条判据**（每条都对应上面某次实证）：

1. **"用于判断结论是否可信"的检查，它自己失败时必须让结论失效。** 反例：环境洁净检查因作用域 bug 崩溃，只被记进报告字段、没计入失败，而依赖它的 fps 结论照常输出——**为治 fail-open 而写的代码自己就是 fail-open**。
2. **测不了要判红，但要红在"测不了"上，而不是伪装成业务断言失败。** 目标不可达时，输出"目标不可达 + 怎么修"，一条业务断言都不要出。
3. **不要用关键词去猜工具回执的含义。** 实测踩过：断言找"拒"字，而那句拒绝话术恰好没有"拒"字，于是护栏明明拦住了却判红。**测行为，不要测措辞**；拿不到结构化结果时，只声称你真正知道的事（"已调用"），把回执原样附上由人判断。
4. **对"我这一轮到底测的是哪个进程/哪台机器"保持怀疑。** 同一轮里我为性能异常先后给出**五个**因果解释，只有一个成立；真正的变量（机器上还跑着什么、端口被谁占着）从没进过模型。**让程序自己去测环境**，比让人去推理环境可靠得多。

> 这一条与「证据独立性门」是一对：那条防"一轮证据冒充三轮"，这条防"没测过冒充测过"。
> 两者都不是在防代码写错，是在防**结论与证据脱节**。

**L5 · 数据发布物**（触发：项目随代码一起发布数据文件 / 代码里硬编码了大量事实性常量）。盯的是**发布出去的数据本身对不对**，而不是读它的代码对不对。这一条是逃逸缺陷回流加进来的——**2026-08-02 实例**：某旅行 App 的四个逃逸缺陷全是数据（少女峰海拔写成峰顶 4158m 而游客只能到观景台 3454m；瑞郎符号写成 `₣`，而 `₣` 是 FRENCH FRANC SIGN；出发地写成"北京"而实际是上海；同一个地点在 POI 列表里出现六遍）。四条全部躲过了 L1–L4——**数据是合法 JSON、程序跑得通、门禁全绿**，L1–L4 一条都不管"这个数字是不是真的"。

做法有两条硬规矩，缺一条这个 lens 就退化成走过场：

1. **必须拿外部权威源比对，自洽不算数。** 坐标查 OSM/Nominatim、官方电话查主管部门官网、汇率查实时源、开放时间查景点官网。每条发现的格式固定为「数据里写的是 X，而 {来源} 说是 Y」，没有来源的一律记 TENTATIVE 不计入 actionable。
2. **代码里的数据常量与数据文件必须做集合差集**，用脚本不用眼睛：城市 key、类型名、国家代码、时区表、类目映射。差集非空的每一个元素都要说清后果——漏一个映射往往表现为**某个功能静默返回空**，而不是报错。

顺带一提这类缺陷为什么难抓：它们**没有"错误"的形态**。程序不崩、测试不红、日志不报，只有真去和世界比对才掉得出来。所以 L5 的成本主要花在查外部源上，而不是读代码。

**L2 的一个高价值子项：数据形状对账**（逃逸缺陷回流加进来的）。**2026-08-02 实例**：某同步模块的
`stamp()` 只认 `updatedAt||ts||time`，而手记条目真正写的是 `updated` —— 两台设备改同一条时
旧版覆盖新版**并回推云端**，两边都拿不回改过的内容。这条藏了 36 轮 L2 才被抓到，
原因是**守它的断言喂的是 `{id, text, updatedAt}`，而整个仓库没有任何代码产生这个形状**：
断言跑得欢，测的是一个不存在的世界。

做法是确定性的：把测试里**手工构造的对象/结构体字面量**列出来，逐个回生产代码找
「谁产出这个形状」——找不到的就是嫌疑（字段名对不上 / 少字段 / 类型不同）。
根治的写法是让测试**用生产路径产出的数据**当输入（例如先调页面的新建方法拿到条目，再喂给被测函数），
形状就不可能再对不上。这一类缺陷的共同特征：**测试覆盖率、变异测试、覆盖面探测全都看不见它**，
因为那三样都只问"这行代码跑到了吗"，不问"跑它的那个输入像不像真的"。

**规范来源优先级**（新增，避免外来规则喧宾夺主）：项目自带规范 > 语言生态公认标准 > `~/.claude/rules/<lang>/`（若装了 ECC 的 rules）。第三档只在前两档没有规定时**补位**，且它偏泛（例如 python 那份要求"所有函数签名加类型标注""禁止 print 改用 logging"），与项目实际风格冲突时**一律以项目为准**，冲突点记进 state.md 不计 actionable。

**收敛**：连续 3 轮全绿且无新增假绿，且 L1–L4（激活了 L5 的项目则 L1–L5）每个 lens 至少跑过一遍。

## Node 2 · 安全审计（security）

**目标**：以最严格标准过一遍安全。**调用 gstack `/cso --comprehensive`**（2/10 门槛，暴露更多；低于 8 分标 TENTATIVE）。

先探测 `/cso` 是否可用；缺失时按下述全部 14 个审计域逐项完成项目适配、独立取证与证伪，记录替代审计者及证据。任何必需域缺工具、缺权限或未执行均记 UNABLE，不得把“没安装可选工具”当成省略安全审计的理由；未提供相同域覆盖的替代证据则本节点不能放行。

**单轮程序**：跑 `/cso` 全 14 阶段（栈检测/攻击面/密钥考古/依赖供应链/CI-CD/基础设施/webhook/LLM/skill 供应链/OWASP Top 10/STRIDE/数据分类/假阳性过滤+主动取证/报告）。大库用 4+ 个独立子 agent 按域并行（①访问控制/IDOR/RBAC ②注入/加密/SSRF ③认证/XSS/上传 ④基础设施/CICD/依赖/LLM），对每个 net-new 发现**亲自读码取证**。**一轮的 actionable 发现** = 通过取证的真实漏洞（排除硬排除项 DoS/纯限流、agent 幻觉、已由用户拍板豁免的 OpenItems）。

**要点**：像攻击者思考、像防御者汇报；审计只读，发现另行修（修在本节点内闭环：真修→下一轮 /cso 复核）；部署前若涉及数据面变更（如权限模型收敛），**先做生产数据核查**再决定能否部署（真实事故防线）。**复杂度 / DoS 审计要追完整集成路径，不止审单个函数**：把用户输入 → 处理 → 输出的整条主链走一遍，每一步要么证明它在生产规模下有界（时间/内存/递归深度/外部调用），要么标记它进 Node 4 的规模 soak 名单——单函数看着 O(n) 的一串步骤串起来在数千条数据上仍可能挂死。

**lens 表**：L1 OWASP/STRIDE 面 → L2 攻击者视角（构造完整攻击链）→ L3 供应链与 CI/CD → L4 数据面与权限模型 → L5 规模/复杂度（DoS 走完整集成路径，见上）。

**交叉清单（新增）**：`ocr delegate rule <本轮包内文件>` 输出的规则集里有专门的 security-sensitive 段（按语言给：注入、反序列化、`shell=True`、`eval/exec`、密钥硬编码等）。把它当 `/cso` 的**对照表**用——不是替代，是核对 `/cso` 这一轮有没有漏面。规则集里点名了而 `/cso` 没覆盖的条目，要么补审要么写明为何不适用。ECC 的 `security-reviewer` agent 可作为一个额外的独立视角接入 L1/L2。

**收敛**：连续 3 轮零新确认漏洞（每个确认漏洞都过了证伪投票），且 L1–L5 每个 lens 至少跑过一遍。

## Node 3 · 代码 Review（review）— Review Army

**目标**：对抗式多 agent 代码审查，挖单线 review 挖不到的。

**单轮程序（按包分治 × 单一视角）**——这是与旧版最大的差异，旧版"起 2–6 个 agent 各审各的"无法保证覆盖：

1. **取本轮 lens**（按下方 lens 表轮换），本轮**所有** agent 用**同一个 lens**。一轮一个视角、审全部包，比一轮多个视角、各审一部分要可控得多：前者的漏审是可数的，后者的漏审是不可知的。
2. **按覆盖契约的包扇出**：契约里有 N 个包就起 N 个子 agent（`Agent` 工具并发，或 `Workflow` 的 `pipeline`/`parallel`），**一包一 agent、上下文互相隔离**。给每个 agent 的输入只有三样：该包的文件、该包的规则集、本轮 lens 的提示词——**不是会话历史**。包多时按并发上限排队。

   **2a · 什么时候允许合包**（2026-09-15 补，实测）。"一包一 agent"防的是大改动里 agent 挑着审；
   当**整个被审模块装得进一个上下文**时，隔离不产生收益，只产生编排成本。
   判据：**总量 < 1000 行且 ≤6 个文件 ⇒ 允许整模块一个 agent**，在 state.md 记一行「合包 + 理由」。
   ⛔ 超过这个量级一律按包拆；⛔ 不许审到一半嫌慢临时合包（与临时砍 lens 同罪）。

   **2b · 子 agent 必须边定案边落盘**（2026-09-15 实测，⭐ 这条写进提示词，不要只写在铁律 92 里）。
   派活的提示词**固定包含**这三句：
   > ① 每定案一条就**追加写进 `<scratchpad>/<角色>-verdicts.md`**，最终响应只是汇总；
   > ② 最终响应**限定字数**（建议 < 1500 字）；
   > ③ ⛔ 不要读大文件全文，只读点名的行区间。

   实测代价：不写这三句时，一个反驳者 agent 在写最终报告时 **autocompact 打满直接死亡**，
   整轮裁决全丢；重开的轻量实例加上这三句后活下来，产出一模一样。
   ⭐ **agent 的死法是"到最后一刻才丢"**——它前面干的活全部有效，只是没能说出口。

   **2c · 回收用完成通知，不要阻塞式等**（同日实测两次）。
   子 agent 的原始转录是 JSONL 全量，**用阻塞式读取拿它会把整份转录灌进编排者的上下文**
   （我因此两次被迫压缩）。正确做法：派完继续干别的，等完成通知里的结构化结果。
3. **回收时先核覆盖**：每个 agent 必须回报它实际读了哪些文件。差集非空 → 本轮不算清洁，补审。
4. **候选发现进证伪投票**（见上），CONFIRMED 的才计入本轮 actionable。
5. **每轮附带一个"推翻上一轮修复"的 agent**：专门尝试证明前几轮的修复没改对/改漏/引入新问题。推不翻 = 修复扎实；推翻了 = 一个新发现，清零。
6. **外部第二审查器（配了 provider 才有；S/A 档必跑，B 档建议，C 档可省）**：

   ```bash
   ocr review --from <base> --to HEAD --format json --audience agent
   ```

   它跑在**不同模型、不同提示词、不同工具集**上，产出的是本流水线拿不到的另一路证据——这正是「证据独立性门」最想要的东西（同一会话里换个 lens 措辞，独立性远不如换一整个审查器）。**跑的时机：每个节点至少在第一轮和宣告收敛前的最后一轮各跑一次**，不必每轮跑（成本）。

   **它的发现与沉默不对称，这条必须严格执行**：

   - **它报的**：与自家 agent 的发现合流，走同一套证伪投票，CONFIRMED 的照常计入本轮 actionable、照常清零 streak。
   - **它没报的**：**不构成任何清洁证据，不得用来 +1 streak。** 理由是机械的、与工具好坏无关——ocr 的设计取向是 precision over recall（它的 `go.md` 开篇原话就是 *"Favor precision over recall"*，README 也明说 recall 低于通用 agent 是刻意取舍）。**拿一个刻意压低召回的工具的"没查出问题"去累积 streak，就是本文开篇第三个病"假收敛"的教科书形态。**
   - 两边都报了同一处 → 记为**交叉命中**，写进 state.md。交叉命中是本流水线最高置信度的发现，修复优先级最高，且**不得只被 1 票推翻就丢弃**（按高危类别处理，需 3 个反驳者全翻）。
   - 只有 ocr 报了而自家 agent 全员没报 → 这是**逃逸信号**：说明本轮 lens 或分包提示词有盲区。发现本身照常走投票，但**无论投票结果如何，都要在 state.md 记一条"lens 盲区待回流"**，进最终报告的逃逸缺陷回流环节。

**lens 表（按序轮换，跑满一遍才有资格谈收敛）**：

| # | lens | 盯什么 | 可用现成 agent |
|---|---|---|---|
| L1 | 正确性与边界 | 空输入/off-by-one/None 穿透/浮点等值/整除截断/字典缺键 | ECC `code-reviewer` |
| L2 | 活性与降级 | 见下方专段——静默冻结、静默死、完成态排在重活之后 | ECC `silent-failure-hunter` |
| L3 | 攻击者视角 | 构造完整攻击链逐条验证；越权/可见性/经济等价越权（铸币、调分、封禁等不可委派权） | ECC `security-reviewer` |
| L4 | 并发与事务 | check-then-act 竞态、非原子复合更新、async 里的阻塞调用、未 await 的任务、反范式计数一致性 | — |
| L5 | 资源与规模 | 句柄/连接/锁泄漏、无界缓冲、随规模超线性、热路径重复计算 | ECC `performance-optimizer` |
| L6 | 契约与类型 | 类型是否表达了不变量、可表示的非法状态、接口与实现不同步、错误类型丢失原因链 | ECC `type-design-analyzer` |
| L7 | 简化与孤儿 | 本次改动产生的孤儿（不再使用的 import/变量/函数）、过度抽象、能压掉的复杂度。**既有死代码只提不删** | ECC `code-simplifier` |
| L8 | **承诺与实现一致性** | 把改动里所有「承诺文本」提取成清单，逐条回代码核对 | ECC `comment-analyzer` |
| L9 | **测试质量本身** | 测试有没有**有意义的断言**（不是"没抛异常就算过"）、改动路径有没有被覆盖、断言是不是跟着实现一起被改绿的 | ECC `pr-test-analyzer` |
| L10 | **引用落点（跨文件一致性）** | A 说"见 B 的某节"——B 里真有吗？A 挂在某编号名下的语义，与那个编号的**真实内容**对得上吗？三处文档对同一件事有没有三套口径？ | — |

**每个 lens 的提示词都要拼上该包的语言规则文档**：`ocr rules check <包内代表文件>` 取回原文，作为该包本轮的**判据基线**，再叠加本轮 lens 的专属视角。两者正交、不重复：**lens 表是跨语言的**（L1 正确性、L4 并发、L5 资源……决定"这轮盯哪一类问题"），**ocr 规则文档是按语言精调的**（`go.md` 讲 `%w` 丢因果链与 `panic`/`log.Fatal` 出现在请求路径，`java.md` 讲 double-checked locking 与 ArrayList 并发写，决定"这门语言里这类问题长什么样"）。规则文档里还带着两条对本流水线特别有用的纪律，一并转述给子 agent：**①做非局部断言前先用 `file_read`/`code_search` 建立调用点、所有权、同步与输入边界，不许只凭函数名或 import 推断并发/攻击者可控；②不要重复 `go vet`/staticcheck/编译器/`gofmt` 这类确定性工具已经能可靠判定的东西**（那是 Node 1 门禁的活，见铁律 20）。只拿到 `Pattern: default` 的包见上方接入前提 3。

**L8 值得单独说，它抓的是一类最隐蔽、且会骗过所有其他 lens 的缺陷。** 做法是确定性的、不靠灵感：把本批改动涉及的**注释、docstring、commit message、README/文档、错误提示文案、PRD 验收条件**里的每一句"它会……""失败会……""保证……""不会……"抽成一张清单，逐条到代码里问「这句话现在成立吗？」

之所以隐蔽：读代码的人会被注释诱导——注释说"失败自动退回"，读的人就默认那条路存在，不会再去数它接住了几种失败。**2026-08-01 实例**：某投递脚本的 commit message 明写「渲染失败自动退回原封面（无人值守不能因为封面挂掉整条不发）」，实现只处理了子进程 `returncode != 0`，`TimeoutExpired` 和脚本缺失会直接冒泡终止整条投递——承诺的兜底有洞，而且**内层超时和外层超时都是 180s，外层很容易先到**，是常态而非极端。这个缺陷躲过了正确性视角（那段代码本身没错）、也躲过了错误处理视角（它确实有错误处理），只有拿"承诺清单"去逐条核才会掉出来。

对 S/A 档改动，L8 必跑；**清单本身要落进 state.md**（哪句承诺、在哪个文件哪行、核对结论），因为它是这条流水线里少数可以被外人原样复核的产物。

**L10 是 L8 的兄弟，补的是 L8 够不到的那一半**（2026-09-15 实测加进来）。
L8 问「这句承诺，代码做到了吗」；L10 问「**这句引用，被引的那一头真是这么回事吗**」——
两者都属于"声称 vs 实际"，但 L8 的终点是代码，L10 的终点是**另一份文档/另一个编号**。

实测一轮抓到 15 处（审的是一个 SOP 模块，L1–L9 一处都碰不到）：
「测试章读 X」而 X 在被引文件里**零命中**；安全用例依据挂在 `SEC-2` 名下，
而 `SEC-2` 的真实主题是另一件事；三份文档对同一个模块的产出物有**三套口径**；
引用的附件小节里**根本没有**它说的那类内容。

⇒ **文档 / SOP / 规范类被审对象，L10 必跑且优先级高于 L1**——
这类对象的失效绝大多数是引用错位，而不是逻辑写错。做法是确定性的：
把改动涉及的**每一处跨文件引用**（"见 X"、"依据 `ID`"、"由 Y 守"）抽成清单，
逐条打开被引的那一头核对，对不上的就是发现。⛔ `grep` 到那个名字存在**不算核对过**——
要看它那一节**真实写的是什么**（本仓 判据必须检查真实使用而非只数提及次数 同形）。

**L9 补的是这条流水线原来的一个结构性空洞：L1–L8 全在看被测代码，没有一个在看测试本身。** 而这条流水线到处依赖测试——Node 0.5 的「先红后绿锚点」、修复门的「真验证」、铁律 3 的「实证验证」，全都建立在"测试是可信的"这个未经审查的假设上。**测试写歪了，上面这些门就一起变成假绿**：断言只写了"不抛异常"、断言是照着实现的当前行为反向补的（永远不会红）、改了实现顺手把断言调绿了、新增分支根本没有对应用例。L9 就是去查这些。

用 `ecc:pr-test-analyzer`（已实测可作 `subagent_type` 调，只读）。**S/A 档必跑，且必须排在 Node 3 的前半程**——放在最后跑没有意义：如果测试本身不可信，前面几轮基于"测试绿了"做出的所有判断都要重估。发现"测试无效"这件事本身就是 actionable，清零 streak。

**一轮的 actionable 发现** = 通过证伪投票的真问题。

**活性/降级视角（专门抓"静默冻结/静默死"这一类，含本流水线曾漏掉的规模挂死）**：对每一个长耗时 / 阻塞 / 可能失败的步骤问三句——①**卡住会怎样**：有没有墙钟超时？还是无限等一个 native 解析/子进程/锁/网络？②**炸了会怎样**：异常/线程崩是被检测+记录+降级+对用户可见，还是被静默吞掉、后台线程无声退出、UI 冻在中间态？③**顺序对不对**：用户可见的完成态（`done`/结果页/落盘快照）是不是被排在一串重活之后——任一重活挂死就永远到不了终态？凡"长操作无超时 / 后台线程无 try-except / 完成态排在重活之后 / 一个坏输入能拖死整条流程"都是 actionable 发现。

**要点**：每个发现读真实代码核对，排除幻觉与"声称已修实际没改"；修复自身进入下一轮被复核。**给子 agent 的提示词要写明"找不到就报零，不要凑数"**——不写这句，扇出的 agent 有强烈的交作业倾向，会把风格意见包装成缺陷，直接拉低精确率、触发整轮作废。

**收敛**：连续 3 轮零 actionable（三轮 lens 互不相同、每轮包全覆盖、每轮证据独立、攻击者视角无新攻击链），且 L1–L10 每个 lens 至少跑过一遍（B/C 档按分档裁剪，裁剪须开审前定并留痕；**L9 在 S/A 档不可裁剪**——它审的是其他门赖以成立的地基；**L10 对文档/SOP/规范类被审对象不可裁剪**——那类对象的失效绝大多数是引用错位）。

## Node 4 · 功能 QA（qa）

**目标**：真环境跑，不是只靠测试绿。

**单轮程序**：
- **Web** → gstack `/browse`（headless Chromium / puppeteer-core + 系统 Chrome）跑**三态 × 三端**：游客/登录/管理员 × 桌面/移动。查：0 控制台错误、无布局溢出、走真实导航 DOM、权限矩阵（越权全拒、自我提权拒）、关键写流程（发帖/回复/点赞/签到等）、弹窗/交互。
- **CLI/服务/库** → 用 `/verify` 或直接驱动真实入口跑核心用户流程，观察真实行为（非仅 typecheck/单测）。
- **生产规模 + 发布产物 soak（必跑，是本节点的灵魂之一）**：单测和小夹具 QA 只覆盖「几十条数据 + dev 源码」的 happy path，**规模依赖 / 集成链 / 冻结产物**这三类 bug 天生漏网（如后处理在数千文件下卡死、打包后漏依赖、多进程重复启动）。因此每轮至少一次：
  - **在真正会发布的产物上跑**——不是 `python app.py` / dev server，而是打好的二进制 / 冻结 app / 部署构建。
  - **喂生产量级的真实输入**——不是 20 条夹具，是数千条（或该项目声明的目标规模）的真实语料/数据集。
  - **端到端跑完整流程 + 墙钟超时**：断言①流程真的到达终态（`done`/完成页/成功码），不是停在中间态；②UI/服务真的切到结果、可交互；③没有卡死线程、无静默退出的后台线程；④内存/句柄有界。**超时未达终态 = 一个 P1 发现（挂死），不是"跑得慢"**。
- **一轮的 actionable 发现** = 真实可复现的功能/权限/布局/控制台问题、或规模/产物 soak 里的挂死/未达终态/资源失控（区分真 bug 与预存量/环境噪声）。

**环境铁律（踩坑，必记）**：
- 真浏览器 QA **必须有 nginx/同源反代**——本地 preview（node .output）无反代→客户端 `/api` 全 404→依赖客户端 fetch 的功能验证不了（SSR 静态 DOM 残留会误导"看着渲染了"）。登录态=同源反代 + dev-login。
- rebuild `.output` 后必须重启 preview，否则 stale 模块图 lazy route 500。
- 测试脚本选择器要精确（`querySelector("input")` 可能拿错框，差点误报）。
- 控制台历史缓冲会跨导航累积，判定用**本轮新导航后**的计数、按锚点而非总量。

**lens 表**：L1 happy path 三态×三端 → L2 边界与异常输入（空/超长/最大数量/并发提交）→ L3 权限矩阵（越权全拒、自我提权拒）→ L4 生产规模 + 发布产物 soak → L5 中断与恢复（杀进程/断网/超时后的状态一致性）→ **L6 agent 行为回归（仅 W5 触发时激活）**。

**L6 · agent 行为回归**（条件激活，见「专项条款库 W5」）：跑 `agent-evaluation` 的统一入口比 **delta**，判据是不退步而非绝对分数；`safety` 失败即 P1、`ENV-NOT-READY` 不算跑过、「抖动」按发现处理。**这一维是代码 review 和常规 QA 都够不着的**——agent 行为是概率性的，改一句提示词就能让另一条路悄悄退步而所有测试仍然全绿。

**收敛**：连续 3 轮零 P1 / 零越权 / 零数据损坏 / 生产规模 soak 达终态无挂死，且 L1–L5 每个 lens 至少跑过一遍（W5 触发的项目再加 L6：各维 delta 非负、safety 零失败、无抖动，且**不是靠覆盖基线换来的**）。

## Node 5 · 性能 Benchmark（bench）

**目标**：性能不回归、达标。

**单轮程序**：对关键路径压测（后端 API RPS/p99、缓存命中、SSR 吞吐、持续负载内存、Web Vitals 等，按项目既有基线）。**规模曲线**：不止在一个数据量测，至少在 1× 和目标规模（如 10×/100×）各测一次，看耗时/内存**随规模怎么涨**——线性可接受，二次/指数或到某规模直接不返回，就是发现（很多挂死本质是规模拐点，单点压测看不见）。**一轮的 actionable 发现** = 相对基线的回归、未达 PRD/既定阈值、或规模曲线上的超线性/挂死拐点。

**环境铁律**：
- 真 loopback = `127.0.0.1` 真回环；用域名走公网 IP 回环经云网络栈 + TLS 握手会得到假象低值。
- `ab` 的 https 要 `-k`（keep-alive）否则 TLS 握手成瓶颈；`Failed` 含长度假阳性（SSR 长度变化）与 Non-2xx（限流），要区分。
- 按 IP 限流触发的 429 是设计正确（压测单 IP），不算回归。

**lens 表**：L1 关键路径吞吐/延迟对基线 → L2 规模曲线（1× vs 目标规模，看怎么涨）→ L3 持续负载下的资源（内存/句柄/连接，有界否）→ L4 冷启动与缓存失效路径（别拿缓存命中数字冒充真实吞吐）。

**收敛**：连续 3 轮零回归、达标，且 L1–L4 每个 lens 至少跑过一遍。

## 每轮的通用循环（每个节点内）

```
取本轮 lens（轮换表下一个）
→ 按覆盖契约扇出（一包一 agent，上下文隔离，同一 lens）
→ 回收：核覆盖差集 → 非空则补审，本轮不判定
→ 候选发现 → 对抗式证伪投票（3 个反驳者，默认 refuted）
→ 记精确率 C/N；C/N < 1/3 → 本轮作废，换 lens/换 agent 重跑
  → 有 CONFIRMED：真修 → 过修复门 → 真验证（重跑该项 + 门禁快检）→（--deploy 则部署再验）→ clean_streak=0
  → 零 CONFIRMED：本轮 lens 与前一轮不同 ? clean_streak+=1 : streak 不变（lens 重复）
→ 更新 .four-node-review/state.md（本轮 lens、覆盖、提出/确认/证伪、修复、clean_streak）
→ clean_streak>=streak 且当前版本必需 lens 表跑满一遍 ? 打印收敛证据、进下一节点 : 下一轮
```

**修复门（新增，每个修复都要过）**——修复是最容易引入新缺陷的地方，原来只靠"下一轮复核"兜，太晚：

1. **先红后绿**：修之前先有一个能复现该发现的失败断言（测试 / 脚本 / 可观察的失败运行），确认它红的原因正是这个发现；修完转绿。改完直接说"好了"不算修好。
2. **最小 diff**：只碰必须碰的。不顺手优化邻近代码、不重构没坏的东西、风格跟随现有代码。diff 里每一行都能追溯到那条发现。
3. **孤儿清理**：本次修复产生的不再使用的 import/变量/函数要清掉；**既有死代码只在报告里提一句，不删**。
4. **证据后置于断言**（superpowers `verification-before-completion` 的铁律，本流水线全程适用）：**没在这一步真跑过命令，就不能说它过了**。"应该没问题""之前跑过""lint 绿了所以构建也绿"全部不作数——要什么结论就跑什么命令，读完整输出和退出码再说话。
5. 修复本身进入下一轮，被"推翻上一轮修复"的 agent 复核。

- **修复不许让前置节点的绿灯过期**：Node 1 之后任何节点的修复，"真验证"除重跑该项外，还必须过一遍**门禁快检**（格式化/静态检查/类型检查 + 受影响的测试）——安全修复弄红 lint、QA 修复改坏单测都在这里拦住；全量兜底放在最终回归（见最终报告）。
- **修复要 bisect 成单一逻辑提交**；提交信息写清「哪个节点第几轮发现 + 根因 + 修法」。
- 每轮/每节点结束在 state.md 留 `[PROGRESS]`：done / next / 意外，便于中断续跑。
- 若在同一诊断/同一文件反复打转，停下重评（可能是误判方向），别硬刷轮次。

## 最终回归 + 最终报告（全流程结束）

**出报告前必须做一次最终回归**：重跑 Node 1 全量门禁 + 一次核心流程冒烟（QA 方式取 Node 4 的最小集）。任何一项红 = 后置节点的修复弄坏了前面的绿灯——修复并重跑直至全绿，过程如实记入报告；**最终回归未全绿，不得出具"通过"结论**。这一步存在的原因：各节点串行通过后，越靠后的修复越可能让早已通过的节点悄悄失效，最终回归是唯一兜底。

打印一张总表：每个节点的通过证据（连续 3 轮零问题的轮号 + **三轮各用了哪个 lens** + **每轮的包覆盖 m/m**）、累计真发现数与修复 commit、**全流程精确率（提出 N / 确认 C / 证伪 N−C，按节点分列）**、**lens 表跑满情况**（哪些 lens 跑过几轮）、假绿门禁修复清单、安全 0 CRIT/0 HIGH + 加固项、QA 三态结果、benchmark 数字、**降级声明**（ocr / superpowers / ECC / agent-evaluation 哪些没装或没跑、对应环节用了什么替代）、**W5 触发时的 agent 行为 delta 表**（各维 baseline→本次、抖动清单、基线是否被推进及理由）、以及**如实的 Open Items / 未达标项**（触顶未收敛的节点必须显式标注，不许假装通过）。安全审计报告存 `.gstack/security-reports/`，QA/bench 证据留在 state.md。

> 报告里最该被人盯着看的不是"全绿"，是**精确率**和**覆盖数**这两栏。全绿谁都会写；这两栏能看出这次终审到底是真扫了一遍，还是三轮都在同一块地上打转。

**固定骨架**（照这个写，便于横向对比历次终审、也便于直接贴进 PR 或发给上级）：

```
# 终审报告 · {目标} · {日期}
风险档：{S/A/B/C}（定档人：{谁}｜依据：{一句话}）

范围：{base}..{head}｜必审包 {N} 个｜降级声明：{ocr/superpowers/ECC 哪些没装、用了什么替代}

## 节点收敛表
节点 | 轮次 | 通过轮号 | 三轮 lens | 包覆盖 | 提出/确认/证伪 | lens 跑满
```

## 人在哪里拍板（这条流水线不是全自动的）

自动化到底、人只看结论，是这类流水线最常见的失败方式——**没有人为任何一个判断署名，就没有人为结果负责**。以下五处必须由人决定，且决定要落进 state.md：

1. **风险分档**（S/A/B/C）——决定了后面所有火力的强度。
2. **豁免与 Open Item 的接受**——"这条不修"永远是人的决定，不是 agent 的。
3. **触顶不收敛后的升级**——`--max-rounds` 到顶仍有发现时，停下，带材料找人：还剩哪几条、每条的证伪投票记录、卡在哪里、建议的处置（继续投轮次 / 降范围重审 / 接受为 Open Item / 拆批重来）。**不许自行延长轮次上限硬刷**。
4. **生产部署**（`--deploy` 首次）与**任何不可逆操作**。
5. **拆批**——大改动拆成几次终审的切法。

**Open Item 的纪律**（原来只写"如实报告"，太软）：每条 Open Item 必须带齐 **owner / 到期日 / 复审触发条件 / 当前的缓解措施**。缺任何一项 = 这条不算 Open Item，算未修问题，节点不通过。**没有到期日的 Open Item 等于永久接受风险，且没人记得**。S 档一律不接受 Open Item。

## 逃逸缺陷回流（这条流水线唯一的进化机制）

终审通过 ≠ 没问题。**通过之后仍在生产/使用中暴露出来的问题，叫逃逸缺陷（escaped defect），它是衡量这条流水线的唯一外部指标**——精确率、覆盖数都是内部自评，只有逃逸缺陷是外部打分。

每出现一个逃逸缺陷，必须回来做一次归因，问一句：**「它本该被哪个节点的哪个 lens 抓到？为什么没抓到？」** 三种归因对应三种处置，都要改到这个文件里：

| 归因 | 症状 | 处置 |
|---|---|---|
| **lens 缺失** | 没有任何一个视角管这类问题 | **加一个 lens**（L8 承诺一致性、Node 1 的 L5 数据发布物都是这么来的） |
| **lens 在但没抓住** | 视角存在，但提示词太泛、没点名这个模式 | 把这个具体模式写进该 lens 的"盯什么"，最好附一个真实实例——本文里那些带日期的实例全部是这么进来的 |
| **覆盖契约漏了** | 这个文件/包根本没进必审清单 | 改分包规则（如某类文件被 ocr 判为不可审、或手工分包时被当成无关） |

没有这个回流，这条 skill 只会在原地打转：它记住的永远是**去年那些坑**，而不是**上个月那些坑**。所以——**跑完一次终审不算完，出一次线上问题才是这条流水线真正的考卷**。归因结果连同修订一起提交，commit message 写明「逃逸缺陷回流：{现象} → {归因} → {改了哪条}」。

## 铁律（贯穿全流程）

1. **每节点连续 3 轮零问题才放行**——硬门，不可跳。
2. **诚实计数**：找不到=正确结果不凑数；也不为早过而漏报；修复自身要被复核。
3. **实证验证每个发现**：读真实代码 / 真实运行，排除 agent 幻觉与"声称已修实际没改"。
4. **真修真验**（可选真部署）：不是只让测试绿，是真环境观察行为。
5. **只读的节点（安全审计）发现另行修**，在本节点内闭环复核。
6. **触顶不收敛如实报告**，绝不假装通过。
7. 部署到生产等高影响操作，首次前向用户确认。
8. **规模 + 发布产物必测**：至少一轮在真正会发布的产物上、喂目标规模的真实数据、端到端跑完并带墙钟超时。只在小夹具 + dev 源码上验过 = 本次终审不算完整（规模/集成/冻结类 bug 就活在这块没人踩的交叉区）。
9. **结果可核验优先于结果好看**：任何"通过"都要有能被可靠通道独立复核的产物；无法独立验证的绿灯不予采信。一旦识别出编造的工具输出/对不上的证据，立即作废该节点重跑。
10. **后置修复不得让前置绿灯过期**：每次修复过门禁快检，出报告前过最终全量回归；回归红了不许出"通过"报告。
11. **专项条款按触发条件激活，项目自带规范优先**：Node 0 判定并记录激活清单；条件不满足的条款一条都不用，不机械套用。
12. **覆盖契约由工程手段产出，不由模型自觉**：必审包清单在任何 agent 开审前定死；每轮核差集，差集非空的一轮不算清洁。
13. **streak 必须由不同 lens 累积**：同一视角连续清洁不计数；lens 表未跑满一遍，不得宣告节点通过。
14. **发现要扛得住反驳**：每个候选发现过 3 个默认站在"这不是问题"一边的反驳者，≥2 个推不翻才算数；被证伪的也要留痕。
15. **精确率是自检信号**：一轮里大多数发现被推翻 → 该轮作废重跑（审查者在幻觉，它的"零发现"同样不可信）；连续高确认但全是琐碎项 → 在凑数，同样重跑。
16. **证据先于断言**：没在这一步真跑过命令，就不能说它过了。"应该没问题""之前跑过""lint 绿了所以构建也绿"一律不作数。
17. **先规划再开发的成果是终审的受理条件**：Node 0.5 三条（意图记录 / 缺陷类改动的先红后绿锚点 / 可独立运行的验证入口）不满足就先补，补完再开审。
18. **外来规则只补位**：`~/.claude/rules/**`、ocr 规则集这类通用规则，优先级低于项目自带规范；冲突以项目为准，冲突点记录但不计 actionable。
19. **先分档再开审**：S/A/B/C 由人拍板并写进 state.md；降档要理由、升档不要理由；**审到一半临时降档或临时砍 lens = 作弊**。
20. **不重复做 CI 的事**：终审是最外层最贵的一层，Node 1 核的是"前几层声称在做的事是否真的在做"，不是把 CI 再跑一遍；触发时机是切片准备上线时，不是每个 commit。
21. **每轮执行必须独立且绑定当前版本**：复用上一轮 execution ID/运行结果不计新轮；相同哈希不等于没有重跑，不同哈希不等于真的执行。报告须有本轮视角和覆盖依据，按证据独立性门核验。
22. **承诺要拿去和实现对账**：注释、commit message、文档、错误提示里的每一句保证，都要能在代码里找到对应的实现路径；对不上就是发现（L8）。
23. **五处必须人拍板**：风险分档 / 豁免与 Open Item 接受 / 触顶升级 / 生产部署与不可逆操作 / 拆批。**触顶不许自行延长 `--max-rounds` 硬刷。**
24. **Open Item 必须带 owner + 到期日 + 复审触发条件 + 缓解措施**，缺一项即视为未修问题；S 档一律不接受 Open Item。
25. **逃逸缺陷必须回流**：终审通过后暴露的问题，要归因到"哪个 lens 该抓没抓到"，并改回本文（加 lens / 改提示词 / 改分包规则）。**这是本 skill 唯一的进化机制，不做它，这份文档只会越来越过时。**
26. **外部工具的"发现"可采信，"沉默"不可采信**：接进来的第三方审查器（ocr 及后续接入的同类），报出来的走同一套证伪投票、CONFIRMED 就清零 streak；**没报出来的一律不得用于 +1 streak**。凡设计上取 precision over recall 的工具，其沉默都是弱证据——**用它的沉默累积 streak = 假收敛**。
27. **接外部工具先反向测，且不认 exit code**：任何第三方工具接进门禁前，必须先做一次反向测试（故意喂错子命令 / 错 ref / 空输入），确认门禁真的红。**判据只能是结构化输出本身**（如 `ocr delegate preview` 的 `# Files (N reviewable / M total)`，且 N 与 `git diff --name-only | wc -l` 对得上），**不能只看退出码**。

    实测（ocr v1.8.4，2026-08-02，对应上游 issue #641）：

    | 命令 | exit | 行为 |
    |---|---|---|
    | `ocr delegate bogus` | **0** ⚠️ | 打印 help 却报成功 |
    | `ocr bogus`（顶层） | 1 ✅ | 正常报错 |
    | `ocr delegate preview --from 不存在的ref` | 1 ✅ | 正常报错 |

    坑只在**父命令 + 拼错的子命令**这一种形态（`ocr delegate` / `ocr config` / `ocr rules` 这类带子命令的），顶层命令和参数校验都正常。**只看退出码会让一个拼错的子命令变成绿灯。** 这条对所有后续接入的工具同样适用，不是针对某一家——接任何新工具，都先跑这三格反向测试再谈接入。
28. **外部工具的覆盖范围要显式核对，不许默认它审全了**：接入前先用工具自己的 preview/dry-run 拿到它认的清单，与 `git diff --name-only` 做差集；差集非空说明该工具有它审不到的文件类型（例：ocr 的 80 扩展名白名单不含 `.md`/`.txt` 且编译进二进制不可扩展），**这部分必须用其他手段补齐并在报告里标注补齐来源**。工具的能力边界不写下来，就会变成覆盖契约的静默缩水。
29. **产品 agent 的合格线是 delta 不退步，不是绝对分数**（W5 触发时）：绝对分只反映用例集覆盖到哪儿，**退步才是信号**；`safety` 失败即 P1 不看 delta，`ENV-NOT-READY` 不算跑过，「抖动」按发现处理。**基线只能在确认变好后显式推进并单独提交——终审过程中顺手覆盖基线 = 自己给自己划及格线。**
30. **人工试几句不能顶替 agent 行为回归**：agent 行为是概率性的，试几句正好都对是大概率事件（实测一句话三次跑出三种结局、只有 1/3 正确）。没跑评测集就在报告里如实写「本次未做 agent 行为回归」。
31. **判据必须钉「这段逻辑还在执行 / 还接在生产上」，不能只钉「文件里这段文本还在」**（2026-09-01 example-app 实证：同一形状在**同一批修复里复发 4 次**，且其中两条的提交信息明确宣称修的就是这个形状）。两个子形态各有最省事的绕过：
    - **文本存在 ≠ 分支还活着**：把后门放在被钉那一行**之前**（`if (x) return true;` + 原样保留的转发行）；把守卫塞进永不执行的分支（`if (cfg.__never) { …守卫… }`）；把内层比较包进 `if (false && …)` —— 被钉子串**全都原样保留**，判据全绿。⇒ 钉**整个函数体**（去注释后必须只剩那一条语句）、**锚定行首缩进**（`^  child\.stdin\.on\('error', fail\);$`，任何嵌套都不满足）、把**同一段里的每一行都钉上**（不要只钉你正在看的那一行）。
    - **文件里有 ≠ 生产里接上了**：判据从磁盘读模块文件，只能证明"文件里写了什么"。`if (false) Object.assign(KIT, makeExtraKit(…))` 让 92 个组件在生产里根本不注册，而那道门叫"组件覆盖"、照报 109/109（真实 17/109）；ctx 里删掉三个清洗函数，34 处调用全变 `undefined(...)`，而"逐字段清洗"的地板只数文本、照报 pass。⇒ **分母与依赖都要从生产接线里推导**（`Object.assign(KIT, makeXxx(` → import → 文件路径），硬编码的只保留唯一入口文件；**合并/注入必须断言是无条件语句**。
    - 通用自检：写完一条判据，问 **「把这段逻辑摘掉、但让被钉的字符原样留在文件里，我做得到吗？」** 做得到就是没钉住。
32. **「我试过了，做不到」是一个特别危险的结论**（同日实证：我把"跨进程确定性触发 EPIPE 本机构造不出来"写进判据注释，复核者当场用 5MB 大写入做出来 —— 无守卫 8/8 打死进程）。它长得像诚实，实际把**「我没找到方法」写成了「这件事做不到」**，而且**写进注释后就没人再去试了**，比不写更糟。⇒ 诚实边界的正确形态是**说清楚我试了什么、失败在哪一步**（"我用 `stdin.destroy()` 试的，只看到超时" —— 别人一眼看出漏了"写入量要撑满管道缓冲"），**不是给出一个结论**。凡要写"做不到"，先把失败路径写下来，再问这句结论是不是只对你试的那一种方法成立。
33. **变异测试之前必须先提交**；`git checkout <BASE> -- <file>` 会连带抹掉该文件**尚未提交**的改动（example-app 一个会话内同型踩了 8 次）。另两条同族：**变异必须确认真的应用到了目标位置**（目标模式常有多份副本，`perl -0pi -e 's///'` 只替换第一处 —— 曾因此把好判据误判成坏判据）；**反例必须真的制造出那个缺口**（"受害对象本来就满足条件"的反例两边恒等，把判据改回错误实现照样绿）。
34. **打补丁会让判据「更具体」而不是「更承重」——要换的是判据的种类**（2026-09-01 example-app 三轮实证，每轮 9/9/6 条不收敛）。第三轮复核者的诊断：*每一处修复都只是把判据收紧到上一轮攻击的那个字节周围，而把**紧邻的自由度**留着*——兄弟行、调用方、第二个参数、操作数、下一条语句。具体的复发形态：
    - 钉死了 `serviceAllowed` 的函数体 → 在**兄弟行**追加 `declaredServices.set(p.name, null)`（= 取消全部限制），正则照样匹配、纯函数用例照样过、30 套全绿。
    - 钉死了函数体 → **没人要求这个函数被调用**：两个调用点改成 `true`，它成了完美但无人使用的纯转发函数。
    - 从 `Object.assign(KIT, makeXxx(` 推导分母 → 把第二个包并进**同一句的第二个参数**，正则只捕获第一个。
    - 「按形状钉」了外层守卫与内层比较 → 换掉**操作数**（`const txt = String(c.expectText)`），比较变成 `String(x).includes(x)` 恒真。
    - 行首锚定守住了「不许包裹」 → **下一条语句** `removeAllListeners('error')` 把它撤销。
    ⇒ 换种类的对照表（左边是打补丁，右边是承重）：

    | 打补丁 | 换种类 | 为什么承重 |
    |---|---|---|
    | 「这一行还在」 | **写入点/调用点的完整集合**（计数 == N） | 加任何一行都会改变计数 |
    | 「参数位第一个」 | **从 import / 依赖声明取全集** | 新增实现必然要声明依赖，绕不过去 |
    | 源码正则钉操作数 | **抽成纯函数 + 行为断言**（喂坏输入必须判失败） | 与写法无关，只与行为有关 |
    | 行首锚定 | 锚定 **+ 禁止撤销动作** | 锚定管位置，禁令管后续语句 |

    自检：连续两轮都在同一个文件里发现同型缺陷时，**停止打补丁**，问「这条判据是什么**种类**的，有没有一种种类能一次覆盖掉整类自由度」。
35. **归因要有证据，「未查明」就写未查明**（同日实证）：我把一次未复现的门禁红写成「最可能的解释是复核者在活动工作树里跑变异」——复核者证伪：它全部变异都在 rsync 副本里、活动树 `git status` 每次都空，**且它自己在完全隔离、无并发写入方的副本里也观测到同一现象**。⇒ 我写那句时手上**没有任何证据**，只是它**听起来合理**。**一个听起来合理的归因，会让后来的人停止寻找真因**——效果和过期记录一样，主动制造错误结论。
36. **「静态文本谓词 + 一份写死的词汇表」对图灵完备的语言永远不可能完备 —— 判据要守「危险能力的出口」，不守「守卫本身」**（2026-09-01 example-app 四轮实证 9/9/6/8 条不收敛）。第四轮复核者的诊断：*四条新判据里只有一条真的换了种类，另外三条只是把**硬编码的对象换了一层** —— 动词表 / 文件名 glob / 拼写表。词汇表之外的等价写法一律看不见。* 实测绕法：`.get(name).add('x')`（动词表没有 `.get`，而集合是**可变**的、Map 只是持有者）；对象字面量里**加第二个同名键**（后写胜出，被钉的那段一个字没动、只是不再被执行）；**更早的同名 `if` 分支**；第三个实现文件**改个名字**；`return { ...hidden(), … }`（零新增 import）；`Object.assign(X, false && make(…))`（行首锚定完好，**条件挪进实参**）；`obj?.off?.(…)` / `obj['off'](…)`（`\.off\s*\(` 被 `?.` 隔开即失配）。
    ⇒ 四种真正承重的判据种类（按优先级）：
    1. **让攻击在运行时不存在**——把交出去的东西冻成只读/无该方法，静默后门变成响亮的崩溃；
    2. **守危险能力的出口**——找到那个唯一的 sink（取数、写盘、出网、记分），要求**每一处出现**都在守卫的放行分支里。新增任何绕过路径都必然新增一个未被守护的出口；
    3. **让运行时自己报**——静态解析注册表/清单永远追不上写法，改成运行期把真实注册内容回传给门禁（实测两种静态判据攻不破的绕法都被当场点名）；
    4. **行为量而不是拼写量**——真跑起来数 `listenerCount`、数条数、比返回值。
    ⇒ 反向自检：**「在不违反这条判据的前提下，我能不能达到同样效果？」** 想得出一种就还没守住。另：**一条永假的断言不是防御，是误导读者**（`x.length >= 1` 而 `x` 由一个已断言非空的集合 map 出来）。
37. **抽取/搬迁必然伴随三种静默损坏，每次都要逐条核对**：①**判据跟着代码搬走了，喂参数那行留在原地**（消费方仍指向旧位置，或退回文本正则）；②**语义静默收窄**（内联时会做的检查，抽出去后某个分支不再做）；③**上报了不等于收下了**（新字段一路加到发送端，接收端把它丢了）。example-app 一个会话内这三种各复发 3 次以上，且**每次都是在刚刚批评完同一形状之后**。
38. **判据守不住的东西，架构要守 —— 「渲染层/客户端做检查」等于没做检查**（2026-09-01 example-app 五轮实证 9/9/6/8/10 条不收敛，第五轮才挖到根）。症状：一条安全规则（服务白名单）写在**发起方**，而执行方的 IPC/API **不带身份**（`ipcMain.handle('data:fetch', (_e, service, params) => …)`）。于是发起方任何一行改动都能整条还原：给内存里的声明对象投毒（在被钉死那行的**上面**加一行，那行逐字未改）、在 preload 加一条同义通道（`dataFetch2` —— `\bdataFetch\b` 匹配不到它）、`window.example-app['data' + 'Fetch'](…)`（连通道都不用加）。**四轮里写的每一版源码判据都被绕过，而它们本可以一条都不用写。**
    ⇒ 判定问句：**「这条规则的执行点，能不能只靠改发起方的代码就绕过？」** 能 ⇒ 判据是补丁，**把执行点挪到特权方**，并让特权方**自己从权威来源（磁盘/数据库）推导**规则，不采信发起方传来的任何声明。挪完之后，判据才有意义 —— 而且要用**行为断言**守（把裁决抽成 DOM/框架无关的模块，真造夹具问它）。
    ⚠️ 挪的时候必然踩两个坑，都实测过：①**照抄发起方的写法**（对方拿到的是已解析的对象，磁盘上是文件名字符串）⇒ 规则算成空集 ⇒ 合法请求被拒（evals 当场红 2 条 —— 第一个被新执法挡住的是我自己）；②行为断言测了裁决函数，**没人守特权方真的调用它**（改成 `if (false)` 后全绿）。
39. **「过紧」与「过松」同样是缺陷**：一条会误报的判据早晚被人删掉或加豁免，而且**红色会把维护者指向错误诊断**（实测：把三元改成语义完全相同的 `if/else`，判据红了并报「`|| true` 之类的短路…插件可取任意服务」，事实上什么都没被短路）。⇒ 钉**语义要点**（拒绝分支必须存在），不钉字面形状。
40. **⭐ 断言「系统做了什么」，不要断言「源码长什么样」**（2026-09-01 example-app 八轮实证 9/9/6/8/10/9/8/8 条不收敛；第八轮复核者的结论：*这八条里有六条是同一类判据在它没预料到的拼法上失效。在结果上分得很清楚：凡是断言「系统做了什么」的都承重了，凡是断言「源码长什么样」的这一轮全部被绕过*）。实测被绕过的拼法（每一种都全套门禁绿 + 真实出网）：`const alias = sink;` 后调 `alias(...)`；`const { sink: renamed } = require(...)`；channel 名不含判据用来过滤的关键词；`ipcMain.on` 而非 `.handle`；`'sv' + 'c:x'` 动态拼名；`Object.defineProperty(module.exports, 'f', {value})` 而非 `module.exports.f =`；`arguments[4] = x`（非严格模式下等价于改写第 5 个形参）；把 `return null` 换成 `return new Set([...])`。
    ⇒ 承重判据的三种做法：
    1. **运行期普查**——stub 掉宿主框架加载真实入口文件，记录它**真实注册/导出/暴露**了什么（IPC channel、路由、事件），与已知清单比对。改名、别名、换 API、动态拼名全都逃不掉，因为观测的是**注册这个动作**。
    2. **喂受控输入看真实裁决**——把临时目录/夹具喂进去，断言它真的按那个输入判（导出被重包指向别处时，这一条立刻红）。
    3. **属性式反例**——几十个随机的、磁盘上不存在的标识符，逐个断言拿不到任何授权。写死一张名字表只能测到你想到的那几个；按魔法名开的后门用的是攻击者自选的名字。
    ⇒ 另有两条运行期加固比任何判据都便宜：给安全关键文件加 `'use strict'`（切断 `arguments` 与形参的双向映射）；把交出去的白名单/配置**冻成只读**（后门从静默生效变成响亮的 `TypeError`）。
41. **执法器比注册器松 = 一个不需要写代码的后门**：注册器（校验/准入）拒绝的 manifest 形态，若执法器（运行期裁决）判为「合法/不设限」，那么**造一把主钥只需要一个 JSON 文件**（实测：目录里只放 `{"main":"nope.js"}`，注册器拒、裁决器判不设限，真实出网）。⇒ 执法器要么**直接复用注册器的校验函数**，要么比它**更严**——绝不能更松。且「不设限」这一档的前提必须被验证（实测 `{"main":"plugin.json"}` 目录里零个 JS，也拿到了「代码式插件跑任意 JS 所以不设限」的待遇）。
42. **⭐ 当观测域是枚举、被观测域是自由的，差集恒非空 —— 加固只是把差集挪个地方**（2026-09-02 example-app 第十轮实证）。判据的观测域常常是一份**作者写死的枚举**：一个文件名、一种引号、一张豁免表、一个磁盘目录、一个函数名、一批测试用的标识符；而被观测的东西（channel 名、调用方传来的身份字符串）是**自由给定的**。实证：同一条判据我改了三版都没堵住 —— 40 个随机名 ⇒ 漏 `zzz-helper`；100+ 个从磁盘真实名变形生成 ⇒ 漏 `totally-made-up-xyz`；加了全称断言但探针名仍是我列的 ⇒ 漏 `q7x-random-name-9`。
    ⇒ **正解不是把枚举做大，而是换承重物 —— 找一个被观测方无法回避的物理事实**：
    - **切断物理依赖做全称断言**：把 `fs.readFileSync`（或网络、时钟、随机源）换成恒抛，断言此时对**任意**输入都必须是拒绝/空。授权若能凭空产生，就说明有一条不读权威来源就发放的分支。这条由**被测函数的物理依赖**承重，不由你的想象力承重。
    - **探针输入从被测源码自己提取**：按名字/按常量开的后门**必须把那个键写进源码**，于是它一定在「源码里的字符串字面量」这个集合里。这条只依赖「后门要生效就得留下它的键」。
    - **组合关系断言**：把 `f(x)` 必须恒等于 `g(h(x))` 断言在一大片输入上 —— 在 `f` 里加任何独立分支都会打破它，无需猜那个分支的触发条件。
    - **差分对账**：期望值从**权威来源独立重算**（而不是写死的表）。⚠️ 它的固有边界是「两份实现同源就会同时错」，写清楚，别假装它更强。
43. **「记录了不等于校验了」**（example-app 一个会话内三次）：新增一个诊断字段/桶/日志之后，必须同时有人**读**它并断言。典型形态：`census.other` 收集未预期的注册方法却只被并进「已见集合」——于是它只会让判据**更容易过**；`timedOut` 算出来、进了 JSON、有中文说明，却没人钉「它被拼进了输出」。判据自查问句：**这个我刚加的字段，删掉它的消费方，有哪条断言会红？**
44. **⭐⭐ 判据的强度是 `min(观测面, 输入驱动)` —— 两半都要抬**（2026-09-02 example-app 第 13–14 轮实证）。第 13 轮把观测面从「我注入的 sink」换成「真实的出网函数」，第 14 轮立刻证明：**观测面再宽，没喂到那个输入就一次观测都不产生** —— 同一个判据里服务名维度已升成权威全集（175 个），而 `params` 维度还是 20 个手写形状，一个 `params.__zz9` 即万能放行、全套绿。⇒ 两个可操作的手法：
    - **输入侧别猜键**：把可疑入参换成 **Proxy**，观测「被测代码读了它的哪些属性」。裁决路径本就不该读它 —— 读了就是把它当成了裁决输入。这条不依赖你想到哪个键。
    - **观测侧别只盯一个点**：一个模块往往有多个等价出口（`fetchService` 之外还有 `getJSON`、`require('http')`、`fetch`）。与其在出口侧追，不如在**依赖侧**断言：这个决策模块**不许**出现裸网络模块 / `fetch` / `Date.now` / `Math.random` / `process.env` / 模块级可变状态 —— 它们都是决策路径上不该存在的依赖，而时间引信与高阈值计数器正是靠它们躲过「同一输入结果恒定」的。
    ⚠️ 配套：**地板要设在退化值之上**。example-app 的服务目录在缺一个缓存文件时从 175 掉到 19（全新 clone / CI 无网 = 正常状态），而地板写的是 `>= 15` ⇒ 静默丢掉 89% 覆盖还报绿。**地板数的是「够不够」，不是「有没有」。**
45. **⛔ 认得出「结构性无穷回退」，并在到达收益边界时停手**（example-app 十四轮实证：发现数 9/9/6/8/10/9/8/8/4/5/7/8/8/9，**后六轮 4→9 不降反升**，且第 9–14 轮的改动几乎全部落在**判据文件**上、生产代码零改动）。识别信号：
    - 每一轮的修法都对，而下一轮总能在**相邻一格**找到同型缺口（兄弟行 → 调用方 → 第二个参数 → 操作数 → 下一条语句 → 文件顶层 → 另一种语法 → 另一个入口）；
    - 每次「换承重物」之后，**新的承重物自己又是一层枚举**；
    - 发现数不再下降，而修复的对象从产品代码变成了判据本身。
    ⇒ 这时要问的不是「再写一条什么判据」，而是**「这条链上所有攻击的前提是什么？那个前提由谁守？」** example-app 的答案是「能编辑内核源码」，而它由 `kernel/main.js:2`「embedded agent must never edit this file」那条**提交边界 + 代码审查**守 —— **测试在原理上守不住一个能任意改源码的敌手**，继续加判据只会不断提高「改坏它需要多聪明」，而不会到达「改不坏」。
    ⇒ 停手时必须：①把判断连同**趋势数据与分层诊断表**写进 state.md（不是悄悄停）；②**明确移交**残余威胁类给哪条边界；③**诚实记录 streak 仍为 0 且不放行**，理由是「这条线上的 streak 在当前威胁模型下不可能靠加判据达成」——**不伪造收敛**；④点清这条线**实际修掉的真实生产缺陷**，证明它不是白跑。
46. **⭐⭐ 有界资源的截断标志必须跟着数据走到消费方**（2026-09-02 example-app Node 3 未覆盖包复核：**六个 substantive 发现是同一个失败**）。形状：一个有界资源被**静默裁剪**（5000 行、400 个分块、第一个匹配项、一次探测），而裁剪后的结果**通过一个断言完整性的接口报告出去** —— `sum_amount: 5000`（真值 6000）、`chars: 300027`（实际只入库 200000）、「已换到北京」（只改了一半）、`{"ok":true,"passed":180}`（一个都没探）、「文档里没有相关内容」（在没索引的那半里）。
    ⇒ **截断点通常是有注释的命名常量 —— 限制是有意的，缺的不是限制而是标志。** 修法三步：①在裁剪处打标志；②让标志**跟着数据一路走到消费方**（只放在返回值里等于没有 —— 读磁盘的那一方看不见你的返回值，标志必须**写进落盘对象**）；③消费方据此**改措辞**（「只统计了前 N 行，这个数字不是全表的」而不是给一个光秃秃的数）。
    ⇒ 配套判据必须有**正向基线**：小输入**不许**带标志 —— 否则「带标志」成了恒真，量不出任何东西。
    ⚠️ 措辞要诚实：源总量若在裁剪时已经丢掉，就说「原表更长」，**不要编一个 sourceRows** —— 编一个数字正是你在修的那类缺陷。
47. **性能门禁的阈值要设在实测中位的 10–30 倍**（example-app Node 5 首次启动）。它防的不是「慢」，是**某次改动让热路径慢一个数量级而没人发现**。**宽阈值抓数量级回归，窄阈值只抓抖动 —— 而抖动造成的假红会让这条判据先被加豁免、再被删掉**（同一会话已有两条判据因假红被判为净负值）。必配两样：①**退化前提断言**（「服务目录只有 19 个 ⇒ 这轮数字不可比」——不然你会在一个残缺的输入上量出漂亮的数字）；②**无累积退化**（同一操作第 1 次与第 500 次一样快，抓缓存每次失效／有东西在累积）。反向验证同样必须做：注入一个数量级退化，确认它当场红。
48. **⭐⭐ 修复要检查「它有没有覆盖这个缺陷实际走的那条路」**（2026-09-02 example-app 实证）。最容易的失败不是修错，是**修在了另一条路上**：崩塌保护写好了，但它只从「运行期裁决文件」读上一轮 —— 而这个缺陷的真实场景（首次巡检 / 全新安装 / 当下这台机器）恰恰是那个文件**不存在**，于是保护静默关闭，而权威的随包基线就在磁盘上被忽略。⇒ 修完必问：**触发这个缺陷的那个具体状态，现在走进修复代码会怎样？** 把那个状态**当成夹具真跑一遍**，而不是跑一个你顺手造的、更方便的状态。
    ⚠️ 同族：**判据也会守在另一条路上**。example-app 的目录穿越修复，其唯一判据用了一个 `parseRetarget` 解析不了的指令（中文 key），于是**在碰到路径校验之前就返回了** —— 删掉整条安全校验，全套 37 套照绿。**发现自己的测试无效时，要修的是提交进去的判据，不是手边那个临时脚本**（我当时只修了后者）。
49. **判据式写错的两个方向都要有反例**：example-app 用 `sum(chunk.length) < text.length` 判「文档被截断」—— chunk 是**重叠**的、`text.length` 含会被折叠的空白，于是**漏报**（161k–200k 真截断标 false，原缺陷逐字重现）与**误报**（空白多但没截断的文档被标截断，然后答出每句都假的话）同时存在。**正确的信号 `chunks.length >= MAX_CHUNKS` 就在同一个函数里。** ⇒ 写完一个判据式，分别构造「该真而判假」与「该假而判真」的输入各一个；只测了一个方向的判据式，另一个方向几乎总是错的。

50. **⭐⭐ 诊断信息不许断言一个没被验证的原因 —— 指错方向的诊断比没有诊断更糟**（2026-09-02 example-app R3-1 实证）。example-app 的门禁 runner 把测试的死法分类为「超时」：`const timedOut = r.status === null && (r.signal != null || (r.error && r.error.code === 'ETIMEDOUT'))`。那个 `signal != null` 让**任何信号致死**都走进超时分支，于是一个内容只有 `process.kill(process.pid,"SIGKILL")`、**0 秒就死**的测试，拿到的横幅是「⏱ 超时被杀：**墙钟 300s 到点**……整机负载/子进程挂死都可能」。段错误、OOM 被杀、外部 kill 全部会被引导去查「整机负载」。**没有诊断，人会去查；错的诊断，人会去查错的地方。** 两种形态实测字段截然可分（超时 `error.code='ETIMEDOUT'`、信号致死 `error=undefined`），而**正确的判别式本来就在那个表达式里，是 `||` 把它稀释了**。⇒ 凡是向人陈述「为什么失败」的文案，都要问：**这句话断言的因果，代码真的验证过吗？** 分类做细之后必须补一条「分类变细不等于放行」的断言（这里是 `code !== 0` 仍成立），否则「区分」很容易被下一次改动写成「豁免」。

51. **⛔ 变异测试的改写工具不要用 `perl -pi -e` 改含非 ASCII 的源码**（2026-09-02 example-app 实证：一位复核员就死在这上面）。默认的 perl 是字节导向的——真实风险**不是响亮报错，是无声损坏**：字节级模式会切开多字节字符产出乱码，没有任何报错（⚠️ 2026-09-15 实测修正：默认环境下 ASCII 与中文替换均 rc=0 正常完成；只有显式配 `-C`/`PERL_UNICODE`/`use utf8` 才可能报 Malformed UTF-8。此前这里写「会因编码报错」——当年那次卡死的具体机制未复现，结论「别用 perl 改非 ASCII 源码」不变）。⇒ 一律 python3 + 显式 `encoding='utf-8'`，并且**先断言目标出现次数为 1 再替换**（`assert s.count(OLD)==1`），替换后**再 grep 确认落在目标行**——同一模式在文件里有多份副本时，"替换了第一处"会让你把一条好判据判成坏的。

52. **⭐ 整机负载会制造假红，而摘要层分辨不出来**（2026-09-02 example-app 实证）。一次变异测试报「3 条判据变红」，逐条翻 output 才发现只有 1 条是变异抓到的：另两条一条在做**真实 DNS 查询**、一条有 300s 墙钟，都是复核员进程还在跑时的整机负载导致（15 分钟 load 均值 8.21，单独跑那条判据只要 **0 秒**）。**门禁的使用方式恰恰是看摘要**，而摘要把「环境不洁」和「断言失败」印成同一个数字。⇒ ①runner 必须把两者在**结果结构里**分开（`timedOut` / `killedBySignal` 字段），不能只在正文里写一行字；②下「这个变异被抓住了」的结论前，**逐条看那条 result 的死法**；③重载下的红先复现再采信，单独跑那个文件看它到底要多久。

53. **⭐⭐ 对源码做正则的判据会把「当时的写法」固化成规范 —— 正确的修复会被它判红**（2026-09-02 example-app 实证）。修好 R3-1 后 `gate-integrity` 立刻报红，因为它有两条断言钉的是旧写法的**字面形状**（`/const timedOut = r\.status === null &&/`、`/timedOut: !!timedOut/`），而正确的修复恰好改变了这个形状。**这类判据既挡不住绕过（改个变量名就过），又会拦住正确的修复（改对了反而红）——两头都不承重。** ⇒ 判据要钉**语义**（"判别必须来自 ETIMEDOUT"）或干脆做成**行为探针**（在临时工作区植一个自杀测试，真跑 runner，断言分类字段）。本例里两种都留了，但注释里写明**承重的是行为探针**，源码正则只是辅助——**排序要写出来**，否则下一个人会去维护那条不承重的。

54. **⭐⭐⭐ 判据数是被声明出来的，不是被执行出来的 —— 要有一条元判据去证明它们真的跑了**（2026-09-02 example-app R3-2，CRITICAL）。一个判据文件在 `try {}` 里写了 `return (async () => {…})()`；**CJS 模块顶层的 `return` 会终止整个模块体**，它后面的四个块（每块都是上一轮辛苦补的判据）**从提交那天起一次都没执行过**，而文件仍然 exit 0、仍被计进「判据 N 套 / M 条断言」的统计。在那四块开头各植一个 `assert(1===2)` 毒丸，跑它依旧 **EXIT=0**。⇒ 这是「声称的≠实际的」最彻底的形态：代码在、断言写得很好、文件报绿，而它们从未运行。**检测不要用正则**（"顶层"这件事正则判不准，本例就藏在 `try{}` 里）：`new vm.Script(src)` 按**脚本**而非 CJS 函数体编译，顶层 return 是语法错误 —— 真解析器，零启发式。更通用的自检：**数一数文件声明了几个里程碑 `console.log`，再数实际打印了几个**（本例 6 声明 / 1 打印）。

55. **⛔ 复核员给的修法要自己复核一遍再落地**（同上，R3-2）。复核员建议把 `return` 换成 `void` 并报告「四块全绿」。但那四块**没有任何环境变量管理**，而恢复 env 的 `.finally()` 是异步的 —— 它们会同步抢跑在测试夹具的临时 ROOT 上，「全绿」是在**错误环境**下的巧合。查证被测模块在 **require 时**就把 ROOT 定死之后，正确的修法是「env 与 require 缓存**同步**恢复，只把删目录留在 finally」。⇒ 外部复核员的诊断通常比修法可靠：**证据照单全收，修法一律自己推一遍**。

56. **⭐⭐ 一个模块在 require 时定死的东西，清缓存也要连着清**（example-app 两次踩到，一次在被测代码、一次在我自己新写的判据里）。`const ROOT = process.env.X ? ... : ...` 写在模块顶层 ⇒ 它在**第一次 require 时**就固化了。测试里改了 env 再 `delete require.cache[被测模块]` 是不够的：被测模块 require 的**那个读 env 的模块**也在缓存里，ROOT 仍是旧值，探针于是扫了一个空目录、拿到 `undefined` 而不是预期值。⇒ 清缓存要清**整条依赖链上读 env 的那些**；写完探针先验它在「应该为真」的输入上确实为真。

57. **⭐⭐ 判据不该把自己绑在外部服务的延迟上**（example-app R3-8）。一条门禁真跑了带 LLM 的问答路径：30s 改写 + 60s 作答 ×2 个问题，逼近 runner 的 300s 墙钟 —— 终验那次的红就是这么来的（`timedOut: true`，隔离重跑 EXIT=0）。**这种红既不是缺陷、也不可复现，最后的结局通常是这条判据被加豁免、再被删掉。** ⇒ 把超时做成可注入（生产不设 ⇒ 行为逐字不变，判据设一个极小值），让判据**确定性地**落到它真正要守的那条降级臂上。改完该判据从可能 300s 降到 **1 秒**。附带收益：降级臂（没有 key / 没有本地模型）往往**正是新装用户的默认状态**，本来就更该被守住。

58. **⭐⭐ 「全集对账」必须是闭世界的，否则它就是它要治的那个病**（example-app R3-7）。一条判据**自称**「做全集对账，不再逐个点名」，实现却是一个硬编码的两元素列表 —— 它在结构上**不可能发现缺席的成员**，而漏掉的恰是会毁掉用户文档的那处。⇒ 真正的全集对账长这样：**枚举出这一类的所有实例**（扫全部源文件里每一处 `writeFileSync`），**每一处都必须落进一个已分类的桶**（合规 / 登记为例外并写明理由），**新增一处未分类的 ⇒ 判据红**。写它的时候它当场抓出两处作者没想到的成员 —— 这就是闭世界与点名的区别。⚠️ 分类要按**实际代码文本**登记，不要为了让判据变绿而放宽匹配器。

59. **⭐ 一处修好了，去问「同后果的另一条路补了吗」—— 尤其是主路径**（example-app R3-11，追查 R3-10 时撞出来）。「文档被截断时不许说『文档里没有相关内容』」这条修复，只加在了**检索没过下限**那条路上；而**模型判定 found=false** 才是配置正常时的主路径，那条路上一个字的提醒都没有。⇒ 这类「同一句话有多个产出点」的结构，修法是把措辞抽成**单一事实源**再让所有产出点共用，而不是逐个去补。判据可以直接数这个函数被调用了几次。

60. **⭐⭐⭐ 判据必须消费生产代码本身，不能消费它的副本**（2026-09-02 example-app N4-1，本会话最贵的一次）。生产代码在 `main.js` 里算 `sourceChars = raw.length > cap ? raw.length : undefined`；`main.js` 需要 electron，判据驱动不了它，于是判据在自己内部**照抄了一遍**这行逻辑再去断言。结果：把 `main.js` 改回缺陷写法，**判据纹丝不动 EXIT=0** —— 它测的一直是它自己那份副本。⇒ 遇到「被测逻辑困在一个加载不了的模块里」，正确解法是**把那段逻辑抽成一个不需要重依赖的纯函数**，生产与判据共用它（本例 `kernel/attach-cap.js`）；抄一份到判据里等于没测。⚠️ 这条和铁律 46 是一体两面：**副本会和本体分叉，而判据永远绿。**

61. **⭐⭐⭐ 反向测试没红，先怀疑判据走的是另一条路**（example-app N4-2，同一轮里我自己犯了一次）。给「模型判定 found=false 时要带截断提醒」写行为判据：桩掉 LLM、真跑问答、断言提醒在。基线绿、变异……**也绿**。原因是那个问题过不了检索下限，请求走进了 `miss()` 分支 —— 而 `miss()` 也会加同一句提醒，于是断言在**错误的路径上**照样通过，判据从头到尾没碰过它要守的那条路。⇒ **行为判据必须钉住「我走的是哪条路」**：断言只有目标路径才有的字段（本例 `mode`）、断言答案正是桩返回的那句。写完先做一次「让目标路径失效」的变异，**没红就说明你测的不是它**。

62. **⭐⭐ 白名单/豁免一律按「行为」列，别按文件列**（example-app N4-5）。闭世界写入对账里给两个文件开了整文件豁免（`fake-backend.js`、`atomic-write.js`）。实测：往被豁免的文件里新加一处写**真用户状态**的裸写 —— 判据照绿。整文件豁免正是同一份判据自己批评过的「文件级匹配器」弱点，换了个地方复现。⇒ 豁免要落到**具体的写入目标**（`path.join(dir,'plugin.json')`），文件里新出现的任何一处仍要被对账。同轮另外两条旁路同源：**行内任何位置出现 `.tmp` 就整行跳过**（写个 `// x.tmp` 注释即可绕过 ⇒ 跳过条件要收紧成「这一行写的就是那个 tmp 变量」），**只匹配 `fs.writeFileSync(`**（`require('fs').writeFileSync(…)`、`appendFileSync`、`fs.promises.writeFile`、解构出来的写函数全在面外 ⇒ 扫描面要按**动作**穷举而不是按一个写法）。

63. **⭐⭐ 一条修复很容易把「漏报」改成「误报」——两个方向都要有生产形状的用例**（example-app N4-1）。为了让「超上限被静默裁剪」不再漏报，我让上游把原始长度传下去；而传下去的是 `raw.length`，被比较的却是 `raw.slice(0,cap).trim()` —— **trim 掉的空白**于是被当成「被切掉的内容」，**任何以换行结尾的粘贴（即绝大多数）**都被误报截断：求和明明是完整正确值，却附上一句「这个数字不是全表的」。同一会话里刚在另一个模块消灭掉的误报方向，被这条修复在隔壁重新引入。⇒ 判据的正向对照曾写作 `f(small, small.length)`（两个参数同一个字符串），**永远走不到生产实际走的那条路**。**判据的输入形状必须和生产一致**：照搬调用方的真实构造方式，别自己造一个更方便的。

64. **⭐ 元判据会抓住你自己 —— 那正是它值钱的时候**（example-app，同轮实录）。为 R3-2 加的「判据文件不许有模块顶层 `return`」元判据落地几小时后，我在写**新判据**时原样写了一个顶层 `return`（为了返回一个 promise 链），元判据当场点名报红。⇒ 这是判据承重的最好证据：**它抓的第一个人就是加它的人**。别在这种时候给自己开豁免。

65. **⭐⭐⭐ 「算出来了」不等于「送达了」—— 数调用次数的断言守不住投递**（2026-09-03 example-app N6-1）。截断提醒被抽成纯函数、四个分支都调用了它，守它的断言是 `(code.match(/caveat\(att\)/g)||[]).length === 4`。**删掉模板里的一处插值 `${tblCaveat}`**（那行调用一字不动）：调用数仍是 4、**全套 37/37 照绿**，而截断的表在提示词里重新变回「完整的表」——三轮要消灭的缺陷一次删两个字符全部复活。⇒ 凡是「A 算出来的值要进 B」的结构，断言必须落在 **B 的输出**上，不能落在「A 被调用了几次」。**判据里出现 `.match(...).length ===` 或 `includes(` 就该警觉：它测的多半是形状，不是行为。**

66. **⭐⭐ 同一次提交的一半写下教训、另一半违反它 —— 这是常态，不是意外**（example-app 第 5→6 轮实录）。N5-3 判定「纯源码文本断言是空的」并把措辞抽成纯函数，**同一个 diff 里**守投递的却是数调用次数；N4-1 写下「判据必须消费生产代码本身」，**同一个 diff 里**的自证探针在重算旧匹配器；N5-4 修好了 fire-and-forget，**同一次提交编辑的另一个文件**里还留着一个同型的。⇒ 「知道」和「做到」之间没有自动通路。收尾时要专门做一遍**自我对账**：把本次提交信息里写下的每一条原则，拿去逐条核对本次 diff 的**每一处**改动——尤其是那些不在你注意力焦点上的另一半。

67. **⭐⭐ 一个「具体而错误的定量担保」比什么都不说更坏**（example-app N6-4）。修「降级时不告诉 agent 内容被截断了」，修出来的是沿用上一阶段的数字：提示词宣称「原文 205909 字符、只读入了前 200000」（听起来 97% 在手），而 agent 实际拿到的是 **8000**（3.9% 在手）。不说的时候人还会怀疑；给了个精确数字，人就不查了。⇒ **每一个截断点都要在它自己发生的地方现算标志**，不能把上游的数字传下来当自己的——尤其是链路上有第二次裁剪时。

68. **⭐ 加固要先确认那条路在生产中可达，并回头找同后果的可达路径**（example-app N5-8 → N6-6）。上一轮加固了 `CAPS[kind]` 的原型链命中（`__proto__` 会让整个附件被静默丢弃），而唯一的生产调用方**前一行就把 kind 收敛成四个字面量**——那条路不可达。真正可达的同后果缺陷（首 8000 字符全是空白 ⇒ trim 后内容为空 ⇒ `if (content)` 为假 ⇒ 附件静默消失）当时没被处理。⇒ 报一条缺陷时把「后果」和「触发路径」分开写，然后问：**这个后果还有别的到达方式吗？** 不可达路径的加固无害，但它会让人以为这个后果已经解决了。

69. **⭐⭐⭐ 看门狗/超时不能猜一个大数 —— 要么取被守护路径的确定性上界，要么把那条路确定化**（2026-09-03 example-app N7-2）。给一个可能挂死的异步判据加了 15s 看门狗，数字是从**另一个判据文件原样搬来**的，没有重新测量新宿主：被守护的那段里有三次网络调用，其 DNS 兜底预算本身就是 10s ⇒ **正常最坏耗时超过看门狗**，于是它分不清「挂死」和「慢」。实测单跑 8 次红 3 次（37.5%），而**此前多轮报告里的「全套 N/N 绿」全部建立在走运的那几次上**。⇒ ⭐ **修复把「静默假绿」换成「不确定的假红」是一类独立的失败形态**，比原状态好，但一个随机变红的门禁在下一轮极可能被当噪声调松或删掉，等于把问题推迟。正确解法优先级：①**把被守护的路径确定化**（桩掉网络臂——通常那也更贴近被测语义）> ②取路径的确定性上界的数倍 > ③猜一个大数（永远不要）。改完要**连跑 ≥8 次**证明稳定，并单独验证「真挂起时仍然报红」（别修成永远绿）。

70. **⭐⭐ 「收窄」的动作里最容易夹带放宽 —— 收窄后必须把上一版能抓住的用例重跑一遍**（example-app N7-1，一次净退化）。把豁免从「整行子串匹配」收窄成「锚在第一个实参」时，顺手把豁免键也缩短成 3–4 字符（`dest`/`sig`），而比较仍是 `includes` ⇒ 任何写入目标的标识符**含**这几个字就被放行（`designPrefs`、`assignedState`、`destinyState`、`sigStore`、路径字面量 `"user-design.json"`）。把上一版判据取出来跑同一变异 ⇒ **旧的抓得住**，所以这是退化不是历史遗留。⇒ 判据的每一次「收窄/优化」，都要**把改动前的版本取出来，对同一组变异各跑一遍**，确认新版本至少不比旧版本弱。子串比较改精确相等还有个副产品：它会逼你把登记键写成生产里的**真实实参形态**（`process.env.X` 而不是 `X`），这本身就是一次对账。

71. **⭐⭐ 「审上一轮的修复」这个框架天然只会在判据面上产出 —— 判定收敛前必须换一个不自我指涉的问法**（example-app 第 1–7 轮实录）。连续七轮「专审刚落地的修复」，发现数 12 → 10 → 5 → 8 → 6 → 4，而第七轮的比例走到 **生产缺陷 0 : 判据不承重 4**。原因很直白：**每轮新写的判据就是下一轮的新审查面**，这个循环可以无限进行下去而生产代码早已稳定。⇒ 看到「本轮发现全部落在判据层、生产代码零改动」时，不要直接宣布收敛，也不要继续同一个循环 —— 换成一个**只审生产代码、明确拒收判据质量类发现**的轮次（走真实用户路径、边界值、并发时序、错误路径、跨状态一致性）。**那一轮的零发现才是真的零发现**；仍在同一框架里跑出来的零发现只说明你把自己的判据审干净了。

72. **⛔ 报告里的「全绿」必须是可复现的绿**（example-app N7-2 的直接后果）。我在多轮报告里写下「全套 37/37 + Tier A 20/20」，而其中一个判据有 37.5% 的概率随机变红——那些结论建立在走运的那几次上。⇒ 交付前对**整套**至少跑 3 次、对**新改动的单个判据**至少跑 8 次；任何一次红都要先归因（断言失败 / 超时 / 信号致死 / 整机负载）再决定是不是可以说「绿」。发现自己此前报错了，要**明确更正**，不要在新报告里悄悄换成正确数字。

73. **⭐⭐⭐ 缺陷藏在模块之间的接缝上 —— 每个模块单看都对，错在它们对彼此的假设上**（2026-09-03 example-app 第 8 轮）。连续七轮「审刚落地的修复」把生产代码审到「0 生产缺陷 : 4 判据不承重」，看起来已经稳定。换成**只审生产代码、走真实用户路径**的问法后，一轮抓到 6 条真实缺陷（2 条 HIGH），**没有一条落在前七轮反复加固的点上**（截断标志、原子写、SSRF、白名单、身份裁决全部探过且正确），而是全部落在接缝：意图分类器 ↔ 它的调用点（`换成深色` 被无校验的「换数据」快车道吞掉，改坏数据源还回执「成功」）／队列驻留策略 ↔ await 式 IPC（**驻留是有意的，但驻留 + await = 挂起而非延后**，UI 永久卡死）／内核 limit 语义 ↔ 为 LLM token 预算写的裁剪器（rows 砍到 40 而 count 仍 60）／任务持久化形状 ↔ 重试入口（存的是加工后形状，重试时附件静默消失）／检索打分上界 ↔ 固定下限（**两字提问在数学上不可能命中**）／表头唯一性判定 ↔ 补名顺序。⇒ **单模块审查与「审修复」都看不见接缝**，因为没有哪一次修复动过它们。要专门安排一轮：**沿着一条真实用户路径从头走到尾，在每个模块交界处问「上游给的和下游以为的，是同一个东西吗」**。

74. **历史案例（规范正本见铁律 71；本条不另立收敛规则）。** **⭐⭐⭐ 判定收敛前必须换一个不自我指涉的问法 —— 否则你只是把自己的判据审干净了**（example-app 第 7→8 轮，一次被推翻的收敛判断）。我预先定好了停止条件（「某轮发现全部落在判据侧、生产代码零改动就停手」），第 7 轮正好满足，**而它是错的**：那个框架（审上一轮的修复）天然只在判据面上产出，因为**每轮新写的判据就是下一轮的新审查面**，这个循环可以无限进行而生产代码的真实状态无人知晓。⇒ 收敛的判据不能是「本轮没发现」，而要是「**在一个与前几轮独立的问法下**也没发现」。安排收尾轮时，明确写上「不要报告判据质量类发现」——把提问的方向从「我的检查够不够严」扭到「产品对不对」。

75. **⭐⭐ 「绕过」不是「修复」—— 写测试时被迫做的每一次变通，都是一条待修的生产缺陷线索**（example-app 第 8 轮补）。给一个 IPC 写行为探针时发现 `main.js` 不认 `EXAMPLE_APP_ROOT`（用 `__dirname/..` 拼根），只好把整棵树拷进临时目录才能隔离。**当时以为这只是「测试麻烦」，其实后果是判据会去读写用户真实的运行期状态**（我的第一版探针就这么干了，所幸只读没写）。⇒ 写判据时每一次「只好绕一下」都要记下来并回头问：**这是测试的问题，还是被测代码的问题？** 这一条修完后，隔离从「拷贝整棵树」变成「设一个环境变量」，同时消除了污染风险。同源提醒：同一类配置（这里是 ROOT 解析）在仓库里有 5 个模块做对、2 个做错时，**做对的那 5 个就是现成的正确写法**。

76. **⭐⭐⭐ 一层写得很诚实，不代表下一层会把这份诚实说出口**（2026-09-03 example-app 第 9 轮，一整类缺陷的根因）。内核这一侧被前八轮打磨得很好：写不下时**拒绝并给出可读的原因**、失败带 `stoppedReason`、截断带标志、驻留时返回「先选保留或恢复原样」。**而渲染层几乎从不消费这些返回值** —— `await api.storage.set(...)` 丢弃返回值（实测 80 次点击落盘 52、**静默丢失 28**，条目出现在卡片上、下次开 app 全没了）；四处变更型 IPC 的 `{ok:false,error}` 无人展示（确认了删除对话框、部件还在、零提示）。**最讽刺的一次**：上一轮刚把「挂起」改成「立刻返回可操作的拒绝」，而那个拒绝**没有任何调用方展示**，用户体验和挂起时一模一样。⇒ 修完「让它说实话」之后，必须紧接着问**「谁在听？」**：对每一个返回 `{ok,error}` 的调用做**全集对账**（逐个点名修只会漏），并把「调用了但没检查返回值」做成机械可查的判据。

77. **⭐⭐ 界面声称的语义 ≠ 代码执行的语义 —— 沿一次完整用户动作走一遍才看得见**（example-app N9-1）。「换一版」的语义是**并排候选、由用户挑一个**；而失败后点「重试」时，回传保住了 prompt / refineOf / attachment，**唯独没传 opts**——remix 意图就在 opts 里。于是重试变成**原地改写并直接 commit**，原部件当场消失，而回执照样显示「已换新版」。写这段代码的人**知道**这条路会承载 remix 任务（紧接的一行专门判了 `REMIX_INSTRUCTION`），却只修了回执文案。⇒ 单看任何一个模块都对：渲染层「保住了用户的输入」，内核「按收到的参数正确执行」。**只有沿着一次完整的用户动作从头走到尾，在每个交界处问「上游给的和下游以为的是同一个东西吗」，才看得见。** 把审计单位从「模块」换成「一次完整的用户动作」。

78. **⭐⭐ 作用域写在一个动词上，语义落在另一个动词上**（example-app N9-2，一次真实的用户数据损失）。`git add` 老老实实限定了 `userland`，而同一段代码里的 `git diff --cached --quiet` 与 `git commit` **都没有 pathspec** —— 它们走全索引。后果两重：①用户在终端 `git add` 的半成品被内核以 `feat: <用户的话>` 的名义提交掉并从索引消失；②「有没有改动」的判定被**别处的**暂存内容顶成真，于是一次**零改动**的操作也返回了 hash，让「这次什么都没改」的诚实守卫**永远不触发**。⇒ 凡是「先圈定范围、再执行操作」的两步式 API（git add/commit、glob+delete、filter+update），**检查第二步是否继承了第一步的范围** —— 它们通常不继承，而且不继承时不会报错，只会悄悄多做。

79. **⭐⭐⭐ 「XX 没跑起来」和「XX 跑了、答案是没有」必须长得不一样**（2026-09-03 example-app 第 17 轮，一轮 2 条 HIGH）。底层的 `gitSpawn` **已经生成了准确的诊断**（「git 不可用（未找到可执行的 git）」），并用 `status === null` 把「没跑起来」和真实 git 失败（非零整数）区分开。**而 15 个消费方里只有 1 处读它** —— 其余全部丢弃 stderr、只看 `status`/`stdout`，于是两种截然不同的情况在每个调用点上都塌成同一个业务结论。后果按严重度：**边界审计返回空数组 ＝「边界守住了」**（agent 写到内核目录的文件既不上报也不回滚，下次启动以内核权限被 require）；**每一次「雕刻」都被判成「这次没改动任何东西」**而改动已落盘，还教用户再烧一次生成；「没有更早的版本可回退」而版本确实存在。⇒ 降级要分三类：①正确降级并**如实说明** ②静默失败 ③**给出一个自信而错误的结论**（最坏，因为它还会附赠一条错误建议）。做法：在底层加一个共用判据（`isUnavailable(r)` + `reasonOf(r)`），**让每个消费方都能问出「这是没跑起来，还是跑了但答案是否定的」**，并把底层已经写好的诊断透出去，不要各自编一个原因。

80. **⭐⭐ 一个已经写好的兜底，要沿着它的全部调用点铺开，而不是只留在发现它的那个函数里**（example-app 第 16 轮 N16-1）。`discardUserland()` 是 git-only、git 不可用时是空操作 —— 这件事的 fs 兜底**早就写在 `runTask` 里**，注释把病因写得一清二楚，**却没跟到任何一条 preview 退出路**：10 个调用点里 6 个缺它。后果是被拒绝的候选永久留在桌面上，而且那个部件的「换一版」**从此彻底坏掉**（残骸让下一次生成的 created 差集恒为空 ⇒ 每次都重试满上限再失败，每轮烧一整次真钱）。⇒ 修完一处后，**把这个动作的全部调用点列出来逐个查**（`/usr/bin/grep -n "discardUserland()" file` 就够），而不是看最近改过哪一处。⚠️ 铺开时注意**安全前置**：兜底要 `rmSync` 一个来自持久化状态的名字，而其中两条路径此前没有名字校验 —— 不先补就等于把一个任意路径删除开进去。

81. **⭐⭐ 刹车必须落在磁盘上 —— 内存里的超时跨不过进程消失**（example-app 第 14/15 轮，活体证据）。生成用的子进程有 15 分钟硬超时，**而那个 `setTimeout` 活在父进程内存里**：父进程一消失（force quit / 崩溃 / 任何非正常退出），子进程 reparent 到 PPID=1，超时随之消失，无限期占 ~75% CPU；下次启动重排任务再 spawn 一个 ⇒ **每次中断累加一个孤儿**。`ps` 当场抓到一个已经跑了 4 小时 26 分的。第一次修（退出时调 cancel）**在 Force Quit 路径上原样回来**，而且 `cancel()` 的 SIGKILL 挂在 4 秒定时器上 —— 宿主之后立刻退出，**升级路径结构上不可达**。⇒ 三件事：①退出路径直接 SIGKILL，不留升级余地；②**把 pid 落到磁盘**，启动时回收上次的孤儿（回收前校验该 pid 确实是目标进程，pid 会被系统复用）；③同族全查一遍（语音播报进程同样没有任何退出路径管它，app 关了声音还在念）。⭐ 这个母题还有个副作用：**孤儿进程会把后续所有性能类判据变成假红** —— 我因此花了三轮才归因。

82. **⭐ 判据切函数体不要用固定字符窗口**（example-app 连踩三次：第 12、16 轮各一次，另一次是数窗口行数）。`indexOf('\nasync function ', i)` 在「它之后没有同类声明」时找不到，退回 `i + 9000` 的固定长度 ⇒ **切进了后面的代码**，把另一个函数里的合法写法算成违规 —— **判据的取值范围错了，不是代码错了**。大括号配平也不行（字符串/正则里的括号会干扰）。⇒ 用**结束锚点**：下一个同类声明的起点、或该函数尾部一句独有的文本。同源提醒：判断「守卫在不在 await 附近」时，窗口要**跳过注释与空行**再看紧随的两条代码 —— 守卫常隔着几行解释性注释。

83. **⭐⭐⭐ 修复可能比原病更重 —— 而且同一次提交里的两条修复会互相抵消**（2026-09-03 example-app 第 18 轮，2 条 HIGH 都是第 17 轮的修复引入的）。为了让「静默放行」不再和「零越界」同形，我把降级诊断 `push` 进了 `breaches` 数组 —— **而调用方只看 `breaches.length`**，非空即判越界、且列为不可重试。于是那台机器从「偶尔悄悄漏审」变成**每一次生成都硬失败**，还宣称「已回滚」（诊断串不匹配「无法自动回滚」过滤器 ⇒ 落进「已回滚」文案分支）。更隐蔽的是：这条修复让上游的 `agentOk` 恒假，**同一次提交里另一条修复的救援分支因此结构性不可达** —— 两条修复彼此抵消，修好一条另一条才开始生效。⇒ 三条操作规范：①**诊断不是业务数据**，别塞进那个「消费方按 length 判定」的数组，挂成不可枚举标记再由调用方如实说出；②改一个返回值/状态的语义前，先列出**它的全部消费方各自是按什么判定的**（length？内容？真值？）；③同一次提交里修两处相关的东西时，**显式检查后一处的前置条件会不会被前一处改掉**。

84. **⭐⭐ 判据要钉「保证」，不要钉「实现形状」—— 否则正确的重构会让它变红，而错误的实现会被它钉成规范**（example-app 第 18 轮，一轮三例）。我为上一轮修复写的判据钉的是 `if (commit && commit.unavailable)` 和 `breaches.push(降级说明)` 这样的**具体写法**。下一轮把实现收敛成更好的形式后，两条判据双双报红而行为完全正确；更糟的是后一条 —— **它把下一轮判定为 HIGH 的写法固化成了规范**。⇒ 断言要落在「这个保证还在不在」上：`git-less 必须被认出来`、`诊断必须被说出来且不判失败`。可执行的功能判据 > 源码形状断言；实在只能扫源码时，钉那条**跨越多个环节的数据链**（`snapshotOk → dataRolledBack → 日志二选一`），断哪一环都要红 —— 只钉链条一端的判据，改另一端时照绿。

85. **⭐⭐ 判据会被它要守的那段代码的注释喂饱**（example-app 三次，另一项目一天十次）。我写元判据扫 `breaches.push(...)` 的实参形状，第一版直接在源码上跑 —— 命中了**我上一轮写在注释里的那个反例**（注释正是在解释「不许这么写」）。同理：数某个标识符出现次数、检查某个字面量在不在、确认某个词有没有出现，全都会被注释、字符串、甚至**你解释这条判据本身的那句注释**满足。⇒ 扫源码前**先剥注释行**；更强的做法是只在目标函数体内扫。⚠️ 如果一个仓库里已经有三处各写各的剥注释、能力还不一致（有的只剥 `//`、有的连 `*` 一起剥、都不处理行尾与块注释），那本身就是个信号 —— 至少要知道自己用的是哪一档。

86. **⭐⭐ 两条判据正面冲突时，多半是各对一半 —— 合并，别放宽**（example-app 第 19 轮）。老判据要求「遍历触顶的痕迹必须到达 `breaches`，否则停在内部函数上等于没人看得见」；新发现要求「不许作为 `breaches` 的**元素**，否则会被 `length` 判成越界」。看起来必须二选一，实际是**同一个要求的两个侧面**：痕迹留在**返回对象**上（老判据要的「对用户接口」）但**不作为元素**（新判据要的「不判失败」）。⇒ 写成并存的两条断言，并**各自反向测试**（去掉标记 → 老那条红；重新混进元素 → 新那条红）。任何时候「为了让新代码通过而放宽老判据」都要先证明老判据守的那件事已经由别处守住 —— 否则那是在拆防线。

87. **⭐ 反空转基线本身会被你的修复改变**（example-app 第 19 轮）。判据里那句「至少要匹配到 N 处，否则说明正则失效了」是防「零命中即全绿」的 —— 而我的修复把 6 处 `breaches.push` 减到 5 处，它如实报红了。这不是误报，是它在正常工作：**基线数字是一条需要跟着代码一起维护的断言**。⇒ 调整时把新数字的**含义**写进注释（「5 = 把触顶诊断改成标记后剩下的真实越界路径写入点」），而不是改成一个更松的阈值了事。

88. **⭐⭐⭐ 源码断言只能证明「那行代码在」，不能证明它生效 —— 判据要真跑一遍**（2026-09-03 example-app 第 20 轮，我自己造出来的活证据）。我给一个组件加了「缺列时从首行数据推列名」的兜底，判据写的是 `assert.match(src, /if \(!cols\.length\) return .../)` —— **全绿**。而我把数组传给了一个签名是 `arr(node, key, alt)` 的函数，它去读 `数组.bind` ⇒ 恒为空，**那段推断从来没生效过**。是用最小 DOM 垫片把组件真跑一遍、断言**输出的文本**才抓住的。⇒ 凡是「渲染成什么样」「输出什么文本」「点了会怎样」这类保证，判据必须执行它；源码形状断言只配做补充。真跑的判据还要带**反向保护**（「修 A 不许误伤正常路径」：绑不到数显示 `—` ✅ 同时 `value=70` 仍显示 70 ✅），否则一个把所有分支都改成显示 `—` 的错误实现同样能过。⚠️ 垫片的作用域要覆盖**渲染期间**而不只是构造期间 —— 我第一版在工厂构造后就还原了 `document`，第一个组件当场 ReferenceError。

89. **⭐⭐⭐ 从「代码」出发的审计，看不见「文档承诺了而代码里根本不存在」的东西**（example-app 第 20 轮，一条零注入 HIGH）。文档声明按钮支持 `onTap`，而**全仓只有文档那一处出现过这个词** —— 内核从不读它，点击静默 no-op，按钮的标签配色 hover 全部正常，自动校验全绿。二十轮审计里前十九轮都碰不到这一格：**它们的起点都是代码，而这个缺陷的特征恰恰是「代码里没有」**。⇒ 至少跑一轮以**声明侧**为起点的审计：把「提示词/文档/规格告诉使用者可以写什么」逐项列出，再去代码里找对应的读取点。三种缺口都要看：①声明了而代码不认（静默失效）②代码认而从没声明过（能力在产品不在）③两边都有但语义不一致（最隐蔽）。⭐ 讽刺放大器：那个组件恰好是内联清单里**唯一漏掉、因而最需要查文档**的一个。

90. **⭐⭐ 一个写对了的原则，只被应用到它该管的一小部分**（example-app 第 20 轮，另一条零注入 HIGH）。判空辅助函数 `hasNum` 早就在文件里，它上方原作者的注释写着「a gauge at 0% and a gauge with no value must look different」—— **原则完全正确**，而全仓只有 2 处调用它，另外 8 个同类组件走 `num(v, 0)`：拿不到数就**强制成 0**，于是仪表渲染成「0 / 100」并染成绿色（=健康）、电量渲染成「0%」（=耗尽）、价格渲染成「$0」（=免费）。**用户读到的是一个被测量过的读数，而它从未被测量。** ⇒ 看见一个判空/守卫/归一化辅助函数时，立刻问「**它的同类调用点有几个，它被用在几个**」，把这个比值当成缺陷密度的指标；并为这类原则加**元门禁**（凡把某字段当数值渲染的组件必须命中该守卫），而不是逐个补完就算完。⚠️ 更要留意**别处的注释如何描述这个失败形态** —— 那道字段门的注释把它建模成「会显示破折号」，对 2 个成立、对另外 8 个不成立，于是**没被那道门覆盖的部分，真实风险比注释以为的严重一档**。

91. **⭐⭐ 「能拿到绿灯的坏东西」是一类独立的审计单位**（example-app 第 20 轮的副产物）。当一轮里每条发现的证据都带着同一句「而自动校验是绿的」时，那不是巧合 —— **说明校验的裁决面本身有系统性缺口，而它往往是唯一的把关**。⇒ 把校验器本身当被审对象跑一轮：穷举它**到底检查什么**（从代码读，别信注释）、**明确不检查什么**，以及每一格「不检查」对应的用户可见后果——区分「看起来正常但功能是死的」（最坏）和「肉眼可见的坏」（用户自己会发现）。反向也要问：**它有没有误杀**（把好的判成坏的）——那会让用户为一次假失败白付一次代价。

92. **⭐⭐⭐ 让复核员边跑边把结论落盘 —— 否则一次 502 就丢掉整轮**（2026-09-03/04 example-app 第 21 轮，真实损失）。复核员跑完了十次复现、建了七个夹具、五个工作树，**在写最终报告时被 502 打断，报告全丢**。救回来的唯一原因是它的中间产物（每次运行的 JSON）留在了 scratchpad —— 我据此重建夹具、自己端到端复现，才拿到那一轮的三条发现。⇒ 派活时明确要求：**每定案一条就追加写进一个 md 文件**，最终响应只是汇总；并**限定报告字数**（长响应本身就是挂掉的主因）。同理适用于任何长时子任务：中间结论必须落在进程之外的地方。

93. **⭐⭐⭐ 修复的「绕过口」常常是它自己新引入的输入面**（example-app 第 21 轮 N21-1）。上一轮我把「拿不到数就显示 0」改成了「显示 —」，占位文案取自组件的 `empty`/`fallback` 字段 —— 而**生成模型有很强的倾向给数值字段写 `"fallback": "0"`**（看着整齐）。于是「没测到」又变回「测到的 0」，**只不过这次谎是模型写的、内核照办**。我刚写进文档的明文契约 —— **执行方不执行就不算数**。⇒ 修完一条「不许显示 X」之后，立刻问：**「X 还能从哪条路进来？」** 尤其是那些「由被约束方自己提供」的字段（占位文案、标题、单位、fallback、示例数据）。同一轮里我还犯了它的变体：兜底函数收了个 `hint` 参数，我在调用点把用户写的值当 hint 传进去，**谎从 hint 那条路绕过了刚加的净化**。

94. **⭐⭐ 「零误杀」必须和「有命中」同时成立才算数**（example-app 第 21 轮 N21-3）。我给「空白部件」加门禁，跑完绿基线报告「13 个真实部件零误杀」—— 看着很好，**但同一次运行里那个已知的空夹具也没被抓到**。判据数的是 `querySelectorAll('*')`，而一个空容器仍会产出它自己那个元素 ⇒ 计数恒 ≥ 1，**门是哑的，却看着像在干活**。⇒ 任何新判据的验收都要**两侧同时报**：正例集零误伤 ✅ **且** 已知反例被抓 ✅。只报一侧的验收等于没验收 —— 而「零误杀」这一侧尤其容易给人虚假的安心。

95. **⭐⭐ 你为自己代码调用的字段，可能是你刚编出来的**（example-app 第 21 轮）。我给一条诊断加部件身份，写了 `spec.__name` —— **这个字段整个仓库里不存在**，恒为 undefined，标签永远只剩冒号后半截。语法检查、类型检查、全套测试**没有任何一环会报错**。这是 AI 写码最典型的幻觉形态：名字合理、位置合理、读起来像真的。⇒ 凡是从一个对象上取自己没亲眼见过的属性，**先 `/usr/bin/grep` 一次这个名字在仓库里是否存在**；取不到时不要静默降级成空串 —— 那正是它能长期不被发现的原因。（本例的正解 `api.pluginName` 一次 grep 就能确认。）

96. **⭐⭐⭐ 读源码的判据守不住东西 —— 把它跑起来**（2026-09-04 example-app 第 25–31 轮，100+ 个定向变异的统计结论）。同一批变异下，**靠正则/计数/字符窗口的判据累计 14 次假绿 + 5 次误红；真跑行为的判据 0 次错判**。而且假绿**全部**落在渲染/接缝层，被抓的**全部**落在有真跑用例的模块 —— **接缝没有主人，所以没人守**。绕过一条正则判据简单到令人不安：把 `n.empty` 写成 `n?.empty`、把豁免串粘成行尾注释、把被查的标识符挪进一个对象字面量。更糟的是同一批判据还**误红正当写法**（换引号、抽常量、实参换行、改个变量名）—— **误红比漏判更坏：它会让人给判据加豁免，然后就没人跑它了**。⇒ 凡是「渲染成什么样」「点了会怎样」「失败时留下什么」这类保证，判据必须**执行它**；源码形状断言只配做补充。真跑不一定要重型环境：一个 80 行的 DOM 垫片就够把整个 UI 层跑起来，一次裁决 1.2 秒、不需要 Electron。

97. **⭐⭐⭐ 判据的默认倾向是「挑一个最容易观测的量来代表要守的那件事」**（example-app 第 25–31 轮，同一母题**换层复发五次**）。它每次都换一层皮：①守住了「实现在不在」，没守住**谁在消费它**；②守住了「那段文本长什么样」，没守住**跑起来会怎样**；③逐到了组件名，没逐到**调用点**（共享 helper 让 3 条夹具替 16 个组件作证）；④注入点在**链首**，于是**链尾从没被任何断言执行过**（一抛错整条链就断）；⑤夹具描述的世界与**产品真实的世界**不同源（判据对一个虚构元素作证，绿了两个月）。⇒ 每写一条判据都问：**「我观测的这个量，和我要守的那件事，中间隔了几层？每一层都可能是它的逃生口。」** 尤其警惕「数一数有几处」这类判据 —— 计数守不住「这一处到底对不对」。

98. **⭐⭐⭐ 把「多条路」压成「一根串」，任何一条路的失效都能被另一条顶包**（example-app 第 29 轮，旗舰判据自己中招）。断言 `!/\b0\b/.test(全部输出拼成的串)` 看起来很严 —— 而**同时**让两条路失效时，两处输出会**粘连**（`"0"` 与 `"0 items"` 粘成 `"00"`），词边界不成立 ⇒ 判据绿。**只坏一条抓得住，同时坏两条抓不住** —— 而真实回归从来不是一条一条来的。正向断言 `/—/.test(串)` 得同一种病：任何一处满足即过，于是「某一路的诚实占位被删掉」被别路顶包。⇒ **每条路单独渲染、单独断言**；断言的作用域要和它守护的那件事一样窄。⚠️ 修这类问题有**硬顺序**：两处缺陷会互相掩盖，只收紧断言不修地基会当场误红正当重构，只修地基不收紧断言仍然假绿。

99. **⭐⭐⭐ 判据夹具描述的世界，可能和产品真实的世界不是一回事**（example-app 第 31 轮，一次命中 5 个判据）。产品 HTML 里的一个元素在某次重构里被删掉了，而 JS 引用留着；**5 个行为判据的夹具各自造了这个元素** ⇒ 判据一路绿灯，而那条「修复」**从未落到产品上，躺了两个月**。更绕的是：我据此报了一个 HIGH 产品缺陷（「切到空场景会白屏」），而那**是夹具产物** —— 真实产品并不白屏。⇒ 加一道**元门禁：夹具里出现的每一个 id / 类名 / 桥方法 / 清单字段，产品侧必须真有**（在 HTML 里、或在代码里被动态创建）。同类要查的至少六项：DOM id/class、插件清单形状、`window.*` 桥的方法集、服务字段表、持久化结构、CSS 类名。**判据可以对着一个不存在的世界永远绿着。**

100. **⭐⭐ 一个洞能同时封死「发现它」和「守住它」两条路**（example-app 第 31 轮，解释了它为什么能活 31 轮）。测试垫片的 `innerHTML` 写入器是空操作：一方面让「多帧文本累加」类缺陷照绿（**发现不了**），另一方面让任何依赖它的正确代码恒红（**守不住**）—— 于是「只修垫片」原假绿仍全绿，「只写判据」正确代码恒红，两条路各自走都走不通，只有**同时**做才行。⇒ 遇到一个长期没被发现的缺陷，先问：**「是不是有什么东西同时挡住了发现它和守住它？」** 那个东西通常在**测试基础设施**里，而不是在产品代码里。

101. **⭐⭐ 谓词只能看见它那种形态的谎**（example-app 第 31 轮）。「渲染出来不许含数字」这条谓词，覆盖了所有**把读数写成文字**的组件 —— 而**把读数画成图形**的那一类（五个点亮几个、五颗星亮几颗、一个天气图标）**一个字符都不打印**，结构上落在谓词的量程之外。同源问题：通用夹具只设 `value` 字段，于是读 `n.a`/`n.b`/`n.code` 的组件从没被渲染过 —— **前 30 轮所有按 `value` 做的普查，一个都没扫过这些字段名**。⇒ 写完谓词先问：**「哪一类正确的东西，会因为形态不同而天然满足我这条谓词？」** 那一类就是它的盲区，需要另一种观测方式（例如让图形类组件也产出一个诚实的文字占位，把它拉进谓词的量程）。

102. **⭐⭐⭐ 「测试红了」不等于「判据检出了缺陷」**（2026-09-04 example-app 第 34 轮，一条会推翻既往判读的元结论）。做逐门普查时，唯二的两次红都不是检出：一次是性能基线擦着阈值过（140ms vs 120ms），一次是外部服务初始化超时，idle 复测 3/3、10/10 全过。**它们和真检出在 `failed=1` 那一行长得一模一样** —— 只看这一行，会把 5 道无人看守的门记成「已覆盖」。反过来同样成立：一次抖动的红，会让你误以为某条判据守住了那段代码。⇒ 判读变异结果时，**红必须验到「是哪条断言、为什么红」**，而不是只看退出码；对含时间阈值或外部依赖的用例，复测 3 次以上再下结论。⚠️ 更要紧的是它的追溯后果：**凡是靠「全套红不红」下过的结论都要重读一遍**。

103. **⭐⭐⭐ 防假绿的门，自己可能从来没有过正例**（example-app 第 34 轮，10 道门里 9 道）。把校验期的每一道门**整段删掉**再跑全套 —— 10 道里 9 道**全绿**。原因很朴素：正例集里的样本全都合规，那些门的命中集恒空，**它们从上线那天起就没开过火**。一道从没开过火的门，和一道被删掉的门，在测试结果里完全一样。⇒ **每道门必须有一个「只有它能接住」的独占反例**，并断言**是哪道门抓的** —— 否则一个反例被别的门顺手接住，那道门等于仍没被测过（实测就有一对 1-of-2 冗余的门，单拆任一仍绿）。⚠️ 做这件事时先自查方法：把门的**文案**改掉再跑，5/5 全红 —— 但红的是「文案白名单」那条判据，**是「文本变了」冒充「行为被守住」**；必须**整段删除**才看得见真相。

104. **⭐⭐ 一个桩恒定返回成功，会让它下游那道门结构上不可能开火**（example-app 第 34 轮）。为「查询规格无效」那道门写反例时发现：夹具里的数据桩恒返回 `{ok:true}`，于是无论反例怎么写，那条失败分支都到不了 —— **门不是没抓到，是根本没被执行过**。⇒ 写反例前先确认「这条路径真的会被走到」：桩的返回值必须能覆盖失败侧，否则你写的是一条永远绿的用例。这与「夹具前提断言」是同一件事的两面：前提防的是空转的绿，桩的失败侧防的是**结构上不可达**。

105. **⭐⭐ 「看紧邻几行」的判据必须先剥注释，而且要认反着写的判断**（example-app 第 34 轮，我一条新判据一次误红三处正确代码）。判据要求「每个 `prompt()` 的返回值必须在紧邻几行内判过 null」——第一版误红三处，两个原因各占一半：①窗口只看 4 行，而其中一处的检查被一段**解释性注释**推到了第 6 行；②正则只认 `== null`，而 `if (x != null) { … }` 这种**反过来写**同样正确。⇒ 凡是「附近有没有某个检查」这类判据，一律**先过滤注释行再看**，并把等价写法（`!=` / `!==` / 早返回 / 卫语句）一并纳入。⚠️ 顺带一条产品级教训：`prompt` 取消返回 `null`、留空返回 `''`，用 `||` 兜底会把两者折叠 —— 而用户意图完全相反（「我不做了」vs「我不填」）。实测后果是**按取消后满屏部件当场消失**。

106. **⭐⭐⭐ 一道「不许手抄清单」的门，自己就是一份手抄清单**（example-app 第 32 轮，最尖锐的自指形态）。我为「测试夹具不许凭空造元素」加了一道元门禁，它内部手抄了一份 id 清单 —— **而抄的时候恰恰漏掉了触发它诞生的那个 id**，于是**它在落地的那一个提交里就放过了自己的目标**。⇒ 门的被检物必须从**活对象**上取（运行时注册表的键、桩对象自己的 `Object.keys`、对象自己的字段名），再与事实源比对；**手抄一份清单 = 再造一个与被检物不同源的拷贝，正是这类门要治的病**。同轮另一条同族：门的另一半（反向检查）**接进去了却没通电** —— 参数全仓一次都没传过，那半检查在所有接入点恒不报错。⇒ 门加完要问一句：**「它的每个分支，今天真的有人喂过数据吗？」**

107. **⭐⭐⭐ 一道门可能从来没有被执行过 —— 而「没执行」和「判据算错了」在结果里一模一样**（2026-09-04 example-app 第 38 轮，我自己的门）。我为「证据必须点名测试」新建了一道门，判据算得完全正确、在存量上准确报红；**而它放在测试收集器结构上够不到的目录里，全仓没有任何调用方** —— 提交信息写的却是「让今后写不进去」。**我只自证了判据本身，没验它会不会被跑。** ⇒ 新增任何门禁时，**同时提交「它被谁执行」的证据**（哪个文件哪一行调它、或跑一次收集器看它出现在名单里）。同族的第二种形态：门加了参数化的另一半（反向检查），而那个参数**全仓一次都没传过** ⇒ 那半检查在所有接入点恒不报错。⇒ 门写完要问：**「它的每个分支，今天真的有人喂过数据吗？」**

108. **⭐⭐⭐ 判据要求的结构，可能正是让修复失效的那个结构**（example-app 第 39 轮，最尖锐的一次）。我给子进程退出加了「先 SIGTERM、800ms 后 SIGKILL」的升级，并给定时器加了 `unref()` —— 理由是「本仓库刚踩过定时器活引用的坑」。而这条在别处正确的经验，**在这里正好反了**：唯一调用方是退出钩子，其后事件循环随即结束，`unref()` 明确不留住进程 ⇒ **升级从不发生**（真跑：桩服务器 3 秒后仍在跑；改成直接 SIGKILL 后 64ms 消失）。**更糟的是我为它写的判据 `assert.match(fn, /unref\(\)/)` —— 坏实现全绿，产品改对后判据当场报红。** ⇒ 搬用一条经验前先问：**「它成立的那个前提，在这里还成立吗？」** 并且：**凡是「必须写成某某形状」的断言，都要反过来问一次「写成这个形状之后，它真的还能工作吗」。**

109. **⭐⭐⭐ 一处改动可以让全部门禁同时失效**（example-app 第 40 轮，CRITICAL）。测试入口那行 `if (failed.length) process.exit(1)` 加个 `&& !process.env.CI` —— 失败照数、结果照打印 `ok:false`、**进程退 0**，于是 CI 认为一切正常，**49 道门同时降级为「只打印不拦截」**。而既有判据只钉了「统计口径」（怎么数失败），**没有一条钉「统计结果如何变成退出码」**。⇒ 门禁体系必须有一条守**它自己的传导链**：从「判据失败」到「进程非零退出」到「CI 阻断」，每一环都要有人守。同轮另两条同族：安全断言的正则在 `apiKey:` 处**没有词边界**（于是密钥字段畅通无阻）；PATH 顺序断言只认一种赋值写法，**而它自己的失败文案描述的正是绕过它的那个变异**。

110. **⭐⭐ 探针拿到的不是被测对象的输出时，症状与「被测对象没问题」一模一样**（example-app 第 40 轮，我连踩两次）。想验「启动脚本设的 PATH 顺序对不对」，于是在 node 里 require 它再读 `process.env.PATH` —— 而那个脚本需要 Electron，第一句就抛，**我读到的是宿主自己的 PATH**，变异照绿。同轮另一次：把测试入口复制到临时目录跑，而它的根路径是自己的 `__dirname/..`，**于是仍去扫真仓库**；再补依赖时少搬一个就 `Cannot find module` 当场崩 —— **而崩溃也是非零退出，会被误读成「这道门有牙」**。⇒ 探针必须先自证「我拿到的确实是被测对象产出的」（打印它、比对一个只有它会产生的特征值），再谈结论。

111. **⭐⭐ 备份可能已经是变异态**（example-app 第 40 轮）。变异脚本超时被杀，三个产品文件留在变异态；补救时才发现**「备份」是第一次超时时存的、本身就带着变异**。⇒ 反向测试的备份**取自版本库已提交的内容**（`git show HEAD:<file>`），不取工作区；还原用文件复制，不用任何版本控制的还原命令。并且**每条变异独立跑、自带远小于工具上限的超时、用 try/finally 保证还原** —— 整批跑一次超时，就会把一堆文件留在半路。

112. **⭐⭐ 判据宽了会连着错好几次，每次都被自己的基线证伪**（example-app 第 41 轮，我一条判据写宽三次）。要守「插件名在被交给删除操作前必须校验过」：①第一版把**只读**也算进来 ⇒ 报出三处「未校验」，而那三处只是拼路径去读文件 —— **「只读加固与恶意写入同罪」**；②收窄到破坏性调用后仍报两处 —— 而那两处的名字来自目录枚举（**单个路径分量，不可能带分隔符**），实测确认不是缺口；③把「来源」纳入判据后还是红 —— 我用固定字符窗口往回找定义，而定义与使用之间隔着注释，**够不着**（固定窗口，同一项目第五次）。⇒ 终版**顺着变量链往回追**。教训有两层：**「谁在用它」和「这个值从哪来」是两个不同的问题，安全判据要问后者**；以及**每一次误红都是判据在告诉你它的模型错在哪里，不要急着加豁免**。

113. **⭐⭐⭐ `finally` 是异常安全，不是信号安全 —— 而超时恰好落在它够不到的那一半**（2026-09-04，另一会话的实证 + 我本机复现）。变异脚本用 `try/finally` 保证复原，超时被杀之后**文件照样留在变异态**：工具的超时发的是 SIGTERM，**Node 默认直接终止，不展开栈、不执行 finally**。⚠️ 复现这件事本身有个坑：把耗时操作写成 `setInterval` 再发信号，`finally` 会照常执行 —— 因为 **try 块已经同步结束了**，finally 在那一刻就跑完了。必须让进程**真正停在 try 块内**（`await` 一个长 promise）才看得见。⇒ 复原代码要**写在信号处理器体内**：`process.on('SIGTERM', () => { restore(); process.exit(1); })`。实测**只装 `process.on('exit', restore)` 无效**（默认终止不走 exit 事件）。⚠️ **这条我一开始还多写了半句「即便信号处理器里 `process.exit()` 转交给它也无效」—— 那是错的，是我自己的测试脚本把两条路混在一起测导致的误判**（同一个 restore 同时挂在 exit 钩子和 finally 上，而 finally 那条永远不执行，我看到文件不存在就归因给了 exit 钩子）。复测确认：**restore 全同步时，`SIGTERM → process.exit(1)` 转交给 exit 钩子是有效的**；但 `exit` 钩子里**只有同步代码会执行**（事件循环已停），这层依赖太隐蔽，所以实践上仍建议**在信号处理器里直接同步 restore**，别赌转交。SIGKILL 无论如何兜不住 ⇒ **「异常退出后先 `git status` + `git diff --stat`」是最后一道，不能省**。

114. **⭐⭐⭐ `git add <路径> && git commit` 提交的是整个索引，不是你 add 的那些**（2026-09-04，两个空仓库受控实验）。并发会话同树时，别人已 stage 的文件会被你这次提交**一起卷走**：`git add theirs.txt` 之后 `git add -- mine.txt && git commit` ⇒ 实际提交 `mine.txt theirs.txt`。⭐ 最误导的一点：大家（包括我）都以为病根是 `git add -A`，于是把纪律定成「显式列路径 add」—— **那条纪律对这个洞完全无效**，因为问题出在 commit 读索引，不在 add 写索引。正解是把路径给 **commit**：`git commit -m … -- <path>`（`--` 之后全被当路径；实测只提交 mine，theirs 仍留在索引）。⇒ 同树并发时：**提交一律 `git commit -- <path>`**；复原一律精确改回那一行，**不要 `git checkout -- .`**（会连带抹掉并发会话的在途改动）。

115. **⭐⭐ 命中数异常整齐时，第一嫌疑永远是装置**（另一会话的实证，与我这边的同型实录合流）。它的毒丸装置第一版把 11 道门禁**全判成阳性** —— 真因是那 11 道**都以 `process.exit()` 结尾**，毒丸写在它之后，**永远执行不到**：零缺陷被伪装成 11 条缺陷。我这边的同型：变异脚本没插进目标行却改了调用点 ⇒ `ReferenceError`，**而崩溃也是非零退出，被读成「这道门有牙」**；探针 require 一个需要 GUI 的启动脚本，第一句就抛，**读到的是宿主自己的环境变量** ⇒ 变异照绿。⇒ 全中 / 全不中 / 整齐的零，都先怀疑装置；**变异后先做语法检查 + 冒烟跑一次，确认它是个合法且可达的程序**，再谈结论。采信一个「0 命中」之前要做双自证：**正例证明抓得到 + 对照组证明那个位置本来可达**。

116. **⭐⭐⭐ 「谁在报红」和「有没有红」一样重要**（2026-09-05，两个会话同日各撞一次）。对方写了一组新判据，跑变异时看到红就以为生效了 —— **实际报红的是另一道元门禁在告发它那组断言本身**（那 6 条断言把双参数写成单参数，条件被语言静默丢弃，跑起来「全部通过 27 项」什么都没验）。我同日的形态：修完一条判据跑变异得到**绿**，以为判据没守住、去查执法正则，单独测那条正则**是命中的** —— 真因是我的替换打在了**另一个同名站点**上。⇒ 固定动作：**看到红先问「是哪一道红的，和我预期的是不是同一道」**；看到绿先问「**我的变异真的落在被测的那一格上了吗**」。两句话对应同一件事 —— **装置有没有真正进入待测状态**。⭐ 这也是元门禁价值兑现的时刻：写了防某个错的检查，然后**立刻自己犯了那个错** —— 没有那道元门禁，那组假断言会一直显示 ✓ 到永远。

117. **⭐⭐ 时间最好只用来「等」和「算比值」，不用来「判快慢」**（2026-09-05，对方的实践 + 我的反例）。同一台机上并发跑测试时，**中位数与均值都是被污染的估计量** —— 我一道性能门取中位，同一棵干净树同一项实测 69/121/225/262/292ms 对 120ms 阈值，单跑十次红四次；而我据「单跑五次全绿」判过一次抖动，**那是抽样运气**。三种解法按优先级：①**把断言改成倍率**（「数据量 8× 时耗时增长 < 20×」）—— 常数因子被约掉，竞争同时影响分子分母，机器差异自动消失；②时间只用于 `setTimeout` 的**等待上限**（放宽的是等待，不是判定，严格性不变）；③确实必须判**绝对耗时**时（例如「用户拖一张表要等多久」这种面向体验的承诺），取**多次中的最小值**——竞争只会让观测变大，最小值最接近真实成本，而真正的数量级回归会把每一次都抬上去。⚠️ 无论用哪种，都要自证「牙齿还在」：注入一个数量级的人为回归，它必须仍然变红。
    ⚠️ 相关：**不要编一个你算不出来的数**。同一批修复里，csvtable 明确拒绝编造「源表行数」（parse 期已丢），而 docstore 却报了一个由重叠 chunk 求和得来的 `chars` —— 那个数**超过了文档本身的长度**。编一个数字正是你在修的那类缺陷。

118. **⭐⭐ 文档 / SOP 类被审对象，最大宗的缺陷是「引用错位」而不是「逻辑写错」**（2026-09-15 实测，一轮 15 处）。L1–L9 是照着代码设计的，审一份规范时它们几乎碰不到真问题：真问题长这样——「测试章读 X」而 X 在被引文件里零命中；安全依据挂在某个编号名下而那个编号的真实主题是另一件事；三份文档对同一模块有三套口径；引用的附件小节里根本没有它说的那类内容。⇒ 加了 **L10 引用落点**（见 lens 表），文档类对象必跑且优先级高于 L1。⛔ `grep` 到那个名字存在**不算核对过**——要打开被引的那一节看它**真实写的是什么**。

119. **历史案例与交接补充（逐条落盘规范见铁律 92）。** **⭐⭐ 「把结论边定边落盘」是子 agent 的生存条件，不是可选优化**（2026-09-15 实测）。一个反驳者 agent 干完了全部裁决，**在写最终报告时 autocompact 打满直接死亡**，整轮结论全丢；重开的实例在提示词里加了「每定案一条就追加写文件 + 最终响应限字数 + 只读点名行区间」三句，同样的活顺利产出。⭐ **agent 的典型死法是"到最后一刻才丢"**——它前面干的活全部有效，只是没能说出口。⇒ 这三句已写进 Node 3 步骤 2b，**派活时固定带上**，不要指望执行者记得铁律 92。附带一条：回收子 agent 结果用完成通知，⛔ 别用阻塞式读取——那会把 JSONL 全量转录灌进编排者的上下文（同日踩两次）。

120. **⭐ 反驳者的承重物是「角度之间独立」，不是「每条发现各自隔离」**（2026-09-15 实测收编为批裁模式）。一轮 7 条候选按 `3 个角度 × 全部候选` 批裁，实测有 4 条是**两个角度 1:1 对立、靠第三个角度定案**——per-finding 隔离在这个规模下没有提供额外价值，只是把 3 个 agent 变成 21 个。⇒ 候选 ≤8 条且不含安全/数据/资金类时允许批裁（边界见「对抗式证伪投票」）。⛔ 高危三类仍走 per-finding × 3：那里两类错误的代价不对称。
